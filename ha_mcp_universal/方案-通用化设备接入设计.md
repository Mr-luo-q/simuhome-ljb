# 方案：MCP 接口语义 = 外部设备控制语义的最大公约数（v2 分叉）

本文是 `ha_mcp_universal` 的设计文档。原则先写清楚：

```text
我们不做"某品牌设备的专用接口"，也不追求"接口一个字不改"。
目标是把【外部设备接入 HA 之后、控制这件事本身共有的语义】抽出来，
让 MCP 用同一套接口语义覆盖尽量多的设备 —— 也就是控制语义的"最大公约数"。

当新设备接进来时，判断顺序是：
  ① 它能不能投影到现有公约数上？（能 → 直接接，只加配置）
  ② 不能的话，缺的那个维度是不是【多类设备共有】的？（是 → 公约数该扩，扩词表/字段）
  ③ 只是这一类设备特有的？（是 → 不扩，写进 scoping）
```

现状的三道硬编码闸门见 15 号文档；v1（`ha_mcp_server`）保持不动，本工程是从它复制出的 v2。

## 1. 什么是"控制语义的最大公约数"

控制一台设备，无论它是什么，控制器（人或模型）要的东西是同一组：

```text
写（设定）   开关：开 / 关 / 取反
            模式：离散档位（制冷/制热/静音/强力/程序…）
            目标值：一个带范围的数值（温度、湿度、水位…）
            百分比：0~100 的档位或位置（风速、亮度、开合度）
读（反馈）   当前值：设备自报的实测值（当前温度、当前湿度…）
            以及上面四个设定值的回读
```

把这组东西翻译成接口，就是我们现在这套语义（8 个工具 / 8 个动作 / 6 个字段）。
它不是"不许动"的契约，而是**当前版本的公约数快照**：

| 维度 | 覆盖哪些设备类别（≥3 类才算公约数） | 现在落在哪 |
| --- | --- | --- |
| 开关 on/off | 开关、灯、风扇、空调、媒体、扫地机、窗帘（开/合） | `turn_on` / `turn_off` / `toggle` + 字段 `on` |
| 模式 mode（枚举） | 空调 hvac_mode、风扇 preset、扫地机模式、洗衣机程序、select 实体 | `set_mode` + 字段 `mode` |
| 目标值 target（数值+范围） | 空调设定温度、冰箱温区设定、加湿器目标湿度、热水器水温 | `set_temperature` + 字段 `target` |
| 百分比 level（0~100） | 风扇档位、灯亮度、音量、开合度 | `set_percentage` / `set_brightness` / `set_position` + 字段 `level` / `position` |
| 当前值 current | 空调当前温度、冰箱温区温度、加湿器当前湿度、热水器水温 | 字段 `current`（只读） |
| 时间类（剩余时间、倒计时） | 洗衣机/烘干机有，其它类设备没有 | **不在公约数**：不进字段，需要时走 `query_events` |
| 诊断类（故障位图、滤网寿命、电量） | 各类都有但语义不同，也不参与控制 | **不在公约数**：只读、不进接口 |

一句话：**公约数只看"控制回路"需要什么，不看"设备还能报告什么"。**

## 2. 由公约数导出的接口语义（当前版本）

### 2.1 八个工具（模型看到的全部）

| 工具 | 参数 | 返回 | 在公约数里的角色 |
| --- | --- | --- | --- |
| `observe_home` | 无 | 房间 + 环境量 + 时间 | 全局观察 |
| `inspect_room` | `room_id` | 房间环境量 + 设备清单 | 局部观察 |
| `inspect_device` | `device_id` | 六字段 + 动作清单（含范围） | 动作空间（含掩码与参数边界） |
| `execute_action` | `device_id`、`action`、`params?` | state_after + steps + verified | 唯一的写入口 |
| `check_goal` | `conditions`、`keep?` | 两组判定 | 控制是否达成 |
| `query_events` | 时间窗 / 实体 / limit | 事件序列 | 诊断与复盘（时间类信息的出口） |
| `time_control` | op / seconds / at / steps | 快照或预约 id | 等待与调度（未实现） |
| `memory` | 无（简化为只读整段） | 记忆文本 | 长期偏好（未实现） |

### 2.2 八个动作与六个字段

```text
动作词表   turn_on / turn_off / toggle / set_mode / set_temperature /
          set_percentage / set_brightness / set_position
状态字段   on / mode / target / level / position / current
错误码     12 个（HA_UNREACHABLE / UNKNOWN_DEVICE / DEVICE_UNAVAILABLE / … / NOT_IMPLEMENTED）
四道闸门   设备存在 → 实体可用 → 动作支持 → 参数范围
返回外壳   {"ok", "data", "error", "meta"}，失败给 {code, message, hint}
```

### 2.3 两处"命名与公约数不完全对齐"的地方（要拍板）

公约数的视角暴露了两个历史命名问题，v2 应该借这次机会定下来：

```text
问题一   set_temperature 是"温度专用名"，却承担了"目标值设定"这个通用语义：
        加湿器的目标湿度、热水器的水温都是同一形状（一个 number + min/max/step + 单位），
        用 set_temperature 表达不了。

  方案 A   保持现状：温度以外的目标值不接（加湿器、热水器进不来）
  方案 B   泛化成 set_target(value)：单位由设备自报（°C / % / L），参数 schema 不变，
           动作总数仍是 8，只是从"温度专用"变成"目标值通用"
  方案 C   双名并存（set_temperature 作为 set_target 的别名）：模型选择负担增加，不推荐

  建议 B（只在 v2 里做）；v1 的论文实验口径不受影响。

问题二   set_brightness 与 set_percentage 语义重复（都是 0~100 百分比）：
        可讨论合并成 set_level，或在词表里明确"亮度是 level 的一个特例"。
```

## 3. 新维度什么时候允许进公约数（扩展判据）

```text
准入条件（全部满足才扩词表 / 字段）
  ① 跨类别：至少 3 类设备都有这个控制语义（不是一类设备的特产）
  ② 跨来源：至少 2 个不同集成（如 mqtt 自建 + 米家 + 某个 HACS 插件）都能提供
  ③ 可闭环：能读回、能判定（否则进不了 check_goal 与回读验证）
  ④ 可投影：两个后端（HA 与将来的沙盒）都能表达

不满足的怎么办
  只读信息（剩余时间、滤网寿命、电量）→ 走 query_events 或设备属性，不进六字段
  单类设备动作（洗衣机"开始洗涤"、扫地机"回充"）→ 用 turn_on 语义近似表达，或写 scoping
  复合属性（列表、位图、JSON）→ 不映射
```

## 4. 实现层：怎么把任意设备投影到公约数上（这部分随便改）

### 4.1 四步投影

```text
① 识别      读 entity_registry + device_registry + 实体属性，按 claim 规则筛出可接的实体
② 聚合/拆分  按 ha_device_id 聚合；同一角色出现多次时拆成多台逻辑设备（见 4.3）
③ 定角色     用 domain + device_class + unit + 属性，把实体定成 6 个角色之一
④ 投影       角色 → 动作（8 个里选）、角色 → 字段（6 个里选）；投不出来的进 extra 或不收
```

### 4.2 角色 → 动作与字段

| 角色（HA 实体） | 允许的动作 | 落在字段 | 落到 HA |
| --- | --- | --- | --- |
| `power`（switch / light / fan / climate） | turn_on / turn_off / toggle | `on` | `{domain}.turn_on/off/toggle` |
| `mode`（climate / select） | set_mode（enum 取 `hvac_modes` / `options`） | `mode` | `climate.set_hvac_mode` / `select.select_option` |
| `target`（climate / number） | set_temperature（若采用方案 B 则是 set_target） | `target` | `climate.set_temperature` / `number.set_value` |
| `level`（fan / number / light） | set_percentage（亮度可映射到 set_brightness） | `level` | `fan.set_percentage` / `number.set_value` / `light.turn_on(brightness_pct)` |
| `position`（cover） | set_position | `position` | `cover.set_cover_position` |
| `current`（sensor） | 无（只读） | `current` | — |

参数范围一律从实体属性取：

```text
number.*    min / max / step
select.*    options（直接当 enum）
climate.*   hvac_modes / min_temp / max_temp / target_temp_step
fan.*       percentage_step
cover.*     current_position（0~100）
```

### 4.3 多值设备：拆设备，不扩动作

六字段里 `target` / `current` 是单值，所以一台设备有两个温区时，
正确做法是**拆成两台逻辑设备**，而不是给动作加 `zone` 参数（那是在给一类设备改公约数）：

```text
米家对开门冰箱 12 个实体
  select.模式（整机）  number.冷藏设定 / 冷冻设定（两个 target）
  sensor.冷藏温度 / 冷冻温度 / 室内温度（多个 current）
  sensor.故障位图 / 门未关提醒 / 压缩机转速、button.恢复出厂设置、event.门开提醒

投影结果
  fridge_cold     roles: mode（整机 select 共享）、target（冷藏设定）、current（冷藏温度）
  fridge_freeze   roles: target（冷冻设定）、current（冷冻温度）
  其余实体：故障 / 转速 / 报警 / 按钮 → 不属于控制公约数，不接（门开提醒可选进 extra 只读）

对应调用（接口没变）
  inspect_device(fridge_cold) → {on: null, mode: "手动", target: 5, current: 3}
  execute_action(fridge_cold, set_temperature, {value: 6}) → 回读 target=6
  check_goal([{target: "fridge_cold.target", op: "lte", value: 6}]) → pass
```

### 4.4 回读：期望值来自参数，窗口按设备类型

```text
期望值   number.set_value → 等于传入值（容差 step/2）
         select.select_option → 等于选项字符串
         switch / light / fan → on / off；climate → mode 或 target
窗口     本地 MQTT 沿用 500ms × 3（实测命令 + 回读 236~388ms）
         云端设备（米家 cloud_polling）800~1000ms × 4，可按 claim 规则覆盖
未变只标 verified=false，不算失败（语义不变）
```

```yaml
    platforms: [mqtt]

    kind_by_suffix: {_switch: switch, _climate: climate, _fan: fan}
  - name: xiaomi             # 米家：只写规则，不写专有代码
    platforms: [xiaomi_home]

  alias: {2646196763de_jia: home}   # HA 区域 → 对外房间名（只在映射层改）
  hide_empty: true                  # 空区域不返回

  file: ./data/device_aliases.yaml  # 首次扫描生成、可手改（中文名没法 slugify）

  allow_write_domains: [switch, light, climate, fan, cover, number, select]
  deny_entities: ["button.*", "update.*", "*_reset_*"]
```

```text

  execute_action   fridge_cold, set_temperature, {value: 6} → verified=true → 复原成 5
  execute_action   {value: 99} → BAD_REQUEST（本地拦下，不发给 HA）
  check_goal       fridge_cold.target ≤ 6 → pass

③ 回归与扩展性
  v1 沙盒 12 台设备行为一致：契约 12/12、真机端到端 21/21（房间数断言按 3 修）
  再挑一个第三方集成设备（HACS 某开关或灯），只加一条 claim 规则就能用
  用第 3 节四条判据过一遍新增设备：哪些维度进了公约数、哪些进了 scoping，列成一张表
```

## 8. 风险与边界

```text
元数据质量   实测米家 12 个实体全部 entity_category=None（连"恢复出厂设置"都没标），
            所以过滤必须靠"域白名单 + 角色推断 + 黑名单"三重，不能只信一个信号
命名不统一   中文设备名无法 slugify，逻辑 id 依赖别名文件；别名文件要可手改、可版本化
云端设备     落定慢、可能限流：verify 窗口与写频率要按 claim 配
写安全       默认只读，写按域白名单放行；button / update 永不进动作表
语义边界     装不进公约数的量一律不接（时间类、诊断类、复合属性），
            并写清"不支持的设备长什么样"，而不是硬塞
公约数膨胀   每次想扩词表 / 字段都要过第 3 节的四条判据，避免接口被单类设备牵着走
不污染主实验 v1 不动；v2 的 claim 里沙盒与米家并列，论文主实验仍只用沙盒规则
```

## 10. 与论文的关系

```text
现在能写的   "自建投影（SimuHome→HA）上验证了统一语义"
v2 能加的    "接口语义是控制语义的最大公约数：同一套接口零专有代码接入第三方集成设备
            （米家冰箱为例），并用四条判据说明哪些语义进、哪些不进"
不能吹的     不要说"支持所有 HA 设备"；把 scoping 表（时间类 / 诊断类 / 复合属性）附上，
            这本身就是"公约数"论证的一部分
```
