# 方案：把 MCP 从"沙盒专用"改成"通用化接入"（v2 分叉）

本文是 `ha_mcp_universal` 这个新工程的设计文档。起因：米家（Xiaomi Home）接进 HA 成功，
但我们的 MCP 看不见它——因为 v1 的映射是为 SimuHome 沙盒写死的。
本文回答一个问题：**怎么改成"HA 里能接入什么设备，我们就能控制什么设备"，而不是给米家写特例。**

现状分析（三道硬编码闸门、证据、行号）在 15 号文档里，本文不重复，只引用结论；
v1 工程 `ha_mcp_server` 保持不动，论文主实验口径不变。

## 0. 一句话结论

```text
通用化的关键不是"支持米家"，而是三件事：
  ① 认领：从"前缀匹配"改成"读 HA 元数据 + 可配置规则"（平台/域/类别/黑名单）
  ② 聚合：从"一个实体 = 一台设备"改成"一台 HA 设备 = 一台逻辑设备 + 若干实体角色"
  ③ 动作：从"按类别写死动作"改成"角色 + 域 → 动作与服务"的生成规则
做完这三件，米家冰箱不需要一行专有代码就能进来：它的 select/number/sensor 会分别落到
mode / target / current 三个角色上。
```

## 1. 目标与非目标

```text
目标
  1  任意 HA 集成接入的设备（MQTT 自建、米家、Zigbee/Matter、HACS 插件…）都能被认领
  2  多实体设备（米家冰箱 = 12 个实体）能被聚合成一台逻辑设备
  3  动作与参数范围从 HA 元数据推导，不写死设备型号
  4  六字段状态视图保持不变（on / mode / target / level / position / current），缺的给 null
  5  v1 的行为可以作为一条 claim 规则完整复现（沙盒主实验不受影响）

非目标
  · 不做米家专有属性（压缩机转速、故障位图）的语义化，这类留在 HA 侧
  · 不做 scene / script / automation / dashboard 的编排
  · 不做写操作的自动发现（能不能写由域名与动作规则决定，不由"看起来像"决定）
```

## 2. 通用化的依据：HA 自己能提供什么元数据

HA 的注册表已经把"设备是什么、能干什么"写全了，这就是通用化的基础：

```text
实体注册表（config/entity_registry/list）
  entity_id / unique_id / platform / device_id / area_id
  entity_category：config | diagnostic | null      ← 诊断与配置实体的通用标记
  disabled_by / hidden_by / original_name

设备注册表（config/device_registry/list）
  id / identifiers / name / name_by_user / area_id / model / manufacturer / entry_type

实体状态（/api/states/{entity_id}）的属性
  number.*    min / max / step / mode / unit_of_measurement
  select.*    options
  climate.*   min_temp / max_temp / target_temp_step / hvac_modes / current_temperature
  fan.*       percentage / percentage_step / supported_features
  light.*     brightness / supported_color_modes
  cover.*     current_position / supported_features
```

实测提醒（2026-09-27，米家冰箱 12 个实体）：**米家没有给任何实体打 `entity_category`**
（`cat=None`，连"恢复出厂设置"button 和"故障"位图 sensor 都没有）。
所以只靠 `entity_category` 过滤诊断实体是不够的，必须叠加"域白名单 + 角色推断 + 黑名单"。

## 3. 设计：三层拆开改

### 3.1 认领层（claim）：读元数据 + 配置规则

```python
@dataclass(frozen=True)
class ClaimRule:
    """一条认领规则：命中即收。"""
    name: str                            # 规则名，日志里用
    platforms: tuple[str, ...] = ()      # 空 = 不限；如 ("mqtt", "xiaomi_home")
    domains: tuple[str, ...] = ()        # 空 = 不限；如 ("switch","light","climate","fan","cover","number","select")
    entity_id_prefix: str = ""           # 如 "switch.simuhome_"
    unique_id_prefix: str = ""           # 如 "simuhome_"
    id_source: str = "device_name"       # 逻辑 id 从哪来：device_name / identifier / entity_name
    exclude_category: tuple[str, ...] = ("config", "diagnostic")
    exclude_entities: tuple[str, ...] = ()   # 支持通配，如 ("button.*", "update.*")
    kind_by_suffix: dict[str, str] = field(default_factory=dict)  # v1 的 _switch/_climate/_fan 规则
```

判定顺序（每条实体记录）：

```text
1  platform 不在规则里 → 跳过
2  entity_category 命中排除 → 跳过
3  entity_id 命中黑名单/通配 → 跳过
4  domain 不在白名单 → 跳过（button / event / update / sensor 里的非角色实体都挡在这里）
5  必须有 device_id 归属（没有归属的实体不进设备清单；房间传感器单独走 area 分支）
6  命中 → 交给角色推断
```

**房间**同步改成"只收有内容的区域"：

```text
区域里既没有认领到的设备、也没有被用作环境量的传感器 → 不返回
（米家接入时建的那个空区域 2646196763de_jia 会因此自动消失，等它真有设备进来再出现）
```

### 3.2 聚合层：一台 HA 设备 = 一台逻辑设备 + 角色表

```python
@dataclass(frozen=True)
class EntityRef:
    entity_id: str
    domain: str
    device_class: str | None
    unit: str | None

@dataclass(frozen=True)
class DeviceRow:
    device_id: str                 # 对外逻辑 id（可读、可配别名）
    ha_device_id: str
    area_id: str | None
    name: str
    kind: str                      # 主类别：switch/light/climate/fan/cover/number/select/mixed
    roles: dict[str, EntityRef]    # role → 实体；role 见下表
    extra: dict[str, EntityRef]    # 不映射六字段、但保留可读的实体（可选）
```

角色推断规则（纯函数，输入 entity_registry + device_registry + 状态属性）：

| HA 实体 | 判据 | 角色 | 落到六字段 |
| --- | --- | --- | --- |
| `switch.*` | — | `power` | `on` |
| `light.*` | — | `power`；有 `brightness` 再加 `level` | `on` / `level` |
| `climate.*` | — | `power` + `mode` + `target` + `current`（同一实体多角色） | 四字段 |
| `fan.*` | — | `power` + `level` | `on` / `level` |
| `number.*` | `device_class=temperature` 或 `unit=°C` | `target` | `target` |
| `number.*` | 其它 | `level` | `level` |
| `select.*` | — | `mode` | `mode` |
| `sensor.*` | `device_class=temperature` | `current` | `current` |
| `sensor.*` | 其它 `device_class`（humidity 等） | 视配置：`current` 或 `extra` | 视配置 |
| `cover.*` | — | `position` | `position` |
| `button.*` / `event.*` / `update.*` | — | 不收 | — |

一台设备出现多个同类角色时（米家冰箱两个温区：冷藏/冷冻各有一个 `number` + 一个 `sensor`），
用**角色子键**区分：

```text
roles: target.fridge / target.freezer / current.fridge / current.freezer
设备名里带方位词会自动归类：原名含"冷藏"→ fridge，含"冷冻"→ freezer，
归不了类的用 target.1 / target.2 之类序号，最后靠别名文件人工改名
```

**逻辑 id 与别名**：中文设备名没法 slugify 成有意义的英文 id，所以：

```text
首次扫描生成 data/device_aliases.yaml：
  ha_device_id: 2f9aff22…  →  device_id: fridge
  entity: number.…_target_temperature_p_3_2 → role: target.fridge
用户可以手改这个文件；改完重启生效（文件不存在时用自动 id：dev_<id 前 6 位>）
```

### 3.3 动作层：角色 + 域 → 服务与参数

动作不再按"设备类别"写死，而是**从角色生成**：

| 角色 | 生成的动作 | HA 服务 | 参数与范围来源 |
| --- | --- | --- | --- |
| `power`（switch） | `turn_on` / `turn_off` / `toggle` | `switch.*` | 无参数 |
| `power`（light） | 同上（+ `set_brightness` 若有 `level`） | `light.turn_on/off/toggle` / `light.turn_on(brightness_pct)` | `brightness` 0~100 |
| `power`（fan） | 同上（+ `set_percentage`） | `fan.turn_on/off/toggle` / `fan.set_percentage` | `percentage_step` |
| `power`（climate） | `turn_on/off`、`set_mode`、`set_temperature` | `climate.*` | `hvac_modes` / `min_temp`~`max_temp` / `target_temp_step` |
| `target`（number） | `set_target` | `number.set_value` | `min`/`max`/`step` |
| `mode`（select） | `set_mode` | `select.select_option` | `options` |
| `level`（number） | `set_level` | `number.set_value` | `min`/`max`/`step` |
| `position`（cover） | `set_position` / `open` / `close` | `cover.set_cover_position` 等 | `current_position` 的 0~100 |

动作参数 schema 也从同处生成（`type/minimum/maximum/step/enum`），保证 `inspect_device`
与 `execute_action` 用同一份数据。

**回读期望值**：写前读一次目标实体状态做基线，写后按"参数值 → 期望值"比较：

```text
number.set_value → 期望 state == 传入值（数值容差按 step/2）
select.select_option → 期望 state == 选项字符串
switch/light/fan/climate 的开关 → 期望 on/off（或 climate 的 mode）
云设备（米家）落定慢：verify_delay_ms 默认从 v1 的 500 提到 800~1000，attempts 4
```

### 3.4 状态层：六字段保持统一视图

```text
on        power 角色：switch/light/fan 看 state on/off；climate 看 state != off
mode      mode 角色：select 的当前 option；climate 的 hvac_mode
target    target 角色：number 的当前值（多个子键时返回对象 {fridge: 5, freezer: -18}）
level     level 角色：number/fan 的百分比
position  position 角色：cover 的当前位置
current   current 角色：sensor 的数值（多个子键时返回对象）

取不到的字段一律 null（与掉线处理一致），不用 0/false 冒充
```

## 4. 配置草案（v2 的 config.yaml）

```yaml
ha: {base_url: http://localhost:8123, token: ${HA_TOKEN}, timeout_s: 10}

claim:
  - name: sandbox            # v1 的沙盒投影，保持原样
    platforms: [mqtt]
    unique_id_prefix: simuhome_
    id_source: identifier
    kind_by_suffix: {_switch: switch, _climate: climate, _fan: fan}
  - name: xiaomi             # 米家：通用规则就能接
    platforms: [xiaomi_home]
    domains: [switch, light, climate, fan, cover, number, select, sensor]
    id_source: device_name
  # 以后接 Zigbee/Matter/HACS 插件，照抄一条规则即可

roles:
  sensor_metrics: [temperature]        # 只有温度传感器当 current，其余进 extra

execution:
  verify_delay_ms: 800                 # 云设备更慢
  verify_attempts: 4
  allow_write_domains: [switch, light, climate, fan, cover, number, select]
  deny_entities: ["button.*", "update.*", "*_reset_*"]

aliases:
  file: ./data/device_aliases.yaml     # 首次扫描自动生成，可手改
```

## 6. 验收（三步，由小到大）

```text
① 认领与聚合（只读）
   observe_home 房间回到 3 个（空区域被过滤）；inspect_room(kitchen) 不变
   inspect_device(fridge) → {on: null, mode: "手动", target: {fridge: 5, freezer: -18},
                            current: {fridge: 3, freezer: -19}}
   动作清单只有 set_target / set_mode，且参数范围来自实体属性

② 写与回读
   execute_action(fridge, set_target, {zone: "fridge", value: 6}) → 回读 target.fridge=6
   复原成 5；全程 verified=true
   execute_action(fridge, turn_on) → UNSUPPORTED_ACTION（冰箱没有 power 角色）

③ 回归
   v1 的沙盒设备在 v2 里行为一致：契约测试 12/12、真机端到端 21/21（把断言里的房间数改回 3）
   再随便挑一个第三方集成设备（例如 HACS 里某个开关）验证"只加一条 claim 规则就能用"
```

## 7. 风险与边界

```text
元数据不统一   不同集成的 number 语义差异大（有的是设定值，有的是阈值）：
             靠 device_class + unit + 名称关键词推角色，推不出的进 extra，不猜
中文名没法 slugify  必须保留别名文件机制，否则 device_id 只能是一串哈希
云端限流与延迟   米家是 cloud_polling：写后落定慢、频繁写可能被限流；
             claim 规则里要能配 verify 窗口，必要时对云设备限速
写权限安全     通用化后第一次出现"能写别人家设备"的风险：
             默认只读，写操作按域白名单放行；button.* 这类危险实体永不进动作表
HA 版本漂移    米家插件目前就有 entity_id 域写错的告警（HA 2027.5 会失效），
             说明第三方集成的元数据质量参差；认领层要能容忍"这条规则匹配不到"
不污染主实验   v1 目录与口径不动；v2 的 claim 里沙盒规则与米家规则并列，
             论文主实验仍只用沙盒规则那一条
```
