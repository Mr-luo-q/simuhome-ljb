# 方案：8 个接口语义不变，实现层通用化（v2 分叉）

本文是 `ha_mcp_universal` 的设计文档。出发点是一句原则：

```text
最终要的是【接口语义】——8 个工具、8 个动作、6 个状态字段、错误码，这些是给模型看的契约，保持不变；
其他一切都可以改：认领规则、设备聚合、角色映射、动作生成、配置格式、后端实现。
```

所以通用化要回答的不是"支持不支持米家"，而是：**任意一台 HA 能接入的设备，
能不能被投影成这 8 个接口已经能表达的语义**。能就接，投影不出来的就明确不接（写进 scoping）。

现状的三道硬编码闸门见 15 号文档；v1（`ha_mcp_server`）保持不动，本工程是从它复制出来的 v2。

## 1. 不变量：接口语义清单（以 `contract\tools.py` 为准）

这四张表在 v2 里**一个字都不改**，改的是它们背后的数据从哪来、怎么算出来。

### 1.1 八个工具

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `observe_home` | 无 | 房间清单 + 每房间环境量 + 当前时间 + counts |
| `inspect_room` | `room_id` | 环境量 + 设备清单 + `doors:null` |
| `inspect_device` | `device_id` | 六字段状态 + 动作清单（含参数范围） |
| `execute_action` | `device_id`、`action`、`params?` | state_after + steps + verified |
| `check_goal` | `conditions`、`keep?` | goals/keep 两组 pass + all_pass |
| `query_events` | since/until/entity_id/limit | 事件序列 |
| `time_control` | op/seconds/at/steps | 快照或预约 id（未实现） |
| `memory` | 无（简化为只读整段） | 记忆文本（未实现） |

统一外壳也不变：`{"ok", "data", "error", "meta"}`；失败给 `{code, message, hint}`。

### 1.2 八个动作（词表固定，按设备取子集）

```text
turn_on / turn_off / toggle                                 任意可控设备
set_mode(mode: enum)                                        取值来自设备（climate 的 hvac_modes、select 的 options）
set_temperature(value: number)                              温度类目标值（climate 的设定点、number 温度实体）
set_percentage(value: number)                               百分比类（fan 档位、百分比 number）
set_brightness(value: number)                               亮度（light）
set_position(value: number)                                 位置（cover）
```

**动作名与参数名一个都不加、不改**。通用化的任务是把各式各样的设备映射到这套词表上，
而不是为米家冰箱发明 `set_target` 之类的新动作。

### 1.3 六个状态字段

```text
on(bool) / mode(string) / target(number) / level(number) / position(number) / current(number)
取不到就是 null（与掉线时的处理一致），不用 0/false 冒充
```

### 1.4 错误码（12 个）与四个闸门

```text
HA_UNREACHABLE / UNKNOWN_DEVICE / UNKNOWN_ROOM / DEVICE_UNAVAILABLE / UNSUPPORTED_ACTION /
SERVICE_ERROR / VERIFY_TIMEOUT / INVALID_TIME / UNKNOWN_KEY / BAD_TARGET / BAD_REQUEST / NOT_IMPLEMENTED

execute_action 的四道闸门顺序不变：设备存在 → 实体可用 → 动作支持 → 参数范围
```

## 2. 变量：实现层可以改的部分

```text
认领        谁能进设备清单（v1：platform==mqtt 且 simuhome_ 前缀；v2：读元数据 + 配置规则）
聚合        一台逻辑设备对应哪些实体（v1：一个实体一台设备；v2：一台 HA 设备 + 角色表，必要时拆成多台）
角色        实体在设备里扮演什么（power / mode / target / level / position / current）
动作生成    动作清单与参数范围从哪来（v1：按 kind 写死；v2：按角色 + 实体属性推导）
回读        期望值怎么算、验证窗口多长（v1：500ms×3；v2：按设备类型给，云设备放宽）
房间        房间从哪来、空区域怎么处理（v1：HA 全部 area；v2：只收有内容的区域 + 区域别名）
命名        逻辑 id 怎么来（v1：unique_id 截断；v2：设备名 + 别名文件）
配置        config.yaml 的段落结构（claim / roles / aliases / execution）
后端        仍是 HA 后端，但认领与动作生成与后端解耦，为将来沙盒后端留位
```

## 3. 核心机制：把任意设备投影到固定语义上

### 3.1 四步投影

```text
① 识别     读 entity_registry + device_registry + 实体状态属性，按 claim 规则筛出"可接"的实体
② 聚合/拆分 按 ha_device_id 聚成一台逻辑设备；同一角色出现多次时拆成多台逻辑设备
③ 角色     用 domain + device_class + unit + 属性，把每个实体定成 6 个角色之一
④ 投影     角色 → 动作（只能是 8 个之一）、角色 → 状态字段（只能是 6 个之一）
           投影不出来的实体：进 extra（只读可查）或直接不收
```

### 3.2 角色 → 允许的动作（只能用固定词表）

| 角色（HA 实体） | 允许的动作 | 落到 HA |
| --- | --- | --- |
| `power`（switch） | turn_on / turn_off / toggle | `switch.*` |
| `power`（light） | 上述 3 个 + `set_brightness`（有 brightness 时） | `light.turn_on(brightness_pct)` |
| `power`（fan） | 上述 3 个 + `set_percentage` | `fan.set_percentage` |
| `power`（climate） | 上述 3 个 + `set_mode` + `set_temperature` | `climate.set_hvac_mode` / `set_temperature` |
| `mode`（select） | `set_mode`（enum 取 `options`） | `select.select_option` |
| `target`（number，温度类） | `set_temperature` | `number.set_value` |
| `level`（number，百分比类） | `set_percentage` | `number.set_value` |
| `position`（cover） | `set_position` | `cover.set_cover_position` |

参数范围一律从实体属性取，不写死：

```text
number.*   → min / max / step
select.*   → options（直接当 enum）
climate.*  → hvac_modes / min_temp / max_temp / target_temp_step
fan.*      → percentage_step
light.*    → brightness（0~100 百分比，按 HA 的 brightness_pct 约定）
cover.*    → current_position（0~100）
```

### 3.3 多值设备：拆设备，不扩动作

六字段里 `target` / `current` 都是**单值**，所以一台设备有两个温区时，
**不能**给 `set_temperature` 加 `zone` 参数（那会动到接口语义），正确做法是**拆成两台逻辑设备**：

```text
米家对开门冰箱的 12 个实体
  select.模式                     → 整机模式
  number.冷藏室设定温度 / 冷冻室设定温度  → 两个 target
  sensor.冷藏室温度 / 冷冻室温度 / 室内环境温度 → 多个 current
  sensor.故障位图 / 门未关提醒 / 压缩机转速 / 开⻔报警、button.恢复出厂设置、event.门开提醒

拆成两台逻辑设备（同一台物理设备）：
  fridge_cold     roles: mode（共享整机 select）、target、current
  fridge_freeze   roles: target、current
  （整机 `mode` 也可以只挂在 fridge_cold 上，靠别名文件决定；两种都不改接口）
其余实体：故障/转速/报警/按钮 → 不进设备（诊断信息），门开提醒 → 可选 extra（只读）
```

### 3.4 投影不出来的量：明确不接

```text
非温度的 number（音量、阈值、亮度以外的量纲）   → 不映射到六字段；除非它是 0~100 的百分比（走 level）
诊断/维护类实体（button、update、event、故障位图） → 不收；避免出现"恢复出厂设置"这种可写动作
多值复合属性（列表、位图、JSON）                → 不映射，最多进 extra 只读通道
只读传感器（湿度/PM2.5/电量…）                  → 只在"房间环境量"那条通道里出现，不进设备动作
```

这就是这套语义的边界：**接口只承诺六个字段能表达的东西**，其余如实写 scoping。

### 3.5 回读：期望值来自参数，窗口按设备类型

```text
期望值   number.set_value → 等于传入值（容差 step/2）
         select.select_option → 等于选项字符串
         switch/light/fan → on/off；climate → mode 或 target
窗口     本地 MQTT 设备沿用 500ms × 3（实测命令+回读 236~388ms）
         云端设备（米家 cloud_polling）默认 800~1000ms × 4，按 claim 规则可覆盖
         未在窗口内变化只标 verified=false，不算失败（语义不变）
```

## 4. 认领与配置（v2 的 config.yaml 草案）

```yaml
ha: {base_url: http://localhost:8123, token: ${HA_TOKEN}, timeout_s: 10}

claim:
  - name: sandbox                 # v1 的沙盒投影，行为与今天完全一致
    platforms: [mqtt]
    unique_id_prefix: simuhome_
    id_source: identifier
    kind_by_suffix: {_switch: switch, _climate: climate, _fan: fan}
  - name: xiaomi                  # 米家：只写规则，不写专有代码
    platforms: [xiaomi_home]
    domains: [switch, light, climate, fan, cover, number, select, sensor]
    id_source: device_name

areas:
  alias: {2646196763de_jia: home}  # HA 区域 → 对外房间名（不改 HA，只在映射层改）
  hide_empty: true                 # 空区域不返回（米家接入时建的空壳区域因此消失）

roles:
  sensor_metrics: [temperature]     # 只有温度传感器当 current
  percent_numbers: true             # 0~100 的 number 可当 level

aliases:
  file: ./data/device_aliases.yaml  # 首次扫描生成可编辑的别名（中文名没法 slugify）

execution:
  verify_delay_ms: 800
  verify_attempts: 4
  allow_write_domains: [switch, light, climate, fan, cover, number, select]
  deny_entities: ["button.*", "update.*", "*_reset_*"]
```

## 6. 验收（用现有 8 个接口跑，不改接口）

```text
① 只读
  observe_home        房间 3 个（空区域被过滤；米家区域按 alias 归并或隐藏）
  inspect_device      fridge_cold  →  {on: null, mode: "手动", target: 5, current: 3}
                      fridge_freeze → {on: null, target: -18, current: -19}
                      动作清单里只有 set_mode / set_temperature，且范围来自实体属性
  inspect_device      fridge_cold 上不会出现 turn_on/turn_off（没有 power 角色）

② 写与判定
  execute_action      fridge_cold, set_temperature, {value: 6} → verified=true，target=6 → 复原成 5
  check_goal          [{target: "fridge_cold.target", op: "lte", value: 6}] → pass
  越界                {value: 99} → BAD_REQUEST（本地拦下，不发给 HA）

③ 回归
  v1 沙盒 12 台设备行为一致：契约 12/12、真机端到端 21/21（房间数断言按 3 修）
  再挑一个第三方集成设备（HACS 某开关），只加一条 claim 规则就能用
```

## 7. 风险与边界

```text
元数据质量     实测米家 12 个实体全部 entity_category=None（连"恢复出厂设置"都没标），
             所以过滤必须靠"域白名单 + 角色推断 + 黑名单"三重，不能只信一个信号
中文命名       设备名没法 slugify，逻辑 id 依赖别名文件；别名文件要能手工编辑并版本化
云端设备       米家是云端轮询：落定慢、可能限流；verify 窗口与写频率要能按 claim 配
写安全        通用化后第一次能写别人家设备：默认只读，写按域白名单；button/update 永不进动作表
语义边界       装不进六字段的量一律不接（非温度 number、复合属性、诊断信息），
             在文档里写清"不支持的设备长什么样"，而不是硬塞
HA 版本漂移    米家插件已经有 entity_id 域写错的告警（HA 2027.5 起会失效）；
             认领层要能容忍"这条规则匹配不到任何实体"而不报错
不污染主实验   v1 目录与口径不动；v2 的 claim 里沙盒规则与米家规则并列，
             论文主实验仍只用沙盒规则
```
