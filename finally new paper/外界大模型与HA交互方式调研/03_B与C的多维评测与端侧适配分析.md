# B 与 C 的多维评测：端侧模型真实使用时会撞到什么

日期 2026-09-19。对象：B＝HA 官方 MCP Server，C＝社区 hass-mcp 0.6.0，
对照组 E＝我们自建的 MCP。全部数据来自本机实测（脚本与原始 JSON 见文末），
token 数是估算（中日韩 1.5 字/词、其余 4 字/词），只用于比量级。

## 0. 一句话结论

```text
B 的问题是"语义不在模型手里"：名字是自然语言（还会重复）、错误是 Python 对象、
 参数没有必填与范围，工具返回"action_done"时世界还没变（实测落定还要 190 ms 左右）
C 的问题是"面太大、信噪比太低"：工具面 8907 token（8K 上下文的小模型光看工具就爆了）、
 一次 list_entities 2234 token 全是全屋实体，写成功还返回空、错误不置 isError
两者的共同短板：没有参数约束、没有写后验证、没有可跨后端的语义 —— 正好是我们要补的三处
```

## 1. 评测口径

```text
脚本     _tools\mcp_surface_bench.py（量工具面/读输出/错误输出）
         _tools\mcp_write_settle.py（量写调用耗时 vs 状态落定耗时）
档案     b: GetLiveContext、HassTurnOn(不存在的名字)
         c: list_entities、get_entity(存在/不存在)
         e: observe_home、inspect_room、inspect_device、execute_action(不存在的设备)
写路径   B 用 name+area 开/关客厅侧灯；C、E 用各自接口开/关同一盏灯；跑完都还原并确认
原始数据 ..\外界大模型与HA交互方式调研\_measure\b.json / c.json / e.json
```

## 2. 实测数据

### 2.1 固定开销：工具面（模型每轮都要背）

| 指标 | B 官方 MCP | C 社区 hass-mcp | E 我们 |
| --- | --- | --- | --- |
| 工具数 | 12 | 29 | 8 |
| 工具面字节 | 4,551 | 35,663 | 4,182 |
| 估算 token | ≈1,137 | ≈8,907 | ≈1,000 |
| 必填为空的工具 | 12/12 | 19/29 | 2/8 |
| 带 enum / 上下界的工具 | 2/12 | 0/29 | 2/8 |
| 提示 prompts | 1（83 B） | 7（2,927 B） | 0 |
| 资源 resources | 1（259 B） | 1（918 B） | 0 |

读法：**C 的工具清单本身就是 8,907 token**。一个 8K 上下文的端侧模型，在用户开口之前
预算就已经用光；B 与 E 在 1,000~1,200 token 量级，属于"能塞进 8K 还有余量"。

### 2.2 单次调用的输出体量

| 调用 | 结果 | 字节 | 估算 token | 耗时 |
| --- | --- | --- | --- | --- |
| B `GetLiveContext`（全屋上下文） | 正常 | 2,803 | ≈697 | 56 ms |
| B `HassTurnOn`（不存在的名字） | isError=true | 479 | ≈119 | 57 ms |
| C `list_entities`（全部实体，不限域） | 正常 | 8,938 | ≈2,234 | 36~70 ms |
| C `get_entity`（单实体） | 正常 | 174 | ≈43 | 5 ms |
| C `get_entity`（不存在的实体） | **isError=false** | 44 | ≈11 | 4 ms |
| E `observe_home` | 正常 | 864 | ≈216 | 44 ms |
| E `inspect_room(living_room)` | 正常 | 351 | ≈87 | 30 ms |
| E `inspect_device(living_room_ac)` | 正常 | 973 | ≈234 | 31 ms |
| E `execute_action`（不存在的设备） | isError=true | 402 | ≈98 | 2 ms |

### 2.3 写路径：调用多久返回 vs 世界多久变过来

| 路线 | 调用耗时 | 状态落定耗时（从调用开始） | 返回内容 |
| --- | --- | --- | --- |
| B 开灯 | 119 ms | 190 ms | `action_done` + 成功实体清单（约 250 B） |
| B 关灯 | 58 ms | 409 ms | 同上 |
| C 开灯 | 40 ms | 178 ms | **空** |
| C 关灯 | 7 ms | 177 ms | **空** |
| E 开灯 | 572 ms | 190 ms（落在调用内部） | `verified=true` + `state_after{on:true}` |
| E 关灯 | 544 ms | 187 ms（落在调用内部） | 同上 |

读法：B/C 都是"调用先回、世界后变"，中间这个 100~400 ms 窗口里模型如果复查，
看到的是旧状态；C 更极端——写成功了却什么都不返回。
E 用 500 ms 级的回读把世界落定收进调用内部，代价是单次调用变慢（0.55 s 量级）。

### 2.4 名字与歧义（B 专属）

```text
模型看到的设备名是"设备名 + 实体名"拼起来的：
  Air Conditioner Air Conditioner / Dimmable Light Dimmable Light / On/Off Light On/Off Light
其中 On/Off Light On/Off Light 在三间房各有一个 → 只给名字必然歧义
实测：HassTurnOn{name:"On/Off Light On/Off Light"}（不带 area）
      → isError=true，no_match_reason=<MatchFailedReason.DUPLICATE_NAME: 11>
      → 错误内容是 Python 对象 repr，没有任何"请指定房间"的提示
实测：名字写得短一点（"On/Off Light"）→ NAME 匹配失败，同样是 repr
我们的命名要背一部分责任：设备名与实体名相同，拼出来就重复了；传感器还中英混排
（"kitchen 温度"），这是本机命名规范的问题，会原样暴露给任何走 Assist 的客户端
```

## 3. 维度分析：端侧模型真实使用时撞到什么

### D1 固定上下文开销

```text
现象    C 工具面 8,907 token；B 1,137；E 1,000
端侧    4B 级模型常见 4K/8K 上下文：C 直接超预算；B/E 还能留 6~7K 给推理与观察
我们的补法  工具数 8、描述写短、参数用 schema 表达（enum/min/max/step）而不是写进文字
我们还要改  execute_action 的 UNKNOWN_DEVICE hint 会把 12 个设备 id 全列出来（98 token），
          改成"给 3 个候选 + 提示用 inspect_room"更省
```

### D2 读输出的信噪比

```text
现象    C list_entities 返回全屋所有实体（conversation / backup / sun / 我们的 25 个都在），
        一次 8,938 字节；B GetLiveContext 返回全屋 dump，含大量与当前任务无关的设备与属性；
        E observe_home 只给 3 房间 + 4 环境量 + 设备 id（864 字节），inspect_room 只给一个房间（351）
端侧    小模型的注意力被无关实体稀释，还容易"看错设备"；上下文越满，多轮越早撑爆
我们的补法  按房间/设备分层的读接口 + 固定六字段，让"读什么"由模型显式决定
```

### D3 参数形态与可控性

```text
现象    B 的参数是自然语言槽位（name/area/floor），12/12 工具没有必填标记；
        C 是 entity_id + service + 自由 data，0/29 工具带范围约束；
        E 是 device_id + 8 个动作名 + 设备自报的 min/max/step
端侧    自由文本参数 = 小模型最不稳的地方（名字写错、大小写、重复名）；
        没有范围约束 = 越界只能等后端报错（我们实测 HA 对 40°C 返回 500）
我们的补法  动作名固定 8 个、参数带范围、本地先拦越界 → BAD_REQUEST，不发给后端
```

### D4 错误反馈

```text
现象    B 的错误是 Python repr（<MatchFailedError result=MatchTargetsResult(...)>），
        isError=true 但既没告诉模型"错在哪"，也没给下一步；
        C 的错误只是文本 {"error": "HTTP error: 404 - Not Found"}，而且 isError=false；
        E 是 {code, message, hint} 结构化，isError=true（hint 偏长，见 D1）
端侧    错误信息本身就是上下文开销；repr 这种内容对模型零信息量，还会诱导它复述给用户
我们的补法  code 可判定、message 说人话、hint 给下一步；对外不说内部实现细节
```

### D5 写后验证

```text
现象    见 2.3：B/C 返回时世界还没变，C 甚至返回空；E 在调用内部完成回读并给出 verified
端侧    小模型没有"等一会儿再查"的自觉；没有验证就可能报喜不报忧，
        或者复查到旧状态后反复重试（多步级联错误的主要来源）
我们的补法  execute_action 回读 500 ms×3，返回 verified 与 verify_note；
        目标级判定交给 check_goal（conditions + keep）
```

### D6 调用轮次（一次"开客厅侧灯"）

```text
B  名字已知且不歧义：1 次；要先看家里有什么：GetLiveContext + HassTurnOn = 2 次
C  已知 entity_id：1 次；不知道 id：list_entities（或 search_entities_tool）+ entity_action = 2 次
E  已知 device_id：1 次；不知道：inspect_room + inspect_device + execute_action = 3 次
端侧    轮次越多，级联失败越多（SMH-Bench 自己的结论）；
        我们在"已知 id"时只要 1 次，但"探索未知"时比 B/C 多一步——
        inspect_room 的返回里已经带了设备 id 列表，可以省掉 inspect_device
```

### D7 端侧部署面

```text
B  需要一个支持 Streamable HTTP 的 MCP 客户端 + HA 长期令牌；认证走 HA（服务端在 HA 里）
C  需要在本机跑 Python（或用它的 docker 镜像）+ HA 地址与令牌；工具面向来不打折（29 个）
E  需要在本机跑我们的 stdio server（Python）+ 令牌；工具面 8 个
端侧    三条都要把长期令牌放到设备上（同样的信任假设）；差别在"要装多少东西、
        工具面多大、要不要公网"。C 是唯一把"仪表盘/自动化运维"也塞进同一个面的
```

### D8 可判定性与训练

```text
现象    B 的返回值是 Assist 的 speech/response_type，C 返回自由文本或空；
        两者都没有"固定的状态字段"和"动作空间"
端侧    没有稳定契约就没法定义奖励、没法自动判分、也没法比较两个后端是否等价
我们的补法  六状态字段 + 8 动作词表 + check_goal，正是给"可判分"准备的
```

### D9 迁移性与跨后端

```text
B 的语义绑在 Assist 意图上、C 的语义绑在 HA 服务名上 → 换成沙盒后端都要重写一遍
E 的契约在 contract 层，两个后端各写一份翻译即可（这是支柱 3 的前提）
```

## 4. 我们的补法汇总（对着每一维）

```text
D1 工具面    8 个工具 ≈1000 token；下一步把错误 hint 缩短
D2 读信噪比  房间/设备分层读，六字段固定；不接受"全屋 dump"当默认观察
D3 参数      8 动作 + 设备自报范围 + 本地拦截
D4 错误      code/message/hint 三段式，模型可判定、可对用户复述
D5 验证      调用内部回读 + verified；目标级 check_goal
D6 轮次      已知 id 一次调用；未知时 inspect_room 已含 id，可少一步
D7 部署      stdio + Python + 令牌，工具面最小
D8 判分      六字段 + 动作词表 + conditions/keep
D9 迁移      contract 与 backend 分层，接沙盒只加一个 backend 目录
```

## 5. 本次评测的边界（别过度解读）

```text
只测了接口面的静态量与 3 类调用，没有跑模型：所谓"端侧适配"目前是
  "上下文预算 + 参数形态 + 错误反馈"三条可量化的推论，不是小模型成功率
token 数是估算，不是真实分词器的结果；量级比较可靠，绝对数别引用
B 的命名质量有一部分是我们自己的锅（设备名=实体名、传感器中英混排），
  这条要修：改 publisher 的命名，或者至少让 name 不重复
C 只测了 voska/hass-mcp 一个项目，ha-mcp 8.5.0 只下载没跑；结论不代表整个社区
写路径每档只跑了一次，落定耗时是单次观测（与 11 号文档 236~388 ms 的量级一致）
```

## 7. 预实验：端侧场景下现有接入方案的适配性（论文写法草稿）

| 观察项 | B 官方 MCP Server | C 社区 hass-mcp 0.6.0 | E 本工作 |
| --- | --- | --- | --- |
| 工具面固定开销 | 12 工具，≈1.1 k token | 29 工具，≈8.9 k token | 8 工具，≈1.0 k token |
| 单次读的返回体量 | 全屋上下文 ≈0.7 k token | 实体列表 ≈2.2 k token | 全屋快照 ≈0.2 k token |
| 写后验证 | 无（调用 119 ms / 落定 190 ms） | 无（40 ms / 178 ms，且返回为空） | 内嵌回读（≈570 ms，返回 verified） |
| 错误反馈 | Python repr，无下一步提示 | 不置 isError，需自行读文本 | {code, message, hint} |

我们把"端侧模型能否通过 MCP 稳定地控制真实住宅"当成一个可测量的前置问题，为此在同一台机器、同一时刻对三条接入方式做了同口径测量：Home Assistant 官方 MCP Server（B）、社区实现 hass-mcp（C），以及本工作自建的统一语义 MCP（E）。测量项包括工具面的固定上下文开销、单次读操作的返回体量、写调用与设备状态落定的时间差，以及错误反馈的形态。选择这些指标的理由很直接：端侧模型上下文有限、没有"等一会儿再查"的自觉，而住宅控制的正确性最终由世界状态而非调用返回值定义。

官方 MCP Server 的定位是把 Assist 的意图面暴露给任意 MCP 客户端。实测其工具面为 12 个工具、约 1.1 k token，规模尚可接受，但参数形态对端侧模型并不友好：所有工具都没有必填标记，目标以自然语言名字表达，而同一名字会在不同房间重复——本机三盏灯在 Assist 中都显示为 "On/Off Light On/Off Light"，仅给名字时匹配以 DUPLICATE_NAME 失败，错误内容还是一段 Python 对象的 repr。这类反馈既没有告诉模型错在哪里，也没有给出"请指定房间"的下一步，在端侧只能消耗上下文并诱发无意义的复述。

社区实现选择了另一个极端：把 HA 的实体与服务直接暴露出来。能力面因此很大，代价是固定开销急剧上升——29 个工具、约 8.9 k token，单次 list_entities 又产生约 2.2 k token 的全屋实体列表。对于 8 k 上下文的 4B 级模型，工具清单在用户开口之前就已经超出预算。写路径同样缺少可验证性：entity_action 成功时返回空内容，失败时未置 isError，模型只能从一行 44 字节的 {"error": …} 文本中自行判断成败。

把两条路线并置后可以看到，问题并不在"能不能控制设备"，而在三点结构性缺失。其一，动作与参数没有契约：既无必填声明，也无取值范围，模型必须凭记忆或试错来填写，越界往往要等后端以 500 之类的错误回敬。其二，写后没有验证：实测调用返回的时刻与状态真正落定的时刻相差 100–400 ms（开灯 119/190 ms、40/178 ms，关灯 58/409 ms），模型若立即复查，读到的仍是旧状态，于是要么误判自己失败，要么报喜不报忧。其三，语义被绑定在单一平台上：B 的语义是 Assist 意图，C 的语义是 HA 服务名，两者既无法迁移到训练所需的沙盒环境，也无法提供稳定的状态字段用于自动判分。

本工作的设计针对前两点给出了直接回应。契约层把动作收敛为 8 个词表、把状态收敛为 6 个字段，并把设备自报的 min/max/step 写入参数 schema，使固定开销保持在约 1 k token；越界在本地拦截，错误以 {code, message, hint} 返回，模型可以判断发生了什么、可以向用户复述下一步。执行层把回读内嵌进调用本身，返回 verified 与 verify_note，用约 0.55 s 的单次延迟换取"调用返回即可判定"的语义，目标级判定再由 check_goal 的 conditions 与 keep 表达。

第三点通过分层解决：契约定义动作与状态，后端各自翻译，同一份契约下再实现一个带快进的沙盒后端，训练与部署因此共用一套语义。这也是我们把预实验接到训练实验的接口——预实验指出的是接口形状问题，训练要回答的则是"端侧模型能否学会这套形状"。

需要说明的是，以上结论限于接口面与少量调用：本次并未运行端侧模型本体，token 数为估算，社区侧只取了一个项目，写路径为单次观测。因此我们将其作为预实验证据与下一阶段实验的设计依据，而不是最终结论；下一步将在同一批任务上用本地 4B 级模型与云端模型对照，检验"上下文预算、参数形态、错误反馈"三条推论是否会转化为成功率与轮次上的差异。
