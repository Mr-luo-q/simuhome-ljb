# 外界大模型控制 Home Assistant 的现存方式

调研日期 2026-09-18。结论先行：外部大模型想控制 HA，目前有六条现实路线，
它们的分歧不在"用不用 LLM"，而在**谁负责挑工具、暴露什么粒度、有没有验证闭环**。

```text
A  HA 内置 LLM 对话代理      模型在 HA 里面：HA 组 prompt + 工具，模型回工具调用
B  官方 MCP Server           模型在外面：HA 把 Assist 的工具面挂成 MCP（/api/mcp）
C  社区 MCP Server           模型在外面：第三方项目自己调 HA 的 REST/WS，自己定工具面
D  HA 当 MCP 客户端          反向：HA 的对话代理去调外部 MCP server 的工具
E  直接 REST / WebSocket     绕开上面所有层，自己写控制逻辑（我们走的这条）
F  非 LLM 传统通道           Alexa / Google Assistant / HomeKit（对照基线，不是 LLM）
```

## 1. 先把"控制面"拆成三层

```text
① 协议层      Matter / Zigbee / Z-Wave / MQTT / ESPHome …
               ↓ 各自的集成把它翻译成
② HA 抽象层   实体(entity_id) + 服务(domain.service + data)   ← 最底层的控制原语
              意图(intent：HassTurnOn / HassLightSet …)       ← Assist 的语义层
              脚本 / 自动化 / 场景                             ← 可复用的动作组合
               ↓ 再往上，谁来决定"调哪个、传什么"
③ LLM 接入层  A 内置代理 / B 官方 MCP / C 社区 MCP / D 反向 / E 自建
```

路线 A~E 的差别几乎全部落在第 ③ 层：**工具清单由谁给、粒度多细、错了能不能发现**。
第 ② 层是公共底座——所有路线最后都要落到"服务调用 + 实体状态"，包括我们。

## 2. 路线 A：HA 内置 LLM 对话代理（模型在 HA 里）

核心集成（本地源码 `components\` 下都在）：
`openai_conversation`、`google_generative_ai_conversation`、`anthropic`、`ollama`，
社区另有 `home-llm`（本地小模型，1435★）。

```text
运行方式   HA 自己组 prompt 与工具清单 → 调模型 → 模型回工具调用 → HA 执行 → 再回灌结果
关键配置   llm_hass_api：assist（把 Assist 的意图当工具）或 none（纯聊天，不控设备）
工具从哪来  helpers\llm.py 的 AssistAPI：把 intent handler 逐个包成 IntentTool
           工具名是 intent_type 的 slug（HassTurnOn / HassLightSet / HassStartTimer …）
参数形态    intent 的 slot_schema —— 槽位是 name / area / floor 这类自然语言定位，
           不是 entity_id；代码里还会按设备所在区域补 preferred_area_id / preferred_floor_id
可见范围   只暴露"已暴露给 Assist 的实体"（_get_exposed_entities），默认没暴露就等于看不到
被排除的   AssistAPI.IGNORE_INTENTS 明确忽略一批：GetState、GetTemperature、GetWeather、
           Toggle、Nevermind、GetCurrentDate/Time、Respond，以及已弃用的 Open/CloseCover
           —— 其中"读状态"主要靠 GetLiveContext + 动态上下文，而不是一个通用查询工具
```

优点：开箱即用、HA 负责工具循环与会话、和语音（Assist pipeline）共用一套意图。
局限：模型换了工具面就换了（prompt 与 intent 都是 HA 的）；粒度是意图槽位，
拿不到"设备 + 动作类型 + 参数范围"的稳定契约；没有跨后端（沙盒）概念。

## 3. 路线 B：官方 MCP Server（模型在外面，走 MCP）

本地源码实测（`components\mcp_server\`）：

```text
manifest    domain=mcp_server，名称 "Model Context Protocol Server"，
            dependencies = http + conversation，requirements = mcp==1.26.0 + aiohttp_sse + anyio，
            iot_class=local_push，注释者 @allenporter，single_config_entry
端点        /api/mcp                  Streamable HTTP（推荐）
            /mcp_server/sse          旧版 SSE（会话流）
            /mcp_server/messages     SSE 的配套 POST 端点
鉴权        继承 HomeAssistantView.requires_auth = True（helpers\http.py:128）
            → 客户端要带 HA 的长期访问令牌，和调 REST API 同一套凭据
```

它对外暴露三样东西，全部来自"你在集成配置里选的那个 LLM API"：

| MCP 能力 | 内容 | 来源 |
| --- | --- | --- |
| tools | 所选 LLM API 的工具清单（选 assist 就是上面那批意图工具） | `llm_api.tools` |
| prompts | 一个：该 API 的默认 prompt | `llm_api.api_prompt` |
| resources | `assist_context_snapshot`（纯文本上下文快照） | 仅当该 API 带 `GetLiveContext` 工具时 |

调用链是**纯 Assist 语义**：

```text
MCP tools/call → llm_api.async_call_tool → intent.async_handle（意图匹配 + 槽位填充）
              → 落到 entity + service 调用
```

两个只在源码里能看到的细节，对我们有参考价值：

```text
① 工具 schema 被简化过   server.py 的 _format_tool 只把 properties 放进 inputSchema，
                        没有 required —— 也就是说哪个参数必填，模型看不出来
② 会话粒度              每个 MCP 会话建一个 Server 实例，llm_context 按会话给
                        （扬声器/设备的区域偏好就是从这里带进 intent 的）
```

对照我们的实测（`..\HomeAssistant双仓库接口分析\02、03 号文档`）：本机容器 2026.6.4 里
官方 MCP 挂在 `/api/mcp`，Assist 工具用 `name/area/floor` 定位而不是 `entity_id`——
与源码一致。

## 4. 路线 C：社区 MCP Server（各自调 REST/WS）

GitHub 搜索快照（2026-09-18，"home assistant mcp" 命中 234 个仓库）：

```text
4772★  homeassistant-ai/ha-mcp          Python   官方之外的"大而全"实现
 629★  Coolver/home-assistant-vibecode-agent  偏向"帮你在 HA 里写代码/改配置"
 576★  tevonsb/homeassistant-mcp        TypeScript，环境变量 HASS_HOST / HASS_TOKEN / HASS_SOCKET_URL
 342★  voska/hass-mcp                   Python，工具面典型：get_entity / entity_action /
                                        list_entities / call_service_tool / restart_ha …
 106★  robbrad/homeassistant-mcp
  56★  jango-blockchained/advanced-homeassistant-mcp  号称 50+ 工具、3 种传输
```

共同点（也是和我们最大的不同）：

```text
接入方式   都是"外部进程 + HA 长期令牌"，直接打 REST /api/states、/api/services 或 WebSocket
工具粒度   实体级：list_entities / get_entity / call_service(entity_id, service, data)
参数约束   基本没有：服务参数怎么写靠模型记，写错了由 HA 报错
验证闭环   基本没有：调完不核对状态，模型说成功就算成功
工具数量   普遍偏多（几十个），小模型挑工具本身就变成主要失败源——
           homeassistant-ai/ha-mcp 为此换成"先 ha_search_tools 搜，再 ha_call_*_tool 调"的三段式
```

值得注意的是 `homeassistant-ai/ha-mcp` 的三段式模式（搜索 → 读工具 / 写工具 / 删工具），
它承认了一件事：**工具太多时，选工具比调工具更难**。这和我们在 13 号文档里
"按端侧小模型的学习成本倒推接口形状"是同一个问题的两种解法（它减上下文，我们减语义面）。

## 5. 路线 D：HA 当 MCP 客户端（反向）

本地源码 `components\mcp\`：domain=mcp，名称 "Model Context Protocol"，
dependencies = application_credentials，requirements = mcp==1.26.0。

```text
做法     把外部 MCP server 的工具注册成 HA 的 llm.Tool（ModelContextProtocolTool），
         挂成一个 llm.API（ModelContextProtocolAPI），给对话代理选用
方向     和路线 B 相反：不是"模型来控 HA"，而是"HA 的助手去调外部工具"
用途     例如让 Assist 查天气 API、查日程、调企业内部 MCP 工具
局限     只对 HA 内置对话代理有效；外部模型想用，仍然要绕回 B 或 C
```

## 6. 路线 E：直接 REST / WebSocket（我们走的这条）

```text
读取     GET /api/states、/api/states/{entity_id}、/api/logbook、WS config/*_registry/list
写入     POST /api/services/{domain}/{service}（entity_id + data）
鉴权     HA 长期访问令牌（Bearer），和 B/C 一样
我们的加层 在 REST/WS 之上自建 MCP server：统一动作词表（8 个动作）+ 六状态字段 +
         参数约束（设备自报 min/max/step）+ 四道闸门 + 回读验证（verified/verify_note）
```

和 B/C 的差别不是"能不能控"，而是**控完之后能不能说清楚**：

```text
官方 MCP（B）  语义来自 Assist 意图：模型说"HassTurnOn 客厅灯"，
               执行成功与否由意图层返回，参数范围不在契约里
社区 MCP（C）  语义来自 HA 服务：模型自己拼 entity_id + service + data，
               错了才知道错，且没有统一的状态字段
我们（E）      语义来自我们自己的契约：动作只有 8 个、参数有范围、状态只有 6 个字段，
               写后回读并把 verified 一起返回，同一份契约将来能换到沙盒后端
```

## 7. 六条路线对照

| 维度 | A 内置代理 | B 官方 MCP | C 社区 MCP | D 反向 MCP | E 自建（我们） | F 传统通道 |
| --- | --- | --- | --- | --- | --- | --- |
| 模型位置 | HA 内部 | 外部 | 外部 | HA 内部 | 外部 | 无（规则/语音） |
| 工具粒度 | 意图槽位（name/area/floor） | 同 A（Assist 工具） | entity_id + 服务名 | 外部工具原样 | 8 动作 + 参数约束 | 设备别名 |
| 谁选工具 | HA 组清单，模型选 | 模型选 | 模型选 | 模型选 | 模型选 | 无 |
| 读状态 | GetLiveContext 快照 | 同 A（资源） | 各项目自定 | 外部工具自定 | inspect_* + query_events | 基本无 |
| 参数校验 | 意图槽位校验 | 意图槽位校验 | 无 | 看外部工具 | 设备自报范围内本地拦截 | 无 |
| 写后验证 | 无（返回即成功） | 无 | 无 | 无 | 回读 + verified | 无 |
| 换模型 | 换集成即可 | 换 MCP 客户端即可 | 换 MCP 客户端即可 | 换对话代理 | 换客户端即可 | 不适用 |
| 跨后端（沙盒） | 不可能 | 不可能 | 不可能 | 不适用 | 契约层可换后端（设计目标） | 不可能 |
| 端侧小模型成本 | 中（工具多但语义粗） | 中 | 高（工具多、参数自由） | 看外部工具 | 目标是最低（工具少、参数受约束） | 不涉及 |

## 8. 对我们三个支柱的映射

```text
支柱 1（连通沙盒与六任务族）
  A/B 给不了：它们绑死在 HA 的意图与服务上，没有"同一个动作在两个世界里都成立"的概念
  C 给不了：社区实现全部是 HA 单端
  E 是唯一能同时接 HA 与沙盒的形态 —— 这正是我们自建 MCP 的理由

支柱 2（用环境奖励训练）
  A/B/C 都不面向训练：没有稳定的动作空间、没有可判定的状态字段，奖励没法定义
  E 的动作词表 + 六状态字段 + check_goal 就是为"可判分"准备的

支柱 3（双后端同语义）
  A/B 的"语义"是 Assist 意图；C 的"语义"是 HA 服务名 —— 两者都不可迁移
  E 的语义是我们自己的动作词表，两个后端各写一份翻译即可（contract 已按这个原则分层）
```

## 9. 结论与边界

```text
可以直接拿来用的   路线 A/B 做"人对着 HA 说话"这类场景最省事，官方 MCP 也能让
                  Claude Desktop 之类客户端立刻控 HA；我们不做重复建设
不能拿来用的       A/B/C 都不满足"同一动作词表跨后端"与"写后可验证"，
                  也没有为端侧小模型裁剪工具面 —— 这是我们要自己做的那部分
要盯着的          官方 MCP Server 还在演进（本机容器 2026.6.4 已有，源码 clone 是
                  2026.7 开发版）；如果哪天它开始暴露 entity 级工具或参数 schema，
                  我们的差异点要重新核对
没核实的          社区项目的功能细节只看了 README 与星数快照，没逐个跑过；
                  官方 MCP 的鉴权细节只在源码层确认（requires_auth=True），
                  没在真机上逐个端点验证
```
