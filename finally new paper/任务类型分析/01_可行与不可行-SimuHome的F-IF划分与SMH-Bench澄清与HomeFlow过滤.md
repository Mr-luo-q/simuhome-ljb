# 可行与不可行：三种"任务合不合法"的处理方式

日期 2026-09-23。问题来自 SimuHome：它的每个任务类型都分 feasible 与 infeasible 两个变体。
本文回答三件事：这个划分到底在测什么；SMH-Bench 与 HomeFlow 有没有同类设计；
对我们的六任务族、训练数据与强化学习 demo 意味着什么。

## 0. 一句话结论

```text
SimuHome   显式二分：6 个 QT × F/IF = 12 类、每类 50 回合、共 600。
           可行任务用模拟器状态比对判分；不可行任务用带规则的 LLM 评判员判"有没有说明做不到、有没有编造"
SMH-Bench  不标 F/IF，把"该不该动手"变成响应模式选择：澄清 or 执行（TC3 澄清），
           判分看模式选对没有；它的任务生成期就保证设备与能力真实存在，所以没有"物理做不到"这一类
HomeFlow   不把不可行当类别：数据生成阶段用硬约束 + 三重过滤把不可行样本直接丢掉，
           只保留蓝图验证器能判定的样本去训练
对我们     评测要 infeasible（它测的是幻觉与过度执行），训练数据要过滤（否则奖励无法定义）；
           而"正确识别不可行"这件事，我们能用世界状态零变化来判，不必依赖 LLM 评判员
```

## 1. SimuHome：F/IF 是什么

### 1.1 结构

```text
6 个 Query Type   QT1 环境/状态查询、QT2 隐含意图、QT3 显式控制、
                  QT4-1 绝对时间调度、QT4-2 事件锚点调度、QT4-3 双设备协同调度
每个 QT 两个变体    Feasible / Infeasible
规模              12 类 × 50 回合 = 600 回合
```

论文原话（摘要与贡献部分）："每种类型均提供可行与不可行变体，以评估智能体在主动意图推理、
动态状态与物理限制检查以及时间调度方面的能力……可行案例通过比较 SimuHome 中的结果状态与
目标状态进行评分。不可行案例包含错误前提、物理限制或时间冲突，由大语言模型评判员进行评估。"
第 4.1 节又强调："每种类型都配有一个不可行场景，以测试智能体的逻辑一致性与约束处理能力。"

### 1.2 不可行的四种成因（从附录 A.1 的例子归纳）

```text
① 设备不存在      QT1："浴室风扇 1 有哪些模式" → 浴室里根本没有这台风扇，应答"未找到"
② 能力不存在      QT2："办公室太冷了" → 办公室没有热泵，无法升温，应说明做不到
③ 时间矛盾        QT4-1："现在是下午 6 点吧？5 分钟后 6:05 开厨房灯" → 实际时间不是 6 点
④ 约束不可达      QT3：设备存在，但操作依赖或物理限制使目标达不成（论文里最难的子类）
```

### 1.3 判定方式与可行任务不同

可行任务靠**模拟器状态比对**（结果状态 vs 目标状态），不可行任务靠**LLM 评判员**。
附录 A.9.2 的 QT1 不可行评判提示词给出一组通过条件，其中两条最能说明问题：

```text
"设备不存在识别：对于设备_属性目标，智能体明确说明该设备不存在"
"无捏造设备数据：智能体不得为不存在的设备提供虚构的属性值"
```

也就是说，不可行任务的"正确"= **识别 + 说明 + 不编造**，而不是"把事办成"。
同一段提示词还要求房间状态问题照常答对——不可行变体不是"整句话都办不到"，
而是"有一半要求做不到，另一半仍要准确回答"。

### 1.4 论文自己总结的失败模式（针对不可行的三类错误码）

```text
CM  矛盾处理不当   测到了矛盾但处理错了。例：要求用不存在的热泵升高厨房温度，
                  模型反而去操作客厅的热泵
CB  矛盾盲视       没识别出不可行，继续按有效请求执行（QT4 的主要问题：
                  没看出时间矛盾，照样排了调度）
LJ  LLM 评判错误   评判员本身判错（论文把这一类单列出来，说明 LLM 判分有噪声）
```

论文的结论是：模型在"识别不存在的设备"上尚可，但**"设备存在、约束让目标不可达"这类
更难的不可行**普遍处理不好；时间维度最差。

### 1.5 设计意图

```text
测幻觉        会不会给不存在的设备编属性
测过度执行    会不会明知做不到还去动别的设备（CM 那个例子）
测前提校验    会不会先检查请求隐含的前提（时间、设备、能力）
```

## 2. SMH-Bench：没有 F/IF，但有"澄清 vs 执行"

### 2.1 机制

SMH-Bench 的智能体提示词（附录 G.2）写死了响应模式二选一：

```text
"响应模式必须是澄清或执行。
 如果上下文允许你推断出唯一且可执行的目标设备、功能和参数，则直接执行。
 如果存在多种合理的解释，或者关键的目标、功能或方向缺失，请使用澄清模式提出澄清问题。"
```

任务类别里对应的是 **TC3（澄清）**：初始话语故意欠定义（缺房间、缺设备、缺模式、缺数值、
缺时长或时间），隐藏目标通过"预期查询 / 参考澄清轨迹"给出。

### 2.2 判分方式

```text
澄清任务   看澄清行为是否恰当，由 GPT-5 评判（论文明确写了这一点）
错误分类   表里专门有两项"模式选择"错误：
           "执行预测为澄清" 与 "澄清预测为执行" —— 把该动手时问问题、
           该问问题时动手，当作一类独立的失败来看待
```

### 2.3 与 SimuHome 的关键差别

```text
SimuHome 的不可行 = 物理/逻辑上做不到（设备不存在、能力没有、时间矛盾、约束不可达）
SMH-Bench 的不可行 = 语义上说不清（欠定义、多个合理解释）→ 处理方式是"澄清"
```

为什么 SMH 没有 SimuHome 那种"物理不可行"？因为在任务生成阶段它就把这一层堵死了：
论文写明任务样本"基于家庭中实际存在的设备、服务和状态进行落地……防止引用不存在的房间或
不支持的操作"。所以 SMH 的不可行性是**语用层面**的，不是**物理层面**的。

## 3. HomeFlow：把不可行排除在训练分布之外

HomeFlow 是数据飞轮（为训练合成轨迹），它不把不可行当任务类别，而是用**构造式过滤**保证
进训练集的样本都是可执行、可验证的：

```text
三重过滤（生成评估函数时）
  ① HomeEnv 沙箱执行可执行性检查 → 拦截解析错误与未定义的设备实体
  ② 对照设备 schema 验证边界有效性 → 参数必须落在硬件允许范围内
  ③ GPT-5 交叉验证条件、指令意图与用户画像的逻辑一致性
  任何一条不通过 → 直接丢弃该条件

硬约束（生成任务时）
  设备约束（只能用环境中显式定义的设备，标识符完全匹配）
  属性约束（只能用服务定义里列出的属性）
  原子性约束（一个任务恰好一个用户意图）
  物理一致性约束（动作必须物理可执行、状态转换真实）
  设备状态依赖约束（改依赖属性前必须先激活设备）

验收方式
  蓝图验证器（Blueprint Verifier）：会话终止时满足全部条件才算成功；
  MCTS-Flow 的搜索里也带通过性指示器，只复用可通过的前缀
```

含义很清楚：**HomeFlow 用"过滤"换"奖励可定义"**。代价是模型在训练分布里见不到
"做不到的请求"，也就学不到拒绝与澄清。

## 4. 三条路线对照

| 维度 | SimuHome | SMH-Bench | HomeFlow |
| --- | --- | --- | --- |
| 不可行怎么处理 | 显式类别（F/IF） | 响应模式（澄清/执行） | 生成期过滤，不进数据集 |
| 覆盖什么样的"做不到" | 设备不存在 / 能力不存在 / 时间矛盾 / 约束不可达 | 语义欠定义、多个合理解释 | 不覆盖（被过滤掉） |
| 怎么判 | 可行比状态；不可行用带规则的 LLM 评判 | GPT-5 评澄清是否恰当 | 蓝图验证器 + 环境执行 |
| 数据用途 | 评测（600 回合） | 评测（TC 分类） | 训练数据合成 |
| 有噪声的地方 | LLM 评判员本身（论文单列 LJ 错误） | GPT-5 判分 | 过滤器的召回（漏放会污染训练） |

## 5. 对六任务族与 RL demo 的影响

### 5.1 评测侧：每个任务族配一个不可行变体，判定用规则而不是 LLM

```text
可以照抄 SimuHome 的结构：每个族一个 F 变体 + 一个 IF 变体
但判定不需要 LLM 评判员：我们能把"正确识别不可行"翻译成可验证的事实
  设备不存在   期望：不改动任何设备 + 返回 UNKNOWN_DEVICE（或明确说明设备不存在）
  能力不存在   期望：目标设备状态零变化 + 说明缺少对应能力
  时间矛盾     期望：不注册任何调度 + 指出时间不自洽
  约束不可达   期望：不执行副作用动作 + 说明依赖/范围不满足
判定式：world_state_after == world_state_before（世界零变化）+ 错误/说明命中
这比 LLM 评判更硬，也避开了 SimuHome 自己都单列出来的 LJ 类错误
```

### 5.2 训练侧：过滤可行样本，但把"拒绝/澄清"做成合法动作

```text
HomeFlow 的教训：训练数据必须过滤（奖励要有定义），否则模型会学到"乱动也拿分"
SMH 的教训：澄清是一种合法的输出模式，不是失败
折中：训练集只用 F 样本；但动作空间里保留一个 abstain / ask_clarification 动作，
     让模型在遇到 IF 时有正确的出口（否则它只能选择"乱动"）
```

我们现在的问题：**MCP 契约里的 8 个动作全是物理动作，没有"拒绝/澄清"这个动作**。
要做"识别不可行"的训练或评测，必须先在契约里把它补上（见 5.4）。

### 5.3 评测口径：F 与 IF 分开报

```text
成功率（F）与正确识别率（IF）是两个不同的指标，混在一个数里会互相掩盖
SimuHome 的做法就是分开列 F/IF 两张成功率；我们也按这个口径出表
另外单列一类"过度执行"（world 变了但目标是做不到的）——它比"什么都没做"更危险
```

### 5.4 落到实现（给训练 demo 的三条待办）

```text
① 契约层加一个 abstain（或 ask_clarification）动作：
   execute_action(action="abstain", reason="...") 或单开一个工具；
   判定时把"世界零变化 + reason 命中"记为正确
② 数据层：每族生成 F 与 IF 两类任务，IF 任务保证"确实做不到"（生成期校验，
   参考 HomeFlow 的三重过滤思路，只是把过滤反过来用——我们要的是"确认做不到"）
③ 评测层：reward 三分量——目标达成、世界保持（keep）、不可行时的零副作用；
   与 check_goal 的 conditions/keep 对得上，不需要新造判定器
```

## 6. 与三支柱的关系

```text
支柱 1（连通沙盒与六任务族）
  加 IF 变体让任务集更像真实住宅：用户经常会提出做不到的请求，
  这也是 SimuHome 与 SMH 都单独设类的原因

支柱 2（用环境奖励训练）
  IF 任务的奖励必须用"零副作用 + 说明"表达，否则模型会学到"乱动拿分"；
  这条规则同时约束了我们的奖励设计与数据生成

支柱 3（双后端同语义）
  "做不到"在 HA 与沙盒两侧要表现一致（同一错误码、同一 world 零变化判据），
  这正好是跨后端一致性的一部分
```
