# Benchmark 任务范畴讨论：第一支柱到底包含哪些任务

本文档只讨论第一个支柱的“内容物”，并把结论接到 SFT+RL 与 MCP 迁移上。要回答的问题是：如果我们要发一篇新论文，benchmark 的任务集合应该由哪几类组成，才能同时做到“比已有四篇更全面”和“有自己真正的新类别”。

核心主张先写出来：

```text
benchmark 用 6 个任务族：
  T1 空间语义与连通推理（我们的核心创新）
  T2 指令执行与控制鲁棒性
  T3 模糊、省略与指代理解
  T4 时间、调度与环境动力学
  T5 长期记忆、个性化与多成员共居
  T6 环境感知与工具型信息获取

另有 4 个横切特性，不单独算任务族：
  有效/无效任务成对出现
  直接推理 vs 工具型智能体两种模式
  episodic 与 long-horizon 两层时间尺度
  环境复杂度与空间拓扑可分档
```

六个任务族加四个横切特性，就是“把别人每篇分别有、但不是都有的东西尽量并进来，同时把空间做深”的最小完整集合。

## 1. 范畴来源：两个文件夹的文献各自贡献了什么

先从“两个文件夹”倒推任务范畴，防止我们凭空自造分类。

### 1.1 四个 bench 各自占住的范畴

```text
HomeBench
  单/多设备显式控制、无效指令识别、组合动作
  → 对应任务族 T2

SimuHome
  环境状态感知、隐式意图、时间/调度、可行与不可行
  → 主要对应 T3、T4，部分 T6

SMH-Bench
  原子控制到组合控制、模糊意图、自动化调度、多轮、记忆、环境查询、复杂度分层
  → 覆盖 T2、T3、T4、T5、T6 的能力谱

PersonalHomeBench
  角色、家庭记忆、反事实、主动推荐、计划生成、部分可观测、工具型 agent
  → 主要对应 T5 和横切特性“直接 vs 工具型”
```

这四个 bench 加在一起几乎覆盖了六类任务中的五类，唯一整类空白是 T1（空间语义），而这正是我们的核心创新位。

### 1.2 方法文件夹贡献的“任务细节”

方法文件夹不能直接给任务类别，但能告诉我们每个任务类别里真正难的子问题长什么样：

```text
主线 B（模糊指令理解）
  01 MvTAP：规则背后隐性意图（节能/安全/舒适）
  03 HomeGenii：复杂条件规则生成
  04 VCU-LLM：端侧模糊指令与控制计划
  09 Sasha：欠明确目标（“让客厅舒适”）
  12 MiCU：真实日志合成 + 端到端理解
  13 PEC-Home：省略等级 1~4、多用户偏好、动态偏好
  → 决定 T3 内部必须有“隐性意图 / 欠明确目标 / 渐进省略 / 指代消歧 / 澄清”五种子结构

主线 C（综合系统）
  06 DevPiolt：操作顺序与长期习惯推荐
  08 IoTGPT：子任务分解与记忆复用
  14 AdaHome：意图路由、偏好免重训适应
  16 MemAura：记忆图、周期性行为预测、画像更新
  18 SAGE：工具化顺序执行、照片消歧、持久命令
  19 HomeFlow：仿真环境 + SFT + 可验证 RL 数据飞轮
  → 决定 T5 必须有“偏好形成/修正/跨成员”，也提示训练支柱要参考 HomeFlow
```

结论：bench 四篇决定“广度”，方法主线 B/C 决定“每个类别里的难度子结构”。

## 2. 六个任务族的定义

### T1 空间语义与连通推理（核心创新类）

这一类是别的 bench 没有、我们必须做深的一类。它不需要精确几何，只需要让空间关系能参与“动作选择、任务可行性、环境传播与副作用验证”。

```text
子结构
  T1.1 空间 grounding：按房间、相对位置、邻接关系找设备
       “客厅离沙发最近的那盏灯”
  T1.2 连通传播任务：设备效果沿连通边影响邻接房间
       客厅空调让无空调厨房降温
  T1.3 空间因果：改变连通关系会改变正确动作
       门开 vs 门关，风量/时间/可行方案不同
  T1.4 空间副作用约束：控制本房间时不得伤害邻接房间
       “卧室降温别让婴儿房过冷”
  T1.5 空间可行与不可行：因拓扑/可达性导致任务无解或需替代方案
```

代表性样例：

```text
场景：两室一厅，空调只在客厅
任务：让厨房在 20 分钟内达到舒适温度
可接受答案：开客厅空调强档并接受厨房间接降温，
            而不是报“厨房没有空调”或虚构厨房空调
变体：客厅与厨房的门从开变关后，同样的任务不再可解或需要换策略
```

这一族的评测价值在于：只给房间 ID 和“哪间房有空调”时模型答不对，只有查询到连通关系并把它用于推理时才可能答对。

### T2 指令执行与控制鲁棒性

承接 HomeBench 和 SMH-Bench 的原子/组合控制。

```text
子结构
  T2.1 单设备显式指令
  T2.2 多设备/组合指令（一句话里控制多个设备）
  T2.3 有效与无效指令成对
      设备不存在、功能不支持、参数越界、目标无法达成
  T2.4 动作合法性（前置条件、约束、副作用）
  T2.5 环境条件变化后的鲁棒执行
```

注意：无效指令不是一类独立任务，而是几乎所有任务族的横切变体。T2 只保留“以控制为目标”的无效/鲁棒问题。

### T3 模糊、省略与指代理解

承接主线 B 的六篇和 SMH-Bench 的模糊意图。

```text
子结构
  T3.1 隐性意图（规则或指令背后的目的：节能/安全/舒适）
  T3.2 欠明确目标（“让客厅舒适”，无设备无动作）
  T3.3 渐进省略（“还是把灯开大点”，省略等级 1~4）
  T3.4 指代消歧（多人/多设备/空间方向/历史指代）
  T3.5 澄清决策（该问还是该猜、该拒绝还是该执行）
```

建议在任务构造中把“省略等级”和“上下文长度”作为可调参数，这样能复现 13 PEC-Home 的诊断价值，而不是只报平均分。

### T4 时间、调度与环境动力学

承接 SimuHome 与 SMH-Bench 的自动化/调度类。

```text
子结构
  T4.1 延迟执行与定时任务
  T4.2 持续任务与目标达成验证
  T4.3 事件锚定调度（人物离开/设备完成/环境阈值触发）
  T4.4 时间可行性（太早/太晚/窗口错过）
  T4.5 状态演替（动作影响后续状态，且需要多步验证）
```

这一族是 RL 价值最容易体现的地方，因为延迟奖励和时序决策是 RL 的天然优势区。

### T5 长期记忆、个性化与多成员共居

承接 PersonalHomeBench、SMH-Bench 的记忆类，以及 16 MemAura、06 DevPiolt、08 IoTGPT、14 AdaHome。

```text
子结构
  T5.1 偏好形成：从重复行为中提取稳定偏好
  T5.2 偏好修正：新证据出现后更新旧认识
  T5.3 跨成员区分：避免把 A 的偏好用到 B 身上
  T5.4 长期习惯利用：作息、常用房间、常用设备组合
  T5.5 主动推荐与主动执行时机
  T5.6 记忆污染与遗忘：错误信息是否会长期残留
```

这一族应同时提供“被动查询型”（让我想起/告诉我偏好）和“主动服务型”（自行决定要不要做）两种形态。

### T6 环境感知与工具型信息获取

承接 SimuHome 环境查询、SMH-Bench 环境接地、18 TaskSense 的传感器/API 语义，以及四篇 bench 都强调的“先查后做”。

```text
子结构
  T6.1 环境变量查询与推断（温度/湿度/光照/噪声/能耗）
  T6.2 从部分可观测状态决定要查什么
  T6.3 传感器/API 能力 grounding（哪些能力存在、能做什么）
  T6.4 查询成本与信息冗余
  T6.5 信息不可得时的降级与澄清
```

T6 表面像“工具使用”，但真正测的是模型知不知道“自己缺什么信息、去哪里查、查完怎么用”，而不是工具本身是否好用。

## 3. 六类是否“最全面”的覆盖检查

用矩阵检查每个已有工作的方向是否被吸收：

| 已有方向                  | 代表来源                     | 我们放进了哪里           |
| ------------------------- | ---------------------------- | ------------------------ |
| 显式单/多设备控制         | HomeBench                    | T2                       |
| 无效/不可行指令           | HomeBench、SimuHome          | T2 + 横切变体            |
| 隐式意图                  | SimuHome、MvTAP              | T3.1                     |
| 模糊/欠明确目标           | Sasha、MiCU                  | T3.2                     |
| 渐进省略                  | PEC-Home                     | T3.3                     |
| 时间/调度/状态演化        | SimuHome                     | T4                       |
| 记忆/画像/偏好            | PersonalHomeBench、MemAura   | T5                       |
| 主动推荐/计划             | PersonalHomeBench            | T5.5                     |
| 环境查询/传感器 grounding | SimuHome、TaskSense          | T6                       |
| 工具型/部分可观测         | PersonalHomeBench、SMH-Bench | 横切特性                 |
| 长程连续生活              | PersonalHomeBench 的延伸     | 横切特性（long-horizon） |
| 空间语义                  | 无（我们的空位）             | T1                       |

从这张表看，T1~T6 + 四个横切特性已经覆盖两个文件夹里讨论过的全部任务方向。真正的取舍不是“要不要再加方向”，而是“每个方向做多深、是否都要进第一篇实验”。

## 4. 四个横切特性（决定“全面感”但不占任务族名额）

### 4.1 有效/无效成对出现

四个 bench 都证明无效/不可行是模型死穴。做法：每个任务族都生成 valid/invalid 变体，而不是只给一个全局 invalid 集合。T1 的 invalid 尤其有价值：设备不存在、房间不可达、拓扑不连通导致不可行。

### 4.2 直接推理 vs 工具型智能体两种模式

SMH-Bench 的 DR/EIA 双协议和 PersonalHomeBench 的纯推理/agent 双设置都显示：从“给全信息”切到“自己查”性能会大幅下降。我们的每一类任务都应有两种暴露方式：

```text
直接模式：一次给全所需上下文，测“会不会推理”
工具模式：只给部分信息，模型通过 MCP 工具查询，测“会不会查 + 会不会用”
```

T1 在工具模式下必须隐藏完整拓扑，只允许通过 `query_topology` 查询，否则空间任务会退化成读图题。

### 4.3 episodic 与 long-horizon 两层时间尺度

```text
episodic：T1~T6 单回合任务，成本低、可批量、可消融
long-horizon：把多天的生活轨迹串起来，让 T5/T6 和 T4 的跨天任务自然出现
```

首篇论文不必把六类全部做成 long-horizon，建议只让 T1、T4、T5 有长程变体。

### 4.4 复杂度分档与拓扑分档

```text
设备复杂度：小型(8~20 台) / 中型 / 复杂(100+ 台)
空间复杂度：单连通链 / 多房间网络 / 含不可达或需穿过房间的布局
```

复杂度分档要跟着“连通关系”走：让两套布局设备集合相同、但连通关系不同，是 T1 因果评测的核心手段。

## 5. 任务族与 SFT+RL 如何结合

训练支柱不是独立于 benchmark 的“另一件事”，而是用 benchmark 的任务产生数据、目标和奖励。每个任务族的结合方式不同：

### 5.1 按任务族分工

```text
T1 空间语义
  SFT：规则/LLM 演示产生的“先查拓扑→比较方案→执行→验证”轨迹
  RL 奖励：目标达成 + 空间副作用惩罚（邻接房间越界扣分）
  消融：改变连通关系后，训练模型是否给出不同动作

T2 指令控制
  SFT：显式指令-动作轨迹，覆盖有效/无效
  RL 奖励：成功 + 非法动作惩罚（不存在的设备/越界参数）

T3 模糊理解
  SFT：需要“澄清或推理”的轨迹，参照 PEC-Home 省略分级
  RL 难点：澄清决策稀疏，需在“多问一句”和“猜错”之间做权衡
  奖励可加：澄清代价、错误猜测代价

T4 时间调度
  RL 最直接受益：延迟成功、过早动作、错过窗口都要进入奖励

T5 记忆/个性化
  RL 难点：跨事件长期信用分配
  奖励改用 doc11 的累积效用思路：收益 − 干扰 − 副作用

T6 环境感知
  SFT：教“查什么”；RL 可惩罚无谓查询的 token/时间成本
```

### 5.2 训练流程建议

```text
第一步：先做 SFT
  数据 = 规则生活流 + 任务模板 + LLM 演示，全部在沙盒内验证可执行

第二步：再做可验证 RL
  复现 HomeFlow 的逐步 RLVE/GRPO 路线
  奖励来自沙盒状态验证，不是 LLM 裁判

第三步：分任务族评测
  episodic：成功率、非法动作率、token/时间成本
  long-horizon：累积效用、主动精度、时机误差、干扰率、偏好修正速度
```

训练结果要回答三个问题：

```text
SFT 是否明显优于直接 prompt（尤其 T3/T6）
RL 是否在 T4/T5 比 SFT 进一步受益（延迟奖励区）
训练后的模型是否在“未见连通拓扑”上仍有效（泛化证据）
```

## 6. MCP 迁移如何与任务族对齐

迁移支柱的目标是：训练完成的模型在 HA 上仍然能跑同一套任务逻辑。因为接口语义相同，模型不需要重新学“怎么调用”，只需要适应后端差异。

### 6.1 每个任务族需要的能力

```text
T1 空间     query_topology（房间/连通）
T2 控制     find_devices / inspect_device / execute_device_action
T3 理解     observe_home + conversation（澄清）
T4 时间     wait / query_events / check_goal_state
T5 记忆     memory_read / memory_write
T6 感知     inspect_room / query_events / sensor 查询
```

因此约 10 个接口可以同时服务六个任务族，不需要每族一套接口。

### 6.2 双后端语义映射

```text
沙盒                                 HA
query_topology                       area/floor 配置关系（需用户/注解）
find_devices                         entity/device 检索
inspect_device                       state + attributes + services
execute_device_action                call_service
inspect_room                         group/sensor/zone 聚合
wait / wait_for_event                订阅事件 + 条件等待
query_events                         history/logbook
check_goal_state                     state 条件断言
memory_read/write                    外部记忆服务或 conversation 会话
```

### 6.3 按任务族的迁移难度排序

```text
最容易：T2（HA 的 service 调用最成熟）
较容易：T4（HA 有定时、自动化、状态触发）
中等：T3（HA conversation 可承载，但澄清语义需对齐）
较难：T5（HA 没有原生长期记忆/画像，需外挂）
最难：T1（HA 的 area 关系需要配置，真家不一定有连通语义）
T6：取决于 HA 是否暴露相应传感器/服务
```

### 6.4 迁移论文的正确写法

不要写“同一个 MCP 所以模型能直接用”，要写：

```text
同一策略在 Sandbox 与 HA 双后端跑成对任务
三档迁移：零适配 / 仅 schema 适配 / 少量示例适配
报告：成功率保持、非法动作率、工具调用数、适配修改量
T1 在 HA 缺拓扑时降级为“不可测”，并单独报告覆盖率
```

这样迁移结论仍然成立，但不会在审稿时被“真实家庭没有现成拓扑”一击致命。

## 7. 待继续讨论的问题

```text
Q1 六类是否都进第一篇实验，还是分主实验/辅助展示？
  建议：T1+T2+T3 主实验，T4 增强，T5/T6 长程作展示

Q2 T5 与 T6 是否合并成“长期智能服务”一类？
  合并可减到 5 类，但环境感知会被弱化

Q3 每个任务族生成多少任务、覆盖多少个家庭拓扑才够“全面”？
  家庭数、拓扑类型数、设备规模需要给范围

Q4 invalid 变体要不要六族全配？
  全配最全面但成本高，可先保证 T1/T2/T4

Q5 long-horizon 只做 T1/T4/T5，还是也要 T6？

Q6 训练数据来源：每族都靠 LLM 演示会不会引入风格偏置？
  需要至少一个规则/脚本生活流基线
```

结论一句话：benchmark 的“全面”靠 6 个任务族 + 4 个横切特性实现，其中 T1 是唯一整类创新；训练与迁移都围绕这个任务集合展开，而不是各自独立设计。
