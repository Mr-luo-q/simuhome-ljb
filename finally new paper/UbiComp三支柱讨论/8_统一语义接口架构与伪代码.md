# 统一语义接口：训练端 env、部署端 MCP 的架构与伪代码

## 1. 结论先行

同一套语义接口落在两个端点上：训练端用 Gym env，部署端用 MCP。
本方案选定方案 A 作为唯一主线。三者的分工是：

```
ToolSpec：定义动作/工具语义（工具名、参数、返回、错误、时间） ← 唯一语义来源
Gym：训练时负责一局怎么开始与结束、步进后拿到什么信号        ← 训练层
MCP：部署时负责把同一份工具语义暴露给真实后端调用            ← 部署通道
```

方案 A 的执行路径是：

```
训练：policy → Gym env.step(action) → SandboxBackend → SimuHome world
部署：policy → MCP client → HomeAssistantBackend → HA service
```

训练 rollout 不经过 MCP 传输层，动作与观测语义通过 ToolSpec 与部署侧保持一致。方案 B、C 只在需要做接口一致性验证或统一编排时作为可选手段，不作为训练主路径。

## 2. ToolSpec、Gym 与 MCP 的职责边界

```
ToolSpec 需要回答的问题
  有哪些工具？工具参数 schema 是什么？
  返回结构与错误码是什么？
  时间语义、能力语义与实体映射怎么定义？

Gym 需要回答的问题
  env.reset() 之后初始观测是什么？
  env.step(action) 的动作空间是什么？
  step 返回哪些 obs/reward/terminated/truncated/info？
  一局何时结束？同 seed 能否复现？
  多个 env 实例能否并行采样？

MCP 需要回答的问题
  有哪些工具？工具参数 schema 是什么？
  调用参数是否合法？返回值结构是什么？
  调用失败时返回什么错误？
  工具有哪些资源可以读取？
```

两边有交集的是“动作表示”和“观测内容”。语义对接点就是这两项：

```
Gym action  ←→  MCP tool call
MCP tool result  ──→  observation 的一部分
```

## 3. 三种做法与取舍（采用方案 A）

### 方案 A：Gym 在内，MCP 在外（本方案采用）

训练循环直接调用 Gym env，env 内部直连沙盒后端。部署时把同一份 ToolSpec 暴露成 MCP，由 Home Assistant 后端执行。

```
训练：policy → Gym env.step(action) → SandboxBackend → SimuHome world
                                    ↑
                    同一份 ToolSpec ─┘
                                    ↓
部署：policy → HA MCP server → HomeAssistantBackend → HA service
```

优点是训练吞吐最高，状态隔离简单，训练与部署通过 ToolSpec 保持动作与观测定义一致。代价是训练 rollout 不经过 MCP 传输层，MCP 的延迟、失败与工具发现行为不会出现在训练数据里，需要用域随机化与契约测试补上。

方案 A 的精确表述：

```
语义统一发生在 ToolSpec 层，不发生在传输层
训练时：action schema 映射到 Gym action，直接交给 SandboxBackend
部署时：同一份 action schema 通过 MCP 传输到 HA backend
两者共享动作与观测定义，区别是传输层与后端实现
```

### 方案 B：MCP 作为 Gym 的动作通道

Gym env 的 step 内部通过 MCP client 调用 MCP server。动作映射成 tool call，工具返回进入观测。

```python
class MCPGymEnv:
    def step(self, action):
        result = self.mcp.call(action.tool, action.args)   # 走 MCP
        obs = self.build_observation(result)
        reward, terminated, truncated = self.evaluate()
        return obs, reward, terminated, truncated, {"result": result}
```

优点是训练路径与部署路径完全一致，训练时暴露的问题就是部署时会遇到的问题。缺点是每个训练 step 都要经过 MCP 传输，延迟高、并行需要多 session 隔离、超时重试会进入训练数据。方案 B 适合小规模一致性验证、真实 MCP 接口测试和最终小样本微调，不适合大规模 RL 采样。

### 方案 C：把 Gym 环境本身包装成 MCP server

把 reset/step/get_observation/is_terminated 也暴露成 MCP 工具，训练器作为 MCP client 驱动环境。

```
trainer → MCP tool: reset_env → MCP tool: step_env → MCP tool: get_reward
```

这样做的问题是 Gym 语义与 RPC 语义不匹配：episode 状态、并行实例、seed、轨迹回放、向量化都需要额外约定，现有 RL 框架也无法直接接入。它可以作为环境管理接口存在，但把每条 transition 都做成远程调用不划算。

### 方案对比

| 方案 | 训练吞吐 | 契约真实性 | 并行与隔离 | 实现复杂度 | 适用场景 |
|---|---|---|---|---|---|
| A 训练直连 + MCP 对外 | 最高 | 语义一致，传输不同 | 简单 | 低 | 本方案采用：大规模 SFT/RL 采样 |
| B MCP 作为 Gym 通道 | 中等 | 完全一致 | 需要 session 隔离 | 中高 | 一致性验证、小规模 RL、真实 MCP 训练 |
| C Gym 变 MCP server | 低 | 最低 | 需自行约定 | 高 | 环境管理、外部编排，不适合高频训练 |

本方案采用 A 作为训练主线。B 只在需要验证“训练路径也走 MCP”时使用，C 只在需要把环境本身纳入 MCP 编排时使用；三者共享同一份 ToolSpec。

## 4. 方案 A 的架构

```
                         ToolSpec（唯一语义来源）
               工具名 / 参数 schema / 返回结构 / 错误码 / 时间语义
                                     |
                     ┌───────────────┴───────────────┐
                     v                               v
              Gym Adapter                       MCP Tool List
              action_space                      tools/list, tools/call
              observation_space
              reward / terminated
                     |                               |
                     v                               v
              SandboxBackend                  HomeAssistantBackend
              （训练，进程内）                  （部署，真实时间）
```

四层职责：

```
ToolSpec        语义定义，不包含实现
Gym Adapter     把 ToolSpec 映射成动作空间、观测空间、奖励与回合信号
Backend         真正执行工具：训练是沙盒世界，部署是 HA service
Transport       训练不使用 MCP 传输（进程内直连）；部署使用 MCP 传输
```

## 5. 六个关键对接点

### 5.1 动作：tool call 与 action 一一对应

```python
action = {
    "tool": "execute_command",
    "args": {"device": "living_room_ac", "command": "set_cooling",
             "setpoint": 24},
}
```

这个字典既可以直接作为 Gym action，也可以直接作为 MCP 的 `tools/call` 参数。Gym 侧的 action_space 由 ToolSpec 自动生成，MCP 侧的 tool 列表也由同一份 ToolSpec 生成。

### 5.2 观测：tool result 是观测片段，不是全部观测

```python
def build_observation(backend, profile):
    obs = {"time": backend.call("get_current_time", {}),
           "rooms": {}, "devices": {}, "topology": None}

    for room in profile.visible_rooms:
        obs["rooms"][room] = backend.call("get_room_states", {"room": room})
    if profile.topology_visible:
        obs["topology"] = backend.call("get_topology", {})
    return obs
```

一次工具调用返回的只是观测片段（训练时来自 SandboxBackend，部署时来自 MCP tool result）；Gym 的 observation 是本决策点 agent 看到的完整信息。两者之间需要一个 observation builder，把多个工具结果拼成规范观测。

### 5.3 奖励与终止：由 Gym 环境计算，不放进 MCP 工具

```python
def evaluate(self, backend, goal):
    state = backend.call("get_home_state", {})
    reward = goal.score(state)
    terminated = goal.all_satisfied(state)
    truncated = self.t >= self.max_steps
    return reward, terminated, truncated
```

工具只负责执行与返回状态。奖励与终止条件属于训练环境语义，必须由 Gym wrapper 或独立的 goal verifier 提供，否则部署侧与训练侧的奖励定义会分叉。

### 5.4 时间：把 fast-forward 与真实等待统一抽象

```python
# 沙盒后端
def wait_until(self, when):
    self.world.fast_forward_to(when)      # 虚拟时间，瞬时完成
    return self.world.snapshot()

# HA 后端
def wait_until(self, when):
    self.scheduler.wait_real_time(when)   # 真实定时器/自动化
    return self.ha.get_states()
```

两边工具名与参数相同，内部时间语义不同。Gym 侧只需约定“wait_until 之后返回新的 decision point 观测”。

### 5.5 实例与并行：训练靠 env 实例隔离

方案 A 下训练不需要 MCP session。每个 rollout worker 直接持有一个独立的 Gym env 实例，env 绑定一个独立 world：

```python
class SpaceHomeEnv:
    def reset(self, seed):
        self.world = instantiate(self.scene, seed)   # 每个 worker 一个独立 world
        self.goal = sample_goal(seed)
        return self.observe(), {"goal": self.goal}
```

并行采样就是复制这个过程。部署时 HA MCP 侧才需要考虑 session 与会话状态，训练侧的隔离问题不经过 MCP。

### 5.6 传输：训练直连与部署走 MCP，用开关切换

```python
class SpaceHomeEnv(gym.Env):
    def __init__(self, backend):
        self.backend = backend     # 训练：SandboxBackend；部署：HABackend

    def step(self, action):
        result = self.backend.call(action)
        if action.advances_time:
            self.backend.advance_to_decision()
        obs = self.backend.observe(self.profile)
        reward, terminated, truncated = self.goal.evaluate(self.backend)
        return obs, reward, terminated, truncated, {"result": result}

env = SpaceHomeEnv(SandboxBackend(...))    # 训练主线：进程内直连
env = SpaceHomeEnv(HABackend(...))         # 部署：通过 HA MCP
# 可选：SpaceHomeEnv(MCPBackend("local")) 只用于验证训练路径与 MCP 路径一致
```

同一份 env 代码，训练直连、部署走 MCP；MCPBackend 只在一致性验证时使用。

## 6. 和 LLM Agent RL 的对齐

LLM agent 的 RL 与经典 Gym RL 的粒度不同，需要在对接时明确“一层 step 指什么”：

```
token 层：模型每次生成一个 token
turn 层：模型生成一段回复，可能包含若干 tool calls
tool 层：一次工具调用（训练时直连，部署时对应 MCP tools/call）
episode 层：从 reset 到一个用户请求完成或超时
```

推荐约定：

```
Gym step        = 一次 assistant turn（一个决策边界）
tool call       = 一次工具调用，属于该 turn 内部的子动作
episode         = 一次完整的用户任务
reward          = 由回合结束时的状态条件计算，可选中间进度分
```

这样既兼容 Gym 的 step 语义，也符合多轮工具调用 LLM 的训练方式。Agent-R1 的 step-level trajectory 表示与 AgentGym-RL 的多轮 RL 都是这个方向。

## 7. 完整训练循环（伪代码）

```python
tools = load_tool_spec("smart_home_tools.yaml")
env = SpaceHomeEnv(SandboxBackend(SimuHome, tools))

for episode in range(num_episodes):
    obs, info = env.reset(seed=episode_seed)
    done = False

    while not done:
        # 一次 assistant turn：可能包含多个 tool calls
        turn = policy.generate(render(obs))

        for call in turn.tool_calls:
            result = env.call_tool(call.tool, call.args)
            # 方案 A：这里直接调 SandboxBackend，不经过 MCP
            obs = env.update_observation(result)

        # turn 结束后推进到下一个决策点
        obs, reward, terminated, truncated, info = env.end_turn()
        buffer.append({"turn": turn, "obs": obs, "reward": reward,
                       "terminated": terminated, "truncated": truncated})
        done = terminated or truncated

# RL 更新
for batch in sample_batches(buffer):
    loss = policy_loss(batch)
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
```

部署时把后端换成 HA MCP：

```python
env = SpaceHomeEnv(HABackend(HomeAssistantMCP(tools)))
```

## 8. 一致性、可复现与测试

方案 A 不经过 MCP 训练，因此必须靠契约测试、回放测试与迁移测试保证部署一致性：

```
契约测试
  同一份 ToolSpec 生成的 Gym action 结构
  与 HA MCP 的工具 schema 一致；
  参数、返回与错误码一致

回放测试
  把沙盒里记录的一条 tool call 轨迹在 HA mock 上重放，
  检查每步状态与结果结构是否一致

迁移测试
  同一 policy 在沙盒与 HA 真机上跑同一批任务，
  对比成功率、查询次数、失败类型与安全违规次数

可选路径验证
  用 MCPBackend 跑少量训练或回放，
  验证经过 MCP 传输层时行为与直连路径无差异
```

可复现性依赖 ToolSpec 版本、场景 seed、policy 权重与后端版本四者一起记录。

## 9. 风险与边界

```
工具语义漂移
  两边工具名相同但单位、默认值、错误码不同
  → ToolSpec 版本化 + 契约测试

能力不一致
  HA 设备缺少沙盒里的能力
  → capability discovery + 训练时随机屏蔽能力

时间语义不一致
  沙盒能快进，真机只能真实等待
  → 统一 schedule / wait_until 抽象 + 训练时注入等待成本

状态隔离
  多个 rollout 共享一个 world 会互相污染
  → 每个 worker 一个独立 Gym env / world；
    部署侧 HA MCP 的会话状态不参与训练

安全边界
  真机动作可能造成真实影响
  → 动作过滤器 + 用户确认 + 沙盒预验证
```

## 10. 结论

统一语义接口的分工可以概括为：

```
MCP 负责“动作怎么表示、怎么调用、返回什么”
Gym 负责“一局怎么开始、一步推进到哪、奖励与终止是什么”
ToolSpec 把两者绑在同一个语义来源上
Backend 是可替换的执行后端
```

本方案统一采用方案 A：训练时 Gym 直连 SandboxBackend，部署时同一份 ToolSpec 通过 MCP 调 HA backend。MCP 只承载部署侧的工具调用；训练侧的一致性由 ToolSpec、契约测试与域随机化保证。方案 B、C 仅在验证或特殊编排场景下可选。
