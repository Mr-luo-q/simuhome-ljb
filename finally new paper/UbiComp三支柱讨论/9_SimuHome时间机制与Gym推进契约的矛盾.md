# SimuHome 时间机制与 Gym 推进契约的矛盾

> 撰写日期 2026-09-11。
> 本文只回答一个问题：**SimuHome 内核的时间与推进方式，和 Gym 要求的推进契约，对不上在哪。**
> 依据为 SimuHome 源码实测与 Gymnasium 官方文档，来源清单见 §7。

---

## 0 结论

```python
内核的时间   = tick 数 × tick 长度，而这个 tick 由后台循环按真实时间节奏推进

模型能做的   = 预约未来动作（schedule_workflow）、读当前时刻（get_current_time）
模型不能做的 = 推进时间。工具表里没有任何一个“让世界往前走”的工具

真正握着推进权的 = 后台循环（一直走）与评测脚本（按需跳跃）
```

```python
与 Gym 对不上的地方，集中在四条：

一  推进权     Gym 要求训练循环持有推进权，step 是唯一的推进触发点；
              内核的推进由后台循环与评测脚本分别持有，模型只是插入扰动

二  步长       Gym 要求“一步覆盖多长”由环境声明且保持恒定；
              内核的“一步”不存在，tick 长度还允许中途修改

三  真实时间   内核把真实执行速度带进了虚拟时间，
              同一条策略在不同机器与不同负载下对应不同的虚拟时间跨度

四  结束判定   Gym 由环境在 step 里给出终止信号；
              内核的回合边界由评测脚本在事后跳跃补出来
```

## 1 内核的时间是怎么建立的

### 1.1 时间是算出来的，没有独立存储

```python
虚拟时刻 = 起始时刻 + tick 数 × tick 长度

# 因此
改 tick 长度 → 同一串 tick 数会指向不同的虚拟时刻（内核会补一个偏移量接住）
改 tick 长度 → 设备效应、环境演化、调度节奏一起变
```

### 1.2 tick 长度一身三职

```python
tick_长度 = 物理步长 = 时间单位 = 调度粒度

每 tick 增量  = 每秒速率 × tick_长度      # 物理
虚拟时刻      = 起始时刻 + tick × tick_长度  # 时间
命令节奏      = 每 tick 执行一段           # 调度

# 一个数同时决定三件事，而“一步代表多长时间”在内核里没有独立表达
```

### 1.3 一次 tick 的四段顺序

```python
def 一次tick():
    演化设备()        # 一
    重算环境量()      # 二
    触发到点任务()    # 三
    执行命令()        # 四：外部命令在此被取出

# 环境量先算完，命令后执行
# 因此命令的影响最早在下一个 tick 才进入环境量
```

### 1.4 后台循环按真实时间节奏走

```python
def 主循环():
    while 运行中:
        开始 = 计时()
        一次tick()
        耗时 = 计时() - 开始
        if 耗时 < tick_长度:
            睡( tick_长度 - 耗时 )     # 把本 tick 补足到固定长度
        tick += 1

# 含义
#   一个 tick 的虚拟长度固定，但它占用的真实时间取决于机器负载
#   负载高、单 tick 耗时超过 tick_长度 时，世界会慢下来
#   世界每秒钟推进多少 tick，不是一个受控量
```

### 1.5 内核自带的“压缩时间”能力

```python
def 跳到(目标tick):
    while tick < 目标tick:
        间隔 = 距下一个到点任务() 或 剩余

        if 这段没有内部事件() and 所有环境量都能整段推进():
            环境量.整段推进(间隔)      # 把这段时间压成一个结果
            tick += 间隔
        else:
            for _ in range(间隔):
                走一个tick()          # 逐个 tick 走

内部事件 = { 到点的调度任务, 设备不可跳过的持续工作 }
```

```python
# 两处必须留意
# 一  逐 tick 走的那条分支里不执行命令队列：
#     跳过的这段时间里，外部命令不参与
# 二  到点的定时工作流在跳跃期间会被触发，
#     而且它的多个步骤在同一瞬间连续执行完，步骤之间没有时间间隔
```

## 2 谁握着推进权

```text
通道            能不能推进时间        推进方式
后台循环        一直在推进            按真实时间节奏走 tick
模型            不能                  只能预约与读数
评测脚本        能                    跳跃到指定 tick
场景生成器      能                    用同一个跳跃能力铺初始场景
```

### 2.1 后台循环：持续推进，不可控

```python
# 世界一旦启动，agent 在不在场、思考多久，与世界的推进无关
# 模型的一次工具调用往返，世界就走掉若干 tick
```

### 2.2 模型：只能预约与读数

```python
模型可用的时间相关工具 = {
    读当前时刻(),
    预约未来动作(绝对时刻, 步骤列表),
    查询预约状态(),
    取消预约(),
}

# 没有“等待到某时刻”“快进到某时刻”这类工具
```

```python
# 于是“等”只能这么实现
while 还想等:
    查预约状态()
    真实睡(退避时长)        # 退避 1s → 2s → 4s → 8s，上限 8s，最多轮询 8 次

# 注意这里的 sleep 是真实时间：
#   agent 进程在睡觉，世界在后台继续推进，
#   等待的代价不体现在虚拟时间上，而是体现在真实时间上
```

### 2.3 评测脚本：持有真正的推进权

```python
def 校验一个时间目标(起始tick, 容差, 断言列表):
    for 检查点 in 起始tick ± 容差:
        状态 = 跳跃到(检查点)        # 由评测脚本发起，返回整屋快照
        if 断言全部成立(状态):
            return 通过
    return 失败

# 跳跃是单调的：已经跳过的 tick 不能回头，
# 因此检查点必须按升序依次尝试，越界即判为错过
```

### 2.4 一个能说明推进权多重要的事实：评测要重放一遍才敢判定

```python
def 判定环境控制是否有效(agent 结束时的状态):
    重置到初始配置()
    基线 = 跳跃到(agent 结束时的 tick)     # 同样的 tick 数，但不施加任何动作
    return 比较方向(基线, agent 结束时的状态)

# 因为世界自己也会走，不重放一遍就不知道“变化是 agent 造成的还是时间造成的”
```

```python
# 这条说明
#   agent 的动作只是插进时间流里的扰动，
#   时间流本身的主人是后台循环；
#   评测为了得到对照，只能把同一段时间重新跑一遍
```

## 3 一个真实任务的时间线

取 `qt4-1` feasible 的第一条：要求 13 分钟后把客厅调光开到 30%，
再过 8 分钟调到 20%，29 分钟后打开杂物间灯。

```text
目标          at_tick    容差 ticks    折算虚拟时间      容差
第一动作      7800       300          13 分钟           30 秒
第二动作      12600      300          21 分钟           30 秒
第三动作      17400      300          29 分钟           30 秒

tick 长度 = 0.1 秒
```

实际发生的时间线：

```python
模型:
    读当前时刻()                      # 拿到 base_time 推出的绝对时刻
    算出 当前 + 13 分钟()
    预约未来动作(绝对时刻, [开灯, 设亮度 30])
    算出 再 + 8 分钟() 与 + 29 分钟()，继续预约
    ... 期间可能轮询若干次预约状态，每次真实 sleep
    收尾()

世界（与模型并行）:
    按真实时间节奏推进 tick；模型想多久，世界就走多久
    但没有任何一步真正跑到 13 分钟之后——那需要 780 秒真实时间

评测脚本（事后）:
    跳跃到 7800 ± 300 之间的检查点
    跳跃期间，到点的工作流被触发执行
    读回整屋快照，比对断言
    继续跳跃到 12600、17400
```

```python
# 三点结论
# 一  任务里的“13 分钟”是虚拟时间，模型的每一步耗时却是真实时间，
#     两者之间没有换算关系
# 二  虚拟时间真正跨过 13 分钟，靠的是评测脚本的跳跃，不是 agent 的行为
# 三  如果没有评测脚本那一步跳跃，预约的动作永远不会触发，
#     因为世界在真实时间里只走了几十秒
```

## 4 与 Gym 推进契约的矛盾

### 4.1 推进权归属

```python
# Gym 契约
def step(动作):
    执行(动作)
    推进()          # 只有这一次调用会推进世界
    ...

def reset(种子):
    ...             # 一局从这里开始，世界在被调用之前不动
```

```python
# 内核现状
世界在后台一直动()
模型的动作只是插入扰动()
真正的推进由评测脚本按需发起()

# 对不上
# Gym 要求推进只有一个触发点，且这个触发点在训练循环手里；
# 内核的推进有多个来源，模型不在其中
```

### 4.2 一步有多长

```python
# Gym 契约
步长 = 环境声明的一个确定量，且在环境存活期间保持不变

# 内核现状
推进单位 = tick，长度可以中途修改
模型手上还带着一个“修改 tick 长度”的工具

# 对不上
# Gym 的 transition 要求可比，前提是步长恒定；
# 内核里连“一步”这个单位都不存在，只有一个可变的 tick
```

### 4.3 观测出现在什么时候

```python
# Gym 契约
观测在决策点产生，形状固定

# 内核现状
观测是随时可取的横截面，读到的时刻由调用方决定

# 对不上
# 在内核里，“动作后的状态”没有一个被约定的时刻，
# 因此也就无法保证读到的是动作的后果
```

### 4.4 一局在哪里结束

```python
# Gym 契约
环境在 step 里给出终止信号：任务完成、失败、或超过步数上限

# 内核现状
世界没有回合概念，也不产出终止信号；
时间型任务是否完成，由评测脚本事后跳跃去核对

# 对不上
# 训练需要的终止信号在生产环境里不存在，
# 而它在评测环境里是被补出来的
```

### 4.5 可复现性

```python
# Gym 契约
同 seed + 同动作序列 → 同一条轨迹

# 内核现状
虚拟时间跨度 = 真实执行速度 × 经过的墙钟时间
模型每步耗时由推理延迟决定，世界每 tick 耗时由机器负载决定

# 对不上
# 真实时间通过两个入口渗进了虚拟时间，
# 同一条策略在不同机器上会得到不同的轨迹长度
```

## 5 Gym 生态里对这件事是怎么处理的

以下为 Gymnasium 官方文档的原文要点。

```text
一  一步是什么
    step 的官方定义：用动作运行一次环境动力学的“一个 timestep”，
    返回观测、奖励、terminated、truncated 与 info；
    “一次动作—观测交换称为一个 timestep”

二  一步内部可以包含多个仿真小步，但步长要声明
    Atari 预处理把 frame_skip 默认设为 4，即“两次 step 之间跳过的帧数”
    MuJoCo Ant 直接把步长写成 dt = frame_skip × frametime = 5 × 0.01 = 0.05，
    文档称其为“两次动作之间的时间”

三  时间上限按步数算，不按秒算
    TimeLimit(max_episode_steps) 在超过步数上限时给出 truncated；
    文档强调 truncated 来自外部限制，与 terminated（任务本身结束）必须分开，
    因为两者的回报自举方式不同

四  一局结束后由谁重置
    向量化环境默认在下一步自动重置，
    也就是说“回合边界”是环境的契约内行为，不需要外部脚本补
```

```python
# 归纳
# Gym 生态的做法是：把“一步覆盖多长”固定成一个声明的常量，
# 时间上限用步数表达，回合边界由环境给出；
# 真实时间不参与任何一处。

# SimuHome 的现状是：推进单位可变、时间上限用虚拟秒表达、
# 回合边界由脚本补、真实时间通过两条入口渗进来。
# 差别不在精度，在于“时间归谁管”。
```

## 6 只针对时间与推进的改造含义

```python
一  把推进权收进环境
    世界不再自己往前走；推进只在一次交互里发生

二  给“一步”下定义
    一步 = 从一个决策点到下一个决策点
    决策点的判定（概念层）：
        读类交互         不推进
        改变世界的动作    推进到后果可见为止
        显式等待         推进到指定时刻
        同一轮多次调用    轮末只推进一次

三  把真实时间从虚拟时间里剔除
    推进量由动作语义决定，不由墙钟时间决定
    模型每步耗时多少，与世界走多远无关

四  把预约与等待统一成推进
    预约未来动作 → 推进到该时刻
    等待某时刻   → 同一件事的另一种写法
    两者的语义都落在“推进到指定时刻”上

五  回合边界由环境给出
    目标达成、失败、超过步数上限，都在交互返回时说明
```

```python
# 内核已有的能力可以直接当实现基础
压缩无事件时间的能力 → 推进到一个决策点
调度到点触发         → 推进期间的内部事件
粘贴内核资产         = { 设备演化, 环境量聚合, 依赖校验, 调度 }

# 缺的只有两件
#   一个“推进到哪停”的判定
#   一个“一步覆盖多长”的对外声明
```
