# UbiComp 新论文讨论：轻量空间连通沙盒 + SFT/RL 训练 + 同语义 MCP 现实迁移

## 1. 一句话主张

我们构造一个“中重量级”的智能家居研究沙盒：不做重几何，但让房间/区域具备**连通关系**，并让它与设备、环境变量、人物、任务共享同一套可快进的时间轴；在这个沙盒上同时长出三类工作——一个尽量吸收已有任务谱系并加入空间连通语义的 benchmark、一套 SFT+RL 训练方法、一套与 Home Assistant 语义一致的约 10 个 MCP 接口。后者的作用是让沙盒里微调出的模型可以直接（或近零适配地）在真实智能家居中使用。

```
沙盒（轻空间 + 连续时间 + 可复现 + 高吞吐）
        │
        ├─ ① Benchmark：已有任务特征 + 空间连通任务 + 记忆/长期交互
        ├─ ② 训练：SFT（学行为）→ RL（可验证目标优化）
        └─ ③ 迁移：Sandbox-MCP ≈ HA-MCP（约 10 个同语义接口）
```

## 2. 先给合理性结论

这个方向整体合理，而且和你目前掌握的文献正好形成闭环：方法侧已有 19 HomeFlow 证明“仿真环境+SFT+逐步 RLVE”能训出超强小模型，但它没有空间连通语义，也没有做同接口现实迁移；Benchmark 侧四篇各自覆盖任务、时间、个性化和环境接地，但没有一个把“房间连通”当作可计算的世界约束；你的迁移方案又是对着 HA 的 REST/WS/conversation 真实能力对齐，不是空谈 sim-to-real。

所以“三支柱”本身不缺根据。真正要警惕的不是方向错，而是三件事：**每一支柱单独都够写一篇，合在一起容易都做不深**；**“同一个 MCP 接口”只能保证调用表面一致，不能自动消除真实家庭与模拟器之间的语义差**；**“尽量包含已有特点”如果理解成任务越多越好，论文会失去焦点**。

下面按三个支柱分别写清：什么是该主张的、什么是有风险的、建议怎么收敛。

## 3. 支柱一：中重量级沙盒与空间连通 benchmark

### 3.1 你的“空间”到底轻到什么程度

你举的例子已经把动机说清楚了：SimuHome 里各房间独立调控，但现实房屋是连通的，而且不是每个房间都有空调。因此沙盒只需要回答三个空间问题：

```text
这套房子的房间/区域之间是否连通（房间图）
某个设备位于哪里、它的效果能否沿连通关系影响邻接房间
人和设备当前在哪个房间/区域，移动是否会改变可用的控制选择
```

这对应一个很克制的空间表示：

```text
Room:    类型、邻接集合、是否连通、基础环境状态
Edge:    两个 Room 之间的连通关系（可用门/开放程度进一步细分，首版可不做）
Device:  所属 Room、效果作用域（本房间 / 经连通传播）
Human:   当前 Room
EnvVar:  每 Room 一份温度/湿度/光照，按连通边做轻量交换
```

建议第一版就把空间语义锁定在“房间图 + 连通边 + 效果作用域”，不进入精确坐标、几何、可达路径或 3D 网格。这个选择的好处是：空间信息仍然能参与“任务可行性、环境传播、副作用、指代消歧”，但不会拖慢 RL rollout，也更容易和 Home Assistant 的 area/device 语义对齐。

### 3.2 连通关系必须能改变“正确答案”

光有空间信息不足以构成论文创新。benchmark 的任务要设计成：连通关系改变时，正确动作会变。否则审稿人会说“这只是把房间标签换成图”。

```text
任务族 A：共享设备与邻接房间
  客厅一台空调，厨房没有空调
  开客厅空调后，厨房温度应随时间下降（边连通）
  正确动作可能是在客厅开强档，而不是在厨房找不存在的空调

任务族 B：连通/关闭边的因果
  客厅与卧室之间的门开着 vs 关着，卧室降温速度不同
  模型需要查询连通状态后决定风量、时间或是否需要等待

任务族 C：空间指代与副作用
  “卧室降温时别让旁边的婴儿房过冷”
  需要读邻接关系和传播方向，而不是只读房间名

任务族 D：人物移动改变可用性
  人离开客厅进入卧室后，客厅灯/空调是否应该跟随
  需要人物轨迹 + 房间转换 + 时间延迟
```

与 SimuHome 的差异要这样写：SimuHome 有时间和调度，但房间基本是独立状态容器；我们把“房间连通”做成世界约束，环境传播、任务可行性和副作用都发生在连通结构上。与 SMH-Bench 的差异则是我们不追求设备/任务规模全覆盖，而是把“一个关键约束——空间连通”做深。

### 3.3 “尽量包含已有特点”要分层，不要全塞进同一评测

“各类任务、记忆、长期交互尽量包含”作为沙盒能力是对的，但作为单篇论文的实验范围是危险的。建议沙盒设计成两层：

```text
Episodic 层（承接已有任务谱系，成本低）
  单设备 / 多设备 / 无效指令
  模糊意图 / 指代消歧
  时间延迟与调度
  空间连通任务（新增差异层）

Long-horizon 层（首篇做有限展示）
  连续生活过程
  偏好形成与修正
  主动服务时机与干扰
  跨成员区分
```

首篇论文应把“空间连通任务”作为基准差异主轴，把长程主动服务作为增强展示，而不是让论文同时承诺“任务最多、记忆最强、长交互最长、空间也有”。

## 4. 支柱二：SFT + RL 训练

### 4.1 训练为什么能成立

训练的必要前提是沙盒满足三个条件：

```text
快：无头内核 + 高吞吐 tick + 可并行副本
准：状态、事件、动作、时间顺序完全可复现
可判：每个任务有可验证目标状态（而不是 LLM 裁判）
```

这三个条件你的 mcp/doc8-10 路线本来就在收敛，而且 19 HomeFlow 已经用“可验证环境奖励 + 逐步 RLVE”证明这条路能让 4B/8B 模型在任务成功率上反超前沿大模型。所以训练支柱的可行性不需要从头论证，需要论证的是“在我们的空间连通沙盒上，训练出的空间-时间策略比不训练/只在文本上训练的模型强多少”。

### 4.2 SFT 与 RL 分工

```text
SFT：从高质量轨迹中学行为先验
  来源可包括规则生活流轨迹、LLM 演示、人工标注
  先学会：观察→查连通→选设备→执行→等待→验证

RL：在可验证环境里纠正长程错误
  奖励至少包含：目标达成、空间副作用约束、非法动作惩罚
  可选奖励项：时间效率、打扰/干扰、能耗
  算法先用 HomeFlow 那类逐步/可验证 RL（RLVE/GRPO 路线）
```

SFT 先行、RL 后置的理由是：纯 SFT 容易在长交互中犯复合误差，RL 负责让模型从失败中恢复；但 RL 收益需要消融证明，不能直接声称“RL 一定更好”。

### 4.3 必须警惕的训练陷阱

```text
陷阱 1：沙盒不够快 → RL rollout 不可行
  → 首版必须是无头 Python 内核，不做浏览器依赖

陷阱 2：奖励可被模型钻空子
  → 状态判定必须来自沙盒真相，不是模型自评

陷阱 3：空间连通信息被接口“免费送”
  → 如果模型每步都拿到完整连通图，空间任务会退化成读图题
  → 应让模型通过工具查询连通关系，而不是全量注入

陷阱 4：RL 只在小任务上有效
  → 实验需要同时报 episodic 与 long-horizon 两层的收益
```

## 5. 支柱三：同语义 MCP 与 Home Assistant 迁移

### 5.1 双 MCP 的设想是对的，但要区分两件事

给沙盒和 HA 各做一套 MCP、暴露同一组接口语义，这个方向成立。HA 的 REST/WebSocket/conversation 能力已经被 doc9 梳理清楚，它完全可以作为现实侧的后端，而沙盒侧用自己的世界内核实现同样语义。

要区分的是：

```text
接口表面一致（同名、同参数 schema）
接口语义一致（查询/动作/验证/事件在两边含义相同）
迁移成功（同一策略切到 HA 后性能保持多少）
```

只有第三层完成，才能主张“模型能直接用”。前两层是工程贡献，第三层才是论文贡献。

### 5.2 候选的约 10 个接口

```text
observe_home          结构化全局快照（克制版，不替模型决策）
query_topology        查询房间/区域连通关系（本论文差异核心）
find_devices          按房间/类型/状态/能力检索设备
inspect_device        读取设备状态、动作、参数约束
inspect_room          读取房间环境变量与邻接摘要
execute_device_action 执行设备动作（沙盒走时间核，HA 走 call_service）
query_events          查询事件日志
wait / wait_for_event 等待时间或指定事件（两个后端语义不同，见 5.4）
check_goal_state      验证目标状态是否达成
memory_*（可选）      读取/更新长期记忆与偏好
```

这套清单的原则仍是 doc7/10 里那句：**接口提供观察、定位、执行、验证，不提供自动任务分解、自动调度、自动编排**。模型必须自己决定“查什么、按什么顺序做”。

### 5.3 Home Assistant 侧的语义映射

```text
沙盒 query_topology       ↔ HA area / floor / device 区域关系
沙盒 find_devices         ↔ HA entity/device 检索
沙盒 inspect_device       ↔ HA state + attributes + services
沙盒 execute_device_action ↔ HA call_service
沙盒 query_events         ↔ HA history / logbook / subscribe_events
沙盒 check_goal_state     ↔ 自定义 state 条件检查
```

HA 已经内置 area/device/entity/service 的分层和 Built-in Assist tool 抽象（doc9），所以不建议我们另起炉灶发明一套“HA 新协议”，而应做一个薄适配层：把 HA 的能力映射到这 10 个接口上，语义层自研，底层复用 HA 原生 API。

### 5.4 “直接用”是最强主张，也是最危险主张

真实家庭和沙盒至少有五类不可消除差异：

```text
时间语义：沙盒可以快进，真家只能等待
空间语义：HA 的 area/设备关系需要用户配置，可能缺失或不完整
设备差异：同一语义动作在不同品牌/协议上的真实延迟和结果不同
观测噪声：传感器缺失、漂移、状态同步延迟
事件异步：HA 的服务调用是异步事件流，不是沙盒的同步确定性
```

因此论文不应写死“零迁移”，更稳妥的主张是：

```text
同一策略在 Sandbox 与 HA 双后端执行
分别测零适配 / 仅 schema 适配 / 少量示例适配
报告成功率保持、非法动作率、工具调用数、提示/适配修改量
```

这正是 doc11 里“成对任务迁移评测”的路线：先证明接口语义一致，再量化迁移损失来自哪一层，才算真正的 sim-to-real 贡献。

## 6. 三支柱合起来是否合理：综合判断

合理的地方：

```text
问题闭环完整：benchmark 指出能力缺口 → 训练补齐 → 同接口迁移验证补齐
与文献关系清楚：SimuHome 无连通空间，HomeFlow 无迁移，HA MCP 无训练闭环
“轻空间+RL+同语义迁移”三者目前在你掌握的文献里没有同时出现
HA 的真实适配能力使“最广泛适用性”不是空话
```

危险的地方：

```text
三支柱体量接近三篇论文，单篇容易虚胖
空间只做连通图时，创新必须靠“任务和消融”，不能靠世界本身
“尽量包含”会诱使实验无限扩张
“同 MCP 接口=能直接用”会招来 sim-to-real 最尖锐的审稿质疑
```

建议的单篇收敛形态：

```text
核心主张：一个可 RL 的连通家庭沙盒
主实验：连通空间因果任务 + episodic 任务谱系 + 训练消融（SFT vs SFT+RL）
差异证据：改变连通关系会让正确动作/副作用改变；不给全量连通信息时模型仍需会查
迁移证据：同一 MCP 语义 + 成对任务 + 适配成本测量
辅助展示：一个有限 long-horizon 主动服务场景 + 指标（收益/干扰/时机）
```

## 7. 待你拍板的关键问题

```text
Q1 空间粒度
  第一版是纯连通图，还是连通图+每房间轻量环境传播方程？

Q2 首篇定位
  三支柱全部进一篇，还是把训练+迁移作为 benchmark 论文的增强项？

Q3 “尽量包含”边界
  episodic 任务取哪几族？long-horizon 做多大规模？

Q4 接口清单
  10 个接口的最终名单（wait 的时间语义怎么统一）？

Q5 HA 侧空间数据
  真家的 area/连通关系靠用户配置、自动推断，还是允许降级？

Q6 RL 选择
  先复现 HomeFlow 式可验证 RL（RLVE/GRPO），还是先跑规则生活流+LLM 演示做 SFT？

Q7 与 mcp/doc7-11 的关系
  新构思是取代“3D+2D 双表示”蓝图，还是作为它的轻量实现版？
```

## 8. 下一步建议

先不写完整方案，先写两份短规格把支柱一和支柱二钉住：

```text
规格 1：沙盒空间连通表示与连通任务定义
  房间/边/设备作用域/环境传播的最小 schema
  3~5 个“连通改变正确动作”的任务样例

规格 2：接口清单 + 双后端映射表
  约 10 个接口的签名与语义
  Sandbox 与 HA 各自的实现入口
  明确哪些语义两后端天然不同（时间、异步、观测噪声）
```

这两份规格写清楚后，再决定 RL 选型和首篇论文范围。
