# 从孤立房间到连通之家：空间感知智能家居智能体的基准评测、训练与真机迁移

> 工作稿讨论题目（UbiComp 风格候选）；内部文件名仍保留为 “Benchmark 任务范畴简化版”。

本文是 `Benchmark任务范畴与训练迁移结合讨论.md` 的简化版。两处调整：

```text
一是收敛子类：六类任务族保留，每类只列 2~3 个必须做的子项
二是调整定位：本文不是一篇纯 benchmark 论文，
  benchmark 只是三支柱之一，任务是“够用 + 能接训练和迁移”，不需要穷尽细节
```

## 先定义沙盒：六个任务族跑在什么样的世界上

benchmark 部分不从任务清单开始，而是先从“任务跑在什么世界上”开始。我们构建一个**中重量级家庭沙盒**：比 HomeBench 重（有状态演化、时间推进、跨房间连通），比 SimuHome 轻（空间只到连通关系，不做几何和物理高保真），比 SMH-Bench/PersonalHomeBench 更收敛（只为支撑空间任务、训练和迁移设计，不做大而全平台）。

```text
沙盒的世界内容
  空间层   ：房间节点 + 连通边 + 房间内设备锚点；
             只表达“谁和谁连通、设备在哪、效果能传到哪”，不做网格/精确坐标
  设备层   ：类型、属性、动作、参数约束、环境效应；
             动作合法性由状态机保证，不存在“能调但越界”的歧义
  环境层   ：每个房间维护温度/湿度/光照，按轻量差分演化，
             设备效果沿连通边传播到邻接房间
  人物层   ：只维护位置、活动与事件（轻量）；
             persona、偏好、长期记忆作为外部配置注入，不写进人物本体
  时间层   ：统一虚拟时钟 + tick + fast_forward + 事件调度
  运行能力 ：snapshot / restore / replay / 并行副本 / 固定随机种子

沙箱明确不做的事
  不做 3D 物理仿真、不做精确导航、不自动生成 schedule、
  不自动做多设备编排、不让 MCP 替模型解题
```

这套沙盒直接服务于三支柱：

```text
对 benchmark：空间、时间、设备、人物、环境都在同一世界里演化，
  六个任务族才能在同一沙盒里定义和验证
对训练：无头、可快进、可重置、可并行，才跑得起 SFT 数据生成和 RL rollout
对迁移：空间→HA area、设备→HA entity/service、时间/事件→HA event/state，
  才可能让沙盒 MCP 与 HA MCP 语义一致
```

沙盒能力到任务族的对应关系：

```text
沙盒能力              直接支撑的任务族
房间 + 连通 + 设备锚点   T1 空间语义
设备状态机 + 动作约束    T2 指令执行
MCP 对话/查询接口        T3 模糊与指代（通过工具交互表达）
时间核 + 事件调度        T4 时间与持续任务
人物事件 + 事件日志       T5 记忆/个性化（长期记忆可外部注入或走 memory 工具）
环境变量 + 传感器查询     T6 环境感知
```

## 六个任务族

```text
T1 空间语义与连通（核心创新）
  T1a 空间 grounding：按房间/位置/邻接找设备
      例：“打开梳妆台上的灯”——只给房间名不够，还要按设备位置/邻接定位
      （延伸自 18 SAGE 的照片式设备消歧）
  T1b 连通传播与副作用：设备效果沿连通影响邻接房间
      例：“厨房没有空调，开客厅空调并让门开着，厨房也会逐步降温”
      （SimuHome 等现有 bench 默认各房间独立调控，这正是它们的空缺）
  T1c 拓扑因果：改变连通关系 → 正确动作改变
      例：客厅与卧室的门从“开”变“关”后，
          “让卧室尽快降到 24°C”的风量/时长/可行方案必须改变
      （与 SimuHome 的状态演化、SMH-Bench 的环境验证衔接）

T2 指令执行与鲁棒性
  T2a 单设备/多设备/组合指令
      例：“把水壶和卧室灯调一下”——要识别家里只有空调和风扇具备制冷能力
      （取自 HomeBench 原例）
  T2b 无效与非法指令（设备不存在、参数越界、目标不可达）
      例：“把没有的客厅灯打开”应被拒绝而不是虚构动作
      （取自 11 DS-IA；HomeBench 的无效门窗通风、SimuHome 的不可行任务同族）

T3 模糊、省略与指代理解
  T3a 模糊/欠明确目标与隐性意图
      例：“让客厅变得舒适”比“打开客厅灯”难在要跨概念推断设备和偏好
      （09 Sasha 原例；“离开家就关空调”的隐性意图是节能，01 MvTAP）
  T3b 省略与指代消歧（含该澄清还是该猜）
      例：多轮对话后用户只说“还是把灯开大点”，
          要补全指的是哪盏灯、开多大、在谁的偏好范围内
      （13 PEC-Home 的渐进省略分级）

T4 时间、调度与环境动力学
  T4a 定时/延迟/持续任务
      例：“洗碗机洗完就开厨房灯”——设备完成后触发后续动作
      （取自 SimuHome 调度任务；18 SAGE 的“打开冰箱时提醒我丢牛奶”同族）
  T4b 状态演化与目标验证（动作产生持续后果）
      例：空调设 24°C 后不能立刻判成功，要等虚拟时间推进、
          验证房间温度到达且不因传播把邻接房间带过冷
      （SimuHome 状态验证与 19 HomeFlow 可验证奖励的承接）

T5 长期记忆、个性化与多成员
  T5a 偏好形成与修正
      例：连续三晚把卧室从 24°C 调到 22°C 后形成偏好，
          但用户感冒当天应结合异常条件修正而不是机械执行
      （PersonalHomeBench 的偏好建模 + 16 MemAura 周期行为预测）
  T5b 跨成员区分与长期记忆利用
      例：晚上给儿童房留一盏夜灯，不能因为客厅成员怕亮就把灯关掉
      （PersonalHomeBench 的人物背景 + 14 AdaHome 的多轮偏好区分）
  T5c 主动服务时机（做/等/问/沉默）
      例：老人深夜起身经过走廊时提前开低亮度地脚灯，
          同时不打扰卧室里的其他人
      （PersonalHomeBench 的主动规划 + doc11 主动服务时机示例）

T6 环境感知与工具型信息获取
  T6a 环境/传感器状态查询
      例：用户说“有点闷”，先查室内湿度与空气质量，
          再决定开新风、开窗还是提醒加湿
      （SimuHome 隐式意图示例；17 TaskSense 的传感器查询同族）
  T6b 部分可观测下决定“查什么”
      例：模型知道目标但不知道客厅当前设备状态时，
          应先调用工具查询再规划，而不是凭默认假设执行
      （PersonalHomeBench 从纯推理切到工具型 agent 大幅掉点的直接对应）
```

上面的例子大部分直接取自 `4个bench` 与 `方法相关的论文` 两份文献；括号里注明来源。标为“延伸自/承接/同族”的条目，是把已有论文里的能力缺口转成本论文 T1/T4/T5 的新任务，而不是从零臆造。

横切只保留一条：每类可配 valid/invalid 变体；任务有两种暴露模式（一次给全信息的直接模式 vs 只给部分信息、靠 MCP 工具查询的工具模式）。T1 在工具模式下不预给拓扑，模型必须通过 `query_topology` 查连通关系。

这就是 benchmark 的全部骨架。它已经能覆盖四个既有 bench 的方向（指令、无效、模糊、时间、记忆、环境查询），并把“空间连通”作为唯一整类创新。

## 训练方法：SFT + RL 做四层目标（空间语义显式成层）

因为空间是 benchmark 的核心创新，训练目标里就不能只让空间“隐式出现”在轨迹和安全约束中。这里把训练目标从三层扩成四层，新加一层专门负责“空间语义的理解与运用”，让模型不只学会查拓扑，还要学会根据连通关系选择目标设备、预测传播与副作用。

```text
L1 行为层（SFT）
  教会六类的标准轨迹：观察 → 查空间/设备 → 执行 → 等待 → 验证
  数据来自规则生活流 + LLM 演示，全部在沙盒内验证可执行

L2 空间语义理解与运用层（本论文核心训练层）
  目标：模型会读拓扑、会用拓扑，而不是把拓扑查询结果当摆设
  训练信号：
    a) SFT/RFT 空间推理链：连通 → 传播 → 目标设备/可行方案
       （客厅空调 → 门开着 → 厨房可由邻接间接降温）
    b) 预测验证奖励：模型先输出“预期受影响的房间与副作用”，
       由沙盒状态演化验证是否正确
    c) 方案选择奖励：给多个候选设备/房间时，选错拓扑方案给负奖励
  强调“外化推理”：模型必须先给出可验证的空间预测，再执行

L3 安全与合法性层（RL 常驻约束）
  不控制不存在的设备、不越参数界、不违反空间副作用
  （客厅降温不得把婴儿房带过冷）
  奖励用沙盒状态验证，不用 LLM 裁判

L4 长程效用层（RL 增强目标）
  只作用于 T4/T5：延迟成功、过早动作、错误主动、用户打扰
  指标用累积效用 = 收益 − 干扰 − 成本
```

六类与训练的对应关系只需一句话：

```text
T1 的主战场在 L2（空间理解与运用）+ L3（副作用安全）
T2/T3 以 L1 行为 + L3 合法性为主
T4/T5 是 L4 RL 价值最大的区域（延迟奖励与长期信用分配）
T6 以 L1 教“查什么”，L2 帮它把查到的空间信息真正用起来
```

论文要回答的训练问题保持精简：

```text
① SFT 是否明显好于直接 prompt（取 T1/T3 代表任务）
② 加入 L2 空间语义层后，T1/T3 是否显著提升（同骨干只开关该层）
③ RL 是否在 T4/T5 上比 SFT 进一步受益
④ 训练后的模型在未见过的连通拓扑上是否仍有效
```

## 迁移框架：约 10 个接口，四个语义簇

迁移不需要为六个任务族各造接口。约 10 个接口按语义分成四簇，正好服务全部任务族：

```text
观察/定位簇
  observe_home、query_topology、inspect_room、find_devices、inspect_device

执行簇
  execute_device_action

等待/验证簇
  wait_for_event、query_events、check_goal_state

记忆簇
  memory_read、memory_write
```

沙盒和 Home Assistant 各实现一套 MCP，但暴露完全相同的这组接口：

```text
沙盒侧                          HA 侧
query_topology                 area/floor 区域关系（可能缺失）
inspect_room / inspect_device  state + attributes
execute_device_action          call_service
wait_for_event                 subscribe_events + 条件等待
query_events                   history / logbook
check_goal_state               state 条件断言
memory_read/write              外部记忆服务（HA 无原生记忆）
```

迁移主张采用“同语义 + 三档适配”，不写死“零迁移”：

```text
同一策略在 Sandbox 与 HA 上跑成对任务
零适配 / 仅 schema 适配 / 少量示例适配
报告：成功率保持、非法动作率、工具调用数、适配修改量
```

空间类任务单独说明：HA 的拓扑依赖用户配置，配置缺失的任务标记为“不可迁移”，单独报覆盖率，而不是硬造一个不真实的映射。

## 三部分如何合成一篇论文

```text
benchmark（第一个支柱）
  六个任务族 + 空间核心，作为训练与迁移的公共任务骨架
         ↓
训练方法（第二个支柱）
  SFT 行为层 + RL 安全/长程两层目标，用 benchmark 验证
         ↓
迁移框架（第三个支柱）
  同一 MCP 语义在 HA 上的成对评测，量化策略保持与适配成本
```

三部分共享同一个任务集合，所以论文不是“三个系统各讲各的”，而是一条线：任务骨架定义能力 → 训练补齐能力 → 迁移检验能力是否保留。

细节版本仍保留在 `Benchmark任务范畴与训练迁移结合讨论.md`，需要给某个任务族出任务模板或给某层奖励写公式时再回到那份文档扩充。
