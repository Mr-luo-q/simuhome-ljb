# 沙盒轻量化设计分析：按 HomeFlow 的 Gym 风格环境标准重写

## 1. 用户记忆里的“基本范式”落在附录 A.3

HomeFlow 没有用抽象口号讲“沙盒应遵循什么范式”，它直接把答案做在附录 A.3：HomeEnv 被建成 Gym 风格环境。英文原文：

```
We further build a Gym-style smart home environment that automatically
generates house layouts and embedded devices, including rooms, floors,
and device instances.

env = gym.make("HomeEnv-v0", home=HomeSampler.sample_test())
observation, _, terminated, truncated, info = env.step({...})
```

RL 训练循环能驱动沙盒的前提就是这套公共契约：`reset` 出初始观测，`step` 返回 `observation, reward, terminated, truncated, info`。HomeFlow 正文里的 POMDP 形式化、Blueprint、MCTS-Flow 与 stepwise RLVE，是它在环境之上为数据合成与训练加的层；我们要借鉴的是 HomeEnv 这一层达到的工程标准，而不是照抄它的上层设计。

## 2. HomeFlow 环境层达到的标准，可归纳为五条

```
R1 可配置设备规格（附录 A.1）
   设备用 YAML 声明 attributes 与 services，可随机初始化；
   schema 与执行逻辑解耦，设备类型能低成本扩展。

R2 程序化控制 API（附录 A.2）
   加载规格后可直接 turn_on / set_brightness / 读属性；
   智能体动作落到统一高层设备 API，而不是逐个字段硬编码。

R3 Gym 风格环境外壳（附录 A.3）
   gym.make("HomeEnv-v0", home=...) 注册环境；
   env.step 返回 observation / reward / terminated / truncated / info；
   HomeSampler 能生成不同房屋布局、楼层与设备实例。

R4 可验证任务（附录 A.4 + 正文 3.2.1）
   任务定义为“可由环境状态推导的逻辑条件”；
   条件注册到 env.engine.task，每步检查 task.finished；
   全部条件满足时回合终止，避免 LLM 主观裁判。

R5 执行沙箱 + 部分可观测（正文 3.2.1）
   可执行动作只返回直接执行结果：序列化设备状态、执行反馈、运行时错误；
   模型看不到完整内部状态，必须主动查询并解释反馈。
```

这五条共同回答“什么算能跑 RL 的家居沙盒”：动作语义稳定、step 同步可驱动、任务可自动判定、观测来自真实执行。五条之外的内容属于 HomeFlow 的数据与算法层。

## 3. SimuHome 现状：机制强，但缺 Gym 这层壳

SimuHome 的 `Home` 类（simuprocject/Simuhome_experiment/src/simulator/domain/home.py）已经具备很强的“家居演化内核”：

```
已有机制                          代码位置
tick 主循环                        __simulation_loop
  time_aware_devices → aggregators
  → scheduler_queue → api_queue
设备状态约束                       device 类（先开再调温等）
房间环境聚合器                     aggregators（温度/湿度/照度/PM10）
调度与快进                         schedule_workflow / _fast_forward_to
精确批推进                         exact_batch_advance（无到期任务时）
HTTP 高层工具路由                  simulator/api/routes.py
```

这些机制已覆盖 HomeFlow 环境层中最难的动力学部分：设备状态变化会持续影响房间环境、时间可以快进、未来任务“注册成功不等于执行成功”。

但对照 Gym 风格环境，SimuHome 当前形态有五个硬差距：

```
差距一：驱动方式
  Home 由后台线程 + time.sleep 推进，API 经 queue + Event 异步返回；
  RL 无法在一个进程里直接 reset/step。

差距二：无 Gym 外壳
  没有 env.reset / env.step，也没有五元组返回结构。

差距三：观测过宽
  get_home_state 可一次拿全屋状态；智能体不需要“查询”就能看见一切，
  与执行沙箱的部分可观测原则冲突。

差距四：没有任务条件注册与自动评分
  只有 workflow 的 completed/failed；没有针对目标状态的可验证谓词，
  因此 env.step 无法产出 reward 和 terminated。

差距五：reset 不可并行
  HTTP 层用全局单例 home，reset 是停旧建新；多个 RL worker 会互相抢世界。
```

另外，SimuHome 现有房间之间没有连通关系，这正是我们要补的空间增量所在。

## 4. 轻量化设计：一个同步内核，两个门

“沙盒怎么轻量化设计”的答案，是在 SimuHome 演化内核外挂两个接口层，而不是新建一个 HomeFlow 克隆：

```
           语义动作/观测 Schema（约 10 个工具，单一事实来源）
                              |
             +----------------+----------------+
             |                                 |
       Gym Env（训练用）                MCP Server（评测/迁移用）
       reset/step                    get_room_states / execute_command ...
             |                                 |
             +----------------+----------------+
                              v
                   SpaceHomeWorld（同步内核）
             房间 + 设备 + 环境量 + 房间连通拓扑
             tick / aggregator / scheduler / 邻接交换
```

两条通路共享同一份动作与观测语义：

```
训练路径：
  RL 训练器 → env.step(结构化 action)
           → world.apply(action)
           → world.advance_until_next_decision()
           → obs / reward / terminated / truncated / info

真机路径：
  模型 → MCP 工具（与 env.step 的 action 同构）
       → HA adapter → Home Assistant service/state
```

训练为什么不走 MCP：HomeFlow 的 Gym 环境也是直连执行引擎，不走 HTTP 或服务层。RL 每回合上千次 step，若每步经过网络 MCP，延迟与故障会污染训练。MCP 留给在线评测与真机部署。

这个设计的“轻”体现在：

```
- 房间只作为节点，不建模真实几何；
- 连通只表示“相邻 + 门开/关”，不做路径规划；
- 每房间保留温度/湿度/照度/PM10 四类环境量即可；
- 房间规模 4~6 个，设备用 Schema 化能力描述；
- 设备能力收敛到 HA 能控制的实体/服务语义，不保留 Matter 30+ Cluster 全量。
```

“重”体现在仍保留时间、连续状态演化、动作依赖、调度与未来验证。所以它比纯文本 benchmark 重，比完整物理/协议仿真轻，正好支撑空间时间长期任务与 RL 训练。

## 5. 空间连通加入的位置

SimuHome 的 SimulationConfig 目前只有 rooms→state/devices。我们只需增加 layout：

```
SimulationConfig:
  rooms:  {living_room: {...}, kitchen: {...}, bedroom: {...}}
  layout:
    edges: [
      {from: living_room, to: kitchen,   door: open},
      {from: kitchen,     to: bedroom,   door: closed},
    ]
```

世界内核每 tick 在“房间聚合器算完”之后做邻接交换：

```
world.advance_tick():
  devices.on_time_tick()          # SimuHome 现有
  room_aggregators()              # SimuHome 现有
  scheduler_due_events()          # SimuHome 现有
  for edge in layout.edges:       # 新增
      if edge.door == open:
          exchange(edge.from_env, edge.to_env, rate)
```

举一个能说明问题的例子：

```
场景：客厅有空调，厨房与客厅之间门开着，卧室门关着。
任务：20 分钟后厨房温度降到 24°C，且卧室温度不超过 28°C。

正确行为：模型先 get_topology() 确认“空调在客厅、只能通过开门影响厨房”，
再决定开空调、必要时开门，最后 fast_forward_to 验证结果。
如果模型不查拓扑就默认“每个房间都有独立空调”，它会去控制不存在的设备。
```

房间连通因此成为世界本体约束：它影响状态转移、影响可执行动作集合（门/空调），并进入目标条件与奖励。

## 6. 这种沙盒是否支持 MCP

支持。理由不是“SimuHome 已有 HTTP”，而是先把动作收敛成同一语义 Schema，再分别做 Gym 适配与 MCP 适配。候选工具集保持约 10 个：

```
沙盒 MCP 工具                   HA MCP 同语义工具
get_home_state                 get_home_state（HA states 概览）
get_room_states                get_area_states
get_topology                   get_topology（area/entity 关系推导）
list_devices                   list_entities
get_device_state               get_state
execute_command                call_service（climate/turn_on 等）
write_attribute                set_entity_value
schedule_workflow              schedule（HA 自动化/定时）
fast_forward_to                wait_until（沙盒虚拟时间；真机按真实时间）
get_current_time               get_current_time
```

沙盒的 topology 来自 layout.edges；HA 的 topology 由区域与实体所属区域推导。真实家庭若缺少完整区域关系，需要用用户声明或自动推理兜底，这一点要写进论文的迁移条件。

## 7. 落地切片

最小验证闭环建议按下述顺序推进，每一步都保留 SimuHome 现有内核：

```
阶段一：把 Home 的演化循环抽成同步 world.advance_until(...)，
        保留 tick 顺序、fast_forward 判定与 aggregator exact_batch。
阶段二：加 SpaceHomeGymEnv：
        reset(seed, layout_id, goal_id) -> obs
        step(action) -> obs, reward, terminated, truncated, info
阶段三：加 ConditionChecker，把任务写成房间状态谓词，
        验证“目标 + 空间副作用 + deadline”。
阶段四：把同一语义动作注册成 MCP 工具，沙盒与 HA 各实现一份。

验收：3 房间连通场景完成 1,000 条 SFT 轨迹 + 小规模 RLVE；
      同一策略的 env.step 轨迹与 MCP 在线轨迹行为一致。
```
