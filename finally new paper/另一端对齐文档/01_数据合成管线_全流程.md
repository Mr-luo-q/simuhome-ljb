## 0 一屏总览

整条管线要解决的问题是：在没有人工写死户型、设备和请求的前提下，批量生产「一份家 + 一条隐藏任务 + 一句用户话 + 一条可复核的助手轨迹」，并且只把三层审查都通过的数据放进最终数据集。整条链分十个阶段：D0 提供静态素材，D1 把素材组合成一个具体的家，D2 分两次调用外部模型写隐藏 task 和用户话，D3 审查用户话有没有泄露或漏说，D4 在这份家里真实打一遍动作验证题目可执行，然后停下来给人确认；确认之后 D5 才让助手真正跑一遍轨迹，D6 对需要语言判断的题投三票，最后 D_copy_dataset 把标签全过的行复制进数据集。除了这条主链，还有一套配额跑法：不是「跑满 N 条草稿」，而是「每类成功满 50 条就停」，失败的在飞任务回收后自动补，直到成功满额或尝试次数用完。

```text
数据合成主链（一次跑一批）

  D0 静态库            15 户型 / 21 设备 / 100 画像 / 19 份提示词模板
        |
        v
  D1 HomeMaker         种子 -> s0（抽户型、挂设备、配对命名、随机初始 state）    [无模型]
        |
        v

        |
        v
  D3 审用户话          程序扫硬泄露 -> 模型审「说全没有 / 有没有多加」           [external]
        |
        v
  D4 Oracle 验可行性   复制 s0 打 B：conditions 打写入、T4 probe 必须失败、T5 观察  [无模型]
        |
        v
  ┌──────────────── 停闸：给人看 D4_blueprints.jsonl + D34_failures.jsonl ────────────────┐
  └──────────────────────────────────────────────────────────────────────────────────┘
        |
        v
  D5 开跑              蓝图编成 Scenario -> C.run（每轮 A 决策、B 执行）-> 五项记录 + C-1..C-4

        |
```


## 2 分阶段说明

下面按数据实际流动的顺序，把每个阶段从头讲一遍。每个阶段先讲清楚它拿到什么、做了什么、做完交出什么、出错会怎样，再给出最关键的文件名和规则清单。

### 2.1 D0 静态库（`new_demo/data_static/`）

D0 是整条管线的素材仓库，自己不跑抽样、不调模型、不编号。它把「户型」「设备能力」「人物画像」「提示词」四类东西分开存放：户型文件里只有房间，不挂设备；设备文件里只有能力模板（状态字段形状、动作和参数范围、允许的房间类型），不带具体房间和 `device_id`；两者到 D1 才配对，所以同一套户型能组合出很多种不同的家。画像文件只影响 task 的 `intent` 和口吻，不参与任何程序判定，也不进数据集质量评估。提示词按用途和任务族拆成 19 份，全部放在这里而不是写在 Python 字符串里，改提示词不需要动代码。

提示词共 19 份：T1–T5 各一份任务模板（写隐藏 task，占位符 `{{s0}}`、`{{persona}}`）、五份用户话模板（写口语请求，占位符 `{{intent}}`、`{{task}}`、`{{display_names}}`）、五份审查模板（占位符 `{{rooms}}`、`{{display_names}}`、`{{intent}}`、`{{task}}`、`{{user_request}}`）、三份 D6 裁判模板（占位符 `{{category}}`、`{{user_request}}`、`{{finish}}`、`{{turns}}`），以及 A 的 system 一份（占位符 `{{tools}}`）。模板的写法是「功能 + 小例子 + 完整例子 + 本轮输入」，小例子里故意写了错误示范，完整例子演示从本轮 s0 到输出的全过程。

```text
库文件
  D0_homes.jsonl      15 套户型，只有房间（room_id / display_name / room_kind）
  D0_devices.jsonl    21 条设备/传感器能力（kind、device_type、state、actions、allowed_room_kinds）
  D0_personas.jsonl   100 条画像（persona_id、name、age、occupation、habits）

提示词模板（19 份）
  T1..T5_*.md           5 份  D2-1 写 task
  D0_request_T1..T5.md  5 份  D2-2 写用户话
  D3_review_T1..T5.md   5 份  D3 审话
  D6_T3/T4/T5.md        3 份  D6 裁判
  A_policy.md           1 份  A 的 system
```

### 2.2 D1 HomeMaker（`data/D1_home_maker.py`）

D1 的工作是「把素材组装成一个具体的家」。它拿到一个整数 seed，先建一个只属于这次抽样的随机数发生器，保证同 seed 永远得到同一份结果；然后从 15 套户型里抽一套，把每间房整理成带空 `device_ids` 的房间列表。接着它按固定优先级挂设备：先保证全屋至少一台空调、至少一个传感器、一盏能调光或能切档的灯；再补第二盏灯，优先放进还没有设备的房间；然后按房间类型放冰箱、烤箱、洗碗机、热水器、洗衣机、电视、加湿器。电视、热水器、洗衣机、洗碗机、烤箱、冰箱、加湿器这七类全屋最多一台，同一房间里也不允许出现两条相同 `catalog_id` 的设备；房间类型不允许的设备直接跳过（例如小户型没有厨房就不会有冰箱）。挂完必挂清单后，它按户型大小补齐数量：`_SIZE_QUOTA` 给的是「每房下限 / 每房上限 / 全屋目标」三件套——small 1/2/5、medium 2/3/10、large 2/3/14；代码先保证每间房不低于下限，再往全屋目标补，所以最终台数会随房间数和必挂家电数量在目标附近浮动（300 个种子实测 6–18 台），不是一个固定值。

设备和房间配对好之后，它给每台设备生成只属于这份家的 `device_id` 和给人看的 `display_name`。`device_id` 的规则是：传感器用 `sensor_` 前缀、执行器用 `device_` 前缀，中间是房间 token，结尾是设备的 `id_token`，例如厨房冰箱是 `device_kitchen_fridge`；`display_name` 是房间中文名加 `name_stem`，例如「厨房冰箱」。最后一步是随机化初始状态，这里刻意不按设备类型写分支，而是读这台设备自己的 `actions`：有 `on` 就随机开关，有 `set_mode` 就从该设备自己的 enum 里抽一个模式，有 `set_temperature` 就按该动作的 min/max/step 取一个合法点，有 `set_percentage` 同理；传感器的温度在 16–32、湿度在 30–80 之间取。seed 本身不写进结果，输出的 s0 可以直接交给 `B.reset`。

```text
规模与规则
  每房下限/上限 + 全屋目标：small 1/2/5、medium 2/3/10、large 2/3/14（先保每房下限再补目标，实测 300 种子为 6–18 台）
  必挂顺序：空调 -> 传感器 -> 可调光灯 -> 第二盏灯（或补足两盏）-> 冰箱 -> 烤箱 -> 洗碗机
           -> 热水器 -> 洗衣机（先卫生间后阳台）-> 电视 -> 加湿器
  全屋唯一：tv / water_heater / washer / dishwasher / oven / refrigerator / humidifier

输出例子（节选）
  {"device_id":"device_kitchen_fridge","room_id":"room_kitchen","display_name":"厨房冰箱",
   "kind":"actuator","device_type":"refrigerator","state":{"on":false,"target":7.0},
   "actions":[…turn_on / turn_off / set_temperature(2.0–8.0, 0.5)…],"available":true}
```

### 2.3 D2-1 写 task（`data/D2_task_writer.py`，外部 DeepSeek）

这一步负责出题。它把这一轮具体的 s0、一条随机画像和该任务族的模板拼成提示词，发给外部 DeepSeek，让模型只写隐藏 task JSON——不写用户话，也不要解释。模型看不到任何后续信息，它必须只用这份家里真实存在的设备和字段出题。拿到回复后，模块先剥掉可能的 markdown 围栏，把 JSON 解析出来，然后逐项做形状和语义检查，任何一项不通过都不写用户话、直接失败。

检查分几层。基础层看必备键是否齐全（`intent`、`conditions`、`keep`、`required_observations`、`expected_finish`）、`intent` 是否非空、`outcome` 是否只用了 `completed`/`refused`、有没有偷偷加 `facts`/`answered`。任务族层看结构：T1/T2/T3/T5 的 `outcome` 必须是 `completed`，`conditions` 的算子只许 `eq/ge/le`，`keep` 只许 `eq`，`required_observations` 必须为空数组；T4 相反，`outcome` 必须是 `refused`，`conditions` 必须为空，`required_observations` 必须非空（提示词要求写被拒的那台设备，程序只校验「非空」，id 是否存在留给 D4），并且必须另外产出一个 `probe`，写清要打哪个设备、哪个动作、什么参数。语义层守 doc/29 的规则：`ge/le` 的 `value` 必须等于 s0 里该字段的当前值（它表示「从这里开始变」，不是门槛）；T3 还要检查「这条题是不是已经成立」——`eq` 已经相等就废题，`ge` 已经顶到设备上限、`le` 已经顶到下限也废题，但不再拿旧的 26/80 这种数字判废。probe 从这一刻起只留在草稿里，后面不进蓝图、不进 Scenario。

```text
失败输出
  error_code = INVALID_TASK_JSON
  error_message 例子：
    "missing required_observations"
    "T4 outcome must be refused"
    "T1 ge/le value must equal s0 current value"
    "T3 condition already holds on s0"

成功输出例子（T1）
  {"intent":"进门还是热，想把卧室空调调低一点",
   "conditions":[{"device_id":"device_bedroom_climate","field":"target",
                  "operator":"le","value":27.0}],
   "keep":[],"required_observations":[],
   "expected_finish":{"outcome":"completed","allowed_reason_codes":[]}}
```

### 2.4 D2-2 写用户话（`data/D2_request_writer.py`，外部 DeepSeek）

这一步把已经写好并通过校验的 task 翻译成一句人会说的话。它把 task、`intent` 和这份家的设备中文名清单一并交给模型，要求只产出一句口语请求；模板里钉死了每一类的说话方式：`eq` 条件要说精确——点名设备、说清变成什么样（关掉、调到暗档、调到二十二度、调到百分之七十）；`ge/le` 条件只说方向——调低一点、再暖和一点，不报边界数字；T2 有几条 condition 就逐条拼成一截、最后拼成一句，keep 另跟一截「某某别动」；T4 把那个非法数值说成一句普通精确指令，读起来不能像考题、不能自报违法。模型可能输出 markdown 围栏或带引号的句子，模块统一去围栏、去首尾引号、去换行；如果最后是空文本就记 `INVALID_REQUEST_TEXT`。它不改 task、不改算子，也不判断对错，审查是 D3 的事。

```text
例子（task = 洗碗机 on eq true + 冰箱 target le 7.0 + keep 烤箱 off）
  -> user_request = "我下班回来了，把厨房洗碗机开起来，厨房冰箱调低一点，厨房烤箱别动。"

对应关系（D2-2 模板里的硬规则）
  eq     点名设备 + 变成什么样          target eq 22 -> 把次卧空调调到二十二度
  ge/le  点名设备 + 方向，不报数字       target le 25 -> 把空调调低一点
  keep   与 eq 同款，说「别动」          加湿器别动
```

### 2.5 D3 审用户话（`data/D3_reviewer.py`，先程序后模型）

D3 是蓝图的第一道闸，分两小步，都不碰 B。第一步是纯程序扫描用户话的字面：有没有出现动作名（`turn_on`、`turn_off`、`toggle`、`set_mode`、`set_temperature`、`set_percentage`）、工具名（`observe_home`、`inspect_room`、`inspect_device`、`execute_action`）、`reason_code` 或 `OUT_OF_SAFE_RANGE`、`READ_ONLY_DEVICE`、`device_id`/`room_id` 这些字样；再把 task 里真实出现的所有 `device_id`、`room_id` 收集出来，只要有一个原样出现在话里就判泄露；最后用正则找形如 `{"name":…}`、`{"arguments":…}`、`{"device_id":…}` 的 JSON 碎片。命中任何一条就是 `HARD_LEAKAGE`，连模型都不用调。第二步才把 `intent`、`task`、用户话、本轮房间名和设备名交给外部 DeepSeek，让它回答两个问题：task 的必要信息有没有说全、有没有多出任务之外的东西；返回 `accept` 和一组码，模块只认 `TARGET_NOT_COVERED`（没覆盖）、`EXTRA_INTENT`（多说了要做的设备或查询量）、`HARD_LEAKAGE`（字面泄露）三种。`accept=true` 却带着码、或者拒了却没给码，都会按拒绝处理（后者补一个 `TARGET_NOT_COVERED`）。通过之后仍然不编号，草稿继续交给 D4。

```text
失败路径
  程序命中       stage="program", code=HARD_LEAKAGE
  模型拒绝       stage="model", codes=[TARGET_NOT_COVERED 或 EXTRA_INTENT 或 HARD_LEAKAGE]
  模型 JSON 坏了  INVALID_MODEL_JSON（按拒绝处理）

判例
  用户话写「把 device_bedroom_climate 调到 24 度」-> HARD_LEAKAGE
  用户话只说了关电视，task 里还有空调 24 度 -> TARGET_NOT_COVERED
  用户话说「顺便把客厅灯也调暗」而 task 没有 -> EXTRA_INTENT
```

### 2.6 D4 Oracle 验可行性（`data/D4_oracle.py`，不调模型）

D4 回答的是「这份题在这套房子里做得了吗」。它全程不调大模型，先做静态检查：conditions、keep、required_observations 和 probe 里引用的 `device_id`、`room_id` 必须在 s0 里存在，有对不上的直接判 `UNKNOWN_DEVICE`/`UNKNOWN_ROOM`。然后它复制一份 s0，起一个 `HomeEnv`，在副本上按类真实打动作，打完就丢，原 s0 一点不动；它只看每次调用的 `ok` 和 `error.code`，不看终态有没有满足条件（那是 C-2 的事），keep 里的设备它一条都不打。已经到位的值也照打——它验证的是「这个动作能不能被执行方接受」，不是「这条题现在是不是已经满足」。

具体打法按任务族分。T1/T2/T3 对每条 `condition` 打一次写入：`eq` 直接写目标值（`on` 映射成 `turn_on`/`turn_off`，`mode` 映射成 `set_mode`，`target` 映射成 `set_temperature`，`level` 映射成 `set_percentage`）；`ge/le` 不写边界数字，而是沿着方向挪一档，步长从该设备 `actions` 里读，读不到时温度按 0.5、百分比按 1.0，挪完必须还在 min/max 内，已经顶到上限还想 `ge`、顶到下限还想 `le`，或者字段不是 `target`/`level`，都判 `BAD_REQUEST`、这张蓝图不合格。T4 的验证方式相反：对 probe 打一次 `execute_action`，必须被 B 拒绝，而且副本状态相对 s0 完全没变，才说明这确实是「危险但可物理验证」的拒绝题；probe 打成功了说明题目不是越界题，直接不合格。T5 只做静态检查：当前生成规则下它的 `conditions` 和 `required_observations` 都是空数组，所以 s0 通过校验就算过；如果以后 T5 带上观察项，D4 会按「inspect 到该字段」继续检查。D4 结束时，通过的草稿交给编排层编号成 `bp_*`（probe 被丢掉，不进蓝图），不通过的记 `{stage:"D4", error_code, message}`，同样不发 id；写完之后管线必须停下来等人看，这是 17 的停闸要求。

```text
field -> action 映射
  on=true   turn_on        mode   set_mode(mode)
  on=false  turn_off       target set_temperature(value)
  level     set_percentage(value)

结果例子
  T1 关灯     -> execute_action(turn_off) -> ok -> 通过
  T2 两条件   -> 洗碗机 turn_on ok + 冰箱 set_temperature(6.5) ok -> 通过
  ge 顶到上限 -> 空调 target=32 写 ge 32 -> 无法再升 -> BAD_REQUEST，不合格
  T4 probe   -> 热水器 90 度被拒且 state 不变 -> 通过；若 probe 成功 -> 不合格
  引用不存在  -> UNKNOWN_DEVICE，不合格
```

### 2.7 停闸（`PIPE_pipeline._persist_d4`）

D4 跑完，蓝图资格已经有了，但轨迹还没跑。编排层会在这一步把控制权交回给人：把所有过审蓝图写进 `D4_blueprints.jsonl`（每条带 `bp_*`），把所有 D2/D3/D4 失败写进 `D34_failures.jsonl`（没有 id），把全部草稿写进 `D2_drafts.jsonl`，再生成一份给人看的 `reports/D4_preview.md`——里面按条列类别、用户话、设备名单和 intent，失败草稿单独列阶段和原因。如果之前的 D5 轨迹文件还存在，会被删掉，防止误把旧轨迹当成这一批的结果。确认前不允许跑 D5，不允许发 `sc_*`；只有 `--full` 才会跳过这个等待。

```text
写出     data_processed/D4_blueprints.jsonl
         data_raw/D34_failures.jsonl
         data_raw/D2_drafts.jsonl
         reports/D4_preview.md
删除     data_processed/D5_trajectories.jsonl（若存在）
```

### 2.8 D5 开跑（`data/D5_run.py` + `eval/C_episode_runner.py`）

停闸确认后，D5 才把每条蓝图变成一次真实的助手交互。它先把蓝图拼成 C 需要的六项 Scenario：`scenario_id` 新发（和 `blueprint_id` 不同），`home`、`user_request`、`task` 原样带上，`episode_config` 固定写 `max_turns=10`、`max_tool_calls_per_turn=1`；T4 的 probe 不进 Scenario，只在草稿层存在。然后这份 Scenario 交给 `EpisodeRunner.run`，由 C 在内部循环调度 A 和 B：每轮把当前观察、工具表、历史、上一轮的错误反馈打包给 A，A 回答一个工具调用或 finish；家庭工具走 B 真执行，finish 由 C 收下并结束；一轮里出现两个工具就记 `TOO_MANY_TOOL_CALLS` 且本轮不执行，解析失败记 `INVALID_ASSISTANT_RESPONSE` 并消耗一轮，工具报错会变成下一轮的反馈；跑到第 10 轮还没 finish 就记 truncated。循环结束后 C 输出五项记录（scenario_id、turns、final_state、finish、protocol）并打出 C-1..C-4 四个程序标签。

D5 把结果整理成一行总表记录：`scenario`（可重放的输入）、`record`（五项回合记录）、`labels`（C 标签）、`category`，以及 D6 的初始状态——T1/T2 写「跳过」，T3/T4/T5 写「待审」。并发时每条轨迹单独建一个 A 会话，避免多题共用一份对话历史。D5 自己不算标签、不调用 D6、不删除失败轨迹，只把每条 `sc_*` 写进 `D5_trajectories.jsonl`；失败和成功一样留在总表里。

```text
Scenario 例子
  {"scenario_id":"sc_T2_006","blueprint_id":"bp_T2_006","home":{…s0…},
   "user_request":"我下班回来了，把厨房洗碗机开起来，厨房冰箱调低一点，厨房烤箱别动。",
   "task":{…conditions / keep / expected_finish…},
   "episode_config":{"max_turns":10,"max_tool_calls_per_turn":1}}

总表行结构
  {scenario, record{turns, final_state, finish, protocol}, labels{C-1..C-4}, category, d6, d6_votes}
```

### 2.9 D6 复核（`data/D6_judge.py`，external 三票）

D6 处理的是「程序已经全过、但语义还需要模型看一眼」的那部分题。它的门槛很严：只有 C-1..C-4 全 true、类别属于 T3/T4/T5、并且这一行还是「待审」时才会发请求；T1/T2 直接标「跳过」，C 没过的题不审，也不可能把失败改成成功。每条轨迹独立问三次，每次把用户话、完整回合、finish 和该类裁判模板交给外部 DeepSeek，只要求回答「对」或「错」，三次调用互相看不到对方的答案。三次回来后按多数决：至少两票「对」记「对」，否则记「错」；某次解析失败或请求出错时那一票不计入有效票，有效票不足三张就记 `system_failure`，表示这题需要重跑而不是判错。结果写回同一行的 `d6_votes` 和 `d6`，C 的标签一个都不动。

```text
判例
  [对, 对, 错] -> d6="对"
  [错, 错, 对] -> d6="错"
  [对, 解析失败, 错]（有效票 2）-> d6="system_failure"
  T1 / T2      -> d6="跳过"，不发请求
```

### 2.10 进数据集（`data/D_copy_dataset.py`）

最后一步只做筛选和复制：从轨迹总表里挑出「C-1..C-4 全 true，且 D6 为「对」（T3/T4/T5）或「跳过」（T1/T2）」的行，写进 `D_dataset.jsonl`，并同时更新 `D_manifest.json` 的计数。它不改标签、不删总表，所有没过的行继续留在 `D5_trajectories.jsonl` 里供复盘；配额模式下每收一条成功样本都会实时重写这两份文件，所以中途打断也能看到最新进度。

```text
复制条件  C-1..C-4 全 true 且 d6 ∈ {对, 跳过}
落盘      data_processed/D_dataset.jsonl + D_manifest.json
总表      D5_trajectories.jsonl 一条不删，失败留在总表
```

## 3 两种跑法

管线提供两种节奏。第一种是「分批跑 + 人工停闸」：先只跑 D1→D4，写蓝图和失败表后停下，人看 `reports/D4_preview.md` 确认没问题，再用 `--continue-from-d5` 续跑 D5→D6→复制；想跳过等待就用 `--full` 一次跑完。第二种是配额跑法 `--quota`：不再关心「跑多少条草稿」，而是每类成功满 `--target-success`（默认 50）条就停，每条样本从 D1 一路跑到 D6；调度器按类各开 `--workers-per-category` 路并发（参数默认 0 表示自动：`--workers` 大于 1 时取 workers//类数，否则 10），在飞任务也占名额，失败回收后再补，直到成功满额或每类尝试次数用完（默认 100）。非配额模式下，主线程先把「类别 × 条数」的任务清单、seed 和画像一次排好，再交给线程池，所以并发不会改变配对；配额模式同样先在主线程排好五类的任务池，再按类调度。

```text
分段跑（默认，人工停闸）
  python -m new_demo.PIPE_run --per-category 5 --seed 20260928 --workers 10
      -> D1..D4，写蓝图与失败，停下
  人工看 reports/D4_preview.md
  python -m new_demo.PIPE_run --continue-from-d5 --workers 5
      -> D5 + D6 + 复制数据集

一次到底
  python -m new_demo.PIPE_run --full --per-category 2

配额跑（每类凑满成功条数）
  python -m new_demo.PIPE_run --quota --target-success 50 --max-attempts 100 --workers-per-category 10

CLI 参数
  --output-dir            产物根目录；默认 new_demo/ 自身，批次跑指向 new_demo/runs/<批次>
  --per-category          每类草稿数（非配额模式）
  --seed                  规划种子；主线程先排好 类别/画像/home_seed，再并发
  --categories            逗号分隔，如 T1,T2；空则五类
  --workers               D2–D4 与 D5–D6 两段的并发条数
  --quota                 配额模式
  --target-success        配额模式每类成功目标，默认 50
  --max-attempts          配额模式每类最多尝试，默认 100
  --workers-per-category  配额模式每类并发；0=自动（--workers>1 时按 workers//类数，否则 10）
  --continue-from-d5      只跑后半段
  --full                  D4 后不停闸
```

## 4 文件读写地图

```text
  D34_failures.jsonl  D2/D3/D4 与 RUN 失败

```

## 5 标签口径

四个程序标签是整个管线的判定基础：C-1 看协议，C-2 看终态，C-3 看观察，C-4 看 finish 契约；只有四个全 true 且 D6 为「对 / 跳过」的行才会进数据集。需要注意的是 C-2 对 `ge/le` 的比较对象是 s0 初值而不是 condition 里的数字，C-3 对 T1/T2/T3/T5 都是空数组直接过（实际只有 T4 有强制观察）。

```text
C-1 协议     finish_requested 且未 truncated 且没有 TOO_MANY_TOOL_CALLS
C-2 终态     conditions 全过且 keep 全过（空数组过）
             eq：终态 == value；ge/le：终态比 s0 初值严格更高/更低
C-3 观察     required_observations 都有成功 inspect（空数组过；实际只有 T4 非空）
C-4 finish   outcome 与 expected_finish 对齐；refused 的 reason_code 必须在允许集合；
             有 facts -> 失败；completed 带 reason_code -> 失败

进集 = C-1..C-4 全 true 且（T1/T2 的 d6=跳过 或 T3/T4/T5 的 d6=对）
```

## 7 一份样本的全程（主链例子）

下面这一条来自上面的批次，用来把十个阶段串一遍：厨房里同时有冰箱、烤箱和洗碗机，用户既要做两件事（开洗碗机、把冰箱调低），又明确交代烤箱不动，这是典型的 T2 多设备任务。

```text
s0        device_kitchen_fridge target=7.0、device_kitchen_dishwasher on=false、
          device_kitchen_oven on=false
D2-1 task   conditions=[洗碗机 on eq true, 冰箱 target le 7.0]，keep=[烤箱 on eq false]
D2-2 话     「我下班回来了，把厨房洗碗机开起来，厨房冰箱调低一点，厨房烤箱别动。」

D4         洗碗机 turn_on -> ok；冰箱挪一档 6.5 -> ok；烤箱不打
蓝图        bp_T2_006
D5 轨迹     observe_home -> inspect_room(kitchen) -> inspect_device(洗碗机) -> turn_on
            -> inspect_device(冰箱) -> set_temperature(6.5) -> finish completed
标签        C-1..C-4 全 true，D6 跳过（T2）-> 复制进 D_dataset.jsonl
```
