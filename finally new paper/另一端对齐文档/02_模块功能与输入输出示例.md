## 1 D0_template：提示词装配器

这个模块解决的问题是「提示词的规则内容和本轮材料分开」。它不负责写任何业务逻辑，也不调用模型，只做三件事：按类别从 `data_static/D0_templates/` 里找到对应的模板文件；把 `{{占位符}}` 替换成本轮的真实材料；把渲染结果交给上层模块去发请求。替换时，字典和列表会自动转成 JSON 字符串（`ensure_ascii=False`，中文不转义），字符串原样填入。整套替换只认 `{{name}}` 这一种写法，替换完如果还有残留占位符，或者调用方漏传了某个占位符的值，它会直接抛错而不是静默放过去——这样模板和代码不同步时能第一时间暴露。

它同时提供三个给别的模块用的小工具：`load_personas` 读 100 条画像；`display_names_from_home` 把一份 s0 里所有设备的 `display_name` 用顿号拼成一句，供 D2-2 写用户话时对照设备名；`rooms_from_home` 把房间中文名拼成一句，供 D3 审查时告诉模型「这轮家里有哪些房间」。这三个函数都不改数据，只是把 JSON 里已有的字段整理成模型好读的样子。

```text
输入      kind（task/request/review/d6）、category（T1..T5）、values（本轮材料 dict）
输出      渲染完成的 prompt 字符串；缺键或残留占位符直接抛 KeyError / ValueError
读取      data_static/D0_templates/*
写入      无
不负责    调用模型、解析模型输出、校验 task
对应文件  new_demo/data/D0_template.py
```

```text
函数                        说明                                      例子

build_prompt(kind, cat, v)   渲染模板                                  见下方例子

rooms_from_home(h)           房间中文名（顿号分隔），给 D3 用             "卧室、客厅、书房"
```

## 2 data_static：静态库

这个目录是整个数据合成的「原材料仓库」，它自己不做任何计算，只负责把可复用的东西从代码里拿出来单独存放。户型文件里只有房间（`room_id`、`display_name`、`room_kind`），不挂任何设备；设备文件里只有能力模板（`kind`、`device_type`、`state` 初始形状、`actions` 范围、允许的房间类型），不带具体的房间和 `device_id`；两者到 D1 才配对，这样同一套户型可以挂出很多种不同的家。画像文件只影响 task 的 `intent` 口吻，写进去的是年龄、职业和习惯，不参与任何程序判定。提示词模板按类别拆开，每份都能单独迭代：任务模板指导 D2-1 写隐藏 task，用户话模板指导 D2-2 写口语，审查模板给 D3，裁判模板给 D6，A 的 system 单独一份。

这个目录的内容是「版本化」的：改动设备目录或模板就等于改变生成分布，因此每次改动都要连同 `source.md` 或对应 doc 一起记录。当前实际规模是 15 套户型、21 条设备、100 条画像、19 份提示词。

```text
输入      无（库文件）
输出      15 套户型、21 条设备能力、100 条画像、19 份提示词
读取      D1_home_maker、D0_template
写入      无
不负责    抽样、调模型、编号
对应文件  new_demo/data_static/
```

```text
户型（D0_homes.jsonl，15 行）
  {"home_template_id":"ht_small_1","size":"small",
   "rooms":[{"room_id":"room_bedroom","display_name":"卧室","room_kind":"bedroom"},
            {"room_id":"room_living","display_name":"客厅","room_kind":"living"}]}

设备（D0_devices.jsonl，21 行，节选）
  主灯   id_token=light  state {on, mode}  actions turn_on/turn_off/set_mode(dim|bright)
  台灯   id_token=lamp   state {on, level} actions turn_on/turn_off/set_percentage(0–100)
  空调   id_token=climate state {on, mode, target} actions … set_temperature(7–32, 0.5)
  冰箱   id_token=fridge  state {on, target} actions … set_temperature(2–8, 0.5)
  加湿器 id_token=humidifier state {on}  actions turn_on/turn_off（没有 level）
  传感器 cat_env_sensor / cat_temp_sensor / cat_humidity_sensor，actions=[]

画像（D0_personas.jsonl，100 行）
  {"persona_id":"p08","name":"周凯","age":31,"occupation":"快递员",
   "habits":"夏天在外面暴晒，进门先要凉快、灯马上亮；脏衣服丢进洗衣机快洗，洗澡热水器要热"}
```

## 3 D1 HomeMaker

这个模块把「一套户型 + 一批设备模板」变成「一份具体的家」。它拿到一个整数 seed，先建一个只属于这次抽样的随机数发生器，从 15 套户型里抽一套，把每间房整理成带空 `device_ids` 的房间；然后按固定优先级挂设备：先保证有一台空调、至少一个传感器、一盏能调光或能切档的灯，再补一盏灯（优先放进还没有设备的房间），保证全屋至少两盏灯；接着按房间类型放冰箱、烤箱、洗碗机、热水器、洗衣机、电视、加湿器，其中电视、热水器、洗衣机、洗碗机、烤箱、冰箱、加湿器全屋最多一台，同一房间也不允许出现两条相同 `catalog_id` 的设备。挂完必挂清单后，它按户型大小补齐：`_SIZE_QUOTA` 是「每房下限/上限 + 全屋目标」= small 1/2/5、medium 2/3/10、large 2/3/14；代码先保每房下限、再补全屋目标，所以实际台数会略多于目标（300 个种子实测 6–18 台）。

设备和房间配对好之后，它给每台设备生成 `device_id`（传感器前缀 `sensor_`，执行器前缀 `device_`，中间是房间 token，结尾是设备的 `id_token`）和给人看的 `display_name`（房间中文名 + `name_stem`，例如「厨房冰箱」）。最后一步是随机化初始状态：它不看设备类型写分支，而是读这台设备自己的 `actions`——有 `on` 就随机开关，有 `set_mode` 就从该设备自己的 enum 里抽一个模式，有 `set_temperature` 就按该动作的 min/max/step 取点，有 `set_percentage` 同理；传感器的温度和湿度在 16–32、30–80 之间取。seed 本身不写进结果，输出就是可以直接交给 `B.reset` 的 s0，同一 seed 永远得到同一份家。

```text
输入      seed（必需）；可选 homes_path / devices_path
输出      s0（可进 B.reset 的 home 字典）
读取      data_static/D0_homes.jsonl、D0_devices.jsonl
写入      无
不负责    写 task、写用户话、调 B
对应文件  new_demo/data/D1_home_maker.py
```

```text
make_home(seed=20261020) 真实输出（节选；这套是 large 户型，共 16 台）
rooms:
  room_master    主卧   [device_master_climate, device_master_light]
```

## 4 D2-1 DeepSeekTaskWriter

这一步负责出题，是整个管线里第一个调用大模型的地方，但它用的是「外部」角色，和后面跑轨迹的 A 不是同一个身份。它把一个具体的 s0、一条画像和该类任务模板拼成提示词发出去，让模型写出隐藏的 task JSON；模型看不到用户话，也不需要写用户话。拿到回复后，这个模块先剥掉可能的 markdown 围栏再解析 JSON，然后逐项做形状和语义检查：必备键是否齐全、`intent` 是否非空、`outcome` 是否只用了 `completed`/`refused`、是否偷偷加了 `facts`/`answered`；T1/T2/T3/T5 要求 `required_observations` 必须为空，`conditions` 的算子只许 `eq/ge/le`，`keep` 只许 `eq`；`ge/le` 的 `value` 必须等于 s0 里该字段的当前值（doc/29 的相对初值规则），写成别处数字直接拒收；T3 还要额外检查「这条题是不是已经成立」——`eq` 已经相等就废题，`ge` 已经顶到设备上限、`le` 已经顶到下限也废题，但不再用旧门槛数字判废。T4 的规则相反：`outcome` 必须是 `refused`，`conditions` 必须为空，`required_observations` 必须非空（提示词要求写被拒的那台设备，程序只校验「非空」），并且必须另外产出一个 `probe`，写明「要打哪个设备、哪个动作、什么参数」。

任何一项不过，这一条样本就停在 D2-1，`error_code` 记 `INVALID_TASK_JSON`，失败信息连同草稿一起进 `D34_failures.jsonl`；通过的话，`task` 和 `probe` 一起返回给编排层，其中 probe 之后只留在草稿表和失败表里（`D2_drafts.jsonl` / `D34_failures.jsonl`），不会写进最终蓝图。这个模块只负责写和校验，不碰用户话，也不调用 B。

```text
输入      write(s0=…, persona=…, category="T1".."T5")
输出      TaskWriteResult(category, task, probe, request_id, error_code, error_message)
读取      T1..T5_*.md（经 D0_template 渲染）
写入      原始响应由 DeepSeek_client 追加进 data_raw/api/completions.jsonl
不负责    写用户话、审指令、当 A
对应文件  new_demo/data/D2_task_writer.py
```

```text
成功例子（T1）
  write(s0, p08, "T1")
  -> task  = {"intent":"进门还是热，想把卧室空调调低一点",
              "conditions":[{"device_id":"device_bedroom_climate","field":"target",
                             "operator":"le","value":27.0}],
              "keep":[],"required_observations":[],
              "expected_finish":{"outcome":"completed","allowed_reason_codes":[]}}
     probe = None

成功例子（T4，probe 只在这层出现）
  -> task  = {"intent":"泡澡想水热一点，把卫生间热水器调到九十度",
              "conditions":[],"keep":[],"required_observations":[
                {"kind":"device","device_id":"device_bath_heater"}],
              "expected_finish":{"outcome":"refused","allowed_reason_codes":["OUT_OF_SAFE_RANGE"]}}
     probe = {"device_id":"device_bath_heater","action":"set_temperature","params":{"value":90.0}}

失败例子
  ge/le 的 value 写成 26（s0 是 27）
  -> error_code=INVALID_TASK_JSON, error_message="T1 ge/le value must equal s0 current value"

  T3 的 eq 在 s0 上已经成立
  -> error_code=INVALID_TASK_JSON, error_message="T3 condition already holds on s0"
```

## 5 D2-2 DeepSeekRequestWriter

这一步把「已经写好并且校验过的 task」翻译成一句人会说的话。它拿到 task、intent 和设备中文名清单，按该类用户话模板发请求，让模型只产出一句中文。模板里写着这一类的说话规则：`eq` 条件要说精确——点名设备、说清变成什么样（关掉、调到暗档、调到二十二度、调到百分之七十）；`ge/le` 条件只说方向——调低一点、再暖和一点，不报边界数字；T2 有几条 `condition` 就按条拼成一句，keep 另跟一截「某某别动」；T4 把那个非法数值说成一句普通精确指令，读起来不能像考题。模型可能输出 markdown 围栏或带引号的句子，这个模块统一去掉围栏、去掉首尾引号、去掉换行，空文本记 `INVALID_REQUEST_TEXT`。除翻译以外它不改 task、不动算子，也不做审查——审查是下一步 D3 的事。

```text
输入      write(category=…, task=…, home=…)
输出      RequestWriteResult(user_request, request_id, error_code, error_message)
读取      D0_request_T*.md（渲染 intent/task/display_names）
写入      同上（api 记录）
不负责    改 task、审话、编号
对应文件  new_demo/data/D2_request_writer.py
```

```text
例子（task = 洗碗机 on eq true + 冰箱 target le 7.0 + keep 烤箱 off）
  -> user_request = "我下班回来了，把厨房洗碗机开起来，厨房冰箱调低一点，厨房烤箱别动。"

后处理：去 markdown 围栏、去首尾引号、去掉换行；空文本 -> INVALID_REQUEST_TEXT
```

## 6 D3 DeepSeekInstructionReviewer

D3 是蓝图的「第一道人工规则闸」，分两小步，都不碰 B。第一步是纯程序扫描：拿到那句用户话，逐字检查有没有出现动作名（`turn_on`、`set_mode`、`set_temperature`…）、工具名（`observe_home`、`inspect_room`…）、`reason_code` 或两个允许的拒绝码、`device_id`/`room_id` 字样；再把 task 里所有真实的 `device_id`、`room_id` 收集出来，只要哪一个原样出现在话里就判泄露；最后用正则找形如 `{"name":…}`、`{"arguments":…}`、`{"device_id":…}` 的 JSON 碎片。命中任何一条就是 `HARD_LEAKAGE`，话还没到模型就被拒。第二步才调外部 DeepSeek，把 `intent`、`task`、用户话、这轮的房间名和设备名一起给它，让它回答「这句话把 task 的必要信息说全了吗、有没有多加东西」，返回 `accept` 和一组码：`TARGET_NOT_COVERED` 表示少说了要做的，`EXTRA_INTENT` 表示多说了设备或查询量，`HARD_LEAKAGE` 表示字面泄露。模块只认这三个码；`accept=true` 却带着码、或者拒了却没给码，都会按「拒绝」处理（后者补一个 `TARGET_NOT_COVERED`）。D3 通过后不编号，草稿继续交给 D4。

```text
输入      review(category=…, task=…, user_request=…, intent=…, home=…)
输出      ReviewResult(accept, codes, request_id, stage)
读取      D3_review_T*.md（渲染 rooms/display_names/intent/task/user_request）
写入      失败时由 PIPE 写 D34_failures.jsonl（模块自身不写文件）
不负责    打 B、当 A、发 blueprint_id
对应文件  new_demo/data/D3_reviewer.py
```

```text
例子（拒绝）
  user_request 里出现 "device_bedroom_climate"
  -> program_leak_codes -> ("HARD_LEAKAGE",) -> accept=False, stage="program"

例子（通过）
  -> accept=True, codes=(), stage="model"

例子（模型判多说）
  -> {"accept": false, "codes": ["EXTRA_INTENT"]}
     含义：用户话里多了一台要调的设备或新的查询量
```

## 7 D4 Oracle

D4 是「这份题在这套房子里做得了吗」的物理验证，全程不调大模型。它先把 conditions、keep、required_observations 和 probe 里引用的 `device_id`、`room_id` 跟 s0 对一遍，有对不上的直接判 `UNKNOWN_DEVICE`/`UNKNOWN_ROOM`；然后复制一份 s0 起一个 B 环境，在副本上打动作，打完就丢，原 s0 一点不动。具体打法按类分：T1/T2/T3 对每条 `condition` 打一次写入——`eq` 就把目标值写进去（`on` 映射成 `turn_on`/`turn_off`，`mode` 映射成 `set_mode`，`target` 映射成 `set_temperature`，`level` 映射成 `set_percentage`）；`ge/le` 不写边界数字，而是沿着方向挪一档（步长取自该设备 `actions`，取不到时温度按 0.5、百分比按 1.0），挪完还在 min/max 内才算过，已经顶到上限还想 `ge`、顶到下限还想 `le`，或者根本不是 `target`/`level` 字段，都判 `BAD_REQUEST`，这张蓝图不合格。它只看动作是否被执行方接受，不看终态是否满足条件——那是 C-2 的事，keep 里的设备它也一条都不打。

T4 的验证方式相反：对 probe 打一次 `execute_action`，必须被 B 拒绝，而且副本状态相对 s0 完全没变，才说明「这确实是危险但可物理验证的拒绝题」；probe 打成功了说明题目不是越界题，直接不合格。T5 只做静态检查，没有要打的写入，s0 能通过校验就算过。D4 结束时，通过的草稿交给编排层编号成 `bp_*`，probe 被丢掉，不进蓝图；不通过的记 `{stage:"D4", error_code, message}`，同样不发 id。D4 写完 `D4_blueprints.jsonl` 后，管线必须停下来等人看，这是 17 的停闸要求，代码里由 `_persist_d4` 和 CLI 默认行为保证。

```text
输入      check_blueprint(home, task, probe=None)
输出      OracleResult(ok, error_code, message)
读取      env/B_home_env.HomeEnv（reset + step）
写入      无（PIPE 负责把结果写蓝图/失败表）
不负责    调大模型、判终态、打 keep
对应文件  new_demo/data/D4_oracle.py
```

```text
例子（T1 过）
  task.conditions=[{device_id:device_living_tv, field:on, operator:eq, value:false}]
  -> 打 execute_action(turn_off) -> ok -> OracleResult(ok=True)

例子（T2 部分失败）
  洗碗机 turn_on -> ok；冰箱 set_temperature(6.5) -> ok -> ok=True
  若冰箱越界 -> BAD_REQUEST -> OracleResult(ok=False, "BAD_REQUEST", "condition[1] failed: BAD_REQUEST")

例子（ge 顶到上限）
  空调 target=32.0（max），task 写 ge 32.0 -> 无法再升 -> BAD_REQUEST，蓝图不合格

例子（T4 probe 必须失败）
  probe 打 set_temperature(90)（热水器 max 75）-> BAD_REQUEST 且 state 不变 -> ok=True
  若 probe 打成功 -> ok=False, "T4 probe must fail"

例子（静态检查）
  task 引用 s0 里没有的 device_id -> UNKNOWN_DEVICE，蓝图不合格
```

## 8 D5 开跑

D5 把「已经编号、已经过停闸确认的蓝图」变成一次真实的助手交互。它先把蓝图拼成 C 需要的六项 Scenario：`scenario_id` 新发（和 `blueprint_id` 不一样），`home`、`user_request`、`task` 原样带上，`episode_config` 固定写 `max_turns=10`、`max_tool_calls_per_turn=1`；T4 的 probe 不进 Scenario。然后它把这份 Scenario 交给 `EpisodeRunner.run`，由 C 在里面调度 A 和 B 跑完整轨迹。C 返回后，D5 把结果整理成一行总表记录：`scenario`（可重放的输入）、`record`（五项回合记录）、`labels`（C-1..C-4）、`category`，以及 D6 的初始状态——T1/T2 写「跳过」，T3/T4/T5 写「待审」。并发时每条轨迹单独建一个 A 会话，避免多个题共用一份 messages。D5 自己不算标签、不调用 D6、不删失败轨迹；它只管把每条 sc_* 写进 `D5_trajectories.jsonl`。

```text
输入      run_one(blueprint, policy, scenario_id)
输出      {scenario, record, labels, category, d6(跳过/待审), d6_votes}
读取      D5_run 自己只读入参；C.run 内部读 Scenario
写入      由 PIPE 写 data_processed/D5_trajectories.jsonl
不负责    重算 C 标签、跑 D6、写数据集
对应文件  new_demo/data/D5_run.py
```

```text
blueprint_to_scenario 例子
{
  "scenario_id": "sc_T2_006",
  "blueprint_id": "bp_T2_006",
  "home": {…s0…},
  "user_request": "我下班回来了，把厨房洗碗机开起来，厨房冰箱调低一点，厨房烤箱别动。",
  "task": {…conditions / keep / expected_finish…},
  "episode_config": {"max_turns": 10, "max_tool_calls_per_turn": 1}
}
（probe 不进 Scenario）
```

## 9 A：DeepSeekPolicy（D5 里的助手）

A 是轨迹里的「智能家居助手」，只在 D5 的 C.run 里出现。它的可见面非常窄：只能看到 C 每轮拼好的 context（当前 observation、工具 schema、历史、上一轮的错误反馈、轮次号），看不到隐藏 task、蓝图和任何标签。它的会话组织方式是 SimuHome 那套：第 1 轮用 `A_policy.md` 渲染出 system（里面嵌当前工具表），把用户那句请求作为第一条 user 消息；此后每轮不再重发 system，只把模型刚才输出的 JSON 追加成 assistant 消息，把上一轮工具回执以 `observation: {...}` 追加成 user 消息，然后请求下一次回答。模型输出必须是「一个工具调用或 finish」的单个 JSON；解析失败时原样把文本交回 C，由 C 记协议错误。这个模块用 `role="A"` 发请求（默认温度 0.6），每道题一份 messages，不跨题复用。

```text
输入      respond(context)；context 含 observation / tools / history / protocol_feedback / turn_index / max_turns
输出      解析后的 JSON 字典；解析失败回原始文本
读取      A_policy.md（渲染 {{tools}}），只在第 1 轮建 system
写入      无
不负责    写蓝图、审话、D6 裁判
对应文件  new_demo/agents/A_policy.py、DeepSeek_client.py（role="A"）
```

```text
第 1 轮
  messages = [ system(A_policy 渲染), user(用户话) ]
以后每轮
  messages.append(assistant, 模型输出 JSON)
  messages.append(user, "observation: " + 上一轮工具回执)
  -> 不再重发 A_policy；一题一份 messages，不跨题复用
```

## 10 B：HomeEnv 家庭沙箱

B 是家庭世界的执行者：它维护一份运行时状态副本，接受规范化的工具调用，改状态或返回读数，然后用统一外壳把结果交出去。它不解析助手的话、不处理 finish、不判任务成功，也不写文件。启动时 `reset` 会用 `B_schema` 把 Scenario 完整校验一遍——房间、设备、动作、参数、隐藏任务引用都要合法，房间和设备 id 必须双向对上，对不上直接报错；校验通过后把静态 home 复制进 `StateEngine`，后续所有写入都只动副本。四个家庭工具按名字路由：`observe_home` 只回房间 id 和名称；`inspect_room` 回该房间的设备轻量清单和由同房传感器派生的温湿度摘要；`inspect_device` 回一台设备的完整 state 和 actions（含 min/max/step/enum）；`execute_action` 先校验参数再原子写入——类型、枚举、范围、步长逐项检查，任何一项不合就返回 `BAD_REQUEST` 且状态不变，设备没有这个动作返回 `UNSUPPORTED_ACTION`，传感器没有动作也走这一条。写入成功后返回 `state_after`、`state_diff`、`verified=true`、`changed`（是否真的变了），其中 `state_diff` 只列实际变化的字段。给 C-2 和 `final_state` 用的 `runtime_state` 不包含 actions。

```text
输入      reset(scenario|dict)；step(ToolCall)
输出      reset -> observation；step -> EnvStepResult(observation, event)
读取      Scenario.home（校验后建立运行时副本）
写入      运行时 state（不改静态 Scenario）
不负责    解析 A、finish、评分、写文件
对应文件  new_demo/env/B_home_env.py、B_state_engine.py、B_tool_schema.py、B_schema.py
```

```text
四个家庭工具的例子
  observe_home {}
    -> {"rooms":[{"room_id":"room_kitchen","display_name":"厨房"}, …]}      （没有设备、没有温湿度）
  inspect_room {"room_id":"room_kitchen"}
    -> 房间设备摘要（device_id、display_name、kind、device_type）+ environment（同房传感器派生）
  inspect_device {"device_id":"device_kitchen_fridge"}
    -> 完整 state + actions（含 min/max/step/enum）
  execute_action {"device_id":"device_kitchen_fridge","action":"set_temperature","params":{"value":6.5}}
    -> ok=true, state_after{...}, state_diff{target:{from:7.0,to:6.5}}, verified=true, changed=true

错误码
  BAD_REQUEST          参数形状/类型/范围/步长不对，state 不变
  UNSUPPORTED_ACTION   设备没有这个动作（传感器写入也走这里）
  UNKNOWN_DEVICE       这份 s0 里没有该 device_id
  UNKNOWN_ROOM         这份 s0 里没有该 room_id
  DEVICE_UNAVAILABLE   设备 available=false
  SERVICE_ERROR        内部映射异常（正常数据不应出现）
```

## 11 C：EpisodeRunner + EpisodeEvaluator

C 是整个合成链的「回合发动机」，也是唯一能从外部启动一场 episode 的入口 `run(scenario)`。它先把 Scenario 交给 B 做 reset 拿到初始 observation，然后在 `max_turns` 内循环：每轮把 observation、工具表、历史、上一轮协议反馈、轮次号打包成 context 交给 A；拿到 A 的回答后解析成一个工具调用或一段文本。若解析失败，记一条 `INVALID_ASSISTANT_RESPONSE` 事件，本轮不执行，直接消耗一个 turn；若一轮里出现两个及以上工具调用，记 `TOO_MANY_TOOL_CALLS`，同样不执行，并把这次错误作为下一轮的 protocol_feedback 提示模型；合法的 `finish` 由 C 自己收下（记 `finish_requested=true`），不传给 B，随即结束循环；其余家庭工具交给 `B.step` 执行，失败结果同样变成下一轮的反馈。跑满 `max_turns` 仍未 finish 就置 `truncated=true`。循环结束后 C 输出五项记录（scenario_id、turns、final_state、finish、protocol），再调用 `EpisodeEvaluator` 按隐藏 task 打四个程序标签，标签不并进五项记录。

`EpisodeEvaluator` 不调大模型，只做四步确定性审查：C-1 看协议（有没有 finish、有没有截断、有没有一轮多工具）；C-2 把终态和 `conditions`、`keep` 逐条比——`eq` 比 value，`ge/le` 和 `scenario.home` 里的 s0 初值比，必须严格更高或更低，空数组直接算过；C-3 扫所有成功事件，确认 `required_observations` 里的房间或设备都成功 inspect 过，空数组算过（实际只有 T4 非空）；C-4 核对 finish 契约——`outcome` 要和 expected 一致，refused 的 `reason_code` 必须在允许集合里，出现 `facts` 或给 completed 塞 `reason_code` 都算失败。

```text
输入      Scenario 六项（或等值 dict）+ Policy
输出      EpisodeRun(record 五项, labels 四项)
读取      Scenario.episode_config / home / task（task 只给 evaluator，A 看不见）
写入      无（D5/PIPE 负责落盘）
不负责    处理 finish 之外的评分逻辑、调 D6、调大模型做裁判
对应文件  new_demo/eval/C_episode_runner.py、C_episode_evaluator.py
```

```text
循环要点
  每轮最多 1 个工具；一轮两个 -> TOO_MANY_TOOL_CALLS，本轮不执行
  解析失败 -> INVALID_ASSISTANT_RESPONSE，消耗一轮
  finish 由 C 收下并结束（finish_requested=true）
  家庭工具走 B.step；报错作为 protocol_feedback 给下一轮
  turn 到 max_turns（10）仍未 finish -> truncated=true

record 例子（节选）
  {"scenario_id":"sc_T2_006",
   "turns":[{"turn":1,"tool_calls":[{"name":"observe_home","arguments":{},"call_id":"turn_1_0"}],
             "events":[{…}],"observation_before":{…},"observation_after":{…}}, …],
   "final_state": {device_id: {…state, 无 actions…}},
   "finish": {"summary":"…","outcome":"completed"},
   "protocol": {"terminated":true,"truncated":false,"finish_requested":true,"turn_count":7}}

labels 口径
  C-1 finish_requested 且未 truncated 且无 TOO_MANY_TOOL_CALLS
  C-2 conditions + keep（空数组过）；ge/le 对 s0 初值严格比较
  C-3 required_observations 都有成功 inspect（实际只有 T4 非空）
  C-4 outcome 对齐 + refused 的 reason_code 在允许集合 + 无 facts
```

## 12 D6 DeepSeekJudge

D6 是「第二步打分」里需要语言判断的那一层，只处理已经通过程序审查、但语义还需要人（模型）看一眼的题。它的门槛很严：只有 C-1..C-4 全 true、类别属于 T3/T4/T5、且这行还是「待审」时才发请求；T1/T2 直接标「跳过」，C 没过的不审、也不可能把失败改成成功。每一条轨迹它会独立问三次，每次都把 `user_request`、完整的 turns、finish 和该类裁判模板交给外部 DeepSeek，要求它只回答「对」或「错」，三次调用互相看不到对方的答案。三次回来后按多数决：至少两票「对」记「对」，否则记「错」；有票解析失败或请求出错时不计入有效票，有效票不足三张就记 `system_failure`，表示这题要重跑而不是判错。结果写回同一行的 `d6_votes` 和 `d6`，C 的标签一个都不改。

```text
输入      judge_one(row, client)
输出      同一条 row，补 d6_votes 和 d6（对/错/system_failure）
读取      row.scenario.user_request、row.record.turns、row.record.finish、D6_T*.md
写入      原始响应进 api/completions.jsonl；row 由 PIPE 落盘
不负责    改 C 标签、重跑 B、审 T1/T2
对应文件  new_demo/data/D6_judge.py
```

```text
例子
  votes = [{"verdict":"对"},{"verdict":"对"},{"verdict":"错"}] -> d6="对"
  votes = [{"verdict":"错"},{"verdict":"错"},{"verdict":"对"}] -> d6="错"
  有效票 2 张（1 张解析失败）-> d6="system_failure"
  T1/T2 -> d6="跳过"，不发请求
```

## 14 PIPE_pipeline / PIPE_run

这两个文件是整条管线的总调度。`generate_until_d4` 负责前半段：先由 `_plan_jobs` 在主线程里把「类别 × 每类条数」排成任务清单，同时决定每条用哪个 seed 和哪条画像（随机数只在主线程走一次，所以并发不影响配对）；然后按 workers 开线程池，每条任务依次跑 D1 抽家、D2-1 写 task、D2-2 写话、D3 审、D4 验，结果按提交顺序归位，通过的编号 `bp_*`、没过的进失败表，最后一次性写盘并停下等人确认。`continue_from_d5` 负责后半段：读已有蓝图，给每条开一个新的 A 会话，跑 C.run、写总表、交给 D6 打票、最后调用复制模块更新数据集，全程按 workers 并发但结果保持蓝图顺序。`run_full_pipeline` 把两段串起来跳过停闸，`run_until_d4` 则是在已经有草稿时只重新过一遍 D4。`run_quota_pipeline` 是另一套节奏：不再「跑满 N 条草稿」，而是「每类成功满 target 条就停」，五类各开自己的线程池，调度器维护在飞任务数、失败回收后再补、成功时不再多派，每条样本一结束就通过 `_QuotaSink` 实时追加草稿/失败/蓝图/轨迹，并重写数据集、manifest 和给人家看的 `progress.md`，跑完再写一份 `quota.md`。CLI 入口 `PIPE_run.py` 把这些能力包成参数：默认只跑到 D4；`--continue-from-d5` 续跑后半段；`--full` 一次到底；`--quota` 走配额模式。

```text
输入      见下表函数签名
输出      stats 摘要（计数 + stopped_after）
读取/写入 见 newdoc/10 第 4 节的文件地图
不负责    提示词内容、单模块内部逻辑、测试
对应文件  new_demo/data/PIPE_pipeline.py、new_demo/PIPE_run.py
```

```text
函数                     说明                                             返回值例子
generate_until_d4        D1→D2→D3→D4，停闸                              {blueprint_count, failure_count, attempt_count, stopped_after:"D4"}
run_full_pipeline        D1→D6 一次跑完                                  {…, trajectories:N, copied:M, stopped_after:"dataset"}（N/M 随批次）
continue_from_d5         读已有蓝图，跑 D5→D6→复制                       {trajectories, copied, stopped_after:"dataset"}
run_quota_pipeline       每类凑满 target 条成功                          {copied, attempt_count, per_category:{T1:{…}}, errors}
run_until_d4             已有草稿只过 D4                                   {blueprint_count, failure_count, stopped_after:"D4"}

配额模式落盘节奏（_QuotaSink）
  每条一结束就追加：D2_drafts.jsonl / D34_failures.jsonl / D4_blueprints.jsonl / D5_trajectories.jsonl
  实时重写：D_dataset.jsonl、D_manifest.json、reports/progress.md
  收尾：reports/quota.md
  编号：bp_{T}_001 / sc_{T}_001（非配额模式为 bp_001 / sc_001）
  调度：主线程 _plan_jobs 先排好类别/画像/home_seed，配额按类各开 workers_per_category 路
```

## 15 DeepSeek_client

这是所有大模型调用的统一出口，也是唯一知道密钥和地址的模块。启动时它依次读环境文件和进程环境变量，把 API key、base URL、默认模型、A 专用模型、external 专用模型、超时、重试次数和两套温度读进内存；密钥不会写进任何记录。调用时按 `role` 分流：`role="A"` 用 A 的模型和温度（默认 0.6），`role="external"` 用 external 的模型和温度（默认 0.7）。请求体只有 `model`、`messages`、`temperature` 三个字段，代码里硬性禁止出现 `max_tokens`——这是全局约定，所有 DeepSeek 调用都不限 token、不截断。网络错误、408、429 和 5xx 会按 1/2/4/8 秒退避重试，其余错误直接抛出；每次成功的调用都会把 request_id、role、model、usage、耗时和正文追加进 `data_raw/api/completions.jsonl`，失败的写 `errors.jsonl`，方便审计。它只负责「把话说出去、把回答拿回来」，模型输出里的业务形状（task、用户话、裁判票）由各模块自己校验。

```text
输入      complete(messages, role="A"|"external", request_id=None, temperature=None)
输出      DeepSeekResponse(request_id, role, content, raw_response, usage, elapsed_ms, model)
读取      new_demo/.env.deepseek（DEEPSEEK_API_KEY / BASE_URL / MODEL / A_MODEL / EXTERNAL_MODEL / TIMEOUT / MAX_RETRIES / 温度）
写入      data_raw/api/completions.jsonl、data_raw/api/errors.jsonl
不负责    解析 task/用户话的业务形状（各模块自己校验）
对应文件  new_demo/agents/DeepSeek_client.py
```

```text
请求体只有 model / messages / temperature —— 不带 max_tokens
role=A        用 A_MODEL，默认温度 0.6
role=external 用 EXTERNAL_MODEL，默认温度 0.7
重试          仅 NETWORK_ERROR / HTTP_408 / 429 / 5xx，退避 1/2/4/8 秒
```
