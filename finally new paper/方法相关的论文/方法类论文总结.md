## 一、TAP / 自动化规则生成

### 01. MvTAP：基于多视图表示学习的 TAP 规则用户意图预测（吉林大学 2024 ESWA）

**研究问题**：触发-动作编程(TAP)里，规则只是“如果触发器，则动作”，但用户创建它的**隐性意图**（节能、安全、舒适）才是关键。现有方法只知道显性需求（关闭空调），读不出意图。困难有三：触发器与动作上下文互相依赖、描述文本太短、功能相似的实体缺领域知识（看不出是“同一类意图”）。

例子（论文开头原例）：规则“如果你离开家，则关闭空调”，显性需求是“关空调”，但**隐性意图是“节能”**。现有推荐只能推功能相似的规则（蓝箭头），跨功能规则（橙箭头）只有靠意图才能连起来。

**解决方法**：用三个视图分别学表示，再用 Transformer 融合成多标签分类。

```
MvTAP 框架
  用户视图   : 触发器-动作构成的图（学两者协同/依赖）
  开发者视图 : 用 TextCNN 读触发器/动作的功能描述文本
  知识视图   : 知识图谱实体表示（补领域上下文）
  Transformer 融合三视图 → 多标签意图分类
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据集 | 真实 IFTTT：50,067 条规则，取 IoT 相关去重后 1,923 条、302 触发器、523 动作、12 类意图 |
| 基线 | 单视图：TF-IDF/Sentence-BERT/TextCNN、GNN(GAT/EGAT/PNA/DGN/FastGTNs/SeHGNN)、知识图谱(DistMult/ComplEx/RKE)；多视图：TMC、RCML、KGAN；变体：MvTAP-mean/concat |
| 指标 | 灵敏度/特异性/Micro-F1/Macro-F1/准确率 |
| 结果 | MvTAP 准确率 76.79%、Micro-F1 80.35%、Macro-F1 74.69%。准确率比最佳单视图提升 34.65%(开发)/1.8%(用户)/11.33%(知识)；比最强多视图提升 19.28%，Micro-F1 提升 8.55% |
| 消融 | 去掉开发者视图掉最多 —— 功能描述文本最关键；知识视图影响大于用户视图 |

### 03. HomeGenii：检索增强生成增强型 TAP 规则（东南大学 2026 IMWUT）

**研究问题**：平台演进后 TAP 规则变成“增强型”，带脚本、条件逻辑、计算、外部 API 调用。普通用户不会写，而 LLM 只用预训练知识+基础提示（RAG）生成这种规则会吃力。论文问：怎么让非专业用户借助 LLM 造出有表现力的复杂自动化规则？

例子：要表达“只有在湿度低于 40% 且是工作日早晨时才启动加湿器”这类带条件/计算的规则，光靠描述很难让模型一次写对。

**解决方法**：HomeGenii 做“先聚类后检索”的规则库 + 压缩，降低 token 开销、提升对齐度。

```
HomeGenii
  规则库：从 IFTTT applet 分类法构建，先语义聚类再搜索
  检索：取语义对齐的增强型 TAP 规则，压缩最小化 token
  生成：把检索结果以 3 种方式注入 LLM 生成流程
  底座：GPT-5 / Gemini-2.5 Pro / DeepSeek-R1
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | 20 个场景 × 4 种信息条件(最少/丰富逻辑/丰富上下文/两者) = 80 条提示；规则库来自 IFTTT；4 类家庭环境 |
| 基线 | 无 RAG（仅基础提示）、未聚类规则库 |
| 指标 | 准确率（是否通过全部单元测试并端到端执行）、CodeBLEU、检索 F1 |
| 结果 | 准确率 14%(无 RAG)→约 84%；相对提升 70%。语义聚类相对未聚类 +27% 准确率、+16% 检索成功率；上下文检索 F1 约 91% |
| 信息条件 | 同时给“丰富逻辑+上下文”达 100% 准确率、平均 CodeBLEU 60.8 |

## 二、端侧 / 高效部署

### 02. Edge LLM：边缘大语言模型全面综述（中山大学等 2026 CCF TPCCI）

**研究问题**：大模型从集中式云端向网络边缘（手机、PC、IoT、车辆）转移，驱动力是数据隐私、低延迟、离线可靠性、个性化。但资源受限边缘设备放不下大模型，怎么解决？

**解决方法**：这是一篇**端到端工程视角的综述**，不是新系统。它把路径系统规划为：先从设备端适配（参数高效微调 PEFT、联邦学习）切入，再到高效推理三大支柱（模型压缩、架构设计、运行时/系统优化），最后建整体评估框架并盘点应用。

```
Edge LLM 路线图
  设备端适配 : PEFT(微调)、联邦学习 ← 个性化关键
  模型压缩   : 量化 / 剪枝 / 蒸馏
  架构设计   : 注意力机制变体
  运行时/系统 : KV 缓存管理 / 推测解码 / 内存分页
  评估框架 + 跨领域应用盘点
```

**实验效果**：作为综述**无自建实验与基线**，价值在给出一条“算法理论到系统实现”的统一路线图与评估框架。

### 04. VCU-LLM：提示高效、设备端大模型用于模糊指令理解（北京邮电大学 2026 IMWUT）

**研究问题**：用户爱用模糊指令，如“帮我降低客厅的温度”；但现有助手要么只认显式指令，要么把模糊指令丢给云端 LLM（高延迟、隐私、成本）。论文问：能不能把 LLM 直接放**边缘设备**上做本地模糊指令理解与控制计划生成？

**解决方法**：VCU-LLM 是首个端侧模糊指令理解系统，核心是“提示高效”。

```
VCU-LLM
  模糊指令知识检索算法：挑出 prompt 里最相关的设备信息 → 降复杂度、加速推理
  数据集生成：构建 40,000+ 条模糊指令-控制计划对，用于 LoRA 微调
  KV 缓存定制：进一步加速端侧推理
  基线对比：6 条 LLM 工作流，用户问卷调查打分
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | 40,000+ 模糊指令-控制计划对（生成管线造，覆盖多家庭）；真实家庭案例 |
| 基线 | Llama-7B(云A100)、HomeLLM-1.1B、GPT-4o、GPT-3.5、GPT-4o(I)、GPT-3.5(I)（迭代推理） |
| 结果 | 控制计划质量平均提升 **43.3%**（人类打分+LLM 打分）；时间开销比端侧基线(HomeLLM、Llama3.2-1B、TinyLlama-1.1B)平均降低 **8.44×** |

### 14. AdaHome：用本地小语言模型的自适应智能家居助手（南安普顿 2026 arXiv）

**研究问题**：基于大模型的系统依赖重量级推理管线+云端部署，在资源受限环境低效、有隐私隐患，且长期个性化支持有限。论文问：小模型本地部署能否既高效又稳定地做个性化？

**解决方法**：AdaHome 不做一刀切的复杂推理，而是**意图感知规划框架**动态分流，并新增偏好适应机制。

```
AdaHome
  意图路由 : 简单指令→简单提示组件；需理解→轻量推理组件
  链式草稿(chain-of-draft) : 高效且稳定的决策
  偏好适应 : 从长期用户反馈学习，无需改 prompt / 重训
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | 90 条指令 = 30 直接 + 30 间接 + 30 模糊（源自 Sasha 40 条 + SAGE 50 条数据集） |
| 基线 | 统一小模型设置下复现 Sasha、SAGE、Harmony |
| 指标 | 直接指令精确匹配成功率；间接/模糊用 LLM-裁判(与人工 κ=0.834)；延迟、token |
| 结果 | 直接指令准确率 **86.7%**，延迟最多降 **3×**；模糊输入保持竞争力且成本更低；多轮偏好一致率 **88%**，而提示增强基线仅 52.5% |

## 三、指令理解 / 意图

### 09. Sasha：大语言模型的创造性目标导向推理（德州大学奥斯汀 2024 ACM CCS）

**研究问题**：用户常说的是“让这里变得舒适”“帮我节能”这种**欠明确目标**，没点名设备与动作；当前系统无法把“舒适”这类概念与空间、可用设备、个人偏好关联起来。论文先问 LLM 基线到底行不行、坏在哪，再给出改进系统。

例子：“让客厅变得舒适”——人类会联想到温度、照明、音乐，并因人而异；智能家居系统却做不到从抽象概念跳到具体设备动作。

**解决方法**：先做实证基线研究（跨年龄段用户调查，看 LLM 行动计划质量与故障模式），再构建 **Sasha**。

```
Sasha
  计划执行：把用户目标(如"让我睡得更好")变成对可用设备的动作/自动化例程
  锁定相关设备 + 纳入用户偏好
  迭代推理，抑制"幻觉计划 / 锁定无关设备"
  在测试家庭中落地，N=7 用户研究
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 研究 | 跨年龄用户调查看基线计划质量；测试家庭落地 + N=7 用户研究（用户生成场景） |
| 发现 | LLM 能做创造性推理完成挑战性目标，但存在降低实用性的故障模式 |
| 结果 | Sasha 减少了误报、避免把无关设备当目标；用户研究验证了迭代推理每一步与可用性 |

### 11. DS-IA：主动拒绝与环境锚定执行的双阶段意图分析（浙江工商大学等 2026 arXiv）

**研究问题**：LLM 从“信息提供者”变成物联网里的**具身智能体**后，直接执行会实体幻觉（控制不存在的设备）；而迭代框架（如 SAGE）又在“鲁莽执行”和“过度询问”之间摇摆。论文问：怎么既少打扰用户又可靠执行？

例子：用户说“把没有的客厅灯打开”——模型若直接生成动作就是幻觉；但若是真需要澄清的歧义，又不宜反复打断用户。

**解决方法**：DS-IA 把高层意图理解与底层物理执行分离成两阶段。

```
DS-IA 双阶段意图感知
  阶段1 语义防火墙：查当前家庭状态，过滤无效指令、消解模糊
  阶段2 确定性级联验证器：按 房间→设备→能力 逐步规则核查，
                           确认物理可行后才执行
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 基准 | HomeBench、SAGE |
| 指标 | 精确匹配 EM、无效指令拒绝率、自主成功率、人工澄清精确率 |
| 结果 | HomeBench EM 58.56%（较基线提升 >28%），无效指令拒绝率 87.04%；SAGE 上自主成功率 42.86%→71.43%，同时保持对“确实需澄清”歧义的识别精确率 |

### 12. MiCU：端到端智能家居指令理解（武汉大学+小米 2026 arXiv）

**研究问题**：指令理解系统对精确表述（“打开卧室灯”）行，但对模糊/意图不明（“让卧室变得舒适”）不行。LLM 泛化好，但受限于领域数据稀少、任务适配不足、成本高。论文问：怎么造一个专门懂家居指令的模型？

**解决方法**：先合成领域数据，再两阶段训练一个 Qwen3-4B 底座，并可选的令牌压缩。

```
MiCU
  DevCmd 数据集 : 用自动工作流从真实用户日志合成 5 万样本、28 类，缓解数据稀缺
  训练 : 课程学习 + 思维链监督微调 + 强化学习
  MiCU-fast : 把冗长设备描述压缩成特殊 token → 降计算/延迟
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | DevCmd（5 万样本、28 类，来自小米真实日志合成） |
| 基线 | 传统基于规则的选择法 + 少样本 ICL 的流行通用大模型 |
| 结果 | 相对规则法 +28.29%、相对最佳大模型 +20.01% 准确率；令牌压缩使 prompt 长度 -31.9%、准确率仅 -0.6%；在线：用户纠正率 -1.57%、人工审核准确率 +32.05% |

### 13. PEC-Home：智能家居渐进省略指令的解读（北京理工大学等 2026 arXiv）

**研究问题**：人的对话会随共享上下文积累而**渐进省略**（如“还是把灯开大点”），但家庭助手无视这一点。由此引出两大挑战：多用户不同环境预期造成的**指代歧义**；用户偏好随时间/环境演变造成的**意图歧义**。

例子：一家三口对“舒适温度”定义不同（指代歧义）；同样是“该睡觉了”，夏天和冬天想做的事不同（意图歧义）。指令越省略，越考验助手补上下文的能力。

**解决方法**：构建首个专测渐进省略指令的模拟家庭数据集 PEC-Home，并用多种增强手段评测。

```
PEC-Home 数据集
  多用户偏好 + 动态用户偏好
  省略级别 1~4（等级越高越省略）
  评测增强手段：零样本提示 / 上下文学习(ICL) / 检索增强生成(RAG)
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | PEC-Home 模拟家庭数据集（先与 Sasha、IFTTT 等对比其独特性） |
| 基线 | Mistral Instruct-v0.3、Gemma-2-9b/27b、Qwen2.5-7B/14B/32B/72B、DeepSeek-V3、GPT-4o |
| 指标 | 执行准确率 EA、F1 |
| 结果 | 没有模型能仅凭省略指令准确执行；RAG 有帮助但指令越省略效果越差，始终达不到完整指令水平；增大参数量只在等级 2 有用、等级 4 迅速失效；GPT-4o 在 ICL 下处理等级 4 还不如某些配 RAG 的小模型 |

## 四、推荐 / 编排 / 智能体 / 训练

### 05. GenX：面向多模态生成体验的设备编排（保时捷+乌尔姆大学 2026 IMX）

**研究问题**：日常设备编排（如准备在家阅读要开灯/暖气/音乐）繁琐、高度静态，需要多次手动交互且缺乏上下文响应。论文问：如何用多模态生成式 AI 做出动态、自适应的用户体验？

例子（论文原例）：用户读书时，系统自动轮询并编排连接设备——电视显示生成图像、音箱播环境音、AR 设备投射与场景匹配的 3D 全息图。

**解决方法**：GenX 由三模块构成，用视觉-语言模型理解用户对环境感知，再生成并按可用输出模态定制体验，并**实时生成执行源代码**。

```
GenX 流水线
  感知流水线 → 生成式界面控制 → 体验流水线
  VLM 解读用户对环境感知 → 生成多模态体验描述
  → 编排选定的设备 → 实时生成并执行代码(处理意外)
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 评估 | 两个真实场景（餐饮、阅读）+ 用户研究 n=16，定性与定量测量 |
| 结果 | 用户感知积极，支持日常任务有效；无自动化基线对比（研究-通过-设计性质），指出设备编排可扩展性仍待扩 |

### 06. DevPiolt：小米智能家居的物联网设备操作推荐（武汉大学+小米 2025 arXiv）

**研究问题**：根据用户上下文（历史操作、环境信息、设备状态）生成个性化设备操作。现有推荐模型处理不了复杂操作逻辑（多物品+顺序）、多样化用户偏好，且对次优建议敏感。

例子：开空调前往往要先开电源插座，顺序不能反；有人每天固定时刻开窗帘（长期稳定偏好），有人避免频繁开关空调（短期行为）。这些都考验推荐模型理解“一组操作+顺序”的能力。

**解决方法**：DevPiolt 用“预训练+微调+直接偏好优化+曝光控制”四步。

```
DevPiolt
  预训练+微调    : 在设备操作数据集上学 IoT 领域知识
  直接偏好优化DPO : 对齐特定用户偏好
  置信度曝光控制  : 过滤低质量推荐，避免负面体验
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | 小米智能家居多数据集（约 9,000 次交互，7/17 个子数据集） |
| 基线 | CGC（门控推荐）、DeepSeek |
| 指标 | EM-Acc、LM-F1、Rule |
| 结果 | 整体 44.33/57.49/53.03，DeepSeek 32.97/44.68/41.45，CGC 19.95/17.72/23.48；较最佳基线平均提升 95.5%/58.5%/54.0%（摘要口径 69.5%） |
| 在线 | 部署一季，日均 25.5 万用户、32.6 万条建议；独立访客设备覆盖率 +21.6%、曝光接受率 +29.1% |

### 08. IoTGPT：利用大模型实现高效个性化智能家居自动化（亚洲大学等 2025 ACM CHI）

**研究问题**：设备爆炸带来控制复杂度和用户疲劳；基于 LLM 的解法因非确定性、高推理延迟/成本、有限个性化而不可靠、低效。论文问：怎么让 IoT 指令执行可靠、高效又个性化？

```
IoTGPT

```

### 18. SAGE：基于接地执行的智能家居代理（arXiv 2311.00772，2023；文件名标 ACM CHI）

**研究问题**：LLM 有常识推理和通用知识，适合解读智能家居请求，但缺少用户、住宅与设备的具体知识；传统助手依赖预定义例程、固定流程和手工设备代码，处理不了自然、隐晦、多步骤的请求。论文问：能不能让 LLM 自己决定“下一步做什么、做没做成、何时结束”，再用工具把缺的具体知识补回来？

例子（论文原例）：四条需求正好对应四类挑战——“我的球队今晚有比赛吗？”（个性化）、“调低我烘干机的屏幕亮度”（按需读设备 API，不用写设备专属代码）、“打开梳妆台上的灯”（凭房间照片做自然设备指代）、“提醒我在打开冰箱时把牛奶扔掉”（持续监控设备状态）。

**解决方法**：SAGE 用“工具 + LLM 控制的顺序决策”把用户请求变成行动序列，每个控制流决定都由 LLM 做出，不写死决策逻辑。

```
SAGE 框架
  用户请求 → 顶层智能体工具 → 循环：选择工具 / 终止
  提示 Pi = 任务信息 + 工具指令 + 格式信息 + 输入 + 历史信息
  执行观察写回历史 Hi，下一次决策继续携带；可随意外结果改计划(故障恢复)
  关键工具
    个性化   : 长期记忆(稠密检索) + 分层用户画像；人机交互用于澄清
    设备交互 : 规划器 → 按需取 API 文档 → 属性/命令执行；错误文本回传自纠
    设备消歧 : OpenCLIP 算“用户描述 vs 设备照片”的相似度
    监控     : 条件代码编写(生成 Python) + 条件轮询(False→True 才触发)
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | 自建 50 项挑战任务（个性化/意图解析/设备解析/持久性/指令链/直接指令），配置真实 SmartThings 家庭（2 电视、1 冰箱、1 洗碗机、4 灯）并保存状态，消歧用实拍设备照片；另有 10 项开发后新增的留出任务防提示过拟合 |
| 基线 | One Prompt（单提示注入部分设备状态，让模型输出变更）、Sasha（去掉人工澄清/反馈，且无触发器概念，处理不了持久命令） |
| 模型 | GPT-4、GPT-4-turbo、GPT-3.5-turbo、Lemur、Claude2.1；temperature=0，每任务跑 3 次 |
| 结果 | SAGE+GPT-4 成功率 **75%**，基线约 30%；GPT-4-turbo 反而低于 GPT-4；Claude2.1 因格式与工具选择表现最差；GPT-3.5-turbo 与开源 Lemur 相当 |
| 故障分析 | GPT-4 的 9 次失败中 6 次来自误解模糊指令；GPT-4-turbo 的 69% 失败集中在工具使用（API 请求格式/工具参数） |

SAGE 在本文件夹里有两重角色：作为方法，它把个性化、按需设备 API、照片消歧、持久命令监控组装进同一个 LLM 智能体；作为资源，它的 50 任务数据后来被 AdaHome 吸收进 90 条指令，DS-IA 也把 SAGE 当作自主成功率对照环境。

### 19. HomeFlow：面向智能家居智能体训练的可验证数据飞轮（美的/北邮/东华/北大 2026 arXiv）

**研究问题**：LLM 智能体正从纯文本走向物理世界控制，智能家居是代表性领域，但训练高质量智能体需要大规模多轮交互数据，真实家庭采集受成本、部署复杂性和隐私限制；纯文本角色扮演合成数据又缺底层物理环境验证，生成的命令可能是“看着合理但不可执行”的幻觉，且每个场景只产出一条线性轨迹、覆盖不了多样化环境与多轮策略。论文问：能不能用“仿真环境 + 可验证数据生成 + 强化学习”构成一个闭环数据飞轮，把智能体训练出来？

例子（论文原例）：“感觉有点闷”——智能体要根据当前环境推断隐含意图，决定调空调还是开窗通风；这种模糊指令如果只靠文本合成，无法验证生成的动作是否对应有效设备、能否在当前房间执行。

**解决方法**：HomeFlow 把“数据生成、轨迹扩展、多轮策略优化”统一到同一个可验证仿真环境上，形成三段式流水线。

```
HomeFlow 数据飞轮
  HomeEnv 仿真引擎  : 结构化家庭状态 + 隔离执行沙箱 + 规则验证/动作审计
  HomeMaker 场景生成 : 采样真实天气/嵌套户型/设备分布 → 多样化初始状态
  Blueprint 蓝图     : 用户画像+生活片段 → 原子意图 → 可执行布尔成功条件(三重过滤)
  MCTS-Flow 轨迹搜索 : 树状搜索替代线性采样；智能体节点优先扩展(k_agent>k_user)、
                       UCB 选择、已验证前缀复用、环境奖励反向传播
  两阶段训练        : MCTS 成功轨迹监督微调 → 在线逐步 RLVE(动态用户模拟器+
                       HomeEnv 实时奖励：进度+成功+安全审计惩罚)
  评测               : 自建 SmartHome-Bench（1,678 实例、5 类任务）
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 数据 | SmartHome-Bench 1,678 个实例，覆盖房间布局与设备组合；任务分原子控制 QT1、组合控制 QT2、模糊意图 QT3、上下文多轮 QT4、个性化记忆 QT5 |
| 基线 | 前沿闭源/开源模型：GPT-5.5、Claude-4.6 Sonnet、Qwen3.5 Plus、GLM-5、DeepSeek-V4-Flash、MiniMax M2.7；训练基线为同样本量纯文本角色扮演微调（Role-play-4B/8B） |
| 结果 | HomeFlow-RL-4B 整体成功率 **84.60%**、8B 达 **87.03%**，8B 超过 GPT-5.5（85.80%）1.23 个百分点；SFT 相对角色扮演提升 5.88%（4B）/4.67%（8B） |
| 消融 | 数据合成成功率：纯角色扮演 86.33% → 蓝图线性 92.43% → MCTS 完整 96.48%；非对称分支（k_agent=3）84.7% 优于用户侧重扩展 82.6%；逐步 RLVE（87.03%）优于仅终局更新（86.46%），平均工具调用再降 8% |

HomeFlow 的意义是给“智能体训练”补上闭环：HomeEnv 同时承担数据验证与强化学习奖励，使 Qwen3-4B/8B 这种小模型经 SFT+RLVE 后反超同级大模型，说明在交互式可验证环境里训练能克服模型规模限制。局限也很明确：目前依赖确定性仿真，需解决仿真到现实的迁移、厂商协议扩展和 MCTS/在线 RL 计算开销。

## 六、安全

### 15. PromptShield-Home：面向智能家居代理的多模态提示注入防御（宾州州立/清华等 2026 UbiComp Companion）

**研究问题**：智能家居代理用多模态 LLM 直接感知视频/音频，但环境里大量**并非指令**的信号（电视语音、屏幕文字、旁听对话、便签）可能被误当成用户意图，导致误操作或隐私泄露。论文把这种威胁称为**环境多模态提示注入**，问：代理能否区分真用户指令与“看起来像指令的环境信号”，同时不因过度谨慎漏掉真指令？

例子：电视里说“把灯关掉”，代理若照做就会误触发；反之，老人真的跌倒的紧急信号若被“过度防御”忽略，则安全完成率崩掉。

**解决方法**：建一个**三种风险感知决策**（执行/阻断/询问用户）的基准，比较三个抽象层。

```
PromptShield-Home
  L0 传统检测器 : 唤醒词 / 姿态 / OCR
  L1 单多模态LLM代理 : 视觉 / 视觉+ASR / 原生视听
  L2 多代理协调 : 投票 / 角色专家 / 跨模型仲裁
  场景：受话人歧义 / 屏幕与音频注入 / 健康监测误触发 /
       混合占用 / 合法指令 / 占用状态查询
```

**实验效果**：

| 维度 | 内容 |
|---|---|
| 指标 | 因聚合准确率误导（恒“永不行动”预测器即有 82%），分别报**不安全执行率**与**安全完成率** |
| 结果 | 传统检测器**过度执行**；每种多模态 LLM 配置**过度拒绝**（几乎不完成真指令、且每种配置都漏真跌倒）；二者正确集互补 |
| 上限 | 总是选对层的预言机达 94.1%，最佳单层仅 76.5% —— 但路由器未实现，是个上限非系统 |
| 结论 | 更安全的家庭代理应**结合路由与传感器融合**，而非用多模态 LLM 简单替换检测器 |

## 横向结论

把 19 篇叠起来看，智能家居方法研究正在围绕三条主线收敛。

```
  要什么         代表方法                                                 共同手段
  ---------------------------------------------------------------------------
  懂模糊/省略/意图  Sasha、MiCU、DS-IA、PEC-Home、VCU-LLM、MvTAP       意图建模/领域数据/澄清-拒绝
  上得了端         Edge LLM、VCU-LLM、AdaHome、HomeLLaMA                压缩/蒸馏/微调/小模型+自适应分流
  记得住、懂偏好    MemAura、HomeLLaMA、IoTGPT、DevPiolt、LLM个性化UX     记忆图/画像/子任务复用/偏好对齐(DPO)
  安全不误触发     PromptShield-Home                                   多层决策+路由+传感器融合
  编排/智能体系统  GenX、TaskSense、IoTGPT、SAGE、HomeFlow             生成式编排/传感器语言/工具智能体/可验证数据飞轮
```

共通的三个判断：

1. **隐性/省略/无效意图是共同短板**。从 MvTAP 的隐性意图、PEC-Home 的省略指令，到 DS-IA 的主动拒绝、MiCU 的模糊指令，本质都是“读懂用户真正想要的，并敢于在做不到时拒绝”。
2. **端侧小模型的路径正变得可行**。VCU-LLM、AdaHome、HomeLLaMA、Edge LLM 综述说明，靠提示高效、蒸馏、小模型+自适应分流，能把成本/延迟/隐私一起解决，而不是一味上大模型。
3. **个性化依赖“结构化记忆”与“偏好建模”，但记忆与推理常常割裂**。MemAura、IoTGPT、DevPiolt、LLM 个性化 UX 都指出：把长期日志/偏好真正组织成模型可高效检索的结构，是比单纯加大模型更有效的一步。
