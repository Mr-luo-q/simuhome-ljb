# 06 本地 1.5B 模型部署与规则代码生成测试

测试日期 2026-10-05。目标：用本地已有的 1.5B 权重，验证它是否具备基本的
规则代码生成能力（TAP 规则、HA 自动化）。

## 0. 结论

```text
本地确实有权重（GGUF），不需要下载：Qwen2.5-1.5B-Instruct Q8_0 等都在 D:\D_program\models
部署方式：llama.cpp Vulkan 预编译版 + 本地 GGUF，起 OpenAI 兼容服务（127.0.0.1:8090）
性能：加载约 3 秒；生成约 156~169 token/s，prompt 最高 3500 token/s

能力结论
  简单代码：能写对（Python 函数、简单 JSON TAP 规则）
  领域格式：零样本写不对 HA 自动化 YAML（触发器/动作字段全错，HA 返回 400）
  给一条正确示例后：同一请求能生成有效 HA YAML，HA 接口返回 200
  含义：1.5B 有基本代码生成能力，缺的是 HA/IFTTT 的领域 schema；
        对我们做规则接口，优先用结构化参数，或在提示里带一条规范示例
```

## 3. 五个最小测试

### 3.1 零样本：IFTTT filter code（失败）

```text
请求   "Write IFTTT filter code for this TAP rule: if motion is detected in the living room,
        turn on the living room light. Output only the code."
输出   {"source": {"type": "motion", "entity": "living_room_motion_sensor"},
        "filter": {"type": "motion", "entity": "living_room_motion_sensor"},
        "target": {"type": "light", "entity": "living_room_light"}}
判定   不是 IFTTT filter code，也没有"开灯"的动作逻辑；只有实体映射的影子
```

### 3.2 零样本：HA 自动化 YAML（失败）

```text
请求   "Write a minimal Home Assistant automation in YAML: when
        binary_sensor.living_room_motion turns to 'on', turn on light.living_room."
输出   automation:
         - alias: Turn on living room light when motion detected
           trigger:
             - platform: binary_sensor          ← 错：触发器平台应是 state
               entity_id: binary_sensor.living_room_motion
           action:
             - platform: switch                 ← 错：动作应写 service: light.turn_on
               entity_id: switch.light_living_room  ← 错：域与实体名都不对
               turn_on: true
判定   YAML 本身能解析，但 HA 校验拒绝：POST /api/config/automation/config/{id} 返回 400
```

### 3.3 零样本：普通 Python 函数（通过）

```text
请求   写一个 handle_event(event)，当 device==living_room_motion 且 state==on 时
       调用 turn_on("living_room_light")
输出   def handle_event(event):
           if event["device"] == "living_room_motion" and event["state"] == "on":
               turn_on("living_room_light")
判定   正确
```

### 3.4 一条示例（one-shot）：HA 自动化 YAML（通过）

```text
提示里给一条正确示例（platform: state + to: "on" + service: light.turn_on + target.entity_id），
再要求生成同样的规则。输出：

       trigger:
         - platform: state
           entity_id: binary_sensor.living_room_motion
           to: "on"
       action:
         - service: light.turn_on
           target:
             entity_id: light.living_room

判定   HA 接口 POST /api/config/automation/config/{id} 返回 200（接受），随后已删除
```

### 3.5 零样本：简单 JSON TAP 规则（通过）

```text
输出   {"trigger": "motion detected in the living room",
        "action": "turn on the living room light"}
判定   正确（字段名按要求）
```

## 4. 结果汇总

| 测试 | 形式 | 结果 |
| --- | --- | --- |
| 1 IFTTT filter code | 零样本 | 失败（格式错） |
| 2 HA 自动化 YAML | 零样本 | 失败（HA 校验 400） |
| 3 Python 函数 | 零样本 | 通过 |
| 4 HA 自动化 YAML | 一条示例 | 通过（HA 200） |
| 5 JSON TAP 规则 | 零样本 | 通过 |

```text
已验证     1.5B 能写简单代码；零样本不懂 HA/IFTTT 的字段规范；单条示例即可修复 HA YAML
推断       对更复杂的规则（多条件、cron、脚本）仍需要示例或结构化约束，未测
待确认     本地 Qwen3-0.6B 的 SFT / GRPO 各 GGUF 在同类任务上的表现（下一轮可测）
```

## 5. 对设计的直接影响

```text
规则接口优先结构化  让模型填 trigger/condition/action 的参数（或调用"创建_自动化"工具），
                    而不是让它直接写 YAML/JS 自由代码
需要示例就带一条    如果确实要模型产出 HA YAML，系统提示里放一条最小正确示例
小模型可先 SFT      本地已有 Qwen3-0.6B 的 SFT/GRPO 权重，可用来验证"训过之后
                    零样本能否写对规则代码"
```
