## 2 共同底座

### 2.1 ACTION_CALL：立即执行和预约共用的动作调用

```text
ACTION_CALL = {
  device_id : string        设备 id
  action    : string        规范动作名
  params    : object?       动作参数，如 {value: 26} / {mode: "cool"}
}

execute_action 的输入       = ACTION_CALL
time_control 的 steps 元素  = ACTION_CALL（逐字复用，不改名、不加字段）
```

契约里只定义一份 schema：`execute_action` 的 inputSchema 与 `time_control.steps.items`
引用同一个常量，模型在 tools/list 里看到的这两处 schema 完全相同。

### 2.2 写入纪律

```text
① 先校验    形状 / 必填 / 范围，不合法不写
② 再执行    写文件（memory）或调 HA 服务（execute_action、预约到点）
③ 回读验证  文件逐字比较；设备读状态确认
④ 才返回    成功码或结果对象；不谎报成功
```

memory 不是设备，不走设备四道闸门；但"先校验、再写、回读、再返回"这条纪律一致。

### 2.3 时间规则

```text
只用绝对时间，不用相对时间；
接口格式 "YYYY-MM-DD HH:MM"（分钟级），按家庭时区解释；
执行时刻落到整分 HH:MM:00；
验收窗口前后各 30 秒（due-30s ~ due+30s）；
advance / 快进 / 条件等待本期都不做。
```

### 2.4 对内丰富、对外简单

```text
模型只看 tools/list 和每次调用/返回：
  指令对 → 成功；指令错 → 失败。
  返回里不出现重试、回读、校验、状态机这些词。

内部（模型看不到）可以自由设计：
  四道闸门、参数重复校验、回读验证、云设备延迟重试、原子写、
  sqlite、调度器、内部状态机、逐步结果、错误分层、日志。

落地口径
  模型可见字段 = 它决定下一步所需的最小集；
  其余字段一律留在内部记录/日志，不下发。
```

## 3 记忆接口 memory（已定稿）

### 3.1 契约

```text
memory(op?, text?)
  op    string   read | write，默认 read
  text  string   write 必填；read 禁止携带

返回（模型只看到这些）
  read    {"text": "..."}        原文逐字；超长截断在内部做，模型只拿文本
  write   {"code": "OK"}         只回一个更新成功的码

错误（模型只看到这两个码；具体原因只在内部日志）
  BAD_REQUEST    指令错：op 非法 / read 带 text / write 缺 text / 空文本 / 超 200 token
  SERVICE_ERROR  执行失败：文件读、写或回读失败（内部可能重试或修正，模型不感知）
```

已确认的口径：

```text
M1  空文本 write → BAD_REQUEST（拒绝，不当清空）
M2  读取超硬上限 → 截断，返回前 N 个字符并带 truncated 标记
M3  写入 → 整段替换，不做 append
M4  写入成功只返回 {"code": "OK"}，不带 updated_at、不带 chars
M5  错误码只用两个：BAD_REQUEST + SERVICE_ERROR
```

契约变更：现有契约是 `memory(op, key, value)`，实现时改成 `op + text`，
去掉 key / value / UNKNOWN_KEY。

### 3.2 存储与格式

```text
文件      config.memory.file（当前 data/memory.yaml）
编码      UTF-8；返回 JSON 用 ensure_ascii=False（中文不转义）
读取      按纯文本读，不解析 YAML / JSON / Markdown
格式      不强制；03 号五段模板降级为推荐内容
          （version / profile / preferences / constraints），schedules 段废弃
写入      整段替换；临时文件 + 原子替换；单写者加锁
不做      key-value、sqlite、语义检索、跨实例共享、遗忘策略
```

### 3.3 长度与预算

```text
写入      硬上限 200 token；超过 BAD_REQUEST，不落盘
读取      软 200 / 硬 300 token；超过硬线截断并带 truncated 标记
0.6B 档   建议 ≤150 token
估算      中文 0.75 token/字（Qwen 级）、0.94（小词表）；英文约 0.25 token/字符
配置      memory.max_write_tokens（200）、memory.max_read_tokens（300）
```

### 3.4 读取与写入规则

```text
read      文件原文逐字返回；文件缺失 → text="" 并创建空文件；
          每次调用读文件（有写之后缓存会过期）
write     校验 → 临时文件 → flush → 原子替换 → 回读逐字比较 → {"code":"OK"}
          校验不过 → BAD_REQUEST；回读不一致 → SERVICE_ERROR
替换      write 是整段替换；想追加就 read 后拼接再 write
```

### 3.5 与预约、执行的关系

```text
"记住用户喜欢 22 度"          → memory.write
"记住明天 7 点把冰箱调到 4 度" → time_control.schedule
memory 不再有 schedules 段；预约单也不写进 memory 文件
```

### 3.6 暴露与验收

```text
现状    已实现（2026-10-07）+ 已开放
验收    T1 read 逐字一致；文件缺失 → 空文本并建空文件
        T2 write 后 read 内容一致，write 返回 {"code":"OK"}
        T3 op 非法 / read 带 text / write 缺 text / 空文本 → BAD_REQUEST
        T4 超 200 token → BAD_REQUEST 且文件不变
        T5 超读硬上限 → 截断 + truncated=true
        T6 中文 UTF-8 无乱码、JSON 不转义
        T7 写入中途失败不留半文件（原子性）
```

## 4 时间调度接口 time_control（设计稿）

### 4.1 契约

```text
time_control(op, at?, steps?, schedule_id?)
  op           schedule | list | cancel
  at           schedule 必填："YYYY-MM-DD HH:MM"，家庭时区
  steps        schedule 必填：1~8 条 ACTION_CALL
  schedule_id  cancel 必填

返回（模型只看到这些）
  schedule  {"schedule_id": "sch_7f3a2b91", "at": "2026-10-08 07:00",
             "status": "pending"}
  list      {"now": "2026-10-07 21:05",
             "items": [{"schedule_id": "...", "at": "..."}]}
             （只列还没执行的单；已取消 / 已完成 / 失败的一律不出现）
  cancel    {"schedule_id": "...", "status": "cancelled"}
  （due_at、total_steps、逐步结果、内部状态机都不下发，进内部记录）

错误
  INVALID_TIME   at 解析失败 / 已过去 / 超出最远期限
  BAD_REQUEST    op 非法、缺参、steps 空或超限、schedule_id 不存在或不可取消
  UNKNOWN_DEVICE / UNSUPPORTED_ACTION  建单时校验 steps 命中
```

### 4.2 预约单结构

```text
{
  schedule_id   单号 sch_ + 8 位                    模型可见
  at            接口输入的时刻（分钟级）              模型可见
  status        内部：pending / running / completed / failed / cancelled
                模型侧不按状态列单；status 词只出现在确认里
                （schedule 回 pending，cancel 回 cancelled）
  due_at        落到整分的执行时刻（带时区）          内部
  steps[]       ACTION_CALL 列表                     内部
  results[]     每步执行结果 = execute_action 返回对象 内部
  created_at / finished_at / error                   内部
}
```

内部状态词与 SimuHome 对齐（五个），全部留库审计；
对模型不再下发状态化的列表：取消 / 执行完 / 失败的单直接消失（2026-10-09 定）。

### 4.3 时间规则与校验

```text
at 必须落在 now+1min ~ now+7d 之间，格式必须是 "YYYY-MM-DD HH:MM"
不合法 → INVALID_TIME，不建单
执行时刻 = 该分钟的 :00；验收窗口 = due-30s ~ due+30s
窗口内执行且设备确认到位 → 该步算按时
```

### 4.4 执行路径（复用 execute_action）

```text
建单时   逐条 ACTION_CALL 过 execute_action 的同一套校验
         （设备存在、动作支持、参数范围）；错单不落库、不发 schedule_id
到点时   for step in steps:
            调用执行内核 perform_action(context, **step)
            （与模型直接调 execute_action 是同一条代码路径）
         每步结果原样存进 results[]
失败     某一步执行不了 → 记录该步结果，继续执行剩余步骤（不中断、不重试、不补偿）
边界     到点设备掉线（DEVICE_UNAVAILABLE）本期不专门处理，后续版本再定
```

复用边界：

```text
复用     ACTION_CALL schema、四道闸门、参数校验、服务映射、回读验证、错误码
不复用   工具 schema、返回值包装（schedule_id vs 立即结果）、预约单生命周期、存储与调度
```

### 4.5 存储与调度器

```text
存储      sqlite data/schedules.db
          schedules(schedule_id PK, at, due_at, steps_json, status,
                    created_at, finished_at, result_json, error)
          索引 (status, due_at)
调度      runtime 起一个调度线程 + due 最小堆；到点顺序执行
精度      tick 200 ms 级即可（分钟级任务足够）
重启/过期  本期不设计：实验里任务不会跨过执行时刻（T1 不考虑）
启动清理   本期不做特殊设计（T5 不考虑）
协议壳    实现时 server.py 的调用改 asyncio.to_thread，
          避免到点执行阻塞 MCP 事件循环
```

### 4.6 list 与 cancel

```text
list     无参数；只列还没执行的单（内部 status=pending），最多 10 条、按 at 升序；
         每条模型只看到 {schedule_id, at}；
         已取消 / 已完成 / 失败的单留库审计，但不下发。
         （2026-10-09 反转，原"不做 status 过滤"作废：取消后还能在 list 里看到，
         对小模型是纯负担）
cancel   pending → cancelled；取消后该单立刻从 list 消失；
         已取消再取消 → {"status":"cancelled","message":"Already cancelled"}
         completed / failed → BAD_REQUEST
```

### 4.7 与其它接口的边界

```text
execute_action   现在做；time_control 到点做；共享 ACTION_CALL 与执行内核
manage_rule      持久规则 / 周期触发；本文不做、未定稿、无代码
memory           事实与偏好；不存 schedules，不存预约单
```

### 4.8 暴露与实现状态

```text
现状     已实现（2026-10-07）+ 已开放
实现时   contract 参数改造；execution.py 抽出 perform_action；
         time_control.py 实现三 op；runtime 加 sqlite + 调度器；测试离线 + 真机
开放     已加入 tools.expose（2026-10-07）
```

### 4.9 验收

```text
T1 建单    单步 / 多步成功；错设备、错动作、越界 → 创建失败
T2 到点    at=下一分钟；到点执行；HA 状态确实变；执行完该单从 list 消失
T3 取消    pending 取消后到点不执行，且立刻从 list 消失
T4 时间    过去 / 超 7 天 / 格式错 → INVALID_TIME
T5 失败    某一步执行不了 → 该步记录失败，剩余步骤继续执行
T6 复用    预约执行的结果字段与直接 execute_action 完全一致
（重启与到点设备掉线本期不做验收项）
```

## 5 时间查询接口 inspect_time（2026-10-08 实现、已开放）

```text
工具名    inspect_time
输入      无
输出      {"now": "2026-10-08 09:30", "clock": "real|virtual"}
语义      只读、无副作用；返回调度器使用的同一个时钟
          HA 后端 = 家庭时区真实时间（clock="real"）
          沙盒后端以后 = 虚拟时间（clock="virtual"）
错误      无特殊错误；后端不可用时走统一外壳
对应文件  新建 backend_ha\tools\inspect_time.py（+ 同名 .md）
```

为什么单独一个工具（而不是 op=now 或只用 observe_home.time）：

```text
命名      inspect_time 与 inspect_room / inspect_device 同族，读接口语义一致
读写分离   inspect_time 只读；time_control 写预约，职责清楚
token     输出只有 now + clock，比 observe_home（房间 + 环境 + 设备）省很多
先例      SimuHome 的 13 个工具里有 get_current_time，模型会主动调用确认时间
```

与现有字段的关系：

```text
observe_home.time        保留，作为全屋快照里的附赠字段
time_control.list.now    保留，作为便利字段
inspect_time             成为"取当前时间"的规范入口
```

时钟一致性（实现红线）：

```text
inspect_time 和 time_control 必须共用一个时钟助手（backend_ha\clock.py）：
  home_timezone(context) / now_local(context)
不能一个读虚拟时间传感器、另一个用真实时间调度；
模型用 inspect_time 的 now 算 at，再调用 time_control.schedule，必须通过校验。
```

暴露与验收：

```text
暴露     已加入 tools.expose：开放工具 8 条（原 5 + inspect_time + time_control + memory）；
         check_goal / query_events 仍隐藏
验收     T1 无参数返回 now，格式 "YYYY-MM-DD HH:MM"
        T2 clock 与调度器一致；用 inspect_time 的 now + 2 分钟构造 at，
           time_control.schedule 成功（离线 + 真机已通过）
        T3 沙盒后端接上后返回 clock="virtual"（二期）
```

## 7 例子

下面所有返回只画模型看到的字段；内部记录（due_at、逐步结果、状态机、
重试与校验细节）一律不画。

先看 inspect_time 的最小用法（新增）：

```text
{"tool":"inspect_time","arguments":{}}
→ {"now":"2026-10-08 09:30","clock":"real"}
模型拿这个 now 自己加 2 分钟，得到 at="2026-10-08 09:32"，再走下面的 schedule 例子。
```

### 6.1 memory：读 → 写 → 再读

记忆文件初始内容（按 03 号推荐模板，schedules 段已去掉）：

```text
version: 1
profile:
  - 用户是上班族，晚上 10 点后怕吵
preferences:
  - 空调喜欢 22 度
constraints:
  - 冰箱冷藏不要低于 2 度
```

```text
1) 读
{"op":"read"}
→ {"text":"version: 1\nprofile:\n  - 用户是上班族，晚上 10 点后怕吵\n…"}
   原文逐字返回，服务端不解析 YAML

2) 写（整段替换；读旧文本后加一条偏好再写回）
{"op":"write","text":"version: 1\nprofile:\n  - 用户是上班族，晚上 10 点后怕吵\npreferences:\n  - 空调喜欢 22 度\n  - 晚上 10 点后不要开洗衣机\nconstraints:\n  - 冰箱冷藏不要低于 2 度\n"}
→ {"code":"OK"}

3) 再读，确认落盘内容
{"op":"read"}
→ {"text":"version: 1\n…晚上 10 点后不要开洗衣机…"}
```

参数不合法的例子：

```text
{"op":"read","text":"x"}      → BAD_REQUEST（read 禁止带 text）
{"op":"write"}                → BAD_REQUEST（write 缺 text）
{"op":"write","text":""}      → BAD_REQUEST（空文本拒绝，M1-A）
{"op":"write","text":"<超过 200 token>"} → BAD_REQUEST，文件保持不变
```

读取截断的例子：

```text
{"op":"read"}
→ {"text":"<前 300 token 的内容>"}   截断在内部做，模型不另收标记（M2）
```

### 6.2 同一段 ACTION_CALL：立即执行 vs 预约执行

```text
现在做（现有的 execute_action）
{"device_id":"cn_911432173_cold","action":"set_temperature","params":{"value":4}}

到点做（time_control.schedule）
{"op":"schedule",
 "at":"2026-10-08 07:00",
 "steps":[{"device_id":"cn_911432173_cold",
           "action":"set_temperature",
           "params":{"value":4}}]}

返回
{"schedule_id":"sch_7f3a2b91","at":"2026-10-08 07:00","status":"pending"}
```

`steps[0]` 与上面立即执行的参数逐字一致，这就是参数层的复用。

### 6.3 多步预约：到点按顺序执行

```text
{"op":"schedule",
 "at":"2026-10-07 22:30",
 "steps":[
   {"device_id":"living_room_ac","action":"set_temperature","params":{"value":26}},
   {"device_id":"kitchen_fan","action":"set_percentage","params":{"value":60}}]}

返回
{"schedule_id":"sch_1c9d0e42","at":"2026-10-07 22:30","status":"pending"}
```

### 6.4 到点后的结果：每一步就是一次 execute_action 的返回

```text
到点执行后再查单：这两张单已经不在 list 里
{"op":"list"}
→ {"now":"2026-10-08 07:00:05","items":[]}
（执行完 / 失败 / 取消的单都一样：从 list 消失，只在库里留档）

该预约单的 results[0] 是内部记录（模型看不到；与 execute_action 的返回同形状）
{"device_id":"cn_911432173_cold","action":"set_temperature","params":{"value":4},
 "state_after":{"target":4},
 "state_diff":{"target":{"from":5,"to":4}},
 "changed":true,"verified":true,
 "steps":[{"target":"number.…","service":"number.set_value","data":{…}}],
 "elapsed_ms":3800}
```

### 6.5 取消

```text
{"op":"cancel","schedule_id":"sch_1c9d0e42"}
→ {"schedule_id":"sch_1c9d0e42","status":"cancelled"}
取消后再查单：list 里已经没有这张单（items 为空）

已取消再取消
→ {"status":"cancelled","message":"Already cancelled"}

已完成再取消
→ BAD_REQUEST（completed 状态的单不能取消）
```

到点执行失败的场景（例如设备掉线）本期不展开，按 §4.4 的边界处理。

### 6.6 时间窗口与非法时间

```text
{"op":"schedule","at":"2026-10-07 22:30", …}
due_at = 2026-10-07T22:30:00+08:00
窗口   = 22:29:30 ~ 22:30:30
```
