# 09：一次性调度与持久化调度——两个通用语义接口

> 2026-10-07 更新：预约部分以 14 号《记忆与时间调度接口详细设计》为准；

2026-10-06 定稿。本文记录时间语义的最终切分：按对象生命周期把时间拆成两个通用接口。07 号文档里的 manage_rule 提案以本文 §4 为准；12/14 号里 time_control 的混合定义按本文 §9 收紧。

## 1 结论

```text
模型面的三个时间档位：

  execute_action   现在做             立即执行一次
  time_control     到点做一次         一次性预约单（写 / 查 / 取消），episode 级生命周期
  manage_rule      长期按规则做       持久化调度（触发器 + 条件 + 动作），有启停删

两个通用接口的分界：对象生命周期。
  执行一次就消费、可取消、episode 结束清理          → time_control
  长期存在、可启用/停用/删除、重启后仍在            → manage_rule

一句话判据（写进工具描述）：
  "今晚 10 点关灯" → time_control；"每晚 10 点关灯" → manage_rule
```

## 2 为什么按生命周期切

```text
判据可观察       一次性对象到点后置 done，再查为空；持久对象重启后仍在
HA 原生对应      timer helper 是一次性倒计时；schedule helper（每周时间块）与
                automation 是持久对象
后端落地不同     一次性：HA 没有“到点执行一次”的原生接口，由 MCP 自建调度器补
                持久：直接写 HA 自动化配置（POST /api/config/automation/config/{id}，
                07 号已实测 200）
验证方式不同     一次性：到点执行一次、只执行一次、可取消、episode 清理
                持久：配置存在、条件成立/不成立、启停生效、删除后无残留
端侧真歧义       "今晚/每晚"、"这次/每次"只差一个字；合并接口会藏住歧义，
                拆开后可以变成独立评测项（见 §6）
```

## 3 接口一：time_control（一次性调度）

```text
职责      在指定时刻执行一次动作序列；列出与取消未执行的预约（预约单的写/查/取消）
输入      op = schedule | list | cancel
          schedule  at（ISO 未来时间，绝对时间）+ steps[{device_id, action, params}]
          list      status?（pending | done | cancelled）
          cancel    schedule_id
输出      schedule → {schedule_id, due_at}；list → 预约数组；
          cancel → 被取消的预约
读取      HA 真实时间（校验 at、归一 due_at）；不订阅事件
写入      runtime sqlite 的 schedules(id, due_at, steps, status, created_at, result)
生命周期  episode 级：到点执行一次后置 done；cancel 置 cancelled；
          episode 结束全部清理；HA 后端由 MCP 调度器负责重启后恢复
不负责    状态触发规则、周期规则、启用/停用、跨重启持久化（这些归 manage_rule）；
          等待与时间推进（本期不做，相对时间已拍板去掉）
错误      INVALID_TIME / BAD_REQUEST（含 schedule_id 不存在）/
          DEVICE_UNAVAILABLE / SERVICE_ERROR
对应文件  src\home_mcp\backend_ha\tools\time_control.py（当前空实现）
          runtime：schedules 表 + asyncio 调度器（未实现，见 13 号文档 §4）
```

后端映射：

```text
schedule    MCP runtime 调度器到点调 HA 服务；沙盒 → POST /api/schedule/workflow（二期）
list/cancel runtime sqlite 查询与状态修改
等待/快进   本期不做：advance 已拍板去掉（HA 没有阻塞等待接口），快进留给二期沙盒
```

## 4 接口二：manage_rule（持久化调度 / 规则）

```text
职责      创建/修改/删除/查询/启停/手动触发持久规则；规则 = 触发器 + 条件 + 动作
输入      op = create | update | delete | list | enable | disable | trigger
          rule_id（统一 mcp_ 前缀）
          triggers[]      type = time | state | numeric_state | sun
                          time:          at="22:00:00" + weekdays=[...]（周期时刻表）
                          state:         entity_id + to
                          numeric_state: entity_id + above | below
          conditions[]    同上，可选
          actions[]       {device_id, action, params}，复用现有 8 个动作
          script?         分支/等待/循环，二期高级路径
输出      create/update → {rule_id, ha_config_id, enabled}
          list → 只列 mcp_ 前缀规则；trigger → 手动触发结果
读取      device_id → HA 实体映射（registry）；action → 服务调用方案（actions.py）
写入      HA：POST /api/config/automation/config/{id}（已实测 200）；
          沙盒：规则层（二期；未实现前返回 UNSUPPORTED）
生命周期  持久；enable/disable 切换；episode 结束必须批量 delete，防跨 episode 污染
不负责    一次性预约与时钟推进（time_control）；立即执行（execute_action）
错误      UNKNOWN_ENTITY / BAD_TRIGGER / BAD_REQUEST /
          RULE_NOT_FOUND / SERVICE_ERROR
对应文件  新建 src\home_mcp\backend_ha\tools\manage_rule.py
          编译层：rules\compiler.py（device_id + action + params → HA automation JSON）
          复用：registry\actions.py（服务映射）、registry\devices.py（实体解析）
```

编译口径：`type=time` 编成 `platform: time`（周期时刻表；纯周计划可换 HA schedule helper），`state / numeric_state` 编成同名 HA trigger；actions 走现有动作方案，不新增动作词表。

## 5 边界例子（成对）

```text
今晚 10 点关灯        time_control.schedule(at=今天22:00, steps=[turn_off])
每晚 10 点关灯        manage_rule.create(triggers=[{type:time, at:"22:00:00", weekdays:all}])
10 秒后关灯           time_control.schedule(at=now+10s, steps=[turn_off])
有人移动就开灯         manage_rule.create(triggers=[{type:state, entity_id:motion, to:on}])
22:00 且有人在家关灯   manage_rule.create(triggers=[time], conditions=[person=home])
室温高于 30 开风扇 60% manage_rule.create(triggers=[{type:numeric_state, above:30}])
现在关灯              execute_action(action=turn_off)
```

## 6 验证与评测口径

```text
一次性验收
  T1  schedule(now+10s, 关灯) → 到点执行一次；list 显示 done；再次 list 为空
  T2  cancel 未执行预约 → 到点不执行
  T3  不带偏移的 at 按 home 时区解释；过去时间 → INVALID_TIME

持久验收
  T4  create 每晚 22:00 关灯 → HA 配置 200；list 显示 1 条；delete 后回 0
  T5  create 有人移动开灯 → automation.trigger 手动触发，灯亮；disable 后不生效
  T6  episode 清理 → mcp_ 前缀规则数回 0

歧义对评测（论文素材）
  成对指令：今晚/每晚、这次/每次、10 分钟后/每天 10 点
  评分：是否选对接口 + 参数是否算对（一次性给绝对时间；持久给周期规则）
  对照：合并接口 vs 本文拆分接口，看小模型的接口误选率是否下降
```

## 7 与三篇工作的差异声明

```text
SMH-Bench   只有持久规则（TC4），time_cron 与 state_expr 混在同一个 create_automation
SimuHome    只有一次性调度（QT4），没有规则生命周期
HomeFlow    没有规则任务，条件只用于目标验证
本文         同一套通用语义接口下显式两分：time_control（一次性）/
             manage_rule（持久），各自独立接口、独立验证，可做歧义对评测
```
