## 2. Bench 细节

### 2.1 SMH-Bench：TC4 自动化任务调度（最相关）

```text
任务定义   TC4 评估"持久的时间或状态触发规则"（正文 §3.3.1）
           三类玩法：时间特定、状态驱动、时间+状态
实例规模   TC4 150/1,100 例；评测里 TC4 是所有模型最严重的瓶颈之一
工具面     EIA 第三个工具"创建_自动化"：用于计划任务或条件触发的任务，不用于立即执行
参数       conditions.time_cron：Quartz 七字段 cron（秒 分 时 日 月 周 年），无则 null
           conditions.state_expr：如 device('1001').state == "off"，无则 null
           actions：与"控制_设备"同格式（did + locator + arguments）
约束       条件必须同时含 time_cron 与 state_expr（缺的写 null）；
           多个触发时间要拆成多条自动化，不要合并
判分       双重规则验证：触发器验证（cron 时间匹配 / 状态匹配）+ 动作验证（最终状态比较）
```

结论先说：TC4 是**触发式（trigger-based）规则**任务——输入一句话，要求智能体
**存储/创建一条持久规则**（不是立即执行动作），触发条件只能是时间、状态、或两者组合。
主文见 §3.3.1，代表性示例如附录 C，工具定义与 JSON 示例在附录 G。

附录 C 给的三条 TC4 例子（原文摘录，含目标与评判器）：

```text
时间特定
  指令    "今晚10点，锁上父母卧室的门并启用防御模式；将浴室风扇灯设置为最暗的暖光
           和最低风扇速度。"
  目标    存储定时锁、灯和风扇动作
  触发器  time_cron = 0 0 22 27 6 ? 2024
  评判器  设备(8993).防御_启用 == 真 且 状态 == 已锁定；
          设备(9121).灯光状态 == 开启 且 颜色_温度 == 2700 且 亮度 == 1
          且 风扇.状态 == 开启

状态驱动
  指令    "当厨房在十五分钟内没有检测到任何活动时，自动关闭门厅风扇灯，
           并将客厅智能屏幕的音量设置为30。"
  目标    存储风扇灯和智能屏幕的条件-动作规则
  触发器  设备(5267).无_移动_时长 > 900
  评判器  设备(1870).灯光状态 == 关闭 且 风扇.状态 == 关闭；
          设备(7813).音量_级别 == 30

时间+状态
  指令    "每天下午2点，如果厨房温度仍高于35度，则启动客厅吸尘器并将卧室风扇灯风扇
           设为高。"
  目标    仅当两个条件均满足时，才启动吸尘器并将风扇设为高
  触发器  time_cron = 0 0 14 * * ? *；设备(8666).当前_温度 > 35.0
  评判器  设备(2194).风扇.速度_级别 == 高 且 设备(3607).状态 == 清洁中
```

附录 G 的"创建_自动化"工具与 JSON 示例：

```text
工具说明  用于计划任务或条件触发的任务，不适用于立即执行
参数      conditions.time_cron：Quartz 七字段 cron，如 0 0 22 * * ? *
          conditions.state_expr：状态表达式，无则 null
          actions：与"控制_设备"同格式（did + locator + arguments）
```

### 2.1.1 环境模型：温度是状态变量，没有自己的演化机制

```text
结论      SMH-Bench 的 HomeEnv 是离散状态转移模拟器：设备属性（包括"当前_温度"）是
          状态变量；初始状态给定，之后只有服务调用按执行规则更新属性。
          没有时间驱动的物理演化（开着空调不会让房间温度随时间自动下降）

证据 1    §3.2 设备模型：属性描述当前设备状态（电源、亮度、目标温度、湿度、运行模式），
          服务定义可执行操作；操作引擎执行动作 → 更新属性，非法动作拒绝、状态保持不变
证据 2    §3.2 与附录 A：属性 = "具有类型的状态变量"；服务 = "有效的状态转换"，
          验证后更新属性；温度属性的描述只有"测量到的温度"
证据 3    AC 的服务只有 设置_空调_模式 与 设置_目标_温度；没有"运行中 → 当前温度变化"
          这类执行规则，也没有时间步、时钟或效应函数
证据 4    相关工作 §2 明确把"可执行的时间模拟"归给 SimuHome（Seo 等，2026），
          自己强调的是"执行动作 + 校验最终状态 + 无关状态保持"

对任务的影响
  TC4 触发器里的"厨房温度 > 35"就是初始/当前状态变量的值；
  判分比较设备最终状态（如风扇速度=高、吸尘器=清洁中），不比较温度轨迹；
  "开空调降温"这类任务落到"把空调模式/目标温度设成什么"，而不是"等房间降到几度"
```

```text
TC4 的验证到底查什么（不是文字对齐，但也没有时间演化）
  输入        自然语言指令（只有这一句是文字）
  被评判物    智能体输出的结构化自动化：触发器 + 条件 + 动作
              （DR 输出 automations JSON；EIA 调"创建_自动化"工具）
  触发器验证  时间触发器：Cron 表达式与真值触发时间匹配；
              状态触发器：在与真值完全相同的设备状态下触发
              （设备 ID + 属性 + 阈值，如 device(8666).当前_温度 > 35.0）
  动作验证    在 HomeEnv 里应用动作后，比较最终状态（设备/属性/值）
  不做的事情  不把时钟推进到"下午2点"再读一次温度，也不模拟温度随时间的演化；
              状态触发用的就是场景给定的那个离散状态值
  结论        它对齐的是"环境状态空间里的结构化字段"，不是自然语言句子；
              时间/状态触发器都只校验"规则配置成不成立"，不校验"未来跑起来会怎样"
```

### 2.2 SimuHome：调度任务，不是持久规则

```text
QT4-1 未来调度    计算"从现在起十分钟后"的绝对时间，把动作调度到该时刻
QT4-2 依赖调度    给耗时设备（洗碗机）和即时设备（灯）创建协调调度，考虑完成时间依赖
QT4-3 并发调度    按时间约束调度两个或更多运行设备而不冲突
动作形式          "调度工作流(时间: ...)"，属于一次性工作流排程
与规则的区别      没有"持久保存的触发-条件-动作"，不涉及规则生命周期（启用/停用/删除）
```

## 3. 方法论文细节

### 3.1 HomeGenii（IMWUT 2026）：增强型 TAP 规则生成

```text
问题       平台演进后支持"增强型 TAP 规则"：在触发器与动作之间插入脚本，
           包含条件逻辑、计算与外部 API 调用；普通用户写不出来
方法       检索增强生成（RAG）：构建规则库 → 先聚类后搜索 → 压缩提示
结果       规则生成准确率 14%（无 RAG）→ 约 84%（有 RAG）；
           语义聚类相对未聚类基线再提高约 27%
数据       20 个场景 × 4 种提示变体 = 80 个提示；真值由两位博士研究员独立编写；
           输出格式是 IFTTT 过滤器代码，在沙箱运行时里执行验证
平台       明确点名 IFTTT、SmartThings 与 Home Assistant 都是 TAP 平台
```

### 3.2 ESWA 2024：TAP 规则的用户意图预测

```text
问题       用户从大量触发器/动作里组合规则时，意图难判断；手动创建繁琐
任务       把"用户意图预测"形式化为多标签分类：节点是 TAP 规则，标签是用户意图
数据       真实 IFTTT 数据集
例子       图 2："如果日出则关闭加热器"；引言例子："如果有人离开，则关闭空调"
分类       已有规则创建研究分三视角：规则语义解析、规则合成、TAP 规则推荐
```

### 3.3 CHI 2025：TAP 规则 vs 直接控制的分类与生成

```text
任务       把物联网指令分成三类：触发-动作规则、直接控制命令、设备查询
定义       TAP 规则是事件驱动的自动化（例子："当有人在客厅时打开灯"）；
           直接控制命令是即时的设备操作（例子："让卧室准备好睡觉"）
处理       对 TAP 规则，LLM 先分类、再生成规则；生成结果需要用户验证或选择
平台       背景提到 SmartThings 等平台的触发-动作规则在条件满足时被安装并执行
```

### 3.4 Sasha（CCS 2024）：自动化例程创建

```text
问题       未充分指定的指令：即时目标（"让这里变得舒适"）与持续性目标
           （"有阳光时使用自然光"）；后者需要自动化例程
方法       把指令拆成目标/动作/触发器三个槽位；触发器明确程度作为连续谱系；
           实现并在用户研究里评估
与 HA 关系  概念对应 trigger-condition-action，但不是直接面向 HA 平台的实现
```

## 4. 与 HA 自动化接口的对应

```text
TAP 规则            ≈ HA automation：trigger + condition + action
增强型 TAP 规则      ≈ HA 的 script / 模板条件 / 服务调用的组合
SMH-Bench 的 cron   是它内部的任务表示（Quartz 七字段）；HA 侧对应时间触发器
HA 的对外接口       POST/GET/DELETE /api/config/automation/config/{id}（管理员令牌）；
                   automation.trigger / turn_on / turn_off / toggle / reload
现状                我们自己的 MCP 8 工具里没有规则工具；若要把规则纳入语义面，
                   需要作为一个新的契约决策（新增工具或扩动作词表）
```
