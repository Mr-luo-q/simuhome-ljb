# 03 记忆模块：长度、格式与检索分析

2026-10-07 更新：格式从"固定分区 YAML"降级为推荐模板，schedules 段废弃（预约单独立，
见 14 号文档）；长度口径继续沿用。

分析日期 2026-10-04。范围：memory 里"存多大、存什么格式、怎么被找到"。
只做分析，不落实现细节。

## 0. 三个问题的直接回答

```text
长度    记忆读写都按 200 token 量级（≈300 中文字，Qwen 词表）：
        读取 软 200 / 硬 300；写入 硬 200（写比读更严）；0.6B 档建议 ≤150。
依据    多轮交互"最后一次读到的总输入"按 ≈3,000 token 设计，记忆约占 7%；
        约束来自总交互长度与模型能力，不来自训练序列长度（训练在远端）。
输出    中间步骤只输出工具调用（JSON ≤100 token）；单步生成 256 token
        只是端侧延迟的工程上限，与训练长度无关。

格式    固定分区的 YAML：version / profile / preferences / constraints / schedules。
        条目化、浅嵌套、每条约一行；字段名用英文，内容可中文。
        不登记实时状态、设备能力、易变计划（那些从工具现读）。
编码    UTF-8 文件、读时不解析（YAML 当纯文本原样返回）；传输 JSON 必须
        ensure_ascii=False（实测中文不转义省约 3~5 倍 token，见 §2.4）。

查找    本期不做检索接口：整段读 + 共用词表（device_id / room_id / 时间词）让模型自己对齐。
        条目带 scope / applies_to / when 作为"链接锚点"，也是将来分区读、
        标签过滤的挂钩。语义检索（向量）不在当前范围。
```

## 1. 长度：从上下文预算倒推

### 1.1 已知事实（2026-10-04 更新：目标模型 ≤2B）

```text
目标模型    最终不超过 2B：主选 Qwen3-1.7B（非思考模式，端侧 GGUF 量化），
            备选 0.6B / Qwen2.5-1.5B / 2B；SMH-Bench 的 4B 数据只能当上界参考
能力先验    Qwen3-1.7B BFCL v4 实测：Overall 55.49%、Parallel 44.44%、
            Multi-turn 只有 8.38% —— 多轮工具调用是最大短板
训练口径    GRPO 用过 max_completion_length=384；训练在远端、序列可以更长，
            这个数不作为推理侧的记忆/输出上限依据（2026-10-05 修正）
本地实测    Qwen3-1.7B 分词器（vocab 151,643，2026-10-05 拉取实测）：
            中文 0.75 token/字（300 字 → 225 token）、英文 0.32 token/字、
            含设备 id 的中英混合 0.45 token/字
            8 个工具 tools/list：3,458 字符 → 1,174 token（Qwen）/
            1,738 token（MiniMind 词表）
            memory.example.yaml：189 字 → 127 token；带完整返回外壳 169 token
            MiniMind-3（本地小词表 6,400）：中文 0.94 token/字
            InternLM2-1.8B：max_position 32768、词表 92544（缺 sentencepiece，待补测）
我们的实测  observe_home 约 216 token、inspect_room 约 87 token、
            inspect_device 约 234 token（14 号文档 2026-09-23 数据）
未知项      系统提示词长度
```

记忆不是唯一吃上下文的东西。一次 episode 的预算里还有：工具 schema、
系统提示、observe/inspect 的返回、模型输出与多步历史。
按 ≤2B 的实测开销，记忆应控制在单步输入预算的 15%~25%
（1.7B 约 400~800 token），再长就要靠分节读或裁剪。

### 1.2 建议的档位

| 模型档 | 目标值 | 读取 | 写入 | 中文字符（Qwen ≈0.75/字） | 中文字符（小词表 ≈0.94/字） |
| --- | --- | --- | --- | --- | --- |
| 0.6B | 150 | 软 150 / 硬 200 | 硬 150 | 200 / 267 | 160 / 210 |
| 1.5B ~ 1.7B | 200 | 软 200 / 硬 300 | 硬 200 | 267 / 400 | 210 / 320 |
| 2B | 200~250 | 软 200 / 硬 300 | 硬 200 | 267~333 / 400 | 210~260 / 320 |

```text
读写不对称    读取允许到硬上限 300（报错线），写入超过 200 直接拒绝——
              写进来的东西会长期占预算，所以卡得更死
换算口径      中文按词表大小分两档：Qwen 级词表（151,643）实测 0.75 token/字；
              小词表（MiniMind 6400）实测 0.94 token/字；英文约 0.25 token/字符
超限处理      软上限提醒（写日志）；硬上限直接报错，不静默截断
```

### 1.3 约束来自哪里（2026-10-05 修正）

```text
不来自训练       训练在远端、序列长度可调；max_completion_length=384 只是历史实验参数，
                不用它反推推理侧的记忆与输出上限
来自总交互长度   多轮交互最后一次读到的总输入按 ≈3,000 token 设计：
                工具 schema（Qwen 实测 1,174；小词表 1,738）+ 记忆 200 + 观察 ~230/次
                + 历史 ~300~600/步，记忆只占约 7%
来自模型能力     Qwen3-1.7B 的 BFCL Multi-turn 只有 8.38%：多轮与长输入是主要风险，
                所以记忆要小、步骤要少；0.6B 档再降一档
来自判分         记忆类任务要求"每条记忆都可能被用到"，长了会稀释注意力
```

### 1.4 输入与输出（按交互长度，不按训练长度）

```text
总输入目标       多轮累计、最后一次读到的总输入 ≈3,000 token（1.7B）
                 构成（Qwen3-1.7B 分词器实测）：工具 schema 1,174
                 + 记忆 200 + 观察 ~230/步 + 历史 ~300~600/步
                 小词表（MiniMind 实测 1,738）时，留给记忆+观察+历史的约 1,200
记忆配额         200 token ≈ 总预算的 7%；读 300 / 写 200 的界见 §1.2
输出             中间步骤只输出工具调用：JSON ≤100 token；
                 单步生成 256 token 是延迟上限，不做"复述记忆/解释"
为什么            Multi-turn 8.38% + 级联错误：每步短、步数少，成功率最高；
                 记忆保持 200 token，就不需要为它单独做检索或分节
```

## 2. 格式：登记什么、用什么结构

### 2.1 先定"什么该进记忆"

```text
该登记（稳定、跨回合）      用户偏好（睡觉空调 26 度）、硬约束（不要动客厅主灯）、
                            长期事实（作息时间、谁住哪）、地址/昵称等映射
不该登记（易变、能现读）    实时状态（现在几度、灯开着没）→ observe/inspect
                            设备能力与参数范围 → inspect_device
                            当日临时安排、一次性计划 → 属于任务，不属于记忆
判据                        一条信息如果一小时后可能已经不对，就不该进记忆
```

### 2.2 候选格式对比

| 格式 | 可读性 | 机器可解析 | 适合写入 | 主要问题 |
| --- | --- | --- | --- | --- |
| 自由文本 / Markdown | 高 | 差 | 一般 | 结构不稳定，模型要靠语感找条目 |
| 键值行 `key: value` | 高 | 好 | 好 | 没有层次；偏好/约束/日程混在一起 |
| 分区 YAML | 高 | 好 | 好 | 需要注意缩进；深度一多就难维护 |
| JSON | 中 | 最好 | 一般 | 不能写注释、手改容易出错 |
| SQLite / 数据库 | 低 | 最好 | 好 | 对只读文件方案是过度设计 |

推荐：分区 YAML。人和模型都好读，写入时也能做结构校验；
数据库留到"记忆量真的很大、需要检索"的二期。

### 2.3 推荐的登记结构（示意，不展开字段细节）

```yaml
version: 1
用户:            # 长期事实：作息、住址、家庭成员等
  睡觉时间: "23:00"
偏好:            # 偏好条目：每条一行文本 + 可选锚点
  - 内容: 睡觉时空调 26 度、风扇低档
    适用于: [living_room_ac]
    时间: "23:00 之后"
约束:            # 硬约束：不要做什么
  - 内容: 不要动客厅主灯
    适用于: [living_room_side_light]
日程: []         # 可选：与时间相关的习惯
```

```text
分节固定且少    5 个以内；模型先看分节名就知道去哪找
条目化          每条尽量一句话（≤100 字符），不写大段散文
锚点字段        适用于 用设备的逻辑 id（和工具面一致）、时间 用时间词
版本号          version: 1，为将来写入和格式迁移留位置
语言约定        分节名与正文用中文；只剩设备 id（living_room_ac）和 version 用英文；
                实测键名成本两边接近（preferences=1、applies_to=3、
                偏好=1、睡觉时间=2），选中文是为了和用户语言一致、少一层翻译
```

### 2.4 编解码：文件怎么存、怎么传到模型

```text
文件编码    UTF-8（无 BOM）；解码失败直接报错，不静默替换字符
行尾        统一按 \n 读入与写出（文本模式自动把 CRLF 归一）
读侧        不解码成结构：YAML 当纯文本原样返回，没有解析错误，保留注释与顺序
传输        走既有 JSON 返回外壳；必须 ensure_ascii=False（server.py 现在就是）
不采用      base64 / 压缩：200 token 量级不值得，base64 还要膨胀约 33% 且不可读
```

实测（2026-10-05，两种分词器对照）：

| 形态 | 字符 | MiniMind 词表 6,400 | Qwen3 词表 151,643 |
| --- | --- | --- | --- |
| memory.example.yaml 原文（189 字） | 189 | 141 | 127 |
| 完整返回外壳，ensure_ascii=False | 301 | 218 | 169 |
| 完整返回外壳，ensure_ascii=True | 781 | 657 | 547 |
| 300 中文字样例，原文 | 300 | 281 | 225 |
| 300 中文字样例，最小 JSON 包装，False | — | 288 | 未测 |
| 300 中文字样例，最小 JSON 包装，True | — | 1,372 | 未测 |

```text
结论 1  ensure_ascii=True 把中文变成 \uXXXX：189 字样例在 Qwen 分词器下
        127→547 token（4.3 倍）、MiniMind 下 141→657（4.7 倍）。这一条必须守住。
结论 2  完整返回外壳本身约 42 token（Qwen）/ 77 token（MiniMind），预算里要预留。
结论 3  读整段 = 读纯文本；不引入任何额外编解码。
结论 4  YAML 只是"给人写的约定格式"，读侧不解析它；
        将来写入时如需校验，用 yaml.safe_load 只做检查，写回仍按纯文本。
```

### 2.5 语言：存中文还是英文、小模型的词表能覆盖什么

```text
词表不按语言分区    一个 BPE 词表覆盖多语言；"支持几种语言"是训练数据属性，
                    不存在"每种语言一张子词表"的说法
官方口径（2026-10-05 查证）
  Qwen3 模型卡      0.6B 与 1.7B 的卡片写的是同一句 "Support of 100+ languages and dialects"
  Qwen3 官方博客    "Qwen3 models are supporting 119 languages and dialects"；
                    预训练 36T token，覆盖 119 种语言与方言
  Qwen2.5 官方博客  支持 29+ 语言：中、英、法、西、葡、德、意、俄、日、韩、越、泰、阿拉伯等
  InternLM2-1.8B    本地 config 只有 vocab 92,544，没有语言列表（语言信息不在 config 里）
  MiniMind-3        本地 vocab 6,400，中文接近逐字（0.94 token/字），能力另算
```

```text
分词器实测（Qwen3-1.7B，同义句，token/字符）
  zh 0.74 / en 0.23 / ja 0.72 / ko 0.82 / ru 0.43 / ar 0.47 / es 0.34 / fr 0.31
  → 八种文字都能正常切分，不是逐字节兜底；但"能切分"不等于"1.7B 都答得好"
官方说的是家族级     100+/119 种语言是全系列口径；对 0.6B~1.7B，
                     真正稳的是中英，其余语言能读但效果没有保证
本地配置读不出语言   config.json 只有 vocab_size、层数这些，没有"支持哪几种语言"字段；
                     只能靠官方文档或拿分词器逐语种实测

能不能中英混合   1.5B~2B：可以，日常混合（中文正文 + 英文设备 id）没问题；
                 0.6B：也能读，但混合越少越稳，只保留必须的英文（设备 id）
存中文还是英文   内容存中文——和用户语言、指令语言一致，避免翻译损失；
                 设备 id 必须保留工具面的英文形式（living_room_ac），
                 因为要和 inspect_device 的输出直接对上
如果换模型       换成中文弱的小模型（Gemma/Llama 这类）才需要把记忆改英文；
                 我们的目标家族（Qwen/InternLM）都是中文强项，不需要
```

## 3. 查找：整段读之后，模型怎么"链接"到正确的记忆

### 3.1 本期：整段读 + 共用词表

```text
模型拿到 memory() 返回的整段文本，自己判断哪条与当前任务相关。
能成立的前提是"链接锚点"对齐：
  1 记忆条目的 applies_to 用工具面同款 id（living_room_ac），不用"客厅空调"这类别名
  2 时间类偏好写明确触发词（"23:00 之后"、"睡前"）
  3 分节名稳定（preferences / constraints 不要改名）
代价：记忆越长，模型定位越难；这正是硬上限存在的理由。
```

### 3.2 将来可升级的检索层级

```text
L0 整段读（本期）            零参数、零检索决策，靠模型自己对齐；适用 ≤300 token（读硬上限）
L1 按分节读（memory(section)） 省 token；需要分节名稳定，模型要学会选分节
L2 标签/锚点过滤（memory(scope=device|room)） 精确取用；需要结构化条目与参数约定
L3 语义检索（向量/关键词）    记忆规模大时才值得；引入嵌入模型与索引，端侧成本高
升级触发条件：常态记忆超过硬上限，或条目数超过 30 条，或任务类型明显分化
```

### 3.3 一个容易踩的点

```text
记忆里写设备时，用逻辑 id 还是用中文名？
  用 id（living_room_ac）：模型能直接和工具输出对上；缺点是实验方要查 id
  用中文名（客厅空调）：人写起来顺；小模型要自己做一层映射，容易失败
建议：条目正文可用中文，但锚点字段（applies_to）坚持用逻辑 id；
      实验方写记忆时对着 data\device_aliases.yaml 查一遍即可。
```

## 4. 与读写实现的关系（只列约束）

```text
写入 = 整段替换    不做追加、不做增量 patch；写进去的就是下次读出来的全部
写上限与读一致    同一套长度校验，超限拒绝写入
写入时校验        版本号、分节名、单条长度；解析失败拒绝写入（不覆盖好文件）
并发与原子性      留到实现期（临时文件 + 原子替换是候选做法）
范围              只在 v2 做；v1 冻结不动
```
