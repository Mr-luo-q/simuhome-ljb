## 0. 先纠正一个说法：契约里是 8 个工具，真正做实的目前是 6 个

```text
契约（contract\tools.py，唯一语义来源）      8 个工具
已实现并在真机跑通                            6 个：observe_home / inspect_room / inspect_device /
                                            execute_action / check_goal / query_events
仍是空实现（调用返回 NOT_IMPLEMENTED）         2 个：time_control / memory
```

第 7 节写了这两个未实现工具的规划形态；在它们落地之前，做 demo 不要依赖。
验证方式见第 5 节（契约 12/12、真机端到端 21/21、模型冒烟 9/9、降级与恢复 21/21）。

环境规模（真机实测）：3 个房间、25 个 simuhome 实体、12 台可控设备
（9 个 switch + 2 个 climate + 1 个 fan），另有 13 个只读传感器实体。

## 1. 八个工具速查

| 工具 | 状态 | 一句话语义 | 在 RL 回路里的角色 |
| --- | --- | --- | --- |
| `observe_home` | 已实现 | 全屋快照：房间、每房间环境量、当前时间 | 全局 observation（step 起点） |
| `inspect_room` | 已实现 | 一个房间的设备清单与环境量 | 局部 observation / 缩小候选设备 |
| `inspect_device` | 已实现 | 一台设备的六个状态字段 + 可用动作与参数范围 | 动作掩码（action mask）的来源 |
| `execute_action` | 已实现 | 执行一个规范动作并回读状态 | action（唯一的写接口） |
| `check_goal` | 已实现 | 判定"目标达成 + 无关状态保持" | reward / 终止条件 |
| `query_events` | 已实现 | 查时间窗内的事件序列 | 轨迹回放、调试、日志核对 |
| `time_control` | 未实现 | 计划：推进/等待时间 + 预约 | 长时序任务的"等待"语义 |
| `memory` | 未实现 | 计划：只读返回整段长期记忆 | 跨回合的偏好注入 |

统一返回外壳（所有工具一致）：

```json
{"ok": true, "data": { }, "error": null, "meta": {"elapsed_ms": 42, "clock": "none|virtual|real"}}
```

失败时 `ok=false`，`error` 是 `{code, message, hint}`（见 2.3）。

## 2. 统一语义的三件套（RL 的动作空间、状态空间、判定都在这里）

### 2.1 动作词表（8 个动作，按设备类别取子集）

这是 `execute_action` 的合法取值，也是动作空间的边界：

```text
switch（9 台）     turn_on / turn_off / toggle
climate（2 台）    turn_on / turn_off / toggle / set_mode(mode=off|cool|heat)
                  set_temperature(value: 7~32，步长 0.5)
fan（1 台）        turn_on / turn_off / toggle / set_percentage(value: 0~100，步长 1)
sensor（13 个）    只读，没有动作

词表预留（当前无对应实体）  set_brightness(value 0~100) / set_position(value 0~100)
```

要点：参数范围不是写死的，优先取设备自报值（空调实体属性里有 min_temp / max_temp /
target_temp_step）；越界在本地拦截，不发给后端。

### 2.2 状态字段（6 个，按类别取子集）

```text
on        bool     是否有电/在运行             switch / climate / fan
mode      string   运行模式 off|cool|heat      climate
target    number   目标温度（摄氏度）           climate
level     number   档位百分比                   fan（将来 light 亮度同字段）
position  number   位置百分比（预留）            cover
current   number   设备自测温度（摄氏度）        climate

掉线（unavailable / unknown）或读不到状态时，字段值为 null —— 不是 false
```

### 2.3 错误码（12 个）与 RL 里的处理建议

```text
HA_UNREACHABLE     连不上 HA或被超时        → 环境故障：本步作废，重试或终止 episode
UNKNOWN_DEVICE     device_id 不存在         → 策略错误：动作无效，应给负奖励
UNKNOWN_ROOM       room_id 不存在           → 策略错误
DEVICE_UNAVAILABLE 实体掉线（发布器/broker） → 环境故障：命令没下发，不能算策略失败
UNSUPPORTED_ACTION 该设备不支持这个动作      → 策略错误：动作掩码没做好
SERVICE_ERROR      HA 拒绝了服务调用        → 多数是环境/参数问题，少数是设备约束
BAD_REQUEST        参数不合 schema/越界      → 策略错误：本地已拦，不会污染世界
BAD_TARGET         check_goal 的目标写错    → 任务定义问题
UNKNOWN_KEY        记忆键不存在（未实现）    → 暂不涉及
INVALID_TIME       预约时间在过去（未实现）  → 暂不涉及
VERIFY_TIMEOUT     回读未按时变化（未实现）  → 暂不涉及
NOT_IMPLEMENTED    工具未实现               → 目前只在 time_control / memory 出现
```

三类分开很重要：**策略错**给负奖励，**环境故障**重试或丢弃这一步，**任务定义错**要修数据。

## 3. 逐个接口

### 3.1 `observe_home` —— 全屋快照

```text
语义       "家里现在什么情况"：有哪些房间、每间环境量、当前（虚拟）时间、有多少设备/实体
输入       无
输出       rooms{<room_id>: {name, env{temperature, humidity, illuminance, pm10}, devices[device_id]}}
           + time + counts{rooms, devices, entities, metrics}
错误       HA_UNREACHABLE
实测       864 字节（≈216 token），44 ms
RL 用法    episode 开始时的全局 observation；也可以作为"是否需要进一步观察"的依据
```

### 3.2 `inspect_room` —— 单房间

```text
语义       "这个房间里有什么"：环境量 + 设备清单 + 门状态
输入       room_id（三个合法值：living_room / kitchen / utility_room）
输出       room{room_id, name, env{}, devices[device_id], doors:null}
错误       HA_UNREACHABLE / UNKNOWN_ROOM（hint 里给可选房间）
实测       351 字节（≈87 token），30 ms
RL 用法    把候选设备从 12 台缩到 3~5 台；T1 空间类任务的中间观察
注意       doors 恒为 null（本期没有门磁实体），不要把它当可用信号
```

### 3.3 `inspect_device` —— 单设备

```text
语义       "这台设备现在什么状态、我能对它做什么、参数范围是多少"
输入       device_id（如 living_room_ac、kitchen_fan、living_room_side_light）
输出       device{device_id, entity_id, area_id, kind, state{六字段}, actions[{action, params, description}]}
           actions 里的 params 带 type / minimum / maximum / step / enum
错误       HA_UNREACHABLE / UNKNOWN_DEVICE
实测       973 字节（≈234 token），31 ms；空调返回 5 个动作，开关 3 个，风扇 4 个
RL 用法    **动作掩码的唯一来源**：哪些动作合法、参数上下界是多少，都从这里取
注意       掉线时 state 六字段为 null，但 actions 仍然照常返回（能力不随可用性变化）
```

### 3.4 `execute_action` —— 唯一的写接口

```text
语义       "对某台设备执行一个规范动作"，执行后回读状态
输入       device_id, action（2.1 的 8 个之一）, params（按动作给，如 {"value": 25}）
输出       result{device_id, action, params, state_after{六字段}, steps[], elapsed_ms, verified, verify_note?}
           steps 记录真实发生的服务调用，例如 switch.turn_on；空调写设定点会先补一条开机
错误       UNKNOWN_DEVICE / DEVICE_UNAVAILABLE / UNSUPPORTED_ACTION / BAD_REQUEST / SERVICE_ERROR
实测       调用 544~572 ms（含 500 ms × 3 的回读），state_after 已在调用内落定
RL 用法    action 的唯一执行入口；reward 里要不要算成功，看 verified
四道闸门   设备存在 → 实体可用 → 动作支持 → 参数范围（顺序固定，全部在本地先判）
注意       verified=false 表示"HA 收下了命令但状态没在 1.5 s 内变"，
          这不算调用失败——长效应设备可能更慢，但也可能是后端半坏（见第 6 节）
```

### 3.5 `check_goal` —— 目标判定

```text
语义       判定两组条件：conditions（目标）+ keep（必须保持不变的无关状态）
输入       conditions: [{target, op, value}]，keep 同构、可选
           target 命名空间：<room>.<metric>（如 kitchen.temperature）
                           或 <device_id>.<六字段之一>（如 living_room_ac.target）
           op：lt / lte / gt / gte / eq / ne
输出       goals[{target, op, value, actual, pass}] + keep[...] + all_pass
错误       BAD_TARGET（目标写错）/ BAD_REQUEST
实测       目标不成立 + 保持条件成立的两组判定都返回各自 pass
RL 用法    reward 的主要来源与 episode 的终止条件；
          keep 对齐两篇基准的"无关状态保持"口径，别只判目标
```

### 3.6 `query_events` —— 事件查询

```text
语义       查一段时间窗内发生过什么（logbook）
输入       since（ISO，默认最近 10 分钟）、until、entity_id、limit
输出       events[{ts, entity_id, state, name}] + counts{matched, returned, excluded_entities, scoped_to_home}
错误       HA_UNREACHABLE / BAD_REQUEST
实测       近 8 小时约 300 条非虚拟时间记录；默认排除 sensor.simuhome_virtual_time
RL 用法    轨迹回放、调试"世界为什么变成这样"、给 reward 做因果核对
注意       两层默认过滤：只看本家庭实体 + 排除虚拟时间；显式给 entity_id 时两层都关
```

### 3.7 `time_control` —— 时间与预约（未实现）

```text
现状       空实现，调用返回 NOT_IMPLEMENTED
规划语义   op = advance（真等若干秒）/ schedule（绝对时间预约一串动作）/ list / cancel
规划错误   INVALID_TIME（预约时间在过去）
RL 用法    长时序任务里的"等待"；HA 侧时钟 1:1 不能快进，快进留给二期沙盒后端
```

### 3.8 `memory` —— 长期记忆（未实现，已定简化形态）

```text
现状       空实现，调用返回 NOT_IMPLEMENTED
规划语义   只读整段：memory() 返回 data\memory.yaml 的全部内容（无参数、不给 key、不做写入）
理由       对齐 SMH-Bench 的"记忆由题面给、模型只用不写"，也把参数降到零
RL 用法    跨 episode 的用户偏好注入；写入能力留到二期
```

## 4. 用这八个工具搭 RL demo 的建议

### 4.1 一次 step 的推荐回路

```text
observe_home            → 全局状态（房间 + 环境量 + 时间）
inspect_room / device   → 需要时缩小候选设备、拿动作掩码
execute_action          → 唯一动作；读 state_after 与 verified
check_goal              → 目标 + 保持条件 → reward / done
query_events            → 复盘与调试（不参与决策也可以）
```

### 4.2 状态、动作、奖励怎么落

```text
状态（observation）
  房间级：observe_home 的 env（4 个环境量）
  设备级：inspect_device 的六字段（on / mode / target / level / position / current）
  时间：observe_home 的 time（虚拟时间，与真实时间 1:1）

动作（action）
  离散部分：device_id（12 台）× action（该设备合法的 3~5 个）→ 用 inspect_device 的 actions 做掩码
  连续部分：set_temperature（7~32，步长 0.5）、set_percentage（0~100，步长 1）
  非法动作的处理：本地会返回 UNSUPPORTED_ACTION / BAD_REQUEST，可当作负奖励或直接掩掉

奖励（reward）
  目标：check_goal(conditions) 的 pass
  保持：check_goal(keep) 的 pass（对齐基准的"无关状态保持"）
  执行质量：execute_action 的 verified（写入了但没落定，别当成成功）
  成本：elapsed_ms（可选，用于"等待代价"单独统计）

终止
  all_pass 为真，或达到步数上限；两类失败分开记：策略错（负奖励）与
  环境故障（DEVICE_UNAVAILABLE / HA_UNREACHABLE）不要算进策略的账
```

### 4.3 两条工程建议

```text
① 每一步都留证据：动作 + state_after + verified + check_goal 结果写进轨迹文件，
   便于事后核对"模型说成功"与"世界确实变了"是否一致
② 实验隔离：一个 episode 前先快照状态，结束后还原（用 execute_action 写回），
   否则下一轮的起点被上一轮污染
```

## 6. 已知边界与坑（做 demo 前先看这一节）

```text
掉线会拦命令     发布器/broker 掉线时实体变 unavailable，execute_action 直接返回
                DEVICE_UNAVAILABLE，命令不下发；此时六字段为 null，不是 false
回读不保证落定   verified=false 表示命令发出去了但 1.5 s 内没看到状态变化；
                实测 B/C 两条外部路线干脆不回读，我们回读了但要正确解读
参数越界本地拦   把 40°C 发给 HA 会返回 500 且不写状态，所以范围校验必须在本地
时间不能快进     HA 侧虚拟时钟 1:1；空调 1.8 °C/h、风扇 0.72 °C/h，
                分钟级以上的物理过程在真机上做不了，留给二期沙盒后端
冷启动缺 home    SimuHome 重启后若没载入 home_full.json，设备接口全 404；
                一键拉起脚本已内置这一步，手工起服务时别漏
命名约定         device_id 是逻辑 id（living_room_ac）；实体名由改名脚本强制，
                跑过 reset_discovery 后要重跑 rename_entities.py --dry-run 检查
```

## 7. 两个未实现工具的规划形态（别当成已有能力）

```text
time_control   四个 op：advance(seconds) 真等；schedule(at, steps) 绝对时间预约；
               list / cancel 管理预约。runtime 要补 sqlite 的 schedules 表与调度器。
               验收：advance(5) 返回快照；schedule 10 秒后关灯到点执行成功。
memory         简化成只读：memory() 无参数，返回 data\memory.yaml 的整段内容；
               不做 key-value、不做写入、不落库。验收：返回内容与文件一致。
               （这两条的完整口径见 11 号文档 §7.4 与 13 号文档第 3、4 节）
```
