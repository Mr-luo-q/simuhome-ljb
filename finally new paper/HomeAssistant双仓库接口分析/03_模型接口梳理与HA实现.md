# 模型接口梳理与 HA 实现

三件事：一、模拟器现在暴露给模型的接口；二、这些接口怎么用 HA 官方接口实现；三、官方 MCP Server 现在暴露什么。

## 1. 模拟器现在暴露给模型的工具

事实来源不是猜的，是 `simuprocject\Simuhome_experiment\src\agents\tools.py` 里的 `TOOL_REGISTRY`，模型能调用的就是它列出的这些。

```text
共 20 个，不是 10 个：

仿真运维 3   add_device、remove_device、set_tick_interval
观察读取 7   get_home_state、get_rooms、get_room_devices、get_room_states、
             get_all_attributes、get_attribute、get_device_structure
执行动作 2   execute_command、write_attribute
时间调度 5   get_current_time、schedule_workflow、get_workflow_status、
             cancel_workflow、get_workflow_list
领域知识 2   get_cluster_doc、get_environment_control_rules
收尾     1   finish
```

三点值得注意：

```text
一  没有任何“推进时间”的工具。模型只能读时间（get_current_time）、
    预约未来动作（schedule_workflow），推不动世界
二  混进了三类非任务工具：仿真运维（加/删设备、改 tick 间隔）、知识检索、finish
三  定位方式全是沙盒自己的：device_id + endpoint/cluster/attribute
```

## 2. 收敛到 10 个左右：怎么合

20 个里真正面向任务的是 14 个（观察 7 + 执行 2 + 时间 5），把同类项合并后落到 10 个：

| 现状 | 合并后 | 理由 |
| --- | --- | --- |
| `get_all_attributes` + `get_attribute` + `get_device_structure` | `inspect_device` | 都是“看一台设备”，一次给出状态 + 能力结构即可 |
| `get_workflow_status` + `cancel_workflow` + `get_workflow_list` | `manage_tasks` | 状态 / 取消 / 列表是同一件事的三个动作 |
| `get_rooms` | `list_rooms` | 保留 |
| `get_room_devices` | `list_room_devices` | 保留，与上一条是两层空间查询 |
| `get_home_state` | `observe_home` | 保留 |
| `get_room_states` | `read_room_state` | 保留 |
| `execute_command` | `execute_command` | 保留，走命令 |
| `write_attribute` | `write_attribute` | 保留，直接改属性，语义不同 |
| `get_current_time` | `get_time` | 保留 |
| `schedule_workflow` | `schedule_task` | 保留 |
| `get_environment_control_rules` | `read_control_rules` | 辅助，可留可去 |

```text
10 个核心
  观察类 4   observe_home、list_rooms、list_room_devices、read_room_state
  设备类 3   inspect_device、execute_command、write_attribute
  时间类 3   get_time、schedule_task、manage_tasks

另计（合并后总数 16）
  辅助 2     read_control_rules、get_cluster_doc
  运维 3     add_device、remove_device、set_tick_interval（不建议进模型工具面）
  内部 1     finish（属于 agent 循环，不是环境接口）
```

## 3. 这 10 个怎么用 HA 官方接口实现

| 沙盒接口 | 语义 | HA 官方对应 | 结论 |
| --- | --- | --- | --- |
| `observe_home` | 全屋快照 | REST `GET /api/states`；WS `get_states`、`subscribe_entities` | 官方已有，需自己过滤目标实体 |
| `list_rooms` | 房间列表 | WS `config/area_registry/list`（可配 `floor_registry`） | 官方已有 |
| `list_room_devices` | 房间内设备 | WS `config/device_registry/list` + `config/entity_registry/list`，按 `area_id` 关联 | 数据官方已有，关联逻辑要自己写 |
| `read_room_state` | 房间温湿照度 PM10 | 没有房间聚合接口，只能按 area 找 sensor 再拼 | 需自建薄封装 |
| `inspect_device` | 设备结构 + 全部属性 | 状态：`GET /api/states/{entity_id}`；能力：WS `get_services_for_target`、`supported_features`、`device_automation/*/capabilities` | 状态官方已有；统一的“设备能力结构”没有 |
| `execute_command` | 执行设备命令 | REST `POST /api/services/{domain}/{service}`；WS `call_service`；MCP 侧 `HassTurnOn`、`HassLightSet`、`HassClimateSetTemperature` 等 | 官方已有，三层都有 |
| `write_attribute` | 直接改属性 | 无通用属性写入口，只能调对应 domain 的服务，或用 `POST /api/states/{entity_id}` 伪造状态 | 官方没有 |
| `get_time` | 当前时间 | 真实时间：`GetDateTime`、WS `render_template` 的 `now()`；虚拟时间：无 | 概念能对上，语义对不上 |
| `schedule_task` | 预约未来动作 | 自动化、脚本、`wait_for_trigger`；没有“预约一串工具调用”的接口 | 需自建 |
| `manage_tasks` | 查询 / 取消预约 | 无对应，自动化 trace 只能事后看 | 需自建 |
| `read_control_rules` | 环境控制规则 | 无对应 | 需自建 |

汇总：官方直接覆盖 3 个（`observe_home`、`list_rooms`、`execute_command`），半覆盖 2 个（`list_room_devices`、`inspect_device`），缺口 5 个（房间聚合、属性写入、时间、预约、预约管理）。

### 3.1 三条结构性差异

```text
寻址方式
  沙盒  execute_command(device_id="living_room_ac", cluster="Thermostat", command="SetCoolingSetpoint")
  HA    HassTurnOn(name="客厅空调")，或 area + domain，靠名字与区域匹配
  差异  精确 id 对 自然语言名；HA 侧实体名可被用户改动、可能重名
可见性
  HA 的工具与状态都受“实体是否暴露给 Assist”约束（homeassistant/expose_entity）
  沙盒侧由自己的 observation profile 决定给模型看什么
  差异  不把两侧的可见集合对齐，就分不清差异来自策略还是来自信息量
时间
  沙盒可以 fast_forward_to 跳到未来，HA 只能真实等待或靠自动化触发
  差异  HA 侧没有“推进”这个概念，这是最硬的一条
```

### 3.2 两条实现路径

```text
路径 A  写自定义集成，把工具注册进 HA，再由官方 MCP Server 暴露
  做法  llm.async_register_api(hass, api) 注册一个 llm.API
        （工具名 + 参数 schema + async_call_tool）
        再到 mcp_server 的配置项里把它勾进 llm_hass_api（多选，可与 assist 并存）
  优点  复用官方 MCP 的传输、鉴权、客户端生态，工具与官方工具同一个入口
  代价  要把 HA 实体模型翻译成沙盒语义，维护 name/area 与 device_id 的映射
路径 B  在 HA 外面自己起 MCP server，内部调 HA 的 REST / WebSocket
  做法  和现在的 bridge 一个套路，用长期令牌调 /api/states、/api/services、WS 命令
  优点  不动 HA，工具语义完全可控
  代价  两个 MCP 入口并存；鉴权、会话、并发都要自己做
```

## 4. 官方 MCP Server 现在暴露什么

### 4.1 端点

| 端点 | 协议 |
| --- | --- |
| `POST /api/mcp` | Streamable HTTP，无状态，单请求单响应，60 秒超时 |
| `GET /mcp_server/sse` | 旧版 SSE，建立长会话 |
| `POST /mcp_server/messages/{session_id}` | SSE 配套消息入口 |

### 4.2 三类能力

```text
tools/list + tools/call   工具集 = 所选 LLM API 的工具（默认 assist）
resources/read            只有一个：homeassistant://assist/context-snapshot
prompts/get               一个 prompt，内容是 api_prompt（含被暴露实体的静态清单）
```

### 4.3 工具清单（默认 assist API）

| 工具 | 语义 |
| --- | --- |
| `HassTurnOn` / `HassTurnOff` | 开关设备（对锁有语义反转） |
| `HassSetPosition` / `HassStopMoving` | 窗帘阀门位置 / 停止 |
| `HassLightSet` | 亮度、颜色、色温 |
| `HassClimateSetTemperature` | 空调温度 |
| `HassFanSetSpeed`、`HassHumidifierSetpoint`、`HassHumidifierMode` | 风扇、加湿器 |
| `HassMediaNext/Previous/Pause/Unpause`、`HassMediaPlayerMute/Unmute`、`HassSetVolume`、`HassSetVolumeRelative`、`HassMediaSearchAndPlay` | 媒体 |
| `HassVacuumStart`、`HassVacuumReturnToBase`、`HassVacuumCleanArea` | 扫地机 |
| `HassLawnMowerStartMowing`、`HassLawnMowerDock` | 割草机 |
| `HassStartTimer`、`HassCancelTimer`、`HassCancelAllTimers`、`HassIncreaseTimer`、`HassDecreaseTimer`、`HassPauseTimer`、`HassUnpauseTimer`、`HassTimerStatus` | 计时器 |
| `HassBroadcast` | 语音卫星广播 |
| `HassListAddItem`、`HassListCompleteItem`、`HassListRemoveItem`、`TodoGetItems` | 待办 |
| `HassShoppingListAddItem`、`HassShoppingListCompleteItem`、`HassShoppingListLastItems` | 购物清单 |
| `GetDateTime`、`CalendarGetEvents`、`script.<entity_id>` | 时间、日历、脚本 |
| `GetLiveContext` | 唯一的通用状态读取工具 |

### 4.4 参数、可见性与被排除项

```text
定位参数   name / area / floor（三选一必填）
           可选 domain、device_class、preferred_area_id、preferred_floor_id
调用上下文 device_id = None，模型不知道“我在哪个房间”
可见性     工具与状态都随“被暴露给 Assist 的实体”动态增删
被排除项   HassGetState、HassGetWeather、HassClimateGetTemperature、HassToggle、
           HassNevermind、HassGetCurrentDate、HassGetCurrentTime、HassRespond、
           HassOpenCover、HassCloseCover（不进工具面）
```

### 4.5 配置与扩展

```text
配置项    llm_hass_api，多选，默认 ["assist"]  → 官方工具与自研工具能同时出现
扩展方式  自定义集成 + llm.async_register_api()，不改 core 源码
本机状态  2026.6.4 容器里该集成存在且已启用：domain=mcp_server，llm_hass_api=["assist"]
```

### 4.6 官方 MCP 的缺口

```text
偏执行     工具里绝大多数是“做动作”，观察类只有 GetLiveContext 一个
无空间     无拓扑、无房间聚合；房间只是 area 注册表里的归属关系
无时间     不能推进时间，没有“等到某时刻”
无断言     没有“目标是否达成”的接口
无记忆     没有长期记忆与画像
定位模糊   name / area / floor，实体名可被用户改动、可能重名
上下文缺失 device_id = None
```

## 5. 一句话对照

```text
沙盒现有 20 个工具 → 合并同类项后 16 个 → 其中核心 10 个（辅助 2、运维 3、内部 1）
其中 HA 官方直接覆盖 3 个，半覆盖 2 个，
剩下 5 个（房间聚合、属性写入、时间、预约、预约管理）官方都没有，
需要在自定义集成里补，再通过 llm_hass_api 勾选挂到官方 MCP 上
官方 MCP 现在的形状可以概括为：能动手，看不清，不能等
```

最终采用哪一套、以及自建 MCP server 的 9 个接口与实现方式，见 `04_自建MCP接口与HA实现.md`。
