# 09 A 方案实施细节（MQTT discovery）

前置结论见 `08_接入方案综合分析与选型.md`。本文只写怎么落地，参数都按本机实测值定。

## 1. 已确认的前提

```text
路线      A：SimuHome → 发布器 → MQTT broker → HA 官方 MQTT 集成（discovery 自动建设备）
broker    二选一：amqtt（已装好，无需管理员）或 Mosquitto 原生版（安装包已下载，需管理员）
不碰旧桥接 old_simuhome_bridge_project 保持原样，不再基于它扩展；发布器是新项目
实测依据  broker 延迟 1.10 ms（p95 1.30 ms）；broker 内存增量 5.7 MB
          当前轮询 11.6 KB/10 秒 ≈ 98 MB/天，其中 99.9% 是重复内容
HA 侧能力  discovery 的 device 块带 sa（suggested_area），HA 会自动建 area：
          device_registry 里 async_get_or_create(suggested_area) → 不存在就创建
```

## 2. 架构与数据流

```text
                     ┌──────────── 发布器（宿主机 Python 进程）────────────┐
SimuHome :8000 ◄────►│ 轮询 /api/home/state（活跃 1s / 空闲 10s）          │
   ▲                 │ 变化驱动发布 + 死区；订阅命令主题并下发             │
   │                 └────────────────┬──────────────────────────────────┘
   │                                  │ MQTT（qos 0，state 与 discovery retained）
   │                                  ▼
   │                       broker :1883（amqtt 或 Mosquitto，绑 0.0.0.0）
   │                                  │
   │                    ┌─────────────┴─────────────┐
   │                    ▼                           ▼
   │            HA 容器 :8123                录制器（订阅 #）
   │            MQTT 集成（host.docker.internal:1883）  JSONL / sqlite
   └────────────────────┘ 命令回程：HA → topic set → 发布器 → SimuHome
```

## 3. 命名与映射

```text
房间 room_id      living_room / kitchen / utility_room  →  area 名（建议英文，见第 12 节待确认）
设备 device_id    living_room_side_light 等，来自 SimuHome
设备唯一标识      identifiers = ["simuhome", "<device_id>"]
实体 object_id    开关：<device_id>；传感器：<room>_<metric>；虚拟时间：virtual_time
```

主题契约（v1 冻结，改主题段等于换一代实体）：

| 主题 | 方向 | payload | retain |
| --- | --- | --- | --- |
| `homeassistant/switch/<device_id>/config` | 发布器 → HA | discovery 配置 | 是 |
| `homeassistant/sensor/<object_id>/config` | 发布器 → HA | discovery 配置 | 是 |
| `simuhome/v1/<device_id>/state` | 发布器 → 所有 | `ON` / `OFF` | 是 |
| `simuhome/v1/<room>/<metric>` | 发布器 → 所有 | 数值（如 `26.0`） | 是 |
| `simuhome/v1/<device_id>/set` | HA → 发布器 | `ON` / `OFF`，后续复杂设备用 JSON | 否 |
| `simuhome/v1/status` | 发布器 → 所有 | `online` / `offline`（LWT） | 是 |
| `simuhome/v1/events` | 发布器 → 所有 | JSON：时间、设备、命令、结果、错误 | 否 |

## 4. Discovery payload 模板

开关（12 个设备用同一模板，只换 id 与名字）：

```json
{
  "name": "客厅副灯",
  "unique_id": "simuhome_living_room_side_light",
  "state_topic": "simuhome/v1/living_room_side_light/state",
  "command_topic": "simuhome/v1/living_room_side_light/set",
  "payload_on": "ON",
  "payload_off": "OFF",
  "availability_topic": "simuhome/v1/status",
  "availability_template": "{{ 'online' if value == 'online' else 'offline' }}",
  "device": {
    "identifiers": ["simuhome", "living_room_side_light"],
    "name": "SimuHome 客厅副灯",
    "manufacturer": "SimuHome",
    "model": "on_off_light",
    "suggested_area": "living_room",
    "via_device": "simuhome_gateway"
  },
  "origin": {"name": "simuhome-mqtt", "sw": "1.0.0"}
}
```

传感器（3 房间 × 4 指标）：

```json
{
  "name": "客厅温度",
  "unique_id": "simuhome_living_room_temperature",
  "state_topic": "simuhome/v1/living_room/temperature",
  "unit_of_measurement": "°C",
  "device_class": "temperature",
  "state_class": "measurement",
  "suggested_display_precision": 1,
  "availability_topic": "simuhome/v1/status",
  "device": {
    "identifiers": ["simuhome", "room_living_room"],
    "name": "客厅（SimuHome）",
    "manufacturer": "SimuHome",
    "model": "virtual_room",
    "suggested_area": "living_room",
    "via_device": "simuhome_gateway"
  },
  "origin": {"name": "simuhome-mqtt", "sw": "1.0.0"}
}
```

说明：`state_class: measurement` 是补齐 recorder 统计的关键，当前集成缺的就是它；`origin` 是 discovery 的必填块。

## 5. 发布策略（明确"不要一直发"）

```text
轮询间隔    活跃 1 秒 / 空闲 10 秒
            活跃的判定：最近 5 分钟内下发过命令，或有设备处于 on 状态
发布时机    值变化才发；数值型带死区：温度 0.1 °C、湿度 1%、照度 10 lux、PM10 1
            开关状态一变立即发
限流        单实体最快 1 条/秒
全量重发    发布器启动、broker 重连、每 10 分钟一次（防丢 retained）
retain      discovery / state / availability 都 retained；command 不 retained
qos         0；keepalive 60 秒
掉线        LWT：`simuhome/v1/status` = offline
```

## 6. 命令路径与失败处理

```text
HA 点开关 → homeassistant 发到 simuhome/v1/<device_id>/set（payload ON/OFF）
发布器收到 → 映射成 SimuHome 的调用（endpoint_id=1, cluster_id=OnOff, command_id=On/Off）
          → POST /api/devices/<device_id>/commands
          → 读回属性 → 发布 state 主题
不管成功失败都写一条 simuhome/v1/events（含耗时与错误码）

失败时    不改变 state（避免假状态）；HA 侧不用 optimistic；由下一次读回纠正
超时       命令 3 秒未回执 → 事件里标 timeout；状态保持原值
```

## 7. 断线、恢复与重置

```text
SimuHome 挂      发布器发布 status=offline → HA 里所有实体变 unavailable
                 SimuHome 恢复后重新全量发布，status=online
broker 挂        HA 实体 unavailable；broker 起来后发布器重连并重发 discovery + 全量
发布器挂        LWT 让 broker 代发 offline；重启后重发 discovery + 全量
reset 仿真       发布器发现设备集合变化 → 对新设备补发 discovery，
                 对消失的设备向旧 config 主题发空 payload（HA 会删除该实体）
```

## 8. 录制器（论文用）

```text
订阅 simuhome/v1/#（可选再订 homeassistant/# 记录 discovery）
写 JSONL：真实时间、主题、payload；一行一条
用途：完整状态流、可回放；以后 MCP 的沙盒后端可以直接复用这份流
体积估算：变化驱动下实验运行一小时约几百 KB 到几 MB
```

## 15. "不草率"的具体标准（M2/M3 验收清单）

```text
唯一性     同一台设备在 HA 里只出现一次；重跑 reset 后不产生重复设备
完整性     每个实体都有 unique_id；设备有 area；传感器有 device_class 与 state_class
可回执     命令有结果与耗时记录；超时会被标记；状态由回读决定，不写假状态
可观测     断线时实体变 unavailable（LWT），而不是停在旧值
可重建     删掉 HA 里的 MQTT 实体后，发布器重发 discovery 就能恢复
可核对     验收时逐项比对 HA 侧状态与 SimuHome 的属性值，允许误差为死区大小
```

## 16. broker 复审：amqtt 有缺陷，切换到 Mosquitto

M2 收尾时做了一次话题隔离测试，发现一个真问题：

```text
测试   新客户端只订阅 zzz/none（这个主题从来没人发布过），等 3 秒
结果   收到 49 条消息，全是别人的 retained（homeassistant/... 的 discovery 与 simuhome/... 的状态）
结论   amqtt 0.12.1 的 retained 投递不按订阅过滤器走，新订阅者会拿到全部 retained
影响   功能上 HA 仍正常工作（HA 自己按 topic 分发，多余消息会被丢弃），
       但"订阅什么就只收什么"这个前提不成立：任何能连上 broker 的客户端都能读到全部状态，
       录制器、审计、鉴权设计都建立在这个前提上，所以不能接受
版本   amqtt 最新就是 0.12.1，没有修复版本可升
```

决定与做法：

```text
换成 Mosquitto 官方实现（Windows 原生版）
  安装包已下载：_tools\mqtt\mosquitto-2.0.20-install-windows-x64.exe（27 MB）
  安装需要管理员权限，装完后配置与启停脚本已在 simuhome_mqtt_publisher\broker\ 里准备好
  切换步骤：停 amqtt → 起 Mosquitto（1883，仅监听 127.0.0.1）→ HA 的 MQTT 集成重连 → 发布器重发 discovery
过渡期替代方案（如果暂时不装）
  把发布器里的 retained 改成 False，并在 HA 上线（birth 消息）与重连时重发 discovery 与全量状态；
  代价是 HA 重启后要等下一次重发才有实体状态
```
