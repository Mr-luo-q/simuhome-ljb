# 统一能力接口设计：从协议到动作词表的三层归一

本文回答一个问题：**「无论设备走什么协议，只要 HA 能操作它，我们暴露给模型的接口是不是统一的」**。
答案是"是"，但统一发生在哪一层必须说准，否则会把 HA 已经做完的事再做一遍，也会把做不到的事说成做得到。

本文是新增设计，不替代 11 号文档；它细化 11 的 §5.2（工具契约）与 §5.4（后端映射规则）里
"动作词表"那一层，并给出对契约的改动方案。

## 1. 三层分工

```text
协议层     Matter / Zigbee / Wi-Fi / MQTT / ESPHome / HomeKit …
           ↓  HA 的集成层已经抹平：不管什么协议，一律变成 domain + service + attributes
域层       switch.* / light.* / climate.* / fan.* / cover.* / sensor.*
           ↓  这一层没有抹平：同一个物理能力会落成不同 domain，服务名也不含取值范围
能力层     我们的能力标签 + 规范动作词表（本文要定义的东西）
           ↓
模型看到的  turn_on / turn_off / toggle / set_brightness / set_mode /
           set_temperature / set_percentage / set_position / open / close
```

结论先写清楚：

```text
HA 负责     跨协议归一（Matter 的 OnOff cluster、Zigbee 的 on/off、MQTT 的 ON/OFF
            到了 HA 里都是 switch.turn_on）——这件事我们不做，也做不了
我们负责    跨 domain 归一（同一个能力在 HA 里可能是 switch 也可能是 light）
            以及给动作配范围与约束（域层服务名里没有这些信息）
```

一句话：**我们统一的是能力与动作词表，不是协议。**

## 2. 为什么 HA 的域层不够：三条实测证据

### 2.1 同一个能力落在不同 domain

```text
SimuHome 侧的客厅主灯是 dimmable_light，属性里带 LevelControl：
  CurrentLevel=1、MinLevel=1、MaxLevel=254     ← 亮度可调
SimuHome 侧的客厅侧灯是 on_off_light，只有 1.OnOff.OnOff

但发布器把两台都发成了 HA 的 switch：
  switch.simuhome_living_room_main_light
  switch.simuhome_living_room_side_light

结果   主灯的亮度能力在 HA 里根本不存在，模型看到的是一台普通开关
在真家里 可调光灯通常是 light.*（带 brightness 属性）
后果   同一句「把客厅灯调暗」，在这套仿真里做不到、在真家里做得到；
       模型学到的是环境相关的调用方式，迁移实验必然掉点
```

### 2.2 同一种设备在不同家里建模不同

```text
取暖器  这家是 climate（有 set_temperature），那家可能就是一个 switch
窗帘    这家是 cover（有位置百分比），那家可能是 switch + 两个按钮
```

只按 domain 暴露接口，模型每换一个环境就要重学一遍调用方式；按能力暴露，词表不变。

### 2.3 域层给不出"能做什么、值域多少"

```text
get_services_for_target(switch.simuhome_living_room_tv)
  → ["switch.turn_off", "homeassistant.turn_on", …, "homeassistant.reload_config_entry"]
    只有服务名，没有字段；还混进了管理员服务
supported_features(switch.*)  → null        ← 开关没有能力位
范围只能从设备属性读：实测 climate 的 state 里带 min_temp=7.0 / max_temp=32.0 /
target_temp_step=0.5，fan 带 percentage_step=1.0
```

所以能力与范围必须由我们从 domain + 属性推出来，不能指望服务清单。

## 3. 能力标签表

能力标签是本文的核心。判定规则是「domain 命中 且 属性存在」，两个条件都满足才算有该能力。

| 能力标签 | 判定规则（domain + 属性） | 规范动作 | 参数与范围来源 |
| --- | --- | --- | --- |
| `on_off` | 状态在 on/off 之间（switch / light / fan / climate 都有） | `turn_on`、`turn_off`、`toggle` | 无参数 |
| `brightness` | `light` 且状态里有 `brightness` | `set_brightness` | 0~100，步长 1；HA 侧换算成 0~255 |
| `temperature` | `climate` 且状态里有 `min_temp` / `max_temp` | `set_temperature` | 设备自报：min_temp / max_temp / target_temp_step |
| `hvac_mode` | `climate` 且状态里有 `hvac_modes` | `set_mode` | 取值就是 `hvac_modes` 列表（实测是 off / cool / heat） |
| `fan_speed` | `fan` 且状态里有 `percentage`；或 `climate` 带 `fan_modes` | `set_percentage` | fan 取 0~100、步长用 `percentage_step` |
| `position` | `cover` 且状态里有 `current_position` | `set_position` | 0~100，步长 1 |
| `open_close` | `cover`（服务里有 open_cover / close_cover） | `open`、`close` | 无参数 |
| 只读量 | `sensor` 的 `device_class`：temperature / humidity / illuminance / pm10 | 无 | 只出现在 observe_home 与 inspect_room 的 env 里 |

当前这套系统实际命中的能力（实测 25 个实体）：

```text
9 × switch.simuhome_*            → [on_off]
2 × climate.simuhome_*           → [on_off, temperature, hvac_mode]
1 × fan.simuhome_kitchen_fan     → [on_off, fan_speed]
13 × sensor.simuhome_*           → 只读量（不设备）

注意：主灯本来是 dimmable_light，但因为发布器把它压成了 switch，
      现在的能力是 [on_off] 而不是 [on_off, brightness]——能力层只能看见后端暴露出来的东西，
      这条链路的缺口在发布器，属二期（见 §6）
```

## 4. 动作词表与两个后端的映射

能力决定"能不能做"，动作决定"怎么调"。模型只看到左边这一列，其余是后端的事。

| 规范动作 | 参数 | HA 后端落点 | 沙盒后端落点（二期） |
| --- | --- | --- | --- |
| `turn_on` / `turn_off` | 无 | `switch.turn_on` / `light.turn_on` / `fan.turn_on` / `climate.set_hvac_mode` | OnOff 命令 On / Off |
| `toggle` | 无 | 对应域的 `toggle` 服务 | OnOff 命令 Toggle |
| `set_mode` | `mode`: off / cool / heat | `climate.set_hvac_mode` | Thermostat.SystemMode 写入 |
| `set_temperature` | `value`: 摄氏度 | `climate.set_temperature` | Thermostat.OccupiedCooling/HeatingSetpoint 写入（0.01°C 整数） |
| `set_percentage` | `value`: 0~100 | `fan.set_percentage` | FanControl.PercentSetting 写入 |
| `set_brightness` | `value`: 0~100 | `light.turn_on` 带 `brightness_pct` | LevelControl.CurrentLevel 写入（1~254） |
| `set_position` | `value`: 0~100 | `cover.set_cover_position` | WindowCovering.TargetPosition 写入 |
| `open` / `close` | 无 | `cover.open_cover` / `close_cover` | WindowCovering 命令 |

动作语义在两边的差异要显式写出来，不能假装一样：

```text
空调设定温度   HA 侧按当前模式写制冷或制热设定点；沙盒侧同一件事
空调上电依赖   实测：Off 时写设定点会被 SimuHome 拒绝（DEPENDENCY_VIOLATION），
               HA 后端的做法是先补一条开机、并在回执 steps 里写出来
亮度刻度       HA 的 light 用 0~255，模型侧统一 0~100，换算在 HA 后端做
```

## 5. 对契约的改动（M3 前完成）

现在的 `inspect_device` 返回单一 `kind`（switch / climate / fan），这个字段不足以表达
"一台设备同时有多个能力"（空调事实上同时有 on_off + temperature + hvac_mode）。
建议改成能力集合：

```json
{
  "device_id": "living_room_ac",
  "entity_id": "climate.simuhome_living_room_ac",
  "area_id": "living_room",
  "capabilities": ["on_off", "hvac_mode", "temperature"],
  "state": {
    "on": false, "mode": "off", "target_temperature": 24.0,
    "current_temperature": 26.0, "min_temperature": 7.0,
    "max_temperature": 32.0, "temperature_step": 0.5
  },
  "actions": [
    {"action": "turn_on", "capability": "on_off", "params": {}},
    {"action": "turn_off", "capability": "on_off", "params": {}},
    {"action": "toggle", "capability": "on_off", "params": {}},
    {"action": "set_mode", "capability": "hvac_mode",
     "params": {"mode": {"type": "string", "enum": ["off", "cool", "heat"]}}},
    {"action": "set_temperature", "capability": "temperature",
     "params": {"value": {"type": "number", "minimum": 7.0, "maximum": 32.0, "step": 0.5}}}
  ]
}
```

改动清单：

```text
contract\tools.py     ACTIONS_BY_KIND → ACTIONS_BY_CAPABILITY；
                      新增 CAPABILITY_RULES（domain + 属性 → 能力标签）；
                      ActionSpec 增加 capability 字段
backend_ha\mapping.py 新增 capabilities_of(entity_state) 判定函数
inspect_device.py     返回 capabilities 与带 capability 的动作列表
execute_action.py     M3 实现：按 action 找能力 → 校验参数与范围 → 分发到服务调用
测试                  契约测试加"同物理能力不同 domain"的用例（见 §7）
11 号文档             §5.2 工具表与 §5.4 映射规则同步成能力口径
```

为什么现在改而不是等二期：`execute_action` 是第一个按动作分发的工具，它必须知道
"这个动作属于哪个能力、这台设备支不支持"。等写完再改，等于把分发逻辑推倒重来。

## 6. 边界与降级

```text
没发到 HA 的设备
  SimuHome 里的窗帘、冰箱、冷冻柜没有 OnOff 属性，发布器根本没发；
  它们对模型不存在，能力层也无从推断。缺口在发布器，二期补（把窗帘发成 cover、主灯发成 light）

HA 里有、我们没建能力的能力
  色温、摆风、洗涤程序、加湿档位这类：不纳入统一词表，任务需要时按 §3 的格式单独加一行规则

HA 里没有对应 domain 的实体
  number / select / input_* 之类：不强行塞进动作词表；要么在能力表里加专门能力，
  要么明确不暴露（本文倾向后者，避免词表膨胀）

只在一边存在的能力
  沙盒有快进、HA 没有；HA 有真实等待、沙盒没有。这类差异记在时间语义里（见 11 号文档 §6），
  不混进能力表
```

## 7. 怎么验收

能力层的价值要能被测试证明，用一句话概括：**同一物理能力，后端暴露成不同 domain 时，
模型看到的动作词表应当一致**。

```text
用例一（假 HA，新增）
  fixture 里放两台"灯"：
    switch.demo_plain_light     属性只有 on/off
    light.demo_dimmable_light   属性带 brightness
  断言：前者 capabilities = [on_off]，动作只有 turn_on / turn_off / toggle；
       后者 capabilities = [on_off, brightness]，动作多出 set_brightness(0~100)
  意义：证明能力层按能力而不是按设备名/房间出词表

用例二（假 HA，新增）
  同一个 domain 的两种设备：climate（带 min_temp/max_temp）与 switch
  断言：只有 climate 有 temperature 能力，且范围取自设备自报的 7.0 / 32.0 / 0.5

用例三（真 HA，M3 验收时加）
  inspect_device(living_room_ac) → capabilities 含 on_off / hvac_mode / temperature
  inspect_device(living_room_side_light) → capabilities = [on_off]
  execute_action 对一台没有该能力的设备发动作 → UNSUPPORTED_ACTION
    （例：对 switch 发 set_temperature）

用例四（二期，发布器发成 light 之后）
  inspect_device(living_room_main_light) → capabilities 从 [on_off] 变成 [on_off, brightness]，
  而模型侧的动作名不变（仍是 set_brightness）——证明"接入层升级不需要模型重学"
```

## 8. 未决问题

```text
Q1  能力标签要不要跟 Matter 对齐命名（on_off ↔ OnOff、brightness ↔ LevelControl）
    对齐的好处：与沙盒侧 cluster 一一对应，映射表更薄
    代价：Matter 的 cluster 名更长，且 cover / hvac 等语义不完全一一对应
    本文倾向：模型侧用短名（on_off / brightness），沙盒后端内部再做一次短名 → cluster 的映射

Q2  set_brightness 的刻度统一成 0~100 还是保留设备原生刻度（0~255）
    本文倾向统一 0~100（模型好理解、跨设备可比），原生刻度在 HA 后端换算

Q3  没有对应服务的动作（比如某台 fan 不支持 set_percentage）
    本文倾向：能力判定时就把该动作排除，而不是发出去再返回 UNSUPPORTED_ACTION

Q4  要不要给每台设备补一个 raw 兜底动作（直接调 HA 服务名）
    本文倾向不要：一旦留了口子，模型会绕开统一词表，迁移实验就没法比较
```

## 9. 与论文口径的关系

```text
能力层是"同语义 MCP"这句话的具体载体：
  迁移实验里要对比的不是"两个 MCP 名字一样"，而是"同一批能力标签在两个后端上
  是否给出同一套动作与同一套范围"
  因此实验记录里要落三样东西：capabilities、actions、每次动作的 params 与结果
  三样都能从 inspect_device 与 calls 表里直接导出
```
