# 统一能力接口设计：粒度定在"设备 + 动作类型"

本文定义我们对模型暴露的语义粒度，以及它与两篇基准（SimuHome、SMH-Bench）的粗细关系。
结论先行：

```text
统一粒度 = 房间 → 设备 → 动作类型 → 参数约束 → 关键状态
比 SimuHome 粗：不暴露 endpoint / cluster / attribute 三层，也不暴露 Matter 命令名
比 SMH-Bench 粗：不建"每台设备自定义服务名"，不建组件命名空间、状态转移规则、
                unit / precision / 复合类型
动作词表固定 8 个，参数只带 type / minimum / maximum / step / enum
```

粒度方案的取舍过程见本文 §2（三档阶梯），我们选第三档（C）。
投稿策略以 `UbiComp三支柱讨论\12_投稿策略-把三个支柱的故事讲圆.md` 为准，本文服从它的口径：
把承诺收小到能兑现。

## 1. 三层分工：协议归 HA，能力归我们

```text
协议层     Matter / Zigbee / Wi-Fi / MQTT / ESPHome …
           ↓  HA 集成层已经抹平：一律变成 domain + service + attributes
域层       switch.* / light.* / climate.* / fan.* / cover.* / sensor.*
           ↓  这一层没抹平：同一能力可能落成不同 domain，服务名里也没有取值范围
能力层     我们的动作词表 + 参数约束（本文定义）
```

一句话：**我们统一的是动作词表，不是协议。** 跨协议归一由 HA 完成，跨 domain 归一由我们完成。

## 2. 三档粒度阶梯与我们的选择

按粗细排三档，两篇论文落在最细一档之下：

| 档位 | 外面看到什么 | 动作词表 | 参数约束 | 状态 |
| --- | --- | --- | --- | --- |
| A 任务原语 | 只有房间，不暴露设备 | `set_target(room, metric, value)` 等 4 个 | 无 | 房间级环境量 |
| B 设备 + 单动词 | 房间 + 设备，每台一个可调量 | `turn_on` / `turn_off` / `set` 共 3 个 | 只声明语义与范围 | on/off + 一个值 |
| **C 设备 + 动作类型（本文采用）** | 房间 + 设备 + 每台的动作清单 | 8 个动作名，按设备取子集 | type + min/max/step/enum | on / mode / target / level / position / current |
| （参考）SMH-Bench | 设备 + 服务 + 组件命名空间 | 每台设备自定义服务名 | 上述再加 precision / unit / 复合类型 / 状态转移规则 | 带类型的属性表 |
| （参考）SimuHome | 设备 + endpoint / cluster / attribute | Matter 命令名（约 28 个集群） | attribute 类型系统 | cluster 属性全暴露 |

不选 A 的理由：A 把"选哪台设备"这个决策交给后端，而 T1 空间任务考的正是这个决策，接口替模型解题会让任务失去意义。
不选 B 的理由：B 每台设备只能有一个可调量，空调的模式（制冷/制热）会被砍掉，而 QT3/QT4 里明确有模式类指令。
选 C 的理由：三个支柱要的语义它都够（任务能表达、训练能判分、两个后端能对齐），而它比两篇论文都少一大截实现面。

## 3. 两篇论文的语义维度（我们比它们粗在哪里）

事实来源：SimuHome 正文 §3.2/§3.3 与附录 A.2/A.3；SMH-Bench 正文 §3.2/§3.3 与附录 A.1~A.6。

```text
空间
  SimuHome   房间（扁平），房间 → 设备清单
  SMH-Bench  Room{id, type, name, floor, parent?}，支持嵌套（卧室里的浴室）
  我们       同 SMH 的字段，但不做嵌套语义推理（parent 只作为字段保留）

设备
  SimuHome   17 种设备类型，每台用 Matter 三层表示：endpoint → cluster → attribute/command
  SMH-Bench  Device{name, description, attributes[], services[], components[], userdata{...}}
  我们        Device{device_id, room_id, category}；一台设备对外是一个对象

动作
  SimuHome   execute_command(device, endpoint, cluster, command, args) —— 集群级命令名
  SMH-Bench  设备自定义服务名（设置_目标_温度、风扇.设置_速度_等级…）
  我们       固定 8 个动作名（见 §4），按设备类别取子集

参数
  SimuHome   attribute 类型系统
  SMH-Bench  复用属性类型：name / type / range / options / precision / unit
  我们       type + minimum + maximum + step + enum；不做 precision / unit / 复合类型

状态
  SimuHome   cluster 属性全暴露（含电量、测量、运行状态等十几个集群）
  SMH-Bench  带类型的属性表（状态、电池_电量、亮度、色温、目标温度、空调_模式…）
  我们       六个关键字段（见 §5），其余属性不透传

时间
  SimuHome   虚拟时间 + 绝对时间调度一串步骤
  SMH-Bench  Quartz 七字段 cron + 状态表达式触发
  我们       同 SimuHome 的绝对时间调度；cron 与状态触发不做

多组件
  SimuHome   一台设备多个 cluster
  SMH-Bench  组件命名空间（灯.* / 风扇.*，如风扇灯）
  我们       不做组件：一台设备一个对象，多组件设备按主功能发布（写进覆盖缺口）
```

## 4. 动作词表（8 个）

| 动作 | 参数 | 说明 | 当前状态 |
| --- | --- | --- | --- |
| `turn_on` | 无 | 打开设备 | 可验（9 开关 + 2 空调 + 1 风扇） |
| `turn_off` | 无 | 关闭设备 | 可验 |
| `toggle` | 无 | 取反 | 可验 |
| `set_mode` | `mode`: 枚举 | 空调模式（off / cool / heat） | 可验（2 空调） |
| `set_temperature` | `value`: 数值 | 目标温度，范围取设备自报值 | 可验（2 空调，7~32，步长 0.5） |
| `set_percentage` | `value`: 数值 | 风扇档位 0~100 | 可验（1 风扇） |
| `set_brightness` | `value`: 数值 | 亮度 0~100 | 词表预留：当前没有 light 实体 |
| `set_position` | `value`: 数值 | 窗帘位置 0~100 | 词表预留：当前没有 cover 实体 |

参数约束只写三件事：类型、上下界、步长（枚举型动作写选项）。不写单位与精度——
温度的单位固定摄氏度、亮度与档位固定百分比，写进文档而不是写进每个参数。

当前这套系统实际能发出的动作（实测 25 个实体）：

```text
9 × switch.simuhome_*          → turn_on / turn_off / toggle
2 × climate.simuhome_*         → 上述 3 个 + set_mode + set_temperature
1 × fan.simuhome_kitchen_fan   → 上述 3 个 + set_percentage
13 × sensor.simuhome_*         → 只读，无动作
```

## 5. 状态字段（6 个）

对外只给这六个字段，按设备类别取子集：

| 字段 | 类型 | 含义 | 出现在 |
| --- | --- | --- | --- |
| `on` | bool | 是否通电/运行 | switch / climate / fan |
| `mode` | string | 运行模式 | climate |
| `target` | number | 目标值（温度） | climate |
| `level` | number | 档位/亮度百分比 | fan（亮度接入后同字段） |
| `position` | number | 位置百分比 | cover（预留） |
| `current` | number | 设备自测值（如自身温度计） | climate |

不在状态里放的东西：范围（min/max/step 属于动作参数）、单位（文档约定）、
运行阶段与倒计时（SimuHome 的 OperationalState）、电量、测量类属性。
这些都在覆盖缺口里写明，不在接口里假装支持。

## 6. 判定与时间

```text
判定   目标状态达成 + 无关状态保持（两篇论文的评测口径一致：SMH 明说"无关状态保持"，
       SimuHome 用 goal comparison）。我们的 check_goal 只表达这两件事，不发明更强语义
时间   当前时间（虚拟）+ 在绝对时间调度一串步骤
       不做 cron、不做状态触发规则（只有 SMH 有，属共同粒度之外）
```

## 7. 两个后端的映射

| 动作 | HA 后端 | 沙盒后端（二期） |
| --- | --- | --- |
| `turn_on` / `turn_off` | 对应 domain 的 turn_on / turn_off | OnOff 命令 On / Off |
| `toggle` | 对应 domain 的 toggle | OnOff 命令 Toggle |
| `set_mode` | `climate.set_hvac_mode` | Thermostat.SystemMode 写入 |
| `set_temperature` | `climate.set_temperature`（字段名 temperature） | Thermostat 冷/热设定点写入（0.01°C 整数） |
| `set_percentage` | `fan.set_percentage` | FanControl.PercentSetting 写入 |
| `set_brightness` | `light.turn_on` 带 `brightness_pct` | LevelControl.CurrentLevel 写入（1~254） |
| `set_position` | `cover.set_cover_position` | WindowCovering.TargetPosition 写入 |

两边语义差异要显式写出来：

```text
参数改名     HA 服务字段叫 temperature，我们的动作参数叫 value，映射层转一次
上电依赖     实测空调 Off 时写设定点会被 SimuHome 拒绝（DEPENDENCY_VIOLATION）；
            HA 后端先补一条开机，并把这一步写进回执 steps
越界参数     实测把 40°C 发给 HA 的 climate.set_temperature 返回 500（不是 400）且不写状态，
            所以范围要在动作层先校验（用设备自报的 min/max）→ BAD_REQUEST；
            漏过去的才归 SERVICE_ERROR
```

## 8. 覆盖缺口（明确不做的）

```text
多组件设备     风扇灯这种"一台设备两个功能"：按主功能发布，不做组件命名空间
其它属性       色温、音量、吸力、电量、人体存在：不做（SimuHome 有对应集群但当前设备没有，
               SMH 有属性但任务不依赖）
状态转移规则   SMH 的 service.code（如"开亮度前必须通电"）：不做通用规则引擎，
               只保留"设备自报约束 + 后端拒绝"这一条实际路径
cron / 状态触发 SMH 有，SimuHome 没有：不做，任务里用绝对时间调度表达
unit / precision 不进入参数约束，用文档约定（摄氏度和百分比）
复合类型       列表 / 元组 / 字典型属性：不做
房间连通与拓扑 两篇论文都没有：作为我们的 T1 扩展单独记，不混进动作词表
事件历史查询   两篇都没有这个工具：作为扩展单独记
长期记忆        SMH 用 {{memory_list}} 上下文注入，不是工具：作为扩展单独记
```

## 9. 怎么验收

```text
用例一（假 HA，已实现）
  fixture 里放三种设备：switch、climate、fan
  断言 capabilities/动作子集分别是 3 个、5 个、4 个动作，且空调温度范围取设备自报的 7~32 / 0.5

用例二（假 HA，新增）
  同一物理能力不同 domain：一台只有 on/off 的 switch 与一台带 brightness 的 light
  断言：动作词表只按"支持哪些动作"变化（多出 set_brightness），动作名本身不随 domain 变

用例三（真 HA，M3 验收）
  execute_action(living_room_side_light, turn_on) → 回读 on
  execute_action(living_room_ac, set_temperature, {value: 25}) → 回读 target=25
  execute_action(kitchen_fan, set_percentage, {value: 60}) → 回读 level=60
  越界：set_temperature {value: 40} → BAD_REQUEST（本地校验，不发给 HA）
  动作不支持：对 switch 发 set_temperature → UNSUPPORTED_ACTION
  实体不可用：发布器停机后 → DEVICE_UNAVAILABLE（假后端覆盖分支，真机在 M5 验）

用例四（二期，发布器接灯之后）
  living_room_main_light 发成 light 实体 → 动作清单自动多出 set_brightness，
  模型侧动作名不变，证明接入层升级不需要模型重学
```

## 10. 与论文口径的关系

```text
能力层是"同语义 MCP"这句话的载体。迁移实验要比的不是"两个 MCP 名字一样"，
而是"同一批动作名在两个后端上是否给出同一套参数约束与同一套状态字段"。
因此每次实验要落三样东西：设备的动作清单、每次动作的参数与结果、状态字段快照——
三样都能从 inspect_device 与 calls 表直接导出。

粗粒度换来的是可验证性：动作只有 8 个，两个后端的对齐只需覆盖这 8 个，
覆盖率报告能一句话说清（哪几个动作在两个后端都验过、哪几个当前无设备）。
```
