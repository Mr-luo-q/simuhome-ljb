# 接入方案综合分析与选型

目标：把一套可测试的系统（现在是 SimuHome）接进 HA，让 HA 成为实验里能用的前端与控制面。
本文把本机实际情况、三条候选路线、打分与落地步骤一次写清。

## 1. 判据：什么叫“接好了”

```text
实体覆盖    灯、空调、窗帘、风扇、传感器、开关这些类型都要能出现
设备与区域  设备要进 HA 的设备注册表，房间要成为 area 并把设备绑进去
刷新方式    有推送最好；没有推送就得能控制在秒级，而不是 10 秒
命令路径    写操作可靠，能回读验证
依赖与运维  进程与容器数量、是否需要额外常驻服务
代码量      要写多少代码，写完谁维护
可复现性    能不能一键重建、能不能录下来重放（实验平台的关键）
```

## 2. 本机现状盘点（实测）

```text
HA 安装形态   Container（Windows + Docker Desktop + 单容器 homeassistant:2026.6.4）
              没有 Supervisor / HAOS → 没有加载项商店 → 官方 Mosquitto 加载项装不了，
              要用 MQTT 只能自己起一个 broker 容器
SimuHome      :8000，22 条 HTTP API，只有轮询、没有推送
bridge        :8010，无鉴权反代 + 操作日志（07 文档已审出 7 个问题）
现有集成      custom_components\simuhome，YAML 平台、无 config entry
              → 实测 0 个设备、0 个区域，25 个实体 device_id / area_id 全是 null
Python        anaconda 3.13.5，已装 mcp / uvicorn / starlette / yaml / httpx / aiohttp
Docker        Docker Desktop 在跑，可再加容器
网络          可达 home-assistant.io 与 developers.home-assistant.io（均 200）
```

## 3. 三条候选路线

### 方案 A：MQTT discovery

```text
做法     SimuHome 侧（或独立小进程）作为 MQTT 发布者：
           轮询 GET /api/home/state → 按 HA 的 discovery 模板发布状态主题
           订阅命令主题 → 调 POST /api/devices/{id}/commands
         HA 侧启用官方 MQTT 集成，指向自建 broker，实体自动发现
本机落地  compose 里加一个 mosquitto 容器；HA 里装 MQTT 集成（UI 配置）；
         发布器可以做成 SimuHome 的一个可选模块，也可以独立进程
能拿到   实体覆盖：discovery 支持 light / climate / cover / fan / sensor / switch / binary_sensor /
                   number / select / vacuum / humidifier 等（本机源码确认，light 是包式实现，四种 schema）
         设备与区域：discovery 的 device 块可带 identifiers 与 suggested_area 缩写 sa，
                   HA 会据此创建设备并放进对应 area（官方文档确认 sa 缩写存在）
         推送：状态一变就发，HA 立刻更新
         只依赖一个 MQTT 主题契约；主题可以版本化、可以录制重放
代价     多一个 broker 容器；要设计主题结构与 discovery payload；
         命令路径多一跳（HA → broker → 发布器 → SimuHome）
风险     主题命名不规范会导致后期难维护；broker 挂了全体 unavailable，需要 watchdog
工作量   发布器约 300 行 + 主题设计文档 + compose 一段；半天到一天
```

### 方案 B：自定义集成 config entry 化

```text
做法     把现有 custom_components\simuhome 从 YAML 平台改成 config_flow + DataUpdateCoordinator；
           建 area 并把设备绑进去；补 light / climate / cover 实体；把日志搬进集成
本机落地  改 D:\homeassistant\config\custom_components\simuhome\，改完重启容器即可（目录已挂载）
能拿到   最贴合 HA 的实体、设备、区域体系；无新增依赖；可在 UI 配置与重载；
         顺手解决 07 文档里的 7 个问题（含虚拟时间与设备/区域缺失）
代价     1~2 天开发；开发循环是“改文件 → 重启容器”；
         提交 PR 不被上游接受的风险（自定义集成只能自用或发 HACS）
风险     跟 HA 版本走；实体 ID 由集成自己定，改代码可能改变 entity_id
工作量   集成约 600~800 行，含 config_flow、coordinator、平台实体
```

### 方案 C：REST + Template（纯 YAML，不改代码）

```text
做法     configuration.yaml 里用 rest: 定义 sensor / binary_sensor / switch，
         用 template: 定义 light / cover 等；
         rest_command 负责下行命令
能拿到   半小时能跑起来；不需要新进程；适合做对照或临时演示
代价     实体覆盖不全：template 没有 climate；rest 只有 sensor / binary_sensor / switch / notify；
         设备与区域拿不到：YAML 平台没有 config entry，设备与 area 依旧为空（见 07 文档的证据）；
         YAML 冗长，每个设备一段，维护成本随时间增长
工作量   配置文件 200~400 行，零代码
```

### 附：Matter 路线为什么不选

```text
要跑 Matter Server、做节点 commissioning 与 cluster/attribute 映射，
对照料一个仿真平台来说成本与收益不成比例；它更适合“验证 Matter 互操作性”这类课题。
```

| 合计 | **31** | 28 | 19 |

## 5. 结论与推荐

```text
主推 A：MQTT discovery
  它是唯一同时满足“设备与区域进注册表 + 实体类型全覆盖 + 推送 + 可录制回放”的路线，
  而且发布器可以顶掉现在的 bridge —— 进程数从（SimuHome + bridge + HA）变成
  （SimuHome 含发布器 + broker + HA），并没有变复杂，反而把无鉴权的 HTTP 代理换成了标准协议。

备选 B：集成 config entry 化
  如果不想再多一个 broker，就选它；代价是开发量大一倍，而且要跟着 HA 版本走。
  另外 B 与 A 不冲突：集成里也可以再叠加 MQTT。

对照 C：REST + Template
  只用来做“对照组”或临时演示，不作为长期测试床 —— 它拿不到 devices 与 area，
  而这两样正是 MCP 侧 list_rooms / inspect_room 的依赖。
```

## 6. 推荐路线的最小可跑步骤

```text
步骤 1  broker：在 old_simuhome_bridge_project\compose.yaml 里加 mosquitto 服务
        （eclipse-mosquitto:2，映射 1883，挂一个最小配置：允许匿名或账号密码）

步骤 2  HA 侧：设置 → 设备与服务 → 添加集成 → MQTT → 指向 broker；
        集成会自动创建，discovery 前缀默认 homeassistant

步骤 3  发布器：新写一个 publisher（建议放在 SimuHome 侧，或作为 bridge 的重写版）
        轮询 GET /api/home/state（1~2 秒一次，快进时临时加密）
        按 discovery 模板发布：
          homeassistant/switch/<device_id>/config     + state / command 主题
          homeassistant/sensor/<room>_<metric>/config + state 主题
          device 块里带 identifiers 与 suggested_area，把房间变成 area
        订阅 homeassistant/<component>/<device_id>/set

步骤 4  下行：收到命令主题 → POST /api/devices/{id}/commands（Matter 风格 endpoint/cluster/command）

步骤 5  验收：见第 7 节清单
```

## 7. 统一验收清单（三条路线都用这套）

```text
实体      HA 里出现 3 房间 × 4 环境量 + 12 个可控设备（有 light/climate/cover 时数量相应增加）
设备注册表 15 台设备出现在设备页，且每台都有 area
区域      出现 living_room / kitchen / utility_room 三个 area，或与配置一致的命名
写路径    在 HA 里开关某设备 → SimuHome 的属性在 2 秒内变化 → HA 状态回读一致
刷新延迟  仿真器里改状态 → HA 在 2 秒内看到（MQTT 路线应接近实时）
断线表现  broker 或发布器停掉 → 实体变 unavailable，而不是保持假状态
可重置    跑一次 reset → HA 侧实体恢复，且不产生重复设备
录制回放  订阅所有主题录一段，能重放并得到相同的 HA 状态序列（仅 A 路线具备）
```
