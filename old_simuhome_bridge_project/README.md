## 目标

本文档用于定义 `SimuHome` 与 `Home Assistant` 联动的可靠部署方案，面向智能家居仿真科研平台建设。

这个方案的目标不是“先跑起来一次”，而是：

- 在当前 Windows 机器上尽快落地并开始开发
- 保证系统架构足够稳定，能够支撑重复实验
- 为未来迁移到长期运行的 Linux 主机做好准备
- 保持 `SimuHome` 作为独立仿真后端
- 让 `Home Assistant` 主要承担记录、自动化、展示与控制职责

本文档的最高标准是：**可靠性优先**。

## 可靠性原则

当前方案和未来方案都遵循以下原则：

1. `SimuHome` 始终保持为独立后端服务。
2. `Home Assistant` 不承担仿真内核职责。
3. 系统间通信必须通过显式接口完成，优先采用 HTTP API。
4. 部署方式必须尽可能可复现，优先采用 `docker compose`。
5. 对实验有价值的状态必须显式持久化。
6. 当前到未来的迁移应当保留架构，而不是仅仅拷贝文件。
7. 短期便利不能以长期不可维护为代价。

## 系统职责划分

系统整体划分为几个明确角色：

- `SimuHome`
  - 负责虚拟设备、房间状态、环境演化、虚拟时间、工作流
- `Home Assistant`
  - 负责前端展示、Recorder/History、自动化、用户交互控制
- `适配层`
  - 负责将 `SimuHome` 的设备、状态、控制语义映射为 `Home Assistant` 可理解的实体和服务
- `支撑服务`
  - 可选，包括 MQTT、数据库、追踪、指标、可视化面板等

这种职责划分非常重要，因为它直接决定了后续迁移成本是否可控。

## 科研平台特有约束

与普通智能家居部署不同，本项目是一个科研仿真平台，因此必须额外满足以下约束：

1. 平台不仅要“能运行”，还要“能复现实验”。
2. 平台不仅要“能控制设备”，还要“能解释实验语义”。
3. 平台不仅要“有历史记录”，还要“知道这些记录对应的是虚拟时间还是真实时间”。
4. 平台在服务重启、网络抖动、配置迁移后，实验结论不能悄悄变化。
5. 部署方案必须服务于实验设计，而不是反过来让实验去迁就平台限制。

这意味着部署设计不能只考虑运维可靠性，还必须考虑：

- 时间语义可靠性
- 数据语义可靠性
- 故障恢复可靠性
- 迁移后一致性可靠性

## 当前方案

### 总体描述

当前推荐环境：

- 主机系统：`Windows`
- 容器运行时：`Docker Desktop`
- Linux 风格开发环境：`WSL2`
- Home Assistant 运行方式：`Home Assistant Container`
- SimuHome 运行方式：
  - 当前优先：源码方式本地运行
  - 当前阶段后续可选：逐步容器化

之所以推荐这个当前方案，是因为它能在不牺牲未来迁移能力的前提下，把当前启动难度降到较低。

### 当前架构

```text
Windows 主机
|
+-- Docker Desktop
|   |
|   +-- Home Assistant Container
|
+-- WSL2
|   |
|   +-- docker compose 控制面
|   +-- 可选本地开发工具
|
+-- SimuHome 源码目录
    |
    +-- SimuHome API 服务

Home Assistant <---- HTTP API ----> SimuHome
```

### 为什么当前这样设计

当前方案之所以合适，是因为它足够可靠，且适合作为开发与早期实验平台：

- `Home Assistant` 在隔离容器环境中运行，相对稳定
- `SimuHome` 仍然保留源码快速修改能力
- Windows 继续作为日常工作站，减少环境搭建成本
- WSL2 提供接近未来 Linux 主机的操作体验
- `Home Assistant` 与 `SimuHome` 的连接边界已经显式化

### 当前连接策略

主要策略：

- `SimuHome` 暴露 HTTP API
- `Home Assistant` 通过自定义集成访问这些 API

早期联通验证的临时兜底方式：

- 只在最初做 REST 连通性检查时使用简化方案

当前阶段的长期方向：

- 尽快过渡到 `custom integration`

原因如下：

- YAML REST 配置可以用于最初连通验证
- 但一旦设备映射和控制逻辑复杂起来，它不足以支撑长期科研场景

### 当前阶段必须明确的时间语义

`SimuHome` 不是一个普通设备源，而是一个带有**虚拟时间**的仿真器。

因此当前阶段就必须明确：

- `Home Assistant` 的 Recorder、History、Automation 默认基于真实时间
- `SimuHome` 的状态推进、工作流调度、`fast_forward` 基于虚拟时间

这两者不是同一种时间。

因此当前阶段的工作原则是：

1. `Home Assistant` 记录的是“平台观察到状态变化的真实时间”。
2. `SimuHome` 必须单独提供“该状态属于哪个虚拟时间”的信息。
3. 在尚未设计完时间桥接前，不应把 HA 的时间戳误当成仿真世界时间戳。
4. 对于“一天生活交互压缩到几分钟执行”的实验，必须额外保存虚拟时间轨迹。

也就是说，当前阶段可以先联通，但不能偷懒地把“真实时间记录”当成“仿真时间记录”。

### 当前目录策略

即便是在当前阶段，也应尽量按照未来架构组织目录：

```text
workspace/
  simuhome_bridge_project/
    README.md
    compose/
      compose.yaml
      .env.example
    config/
      homeassistant/
      custom_components/
        simuhome/
    docs/
  simuprocject/
    Simuhome_experiment/
```

关键原则：

- 部署文件与集成代码应独立于一次性实验脚本

### 当前可靠性要求

当前环境应满足以下要求：

1. `Home Assistant` 可以通过 `compose.yaml` 重建。
2. `SimuHome` API 地址必须可配置，而不是写死。
3. `Home Assistant` 配置和自定义集成代码必须放在挂载目录中。
4. 关键状态不能只存在于容器内部。
5. `Home Assistant` 与 `SimuHome` 的日志必须可以分开查看。
6. 必须能够明确区分真实时间日志与虚拟时间状态。
7. 在 `SimuHome` 重启后，应当能够判断实验是否失效，而不是静默继续。

### 当前风险

当前方案仍然有天然限制：

- Windows 作为长时间运行平台，不如 Linux 稳定
- Docker Desktop 本身多了一层宿主机抽象
- 某些网络行为不如原生 Linux 清晰
- 如果 SimuHome 暂时还不在 Compose 中，平台复现性仍然是不完整的
- 当前如果只用轮询获取状态，可能无法完整保留快进过程中的中间状态
- 当前如果只依赖 HA Recorder，无法完整复原 SimuHome 内部仿真轨迹

这些限制在当前阶段是可以接受的，因为它本质上仍然是开发与验证环境，而不是最终科研运行平台。

## 未来方案

### 总体描述

未来推荐环境：

- 主机系统：`Linux`
- 运行时：原生 `Docker Engine`
- 编排：`docker compose`
- 长期运行服务：
  - `homeassistant`
  - `simuhome`
  - 可选 `simuhome-adapter`
  - 可选 `mosquitto`
  - 可选 `influxdb`
  - 可选 `grafana`

这才是长期科研平台的正式推荐形态。

### 未来架构

```text
Linux 主机
|
+-- docker compose
    |
    +-- homeassistant
    +-- simuhome
    +-- simuhome-adapter（可选）
    +-- mosquitto（可选）
    +-- influxdb（可选）
    +-- grafana（可选）

Home Assistant <---- HTTP 或 Adapter API ----> SimuHome
```

### 为什么未来推荐这样设计

未来方案更适合长期科研运行，原因如下：

- 原生 Linux 更适合长期运行容器化服务
- 服务整体更容易完整复现
- 网络行为更清晰，排障成本更低
- 更适合全天或多天仿真实验
- 更自然地迁移到实验室服务器或远程主机
- 更方便增加可观测性组件

### 未来连接策略

推荐默认方案：

- `Home Assistant 自定义集成` 直接通过 HTTP 与 `SimuHome` 通信

未来可选增强：

- 如果 HA 到 SimuHome 的映射逻辑变得复杂，可以单独抽出 `simuhome-adapter` 服务

判断标准：

- 如果只是实体映射和服务转发，逻辑留在 `custom integration` 中即可
- 如果涉及时间翻译、事件缓冲、协议桥接、实验控制编排，则应独立出适配层服务

未来方案中，推荐将系统接口逻辑显式分为两层：

1. **实体控制面**
   - 面向 HA 实体、状态、服务调用
   - 关注的是“设备当前是什么状态、能执行什么动作”
2. **实验控制面**
   - 面向 reset、虚拟时间推进、workflow、实验批次控制
   - 关注的是“实验怎么启动、怎么推进、怎么结束、怎么复现”

这两层不应该混在一起。

如果未来发现 `Home Assistant custom integration` 同时承载了实体映射和实验编排，就说明职责边界已经开始模糊，应该考虑抽出 `simuhome-adapter` 或单独的实验控制服务。

### 未来可靠性要求

未来正式平台应满足以下要求：

1. 整个平台可以通过版本化的 compose 文件完整重建。
2. 所有重要实验状态都在挂载卷中持久化。
3. 服务重启不会悄悄丢失 HA 配置、记录器数据或 SimuHome 状态。
4. `SimuHome` 与 `Home Assistant` 日志可分离、可追踪。
5. 平台可在无人登录的情况下持续运行。
6. 一天或多天实验运行不依赖开发者电脑保持开机。
7. 平台升级可逐服务进行，并具备回滚能力。
8. HA 侧记录与 SimuHome 侧虚拟时间轨迹可以对齐。
9. 服务重启后可以明确判定实验是“恢复成功”还是“应判失败重跑”。
10. 同一实验输入在迁移前后应产生一致的关键状态输出。

### 未来推荐服务集合

最小集合：

- `homeassistant`
- `simuhome`

推荐集合：

- `homeassistant`
- `simuhome`
- 如有需要，增加 `simuhome-adapter`
- 如有需要，增加 `mosquitto`

科研增强集合：

- `homeassistant`
- `simuhome`
- `simuhome-adapter`
- `influxdb`
- `grafana`

### 未来数据持久化策略

以下内容必须显式持久化：

- Home Assistant `/config`
- 自定义集成代码
- SimuHome 配置与对实验有价值的状态
- 如有独立 Recorder/数据库，也要单独挂载
- 如有指标数据库，也必须独立持久化

不要把容器文件系统当作真正可靠的长期存储。

### 未来实验数据归属原则

必须提前区分哪类数据由谁负责保存：

#### 由 Home Assistant 负责保存的数据

- 实体状态变化历史
- 自动化触发记录
- 用户操作记录
- Dashboard/Recorder 视角下的家居状态轨迹

#### 由 SimuHome 负责保存的数据

- 仿真输入配置
- 虚拟时间推进轨迹
- workflow 执行轨迹
- reset / fast_forward / run_now 等实验控制事件
- 仿真环境内部关键状态快照

#### 结论

不能只依赖 HA Recorder 作为实验真相来源。

对于科研来说，HA 记录的是“平台观察视角”，而 SimuHome 必须提供“仿真真实轨迹视角”。

这两套数据都需要，并且语义不同。

## 当前与未来如何调节、如何过渡

### 核心过渡原则

迁移不应该采用“推倒重来”的方式。

正确做法是：

- 保持架构一致
- 只替换宿主机与部署包装

也就是说，以下抽象边界在当前和未来之间应尽量保持不变：

- `SimuHome` 始终是独立服务
- `Home Assistant` 始终是消费/控制层
- 两者通过显式网络 API 连接
- 部署方式始终围绕 Compose 组织
- 状态始终外置并持久化

除此之外，还必须补充一条：

- 迁移前后，关键实验语义必须可比对，而不是只保证“服务能启动”

### 过渡阶段划分

#### 阶段 1：当前开发验证环境

环境：

- Windows
- Docker Desktop
- WSL2
- HA 容器
- SimuHome 源码运行

目标：

- 验证 HA 能启动
- 验证 SimuHome API 可访问
- 验证首批实体与控制映射
- 梳理真正需要的集成逻辑
- 明确真实时间与虚拟时间的记录边界

#### 阶段 2：当前结构化环境

环境：

- 仍然是 Windows + Docker Desktop + WSL2
- 但部署定义全面进入 compose 文件
- SimuHome 可逐步进入容器化

目标：

- 使当前环境具备复现能力
- 减少人工操作步骤
- 将配置纳入版本管理
- 让未来迁移主要变成宿主机与路径迁移
- 开始形成可重复的实验运行流程
- 开始定义迁移验收样例

#### 阶段 3：Linux 正式迁移

环境：

- Linux 主机
- 原生 Docker Engine
- 复用同一套 compose 结构

目标：

- 从依赖开发机的运行方式迁移到服务型运行方式
- 支持全天与重复实验
- 降低宿主机相关不稳定性
- 将实验运行、故障恢复、数据留存标准化

### 在过渡过程中必须保持稳定的部分

以下部分尽量不变或仅微调：

- compose 中的服务命名
- 环境变量命名
- HA 与 SimuHome 的 API 协议
- 自定义集成逻辑
- 持久化目录语义
- 操作文档与部署流程
- 关键实验输入输出定义

### 在过渡过程中允许变化的部分

以下部分可以调整：

- 宿主机路径
- 宿主机操作系统
- 端口暴露与反向代理策略
- SimuHome 是源码运行还是容器运行
- 是否增加辅助服务

### 过渡过程中的风险控制

为了使迁移可靠，必须遵守以下规则：

1. 所有部署配置都应为文本文件，并纳入版本控制。
2. 避免写大量只适用于 Windows 的临时 hack。
3. 不要把 Windows 特有路径写进集成逻辑。
4. HA 自定义集成不应假设本地文件系统结构固定。
5. 早期临时联通方案应尽早升级为正式集成逻辑。
6. 只有在科研需求明确时，才引入新的支撑服务。
7. 对快进时间、workflow、reset 等能力，应明确记录实验控制日志。
8. 任何迁移都应通过固定实验样例做一致性验证。

## 故障恢复策略

可靠科研平台不能只考虑“正常运行”，必须提前定义异常情况下如何处理。

### 服务故障分类

#### 1. Home Assistant 重启

影响：

- 前端展示中断
- Recorder 暂时中断
- 自定义集成重新加载

要求：

- HA 重启后应自动重新连接 SimuHome
- HA 恢复后应重新同步当前 home snapshot
- 如果实验继续运行，必须记录“HA 记录存在缺口”

#### 2. SimuHome 重启

影响：

- 仿真状态可能丢失
- 虚拟时间可能重置
- 工作流执行上下文可能丢失

要求：

- 平台必须能明确识别 SimuHome 是否发生过重启
- 如果没有恢复机制，则应直接把该次实验标记为失败或中断
- 不允许在状态丢失后由 HA 静默继续记录，伪装成同一实验仍在继续

#### 3. 网络短暂断连

影响：

- HA 暂时无法读取或控制 SimuHome

要求：

- 应允许自动重连
- 应区分“控制失败”“状态未知”“实验终止”三种不同语义

### 当前阶段故障处理原则

当前阶段先采取保守策略：

- HA 重启：允许恢复
- 网络抖动：允许重连
- SimuHome 重启：默认判该次实验中断，除非后续明确设计了恢复协议

这虽然严格，但更符合科研可靠性要求。

## 迁移验收标准

未来从 Windows/WSL2 迁移到 Linux 时，不能只检查“服务起来了”，还必须做一致性验证。

建议至少准备一组固定实验样例，并检查以下内容：

### 基础一致性

1. 同一 `home_config` reset 后，初始设备数量、房间数量、属性快照一致。
2. 同一设备控制命令执行后，关键属性变化一致。
3. 同一 workflow 运行后，最终状态一致。

### 时间一致性

1. 同一 `base_time` 下，虚拟时间起点一致。
2. 同一 `fast_forward_to` 目标 tick 后，关键房间环境状态一致。
3. 同一调度 workflow 在同一虚拟时间条件下，执行结果一致。

### 记录一致性

1. HA 侧至少能看到相同的关键实体状态变化。
2. SimuHome 侧能够导出相同的关键仿真轨迹。

### 失败判定

如果以上一致性不能满足，应视为迁移未完成，而不是“平台大体可用”。

## 推荐的最终落点

本项目的推荐最终落点是：

- 当前使用 Windows + Docker Desktop + WSL2 作为结构化开发环境
- 在当前阶段就按未来 Linux 平台可迁移的方式组织架构
- 当 HA 与 SimuHome 的交互契约稳定后，再迁移到 Linux 正式平台

这样做可以在以下几个维度取得平衡：

- 当前落地效率
- 未来可靠性
- 迁移风险可控
- 科研复现性
