## 4. 温度动力学与 tick 时间的关键结论

查过 SimuHome 相关文档和代码后，确认默认时间设定是：

```text
1 tick = 0.1 虚拟秒
200 ticks = 20 虚拟秒
30000 ticks = 3000 虚拟秒 = 50 分钟
```

旧温度公式的问题：

```text
旧设定：
  空调 ±0.3°C/tick

换算：
  1 tick = 0.1s
  ±0.3°C/tick = ±3°C/s

结果：
  200 ticks = 20s 内降温过大
  明显不符合现实尺度
```

新温度公式：

```text
new_temp =
  current
  + device_effect_per_second * fan_multiplier * tick_interval_seconds
  + (baseline - current) * natural_rate_per_second * tick_interval_seconds
  + adjacent_exchange_per_second * tick_interval_seconds
```

当前示例参数下，大致结果是：

```text
200 ticks = 20s
  客厅空调制冷：24.0 -> 约 23.9

2000 ticks = 200s
  客厅空调制冷：24.0 -> 约 23.0

30000 ticks = 50min
  客厅接近 21.21
  卧室接近 25.32
```

注意：当前 30000 ticks 后，客厅目标 20±0.8 仍未完全达成，卧室目标 26±0.8 已达成。因此一次运行结束通常是：

```text
达到 max_ticks 上限
不是锁死
也不是两个目标都完成
```

## 5. 前端“曲线不动 / 只剩三条线”的原因

本轮排查过两个现象。

第一个现象：图上像只有三条线。

```text
原因：
  bathroom
  kitchen
  unassigned

这三个区域都没有有效温控设备，温度都保持 24.00 左右。
三条线重叠，看起来像一条灰线。

因此可见线条大致是：
  客厅蓝线
  卧室红线
  三个 24°C 区域重叠灰线
```

第二个现象：跑 30000 ticks 时，曲线像一动不动。

```text
原原因：
  TemperatureTrace 只保留 400 条采样

后果：
  30000 ticks 实际只画最后 400 ticks
  最后 40 秒温度变化很小
  所以肉眼看起来接近水平线

修正：
  max_samples 改到 50000
  前端 x 轴显示真实 tick 范围
```

## 6. api_queue 当前结论

已新增分析文档：

```text
sandbox/firstdemo/api_queue机制分析_结合SimuHome与firstdemo.md
```

核心判断：

```text
api_queue 的价值不是“多一个队列”
而是让外部动作进入时间控制核
在 tick 边界统一生效
```

SimuHome 原始结构大致是：

```text
Home.queue_api(...)
  ↓
api_queue
  ↓
simulation_loop
  ├─ process_time_aware_devices
  ├─ process_aggregators
  ├─ process_scheduler_queue
  └─ process_api_queue
```

firstdemo 当前状态：

```text
5_time_kernel.py
  已有 api_queue
  已有 submit_command
  已有 _process_api_queue

但：
  sandbox.py / server.py / demo_interactive.py 的主要动作路径
  仍然有直接调用 CommandGateway 的情况

结论：
  api_queue 结构已存在
  但还不是主路径
```

下一步要把它改成：

```text
外部动作
  ↓
Sandbox.submit_device_action(...)
  ↓
TimeControlKernel.api_queue
  ↓
tick 边界
  ↓
CommandGateway.execute(...)
  ↓
command_result / event_log
  ↓
WorldState
```

## 7. AGENTS.md 风格讨论

本轮还讨论了两个文档的风格差异：

```text
sandbox/firstdemo/首版沙箱建模层次.md
oldmcp/doc/6_myserver工具边界与REST映射分析.md
```

关键结论不是简单的“文件性质不同”，而是：

```text
早期 Codex 文档容易进入咨询报告模式
  ↓
大量“不是 A，而是 B”
大量碎片化 bullet
大量短句分点
推理链被切断

ClaudeCode + DeepSeek 那篇更像工程规格书
  ↓
总结构
层级图
条件分叉
输入输出
读写边界
文件映射
层层递进
```

建议往 `AGENTS.md` 里补充的方向：

```text
文档表达规则 =
  少碎片 bullet
  少口号式“不是……而是……”
  多递进结构图
  多条件分叉
  多因果链
  每节落到工程后果
```

可加入类似约束：

```text
复杂问题不要写成一堆同级 bullet。
应该写成有层级、有条件、有因果、有落点的结构图。

段落负责解释为什么。
代码框负责呈现结构关系、状态流转、条件分叉、依赖方向。

如果去掉 bullet 后，句子之间没有清晰因果、层级或条件关系，
说明这个分点是碎片化的。
```
