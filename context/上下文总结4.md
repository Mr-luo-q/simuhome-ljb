## 1. 本轮主线从“2D 编辑器底层正确性”切换到了“3D 观察视图首版落地”

在 [上下文总结3.md](/d:/D_coderesource/simuhome/context/上下文总结3.md) 里，核心问题是：

1. 房间矩形如何作为真相
2. 墙如何运行时派生
3. 共享墙拖动如何回写到多个房间边界

而这一轮开始后，用户的重心明显转向了：

> 2D 的基本结构已经有了，现在应该推进 3D，并且先做首版简约、可靠、米家风格的结构观察视图。

这里的几个重要前提被反复确认过：

1. 2D 负责编辑，3D 负责观察
2. 首版 3D 不追求真实材质，不追求户外背景一比一
3. 首版 3D 先只处理房间、墙体、门洞
4. 窗、家具、门片动画都可以暂时不做
5. 代码实现要符合现有 viewer 的设计原则，也要符合高内聚、低耦合的工程原则

也就是说，这一轮的 3D 不是一个独立新项目，而是：

> 建在 `viewer` 现有 2D 数据真相之上的首版 3D 观察层。

## 2. 首版 3D viewer 的总体分层和接口边界已经形成

这一轮里，用户给过一次比较完整的实施计划，后面代码也大致按这个方向落地。当前形成的职责分层包括：

### 2.1 `scene-3d-derive.js`

职责：从共享场景真相派生 3D 所需的轻量结构对象。

当前已经明确：

1. 输入仍然是统一的 `scene`
2. 3D 不额外维护第二套持久化墙表或 mesh 表
3. 3D 的墙、门洞、地面都是运行时派生结果

它当前已经在做的内容包括：

1. 解析 `rooms[]`
2. 调用 2D 的墙段派生逻辑得到唯一墙段
3. 只筛选 `door` 类型 opening
4. 通过把墙切成实体段和过梁段来形成门洞，而不是做布尔挖洞

### 2.2 `viewer-3d.js`

职责：Three.js 侧的场景、相机、材质、重建、销毁与重绘。

这里已经形成一个很明确的工程边界：

1. 它吃派生后的 3D 数据
2. 它不直接理解 2D 编辑语义
3. 它不调用 `applyWallChainDelta` 或 `applyOpeningMove` 这类编辑函数
4. 它只负责“怎么显示”和“怎么观察”

### 2.3 `viewer-3d-style.js`

职责：3D 视觉常量层。

这一层在本轮中越来越重要，因为：

1. 墙体薄厚
2. 墙透明度
3. 地板统一颜色
4. 背景颜色
5. 边线颜色

这些都应该被收束到风格层，而不是散在渲染函数各处。

### 2.4 `app.js`

职责：2D 与 3D 的装配层，而不是 3D 细节实现层。

经过本轮调整之后，一个非常重要的判断已经形成：

> `app.js` 可以初始化 3D，但不应该成为 Three.js 细节堆积的地方。

## 3. 首版 3D 一开始是“能显示”，但远没有“显示对”

这一轮里，最值得保留的一个现实判断是：

> 3D 首版并不是“代码一接上就结束了”，而是经历了多轮“能跑 -> 发现根因问题 -> 重构 -> 再看效果”的过程。

用户后面明确指出过多个问题：

1. 2D 和 3D 曾经一起空白过
2. 3D 背景和风格不满意
3. 相机行为不符合直觉
4. 墙体透明规则存在明显逻辑错误
5. 地板统一颜色虽然改过几次，但因为底层渲染结构有问题，屋内屋外仍会显示成不同色块

这意味着本轮 3D 的工作不能被简单总结为：

1. “写了一个 3D 模块”
2. “把 Three.js 接上了”

更准确的描述应当是：

> 这一轮逐步暴露并处理了多个 3D 渲染与交互层面的根因问题。

## 4. 最严重的一次故障：2D 和 3D 同时空白，后来被定位为模块加载根因

本轮最重要的一次技术排错是：

> 为什么页面里 2D 和 3D 会同时空白。

一开始表面现象像是：

1. 3D 没渲染出来
2. 2D 也没有首帧内容
3. 页面只剩静态骨架和背景

后来经过分析确认：

### 4.1 根因不是 scene 文件坏了

当时已经验证过：

1. `mijia_scene_2d.json` 可正常解析
2. `rooms / openings / furniture` 都还在
3. `app.js`、`scene-derive.js`、`scene-edit.js`、`viewer-3d.js` 本地语法检查都能过

### 4.2 真正根因是 `OrbitControls` 的 CDN 依赖树在浏览器模块解析阶段就炸了

当时 `viewer-3d.js` 顶层直接引了 CDN 版 `OrbitControls`，而那个远端模块内部仍然写着：

- `from 'three'`

在当前页面里又没有 import map、bundler 或 ESM 重写机制，所以浏览器会在 ES module 加载阶段直接失败。

因为 `app.js` 顶层 import 了 `viewer-3d.js`，所以这会连带导致：

1. `main()` 根本没跑起来
2. 2D 首帧也没机会渲染
3. 3D 当然也没初始化

### 4.3 这次排错最后形成了一个很重要的工程结论

> 3D 依赖失败不能再把 2D 一起拖死。

也就是说，这一轮不仅修掉了一个模块依赖问题，还顺手压实了一个装配原则：

1. 2D 启动必须能独立成功
2. 3D 应该被当成可隔离子系统来初始化

## 5. 3D 相机与交互逻辑经历过一次“从伪平移到真正观察相机”的升级

后面用户对 3D 的主要不满之一是：

1. 不能旋转展示
2. 滚轮缩放没问题，但拖动手感不对
3. 往下拖，显示反而往上跑，不符合直觉

这些问题后来被识别为：

### 5.1 一开始的实现并不是“真正的 3D 观察相机”

旧版逻辑更像是：

1. 固定俯视角
2. 改 target 做伪平移
3. 不支持真正围绕房屋的直观旋转观察

也就是说，它不是 Orbit/Map 那种观察器，只是一个带缩放的观察框。

### 5.2 后来重构成了真正围绕房屋中心的旋转观察相机

当前已经形成的结构是：

1. 使用透视相机
2. 用 `azimuthAngle / polarAngle / radius` 管理观察状态
3. 鼠标拖拽时改变相机方位，而不是拖着房屋在平面里“漂”
4. 滚轮控制相机半径，完成缩放

### 5.3 拖动方向还专门做过一轮纠正

后面用户又明确指出：

> 现在往下拖，显示界面反而往上走，不符合直觉。

这说明本轮里“交互手感”已经被当成一等问题来对待，而不是“只要能转就行”。

最后做过一次明确修正：

1. 背景改纯白
2. 竖直拖拽方向反过来，使其更接近直觉

这类问题虽然看上去像细节，但它背后其实体现出一个很重要的判断：

> 首版 3D 不仅要能显示，还要开始对用户直觉负责。

## 6. 墙体透明度问题被明确识别为“逻辑问题”，不是单纯数值问题

用户对 3D 墙体的另一个强烈不满是：

1. 近的墙反而透明度低
2. 远的墙反而更虚
3. 房子在不同屏幕位置时可见性会明显不一致

这个问题后来被定位为：

### 6.1 一开始透明判定和当前相机朝向没有真正绑在一起

也就是说，早期透明规则更接近：

1. 按世界坐标或 bounds 静态判断“哪面墙是前面/后面”
2. 但没有根据用户此刻相机真正站在哪一侧来判断

这样一旦相机观察方向变化，透明逻辑就会失真。

### 6.2 后来一度改成“按当前相机位置判定外墙透明”

这一版的目标是：

1. 当前相机面对的外侧墙更透明
2. 其他墙更实

从结构上说，这一步很重要，因为它把：

1. 墙透明度
2. 相机位置
3. 墙是否外墙

三者真正接到了同一条逻辑上。

### 6.3 再往后，用户视觉方向又变了：不再强调“前后墙差异透明”，而是要更米家式的统一轻薄感

后来用户进一步要求：

1. 所有墙都做薄
2. 所有墙透明度都稍高一些
3. 不要再强调近墙远墙的明显不同

因此后续风格层又被收敛成：

1. 更薄的视觉墙厚
2. 更统一的高透明度
3. 更轻的边线

这个演化过程必须保留，因为它说明：

> 墙体透明不仅是技术问题，也是风格取向问题；它会随着用户对“米家感”的判断继续调整。

## 7. 地板颜色问题最后被证明是一个“渲染结构问题”，不是颜色常量问题

这一轮里，地板颜色改过很多次：

1. 淡蓝
2. 浅棕
3. 浅灰

用户又多次强调：

1. 地板颜色要写死成统一值
2. 房屋内外整块底板都要统一
3. 不要在代码里这里写一个棕色，那里再写一个棕色

这件事最后出现了一个非常典型的“不要头痛医头、脚痛医脚”的案例。

### 7.1 一开始表面现象像是“还有一处颜色没改到”

因为用户看到：

1. 室内地板和门口外沿那一块颜色不一样
2. 直觉上像是某个地方颜色常量没同步

### 7.2 后来真正查清后发现：不是颜色值问题，而是叠了两层地面

当时 3D 里实际上同时画了：

1. 一整块 `base` 底板
2. 每个房间自己的 `floor` 填充层

哪怕它们传的颜色是一样的，只要：

1. 透明度不同
2. 叠层关系不同
3. 受光方式不同

最后屋内屋外看起来就必然不一样。

### 7.3 这次排错最后形成了一个非常关键的结构修正

后来地板逻辑被改成：

1. 整块底板只有一层真正负责填充颜色
2. 房间层不再单独铺第二层填充
3. 房间层只保留轮廓辅助线

同时颜色入口也被收敛成：

1. `floorColor`
2. `baseColor`

统一由风格层控制

这个过程本身很值得保留，因为它正好体现了用户反复强调的工作方式：

> 看到颜色不一致，不要只改颜色值；先查清到底是常量问题还是渲染结构问题。

> 建立在统一场景真相之上的首版简约 3D 结构观察器。

## 11. 这轮对“少说废话”和“多举例子”的理解也被校准得更准确了

这两条虽然看起来像风格偏好，但在本轮里其实也被说得很具体。

### 11.1 “少说废话”不是少沟通，而是少空话

已经明确：

1. 不是不要解释
2. 不是不要汇报
3. 而是不要堆砌无用标题、无用套话、正确的废话

更好的表达顺序应当是：

1. 问题是什么
2. 原因是什么
3. 准备怎么改
4. 怎么验证
5. 结果如何

### 11.2 “多举例子”不是泛泛举例，而是分析别人内容时要靠具体例子讲透

当前这条已经被限定得很明确：

1. 分析别人的代码
2. 分析别人的文章
3. 分析别人的设计方案
4. 分析别人的技术路线

这时不要只说抽象结论，而要举：

1. 某段代码为什么这样写
2. 某个函数承担了什么职责
3. 某个模块边界如何划分
4. 某篇文章的哪段结论如何落到当前问题上
5. 两个实现的差异具体体现在哪

这条规则后面在做调研、读代码、拆论文时都应该继续沿用。

## 12. 目前最需要保留的几条稳定结论

为了方便后续新对话快速续上，这一轮最重要的稳定结论可以压缩成下面几条。

### 12.1 关于 3D viewer 的定位

1. 3D 是观察层，不是编辑层
2. 3D 是结构观察器，不是高真实感渲染器
3. 首版 3D 先只负责房间、墙体、门洞

### 12.2 关于 3D 的工程边界

1. 3D 不单独维护第二套场景真相
2. 3D 基于统一 `scene` 运行时派生
3. `app.js` 负责装配，不应堆积大量 Three.js 细节

### 12.3 关于本轮最关键的技术排错经验

1. `OrbitControls` 的 CDN 依赖树问题，曾导致 2D/3D 一起空白
2. 视觉问题常常不是常量问题，而是渲染结构问题
3. 地板内外颜色不一致的根因，最终被证明是双层地面叠色，而不是颜色值没统一

### 12.4 关于 3D 当前的风格状态

1. 背景白色
2. 墙体整体偏薄、偏透明
3. 地板整块统一单色
4. 当前最后一次统一色是浅灰色
5. 房间层只保留轮廓辅助线，不再单独铺第二层地面填充

### 12.5 关于工作方式

1. 不要先打补丁，再找理由
2. 要先分析清楚根因，再决定改哪一层
3. 改完后不要停在代码层，要尽量运行、观察、截图、继续修正

## 13. 对后续新对话最重要的提醒

如果后续继续推进 `viewer`，最重要的是不要回到下面几种错误路线：

### 13.1 不要把 3D 问题都当成“再调几个参数”

这一轮已经反复证明：

1. 有些问题是依赖树问题
2. 有些问题是相机模型问题
3. 有些问题是透明判定逻辑问题
4. 有些问题是渲染层级或叠层结构问题

如果只是调几个 opacity 或 color，很容易继续在表面兜圈子。

### 13.2 不要忽略实际界面验证

仅看代码是否无报错，不足以说明前端、2D/3D viewer、渲染或交互类任务已经完成。  
这类任务后面应尽量继续保持：

1. 运行
2. 观察
3. 截图
4. 修正

### 13.3 不要把 `AGENTS.md` 写回大段空话

这一轮已经把它压成比较合适的规则密度。后面如果再改，应尽量保持：

1. 短
2. 硬
3. 可执行

而不是重新膨胀成泛泛而谈的说明文档。
