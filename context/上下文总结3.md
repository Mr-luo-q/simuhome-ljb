## 3. src 下各模块的职责已经被明确过

这轮对话中，用户明确要求梳理 `src` 下几个文件分别干什么。

目前形成的职责划分如下。

### 3.1 `scene-store.js`

职责：前端状态仓库。

它维护：

1. `persistedScene`
2. `draftScene`
3. `saveStatus`

它的核心意义是：

1. 将“已保存版本”和“当前编辑草稿”分开
2. 让拖拽操作只改 `draftScene`
3. 让显式保存后再把 `draftScene` 提升为 `persistedScene`

这对应用户非常明确的一条要求：

> 编辑不应自动写回，必须有草稿态与已保存态之分。

### 3.2 `save-client.js`

职责：前端和本地服务之间的 IO 层。

它目前主要负责：

1. `loadScene()`
2. `saveScene(scene)`

它不处理空间语义，不处理渲染，只做加载和保存。

### 3.3 `view-projector.js`

职责：世界坐标和画布坐标的投影层。

这个模块是在处理“拖外边界时整图漂移”问题时新增的。

它的核心作用是：

1. 从房间坐标计算整体 bounds
2. 生成 `scale / offsetX / offsetY`
3. 提供 `point()` 与 `worldFromScreen()`
4. 支撑“冻结投影”的视图策略

### 3.4 `scene-derive.js`

职责：从底层真相派生运行时几何。

它当前主要负责：

1. 从 `rooms[]` 派生最小墙段 `wallSegments`
2. 派生视觉上连续的墙链
3. 派生命中与编辑要用的墙链
4. 把 `openings[]` 映射到派生墙段上

这层非常关键，因为它在回答：

> 真相文件里没有“墙段表”，那浏览器到底画什么、点什么、拖什么？

### 3.5 `scene-edit.js`

职责：把交互动作回写成对 `draftScene` 的修改。

它目前负责：

1. 点到线段距离等命中辅助
2. 拖门窗时修改 opening 的 `offset`
3. 拖墙链时修改房间边界

这一层是本轮讨论中问题最多、回退最多的层。

### 3.6 `app.js`

职责：前端主控层。

它当前同时承担：

1. 页面入口
2. DOM 绑定
3. 交互事件分发
4. 渲染调度
5. 部分具体绘图逻辑
6. 保存与重置按钮行为

所以它现在的准确定位是：

> 前端入口 + 交互控制器 + 渲染调度器 + 局部 renderer

用户后来专门问过这件事，因此这个判断应视作已稳定上下文。

## 4. 本轮首先解决的是“外边界拖动时整图漂移”问题

用户指出：

> 拖动左侧边界墙时，右侧也看起来在动。

一开始容易误以为是共享墙联动算法有问题，但经过分析后，真正原因被定位为：

### 4.1 原因不是房间几何被错误联动，而是投影层在每帧重算

在旧版 [app.js](/d:/D_coderesource/simuhome/sandbox/viewer/src/app.js) 中：

1. `refresh()` 每次都会重新渲染
2. 渲染时又会重新按最新房间 bounds 计算 projector
3. 一旦拖动外边界，`minX / maxX / width / height` 变化
4. 于是整个 scene 会重新缩放和重新居中
5. 屏幕上就表现成“右侧似乎也在移动”

也就是说，这是：

> **投影层 bug**

而不是：

> **房间矩形联动 bug**

### 4.2 解决方案：冻结视图投影

后来加入了 `view-projector.js` 和 `viewState`，实现思路是：

1. 初次加载时按当前 scene 计算一次 projector
2. 拖拽过程中不再每帧按最新 bounds 重算
3. 保存成功、重置、窗口 resize 时再允许重算

这一步对外边界问题是有效的，用户后面也明确承认：

> 这次改完，边界墙的问题解决了。

这说明：

1. 冻结投影策略方向正确
2. 投影层问题已经不是当前最核心矛盾

## 6. 在“共享墙”问题上，曾出现过一次明确误判

这是本轮必须保留下来的重要教训。

### 6.1 当时的误判

为了解决共享墙错位，我一度把 `scene-derive.js` 里的“编辑链”改成按精确房间对分组。

也就是说，像 `x = 4.8` 这一整条连续共享竖墙，本来视觉上是一整列连续墙：

1. `bedroom:right <-> unassigned:left`
2. `bedroom:right <-> kitchen:left`
3. `bedroom:right <-> living_room:left`
4. `bathroom:right <-> living_room:left`

我当时把它拆成了四条独立编辑链。

### 6.2 用户的明确纠正

用户立刻指出：

> 你这不是瞎改吗！越改越乱，一段共享墙怎么能变成四条独立编辑链？共享墙当然是一拖要同时移动！

这句话非常关键，因为它明确固定了一个设计原则：

> **一条连续共享墙，在用户语义上应作为整体编辑对象，而不是按房间对碎裂。**

这个原则后面不能再被推翻，否则会再次走回误判路线。

### 6.3 因此作出的回退

后来我把这次误判撤回了：

1. 不再按精确房间对拆编辑链
2. 重新让连续共享墙作为一个整体联动对象

所以当前上下文中，“连续共享墙整体联动”已经是明确结论，而不是待讨论选项。

## 8. `scene-edit.js` 的底层回写逻辑在本轮中被重构过一次

为了响应用户“改底层”的要求，本轮对 [scene-edit.js](/d:/D_coderesource/simuhome/sandbox/viewer/src/scene-edit.js) 做过一次更本质的重构。

### 8.1 旧逻辑的问题

旧逻辑本质上是：

1. 找到受影响的 boundary
2. 直接改某个房间的 `x / y / width / height`

例如：

1. `left` 边被拖了，就改 `x` 和 `width`
2. `right` 边被拖了，就改 `width`

这种写法的问题是：

1. 它是局部命令式修补
2. 很难统一表达“多个房间共享一条边时”的一致规则
3. 在共享墙、T 形结构、外边界和局部凹凸结构里容易持续出错

### 8.2 新逻辑：先转房间边界，再统一重建矩形

后来 `scene-edit.js` 被重构成了“边界模型”思路：

新增了这些函数：

1. `getRoomEdges(room)`
2. `applyRoomEdges(room, edges)`
3. `collectWallChainImpacts(scene, wallChain)`
4. `buildRoomEdgeOverrides(scene, wallChain, delta)`

新逻辑大致是：

1. 先把房间转成 `left / right / bottom / top`
2. 先收集墙链真正影响到的所有房间边界
3. 生成每个房间的边界覆盖值
4. 最后一次性重建 `x / y / width / height`

这一层的意义在于：

> 共享墙和外边界现在终于走上了同一套底层几何规则，而不再是各自 patch。

### 8.3 这个重构的定位

需要特别注意：

这次重构并不意味着“共享墙问题已经完全解决”，而意味着：

1. 我们已经把底层逻辑从局部修补推进到了统一边界模型
2. 以后如果再错位，至少不是因为还在用最原始的 `width += delta` 那种局部命令式写法

这是一个很重要的结构性进展。

1. 房间矩形是底层真相
2. 墙不是手工维护真相，而是运行时派生
3. 门窗挂在房间边界语义上，不挂死到某个固定墙段 ID

1. 一条连续共享墙应整体联动拖动
2. 不应按房间对把它拆成多个独立编辑链

2. 必须把“墙拖动”统一映射为“房间边界如何变化”

### 12.6 关于当前状态

1. 结构比最初稳定了很多

3. 保存链路、草稿态链路、冻结投影链路已打通

> 这一轮对话把 `sandbox/viewer` 从一个平铺、混杂、容易误判的前端原型，推进成了一个具备明确目录结构、模块分层、草稿态保存链路和冻结投影能力的首版 2D 空间编辑底座；与此同时，这一轮也暴露并确认了一个更深的底层问题：共享墙拖动的真正难点不在“是不是一整条联动”，而在“如何把连续共享墙的移动稳定、统一地回写成多个房间矩形的边界变化”。围绕这一点，曾经出现过把共享墙错误拆成多个独立编辑链的误判，后来已被用户明确纠正。当前代码已经开始从局部命令式 patch 迈向统一边界模型，但共享墙相关的几何与拓扑回写规则仍未彻底收敛，因此后续新对话最重要的不是继续局部修补，而是沿着“房间边界真相 -> 墙段派生 -> 编辑链语义 -> 边界覆盖回写”这条底层路线继续推进。
