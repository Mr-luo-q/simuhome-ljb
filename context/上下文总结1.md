## 1. 项目大方向：我们不是在补一个普通 benchmark，而是在升级 benchmark 的世界模型

当前项目的核心目标，已经不再被理解为：

- 再补一批智能家居任务
- 再做一个工具调用 demo
- 再用 Home Assistant 做一点实验

而是被理解为：

> 重新定义智能家居 benchmark 背后的世界模型，让 benchmark 不再只是“房间-设备-状态-工具调用”，而成为一套具备空间语义、时间连续性、长期生活过程和现实迁移潜力的实验世界。

这条判断来自于对四篇重点参考工作的连续梳理。

涉及的四篇主要论文是：

- `HomeBench`
- `SimuHome`
- `PersonalHomeBench`
- `SMH-Bench`

在多轮讨论中，已经形成了一个比较稳定的共识：这四篇工作虽然各有推进点，但整体仍有一个共同上限。

### 1.1 对四篇工作的共同认识

#### HomeBench

我们认为 `HomeBench` 的优点是：

- 大规模任务构造
- 设备控制覆盖面广
- 单设备、多设备、有效/无效指令评估清楚

但它的主要边界也很明显：

- 空间语义弱
- 时间连续性弱
- 长期用户建模不是重点

因此它更像“强控制与理解基线”，但不是“空间化生活环境 benchmark”。

#### SimuHome

`SimuHome` 在我们讨论中一直占据很关键的位置，因为它是四篇里最接近“动态环境”的一篇。

它的突出点包括：

- 引入环境变量
- 有时间推进
- 有工具交互
- 有状态验证
- 有调度与隐含意图问题

我们后面很多关于“时间机制”的讨论，实际上都在以 `SimuHome` 为参照。

但我们也明确认为它还不够：

- 它的空间建模没有真正成为主结构
- 虽然有动态时间和环境，但长期持续生活过程并没有真正成为环境主线
- 空间拓扑和人物真实活动还没有被强吸收进环境本体

也就是说，它已经把 benchmark 从静态状态机推进到动态环境，但还没有推进到“空间化仿生环境”。

#### PersonalHomeBench

`PersonalHomeBench` 对我们的作用，主要在于提醒我们：

- 个性化是智能家居 benchmark 的重要方向
- 长期上下文和家庭背景不是附属信息，而是服务能力的一部分
- persona、记忆、背景、历史事件这些内容能显著影响智能家居任务难度

这篇工作和我们后面提出的“长期主动智能服务 benchmark”主线关系很近。

但我们同时也判断：

- 它更偏个性化智能体评估
- 环境动力学不够强
- 空间执行语义也不够强

因此它提供了“长期个性化”的方向，但还没有给出“空间化、时空一致”的世界本体。

#### SMH-Bench

`SMH-Bench` 的贡献在我们看来是：

- 更强调环境接地
- 任务分类更细
- 家庭复杂度更分层
- 引入了 `HomeEnv` 作为状态化、可执行环境

这使它比更早的 benchmark 更接近成熟形态。

但我们后面仍然明确指出：

- 它主要还是沿着“结构化环境 + 工具接口 + 任务验证”的路线前进
- 长期共居过程、3D/2D 双表示环境、统一现实迁移接口，都还没有真正成为主贡献

### 1.2 基于四篇工作的总判断

综合这四篇工作之后，我们已经稳定下来的核心认识是：

> 现有工作已经证明了智能家居 benchmark 值得做，也证明了设备控制、环境变量、个性化和环境接地都重要；但它们整体上仍然主要停留在“结构化状态 + 设备调用 + 任务验证”的框架里，还没有真正建立一套兼具空间真实、时间连续、长期共居和现实可迁移性的统一 benchmark 世界模型。

这句话几乎是后面所有讨论的起点。

## 2. 关于论文主线，我们最终是如何重组贡献点的

一开始，想法其实是散的，包含很多点：

- 3D 和 2D 联动
- 空间语义
- 长期交互
- 用户建模
- 多设备、多任务并发
- Home Assistant
- MCP
- 现实迁移
- 沙箱

如果直接把这些点堆进论文，贡献会显得发散。因此后面逐步收敛成了第 7 篇文档里的三条主线。

### 2.1 第一条主线：空间化仿生环境

这条线最终收敛为：

- `3D 校准 + 2D 执行`
- 3D 负责结构合理性、设备位置合理性、轨迹观察、空间关系校验
- 2D 负责低成本、高吞吐、可重复的大规模测评

这里有一个非常重要的讨论结论，后来多次被重复确认：

> 3D 不是为了做一个好看的展示页面，而是为了校准环境；真正的 benchmark 主战场应是 2D。

这是我们反复避免“3D 只是 demo”质疑时的核心表述。

### 2.2 第二条主线：长期主动智能服务 benchmark

这条线来自于我们对“真实智能家居系统应该越用越聪明”的理解。

我们明确认为：

- 之前那几篇 benchmark 大多还是片段式任务
- 真实智能家居不是每次都从零开始理解用户
- 真正有价值的能力，应该包括长期使用中的用户建模和主动服务

所以后面提出：

- 保留 `episodic layer`
- 增加 `long-horizon layer`

也就是：

- 短程任务评测仍然存在
- 但还要有长时间连续生活过程中的评测

并且这里的人类侧不应是一个静态背景，而应由某种人物系统驱动。

### 2.3 第三条主线：统一接口与现实迁移

围绕 `Home Assistant`、MCP 和我们自己的 `myserver`，后面形成了一个更成熟的判断：

- 我们的贡献不是“重新发明一个万能 MCP”
- 真正的贡献应该是“统一接口语义”

也就是说：

- 虚拟 2D 环境有自己的实现
- 3D 校准环境有自己的实现
- Home Assistant backend 也有自己的实现

但它们应当：

> 对大模型暴露一致的 agent-facing 语义

这也是为什么后来我们一直强调：

- 统一语义优先于统一实现

## 3. 关于沙箱，我们是如何一步步讨论到“时间控制核”的

这部分是整个讨论中最重要的一段，因为用户最后特别希望保留这一块的思路演化，而不是只看最后结论。

### 3.1 最初的起点：沙箱不是只谈时间

一开始我们在写第 8 篇时犯过一个错误：

- 太早从“时间机制”开始讨论

用户明确指出：

> 主体应该是完整沙箱如何实现，而不是一上来先讨论时间机制。

这个纠偏非常关键。它让后面的逻辑从：

- “先看时间怎么流”

变成：

- “先明确沙箱里到底有什么，再看时间如何驱动它们”

这也是后来第 8 篇被重写的重要原因。

### 3.2 我们对“沙箱包含什么”的第一次成型理解

在用户连续补充后，我们逐渐明确：

沙箱至少应包含：

- 房间及其主结构与连通关系
- 设备状态机
- 环境变量
- 人物角色
- 轨迹引擎
- 任务执行层
- 虚拟时间
- replay / snapshot / restore

其中用户特别强调了几个点：

#### 环境计算机制不能没有

用户后来明确提醒：

> 这个沙箱没有那么简单，除了设备状态机开闭以外，还必须有一套环境计算机制。

这里最核心的是：

- 温度
- 湿度
- 光照

而且这些变量会随时间变化，并且与设备和任务有联动。

#### 任务执行层不能等价于智能调度器

用户同时也指出：

> 任务执行层可以存在，但不意味着它应该替模型做 schedule。

因此后面我们明确把任务层边界锁成：

- 可以执行
- 可以跟踪
- 可以并行
- 可以产生事件

但不能：

- 自动做高层调度求解
- 自动做完整多设备 orchestration

### 3.3 关于人物层，我们是怎么从“绑在任务里”改成“单独成层”的

这部分是一次很重要的结构调整。

最开始第 8 篇里曾经写成过：

- `人物与任务运行时层`

但后来用户直接提出异议：

> 人物应该单独拆出来，因为它应当和轨迹引擎联系在一起，也方便渲染。

这个提醒让我们重新想清楚：人物不是一个附属对象，它天然连接：

- 空间结构
- 轨迹引擎
- 交互入口
- 2D/3D 渲染

因此后来逐步形成明确判断：

- 人物层必须独立
- 并最终命名为 `人物与轨迹层`

而且这里还进一步讨论了人物层是否应该把 persona、偏好、记忆、对话上下文全都包进去。

最终比较稳定的判断是：

- 人物层主要负责实体、位置、轨迹和渲染语义
- persona、偏好、历史记忆、交互上下文等，更适合作为外部配置注入

### 3.4 关于任务、事件和时间，为什么后来拆成现在这样

这个问题我们讨论得最细。

用户后面提出一个关键直觉：

> 时间机制应该独立，其他层都受时间机制驱动；事件和任务作为一层更合理。

围绕这个直觉，我们实际上比较过多种拆法：

- 人物独立，任务单独，时间和事件合并
- 人物独立，任务并入时间事件层
- 人物独立，任务与事件成层，时间机制独立

最后用户明确拍板的方向是：

- 人物独立
- 任务与事件成层
- 时间机制独立

也就是说：

- `人物与轨迹层`
- `任务与事件运行时层`
- `时间控制核`

这个讨论的关键不只是名字变了，而是职责真的被重新划分了。

#### 人物与轨迹层负责什么

- 人物实体
- 当前位置
- 当前房间
- 当前锚点
- 朝向
- 活动标签
- 轨迹
- 2D/3D 共用渲染语义

#### 任务与事件运行时层负责什么

- 任务对象
- 持续任务 / 定时任务 / 长期任务
- 并行状态
- 任务阶段切换
- 事件生成和事件消费

并且用户后面明确确认了它的边界应该是：

> `仅执行型`

#### 时间机制后来为什么被提升为“时间控制核”

这个结论是后面多轮讨论中最稳定的一条。

一开始只是说：

- 时间机制很关键

后来逐渐升级为：

- 时间机制不该是普通并列层
- 它应当成为整套沙箱的“核心控制”

最终收敛成一句明确的话：

> 时间机制应成为整套沙箱的 `时间控制核`

这个表述背后的逻辑是：

- 空间层本身只是静态骨架
- 设备与环境动力学只有放进时间里才有意义
- 任务与事件的生命周期本质上由时间推进触发
- 快进、暂停、回放、长期交互、Gym-friendly step 全都依赖统一时间控制

因此第 8 篇后来被重写成：

- 先讲世界内容层
- 再讲时间控制核
- 最后讲 2D/3D 与接口层

## 5. 关于 2D / 3D，我们已经达成了哪些很重要的说法

这部分在讨论中反复被确认过，后续新对话最好延续，不要重新摇摆。

### 5.1 2D 和 3D 的主次关系已经确定

当前最明确的说法是：

- 3D 用于校准、观察、结构验证、论文展示
- 2D 用于主 benchmark 执行

不能把 3D 写成：

- 单纯酷炫 demo

也不能把 2D 写成：

- 简陋但和 3D 没关系的另一个系统

更准确的表达是：

> 3D 和 2D 是一套双表示环境，3D 负责校准，2D 负责执行。

### 5.2 二者必须共享世界真相

我们后面反复强调：

- 相同房间拓扑
- 相同设备锚点
- 相同人物轨迹
- 相同任务与事件日志
- 相同环境变量

也就是说：

> 可以有两种渲染，不可以有两套真相。

## 6. 关于 Gym-friendly，我们之前到底是怎么讨论清楚的

这个点也很重要，因为它不是后面临时附会上的，而是较早就被用户主动提出。

用户很早就问过：

> 是不是要为强化学习预留口子，设计成 gym friendly 会更好？

在这之后，我们逐步形成的判断是：

- 当前不是直接做 RL 论文
- 但现在的内核不能把未来 RL 路堵死

因此稳定下来的原则包括：

### 6.1 决策点不应是每 tick

智能家居不是机械臂控制，因此：

- 一个 `step()` 不应等于一个 tick

而应等于：

> 从当前暂停点推进到下一个暂停点

### 6.2 时间控制核要能支撑 Gym 语义

后面明确写出来的对应关系是：

- `reset()`
- `step(action)`
- `observation`
- `reward`
- `terminated / truncated`
- `info`

但这不是要求现在就完美实现 Gymnasium，而是要求：

> 内核从结构上天然能映射成 Gym 语义

### 6.3 世界状态与 agent-facing observation 应分开

这也是后来讨论得比较清楚的一点：

- `world state observation`
- `agent-facing observation`

前者更完整，服务于调试和 RL
后者更克制，服务于 benchmark 中的被测模型

### 7.2 这个原型最初做成什么样，后来又怎么补的

最初的原型只做到了：

- `snapshot`
- `restore`
- `reset`

#### 第二轮补充：浏览器中的 2D 展示

用户明确提出：

> 我要浏览器展示啊，2D 也要看到展示。

于是后来加了：

- 浏览器 HTTP 服务

- 房间、人物、设备的 2D 可视化

#### 第三轮补充：轨迹引擎

用户后来继续指出：

> 我看不到轨迹啊，你可以写一个简单的轨迹引擎。

因此人物从一开始的“瞬移到客厅”，升级成：

- `position_x / position_y`
- `movement_plan`
- `movement_index`
- `trajectory_points`

并且人物会按 waypoint 逐 tick 移动：

- 卧室床边
- 卧室门
- 客厅门
- 客厅沙发

浏览器里现在已经能看到：

- 人物当前位置
- 轨迹线

#### 第四轮补充：事件系统扩展

用户后面又指出：

> 目前的事件太简单了，你多整几个事件啊。

于是事件流又被扩了一轮。

除了最开始的：

- `human_utterance_requested`
- `task_started`
- `task_completed`
- `service_followup_needed`
- `arrival_reached`

后面又增加了：

- `device_state_changed`
- `waypoint_reached`
- `room_transition`
- `environment_threshold_reached`

并且浏览器端不仅显示“最后一个暂停事件”，还加上了：

- 最近事件流 JSON
- 更易读的时间轴 / 事件轴

#### 第五轮补充：按钮语义解释

用户之后又明确吐槽：

> 这三个按钮是啥呀？我完全看不懂。

这说明一个问题：

- 工程结构开始成形了
- 但 demo 交互对人仍不够友好

因此后来按钮被改成了带解释的版本，例如：

- `1. 重置场景`
- `2. 开启空调，并推进到下一个暂停点`
- `3. 不做动作，继续推进到下一个暂停点`

并且加了一段说明，把“暂停点到暂停点”的语义解释清楚。

### 7.3 当前这个原型已经验证了哪些结构判断

虽然用户对整体 demo 仍不满意，但这个原型其实已经验证了几条关键判断并不是空想：

- 时间控制核可以独立存在
- 世界内容层可以被时间控制核统一驱动
- 人物层可以独立出来
- 任务与事件可以合层
- Gym-friendly 的“暂停点到暂停点 step”可以落地
- 浏览器 2D 视图可以挂在外层，而不直接侵入世界真相

从研究意义上看，这些结构判断已经通过原型得到了初步工程验证。

---

## 8. 用户对当前 demo 为什么仍不满意

这个部分也必须保留，因为后续新对话如果只看“我们已经做了很多”，很容易误判当前进展。

用户明确说过：

> “这个 demo 整体而言，我不太满意。”

这并不意味着前面的设计判断错误，而更像是在说：

- 结构有了
- 但展示层还不够自然
- 原型感太强

我们目前能总结出的不满意点主要包括：

### 8.1 它更像“验证结构的原型”，而不是“顺滑的研究演示”

当前 demo 强在：

- 结构对
- 分层清
- 能跑起来

但弱在：

- 展示仍然比较工程味
- 页面和交互不够像成熟演示系统

### 8.2 场景过小且较硬编码

当前仍然只有：

- 两个房间
- 一个住户
- 极少设备
- 一条固定路径
- 一个固定任务

这对于结构验证足够，但难以给人“这是一个像样沙箱”的主观感觉。

### 8.3 事件虽然扩多了，但仍偏 demo 级

虽然事件类型已经比最初丰富很多，但目前仍然是：

- 围绕一个小场景手工组织的事件流

而不是：

- 真正可扩展的、更一般化的事件体系

### 8.4 还没有接到 agent-facing 控制语义

当前虽然有 Gym-friendly wrapper，但还没有真正开始补：

- `get_home_state`
- `find_devices`
- `get_device_state`
- `execute_device_action`
- `check_goal_state`

所以它更像环境内核原型，而不是 benchmark agent 原型。

---

## 9. 一个总收束

如果要用一句较长但准确的话概括当前上下文，可以写成：

> 这一路讨论的真正成果，不是做出了一个成熟 demo，而是把原本散乱的智能家居 benchmark 想法收敛成了一套相对稳定的研究世界观：我们要做的不是再补一个“房间-设备-状态-工具调用”的测试集，而是一套以空间语义为骨架、以环境动力学和人物轨迹为生活过程承载、并由统一时间控制核驱动的智能家居实验世界；其中 3D 用于校准，2D 用于执行，长期交互与 Gym-friendly 暂停点推进机制都已在概念和最小原型层面得到验证。与此同时，当前 `sandbox_v1_demo` 仍然主要是结构验证原型，而不是成熟演示系统，这一点也必须被清楚认识。

如果后续新对话继续推进，最重要的是不要丢掉前面已经讨论清楚的这些结构判断，也不要把当前 demo 的存在误解成“系统已经做得差不多了”。更准确的理解应当是：

> 研究方向和系统骨架已经开始稳定，但展示层、控制层和更一般化的场景化能力还远未完成。
