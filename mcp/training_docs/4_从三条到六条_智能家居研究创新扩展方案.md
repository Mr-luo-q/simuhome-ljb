# 从三条到六条：三个更实际的新增创新方向

本文重新回答：在原有三条创新之外，还应增加哪三条？

原有三条是：

```text
1. 空间—时间一致的连续家庭世界 Benchmark
2. 面向长期共居的闭环主动服务评测
3. 虚拟环境到现实平台的语义迁移与成对评测
```

新增三条不再使用“多成员”“多源请求”“感知闭环”“数字孪生”“自然语言意图”这些宽泛概念。它们应是能直接回答用户、平台和行业实际需求的可执行任务领域：

```text
4. 自动化配置诊断、修复与回归验证
5. 家庭能源灵活调度与舒适约束
6. 家庭安全事件响应与恢复
```

这三条都满足：

```text
有明确输入
有明确动作
有真实可量化的结果
可在沙箱中反复重放
四篇目标 benchmark 都没有将其作为主线
```

---

## 1. 六条创新的完整结构

```text
底座
  1. 连续空间—时间家庭世界

通用智能
  2. 长期主动服务

现实连接
  3. 虚拟到现实语义迁移

实际家庭运维
  4. 自动化诊断、修复与回归验证

实际家庭资源管理
  5. 能源灵活调度与舒适约束

实际家庭风险处置
  6. 安全事件响应与恢复
```

它们不是同一种创新：

```text
1-3 是通用环境与研究框架
4-6 是三条具有独立实际价值的 Agent 应用/benchmark 赛道
```

这比给原有系统再添加“多人”“反事实”“感知”等抽象层次更实际，也更容易形成独立任务集和论文。

## 2. 为什么四篇 benchmark 没有覆盖这三条主线

| 工作 | 设备控制 | 时间/环境 | 个性化 | 通用自动化 | 配置修复 | 能源灵活调度 | 安全事件响应 |
| --- | --- | --- | --- | --- | --- | --- |
| HomeBench | 强 | 弱 | 弱 | 弱 | 无 | 无 | 无 |
| SimuHome | 强 | 强 | 弱 | 调度为主 | 无 | 无 | 无 |
| PersonalHomeBench | 弱 | 弱 | 强 | 弱 | 无 | 无 | 无 |
| SMH-Bench | 强 | 中 | 中 | 有 | 无 | 无 | 无 |

需要特别区分：

```text
SimuHome 的时间调度
  不等于家庭能源灵活调度

SMH-Bench 的自动化任务
  不等于自动化配置诊断、修复和回归验证

视频异常检测或传感器告警
  不等于安全事件发生后的行动、确认、升级和恢复
```

## 3. 创新四：自动化配置诊断、修复与回归验证

### 3.1 现实问题

现实家庭自动化通常不是一次写好就永远正确。常见故障包括：

```text
YAML / 配置语法错误
触发条件与实际实体不匹配
规则引用不存在或已改名的设备
设备状态与规则假设不一致
条件过严，规则始终不触发
条件过松，规则在错误时刻触发
设备替换、房间调整后旧规则失效
修复一个规则后，另一个正常场景被破坏
```

Home Assistant 官方提供 automation traces 和故障排查工具，说明“为什么没有运行、为什么错误运行、哪一步失败”是现实平台的常见工作流。

### 3.2 已有研究做到哪里

```text
TAPFixer
  使用模型检查修复 Trigger-Action 规则交互漏洞

SmartHomeSecure
  检测和修复 Home Assistant YAML 语法/格式/常见语义错误

AutoIoT
  生成自动化规则并做冲突检测
```

因此新增创新不能只是 YAML auto-fix，也不能只是生成规则。应定义为：

> 面向可执行家庭世界的自动化 Agent 诊断与回归验证 benchmark：Agent 根据配置、事件 trace 和世界状态定位行为性错误，生成最小修复，并在覆盖多种家庭情景的沙箱中验证修复是否解决目标问题且不引入回归。

关键差异：

```text
已有静态修复
  配置文件 / 规则集 → patch

我们的修复验证
  配置 + 真实执行 trace + 空间/环境状态
  → diagnosis
  → patch
  → 多情景 replay
  → regression verdict
```

### 3.3 可执行输入

```text
AutomationSpec
  trigger
  condition
  action
  mode
  cooldown
  target entities

FailureReport
  用户描述或测试失败描述

EventTrace
  trigger event
  condition evaluation
  service call
  command result
  state transitions

WorldSnapshot
  房间、设备、环境、时间和相关人物状态
```

### 3.4 任务族

```text
A1：根因定位
  为什么该规则没有在预期时刻触发？

A2：误触发定位
  为什么规则在宠物经过、房间无人或设备已关闭时仍运行？

A3：最小修复
  只改必要的 condition、entity、时间窗口或 action 参数

A4：替换设备
  原设备下线/替换后，更新规则且保持原行为语义

A5：回归验证
  修复后在正常、边界、异常、手动覆盖等情景中执行，检查是否引入新故障
```

### 3.5 自动评价

```text
Diagnosis Accuracy
  根因是否正确

Patch Validity
  配置是否能加载和执行

Bug Fix Rate
  原失败是否消除

Regression-Free Rate
  修复后正常情景是否仍正确

Patch Minimality
  是否避免改动无关规则/设备

Trace Grounding
  诊断结论是否有事件和状态证据支持
```

### 3.6 SimuHome 怎样承接

```text
静态层
  AutomationSpec + scenario

时间核
  执行 trigger / condition / action

事件层
  保存完整 trace

snapshot/replay
  在多种覆盖情景中测试 patch

HA adapter
  后续可导入/导出 Home Assistant automation 语义
```

### 3.7 创新成立条件

```text
需要构造
  真实或合成的 broken automations
  明确 failure oracle
  有 patch 前/后对照
  有 regression suite

需要证明
  一般代码修复 Agent 或 LLM patcher 无法保证家庭行为正确
  世界回放验证能显著降低“修了原 bug 又引入新 bug”的比例
```

### 3.8 判断

```text
现实价值：很高
四篇 benchmark 空白：明确
工程难度：中
最适合的论文定位：HomeAutoFixBench / SmartHomeDevOps
```

## 4. 创新五：家庭能源灵活调度与舒适约束

### 4.1 现实问题

家庭设备并非都必须立即运行：

```text
空调可以提前预冷/预热
热水器可以在低价时段加热
洗衣、烘干、洗碗可在截止时间前调度
电动车可在离峰或光伏发电时充电
电池/储能可在价格和负荷变化下充放电
```

但家庭用户通常还会提出不可违背的约束：

```text
晚上睡觉不能开高噪声烘干机
早上出门前必须完成洗衣
老人/儿童所在房间不可低于最低舒适温度
做饭时空气质量不能因节能而恶化
用户随时可能手动覆盖调度计划
```

ENERGY STAR 的智能温控资料表明，制热制冷在家庭能源账单中占很大比例；传统家庭能源管理已广泛研究成本、舒适和设备调度，但主要是数值优化或 DRL，不是面向工具、规则、解释和用户约束的 Agent benchmark。

### 4.2 与已有能源研究怎样区分

已有 HEMS 研究已经包含：

```text
HVAC / EV / 电池 / 光伏调度
电价、不确定天气、占用状态
舒适与成本优化
MILP、Lyapunov、DDPG 等算法
```

所以不能宣称“首次做家庭能源优化”。应该研究：

> 面向智能家居 Agent 的家庭能源灵活调度：Agent 将用户提出的截止时间、安静时段、舒适下限、设备依赖和手动覆盖转换为可验证约束，并在连续家庭环境中与设备、环境和用户行为交互。

与传统 HEMS 的差别：

```text
传统 HEMS
  预定义数值目标和设备模型
  输出最优控制/调度

家庭 Agent benchmark
  任务约束会通过用户请求、日程、事件和设备状态动态变化
  Agent 必须查询、解释、调整、验证和处理手动覆盖
```

### 4.3 最小世界状态

```text
GridState
  electricity_price
  carbon_intensity 可选
  demand_response_event 可选

DeviceFlexibility
  power
  duration
  interruptible
  earliest_start
  deadline
  dependency
  noise

ComfortConstraint
  room
  person/activity
  min/max temperature
  quiet window

EnergyAsset 可选
  solar generation
  battery
  EV
```

第一版可以不做光伏、电池和碳强度，只做：

```text
分时电价
HVAC
热水器
洗衣/烘干/洗碗等可延期设备
噪声和截止时间
```

### 4.4 任务族

```text
E1：预冷/预热
  用户 30 分钟后回家，在舒适和费用间选择开始时间

E2：可延期家电
  “今晚 10 点前洗完衣服，但 22:30 后不要有噪声”

E3：峰时需求响应
  高电价时降低可延期负荷，不能违反人员舒适和任务 deadline

E4：人工覆盖
  用户要求立即运行，Agent 重新计算影响并解释，不擅自拒绝合法需求

E5：连续环境影响
  开窗、空调、风扇和取暖器对成本、温度和噪声有不同后果
```

### 4.5 指标

```text
Hard Constraint Satisfaction
  deadline、最低舒适、安静时段和设备依赖是否满足

Energy Cost
  费用、峰值负荷或能耗

Comfort Violation Integral
  温度/空气质量偏离可接受区间的累计程度

Schedule Feasibility
  是否给出可执行而非表面正确的调度

Manual Override Respect
  用户临时操作后是否正确重排

Explanation Consistency
  对价格、舒适和时间的解释是否符合真实状态
```

### 4.6 SimuHome 怎样承接

```text
设备状态机
  加入 duration、power、interruptible、deadline

Aggregator
  温度、湿度、光照、噪声、能耗

TimeControlKernel
  分时价格、任务排程、快进和回放

TaskRuntime
  comfort / deadline / energy goal verifier
```

### 4.7 创新成立条件

```text
需要证明
  固定规则、纯 HEMS 优化、通用 LLM Agent 三者各有局限
  Agent 能在动态用户约束和设备状态下保持可行调度
  任务结果不仅节能，而且不牺牲硬舒适/截止时间约束
```

### 4.8 判断

```text
现实价值：极高
四篇 benchmark 空白：明确
已有相关领域：成熟 HEMS/DRL，需要突出 Agent、用户约束和可解释交互
工程难度：中高
最适合的论文定位：FlexHomeBench / HomeEnergyAgent
```

## 5. 创新六：家庭安全事件响应与恢复

### 5.1 现实问题

智能家居安全不是普通设备控制。漏水、烟雾、燃气、未关高功率设备、门锁异常、夜间异常活动都具有：

```text
时间敏感
信息不完整
误报成本高
错误动作可能造成不可逆损失
需要区分自动处置、人工确认和紧急升级
```

现有视频异常检测 benchmark 主要测“能否识别异常视频”。真实家庭 Agent 还需要完成：

```text
检测
  ↓
验证
  ↓
缓解
  ↓
通知/升级
  ↓
恢复与审计
```

### 5.2 与已有研究怎样区分

```text
SmartHome-Bench
  视频异常检测与描述

传感器故障/安防检测工作
  识别异常或定位传感器问题

PromptShield Home
  处理环境多模态提示注入和误执行风险

我们的方向
  将异构告警放入连续家庭世界，
  评测 Agent 的分级响应、行动顺序、误报控制、通知和恢复。
```

不是让 LLM 判断火灾或医疗诊断。高风险事件的检测阈值和紧急规则必须由预定义 policy 控制，Agent 的研究对象是基于可信事件如何做安全处置。

### 5.3 安全事件状态

```text
SafetyEvent
  type: leak | smoke | gas | unattended_appliance | door_anomaly | fall_alert
  severity
  confidence
  source
  observed_tick
  affected_room
  active

SafetyPolicy
  automatic actions
  confirmation requirement
  notification targets
  escalation deadline
  forbidden actions

RecoveryState
  mitigation status
  verification status
  manual acknowledgement
  incident log
```

### 5.4 任务族

```text
S1：漏水
  水浸传感器触发，关闭阀门/通知/验证是否停止扩散

S2：烟雾与烹饪区分
  低置信烟雾事件先查询其他传感器，不能立即错误升级

S3：未关高功率设备
  设备长时间运行且人员离开房间，检查是否应关、提醒或等待

S4：门锁异常
  门锁状态与门磁/时间/在家状态不一致，决定验证、锁定或通知

S5：夜间异常活动
  在明确预设策略下，提供低风险照明、提醒或升级，避免医疗诊断
```

### 5.5 指标

```text
Time to Mitigation
  从可信事件到有效缓解的时间

Critical Action Recall
  高风险事件是否执行必要动作

False Escalation Rate
  低风险/误报事件是否过度通知或处置

Unsafe Inaction Rate
  高风险事件是否不作为或延迟过久

Policy Compliance
  是否遵守预设 emergency policy、权限和禁止动作

Recovery Verification
  缓解后是否确认事件已经解除
```

### 5.6 SimuHome 怎样承接

```text
空间层
  事件发生房间、蔓延/影响范围、可达设备

设备层
  阀门、报警器、排风、门锁、照明、高功率设备

环境层
  烟雾/空气质量/水浸/温度等简单变量

时间核
  告警升级窗口、处置延迟、恢复验证期

事件层
  sensor alert、mitigation、notification、acknowledgement、resolved
```

### 5.7 创新成立条件

```text
需要有
  安全事件 taxonomy
  已知检测可靠度
  明确的 safety policy
  连续事件/行动/恢复状态
  可自动验证的缓解结果

需要证明
  仅做异常检测不能代表安全能力
  通用控制 Agent 会在确认、升级、恢复或误报控制上失败
  安全响应 Agent 能提高缓解率且不过度报警
```

### 5.8 判断

```text
现实价值：极高
四篇 benchmark 空白：明确
工程难度：中高
伦理边界：不做医疗诊断，不让 LLM 决定紧急阈值
最适合的论文定位：SafeHomeBench / IncidentResponseAgent
```

## 6. 六条创新的关系

```text
1. 连续家庭世界
  提供所有任务的空间、时间和状态基础

4. 自动化诊断修复
  让家庭自动化可维护

5. 能源灵活调度
  让家庭资源使用可优化

6. 安全事件响应
  让家庭风险处置可验证

2. 长期主动服务
  贯穿三类实际任务中的个性化、时机和打扰控制

3. 虚实语义迁移
  让自动化、能源和安全任务最终能映射到 HA/真实平台
```

这套结构更像一个实际家庭操作系统：

```text
日常自动化能不能正确维护？
能源设备能不能在约束下合理安排？
安全事件能不能及时且不过度地响应？
```

## 7. 不应全部塞进一篇论文

新增三条都是独立应用方向，最好拆开：

```text
Paper 1：AutoFixHome
  连续家庭世界
  + 自动化配置诊断、修复和回归验证
  + 有限长期主动服务

Paper 2：FlexHomeBench
  家庭能源灵活调度
  + 舒适、噪声、deadline 和人工覆盖约束
  + 可解释 Agent 调度

Paper 3：SafeHomeBench
  家庭安全事件响应与恢复
  + 告警确认、缓解、升级、审计
  + 虚实迁移验证
```

原来的三条仍然是共同底座：

```text
创新一
  每一篇的家庭环境

创新二
  每一篇的长期/主动行为维度

创新三
  每一篇的现实平台验证路径
```

## 8. 当前最实际的优先级

| 排名 | 方向 | 原因 | 当前工程距离 |
| --- | --- | --- | --- |
| 1 | 自动化诊断、修复与回归验证 | 当前时间核、事件和 HA trace 最容易承接 | 最近 |
| 2 | 家庭安全事件响应 | 事件、设备和环境模型天然支持，价值清楚 | 中等 |
| 3 | 家庭能源灵活调度 | 价值大，但需补设备族、价格和任务约束 | 较远 |

若要尽快把现有 `firstdemo` 推成可投稿原型，应先选择：

```text
自动化诊断、修复与回归验证
```

它只需在当前内核上增加：

```text
AutomationSpec
FaultInjection
EventTrace
FailureOracle
Patch
RegressionSuite
```

不需要先实现 EV、光伏、烟雾扩散或复杂多模态感知。
