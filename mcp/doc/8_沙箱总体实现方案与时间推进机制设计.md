# 沙箱总体实现方案与时间推进机制设计

本文档基于四篇相关 benchmark 论文、[7_智能家居空间化Benchmark总蓝图与研究进展梳理.md](/d:/D_coderesource/simuhome/mcp/doc/7_智能家居空间化Benchmark总蓝图与研究进展梳理.md) 以及前面多轮讨论，重新回答第 8 篇真正应该回答的问题：

> 为了支撑我们的空间化智能家居 benchmark，沙箱到底由哪些世界内容构成，这些内容为什么必须由统一的时间机制来驱动，以及 2D/3D 视图与接口层应该挂接在什么位置。

本文的总判断先写在最前面：

> 沙箱不是一个工具集合，而是一套实验世界；时间机制也不是普通子层，而是驱动整套实验世界运转的 `时间控制核`。

因此，第 8 篇不再把时间机制与其他层平铺并列，而是改为一种更强的分组结构：

- `世界内容层`
  - 空间结构层
  - 设备与环境动力学层
  - 人物与轨迹层
  - 任务与事件运行时层
- `核心控制层`
  - 时间控制核
- `视图层`
  - 2D/3D 双视图层
- `接口层`
  - 接口与实验控制层

这样改写的原因很直接。现有四篇工作虽然各有推进，但整体仍大多停留在“房间-设备-状态-工具调用”的框架中：

- `HomeBench` 强在任务规模与设备控制覆盖，但空间和长期性较弱。
- `SimuHome` 强在时间推进、环境变量与可执行模拟，但空间拓扑不是主结构。
- `PersonalHomeBench` 强在 persona、记忆与个性化，但环境动力学和空间执行语义不够强。
- `SMH-Bench` 强在环境接地、任务分层与复杂度控制，但仍主要是结构化环境上的推理与验证。

如果我们的沙箱还继续写成“设备状态机 + 若干工具”的样子，就很难真正形成突破。它必须同时完成三件事：

- 把空间从标签升级为可计算的语义骨架。
- 把环境从静态状态升级为随时间演化的系统。
- 把长期交互从补充展示升级为环境原生支持的运行方式。

---

## 1. 沙箱的世界内容应该包含什么

先讲世界内容，而不是先讲时间。因为如果没有明确“世界里到底有什么”，时间机制就只会变成一个抽象空壳。

### 1.1 空间结构层

这一层定义“房子本身是什么样”。它不是做高保真建筑物理，而是为整套 benchmark 提供空间语义骨架。

它至少应包含：

- 房间列表与房间类型
- 房间边界或区域表示
- 门、走廊和连通关系
- 房间内关键锚点
- 设备与人物的空间挂载点
- 房间之间的邻接与可达关系

这一层是后续以下能力的基础：

- 空间 grounding
- 指代消歧
- 跨房间协同
- 人物轨迹解释
- 2D/3D 一致性

这层有三条可选技术路线。

`方案 A：纯拓扑图 + 锚点`

- 每个房间是一个节点，门是边。
- 房间内只保留少量语义锚点，例如 `door`、`sofa`、`desk`。
- 设备和人物挂在锚点或局部位置上。

优点：

- 最轻量。
- 最容易启动首版 benchmark。
- 语言空间语义比较好接。

缺点：

- 细粒度相对位置表达有限。
- 3D 校准时需要额外映射规则。

`方案 B：2D 栅格 / Occupancy Grid`

- 家庭被离散成二维网格。
- 墙、门、可达区域、设备点位都落在网格上。
- 人物移动、距离、邻近关系直接在网格上计算。

优点：

- 路径与距离计算直接。
- 和 2D 主执行环境天然一致。
- 后续做 RL observation 更容易。

缺点：

- 语义锚点仍需额外命名层。
- 大家庭场景会更重。

`方案 C：房间图 + 局部坐标混合表示`

- 全局用房间图表达拓扑。
- 房间内部用局部 2D 坐标表示设备和人物位置。
- 锚点是局部坐标上的命名点。

优点：

- 比纯拓扑更强，比全局网格更轻。
- 很适合做 2D/3D 一一映射。
- 论文表达也最自然。

缺点：

- 需要额外设计房间内坐标规范。
- 实现复杂度略高于方案 A。

当前推荐：

> 首版优先采用 `方案 C`。如果想快速启动最小版本，可以先用 `方案 A` 打底，再平滑过渡到 `方案 C`。

### 1.2 设备与环境动力学层

这一层回答“这个家不是静止的，而是怎么变化的”。设备状态机和环境变量不能拆开写，因为两者本来就是联动的。

它至少应包含：

- 设备类型、属性与动作集合
- 合法动作与非法动作约束
- 持续型动作与瞬时动作区分
- 房间级环境变量
- 环境变量演化规则
- 设备对环境变量的影响

首版建议明确纳入的环境变量：

- 温度
- 湿度
- 光照

后续若有余力，可以扩展到：

- 空气质量
- 噪声
- 能耗

这层有三条可选技术路线。

`方案 A：规则表驱动`

- 每类设备有一张影响规则表。
- 每种环境变量按固定增减、衰减、上下限更新。
- 开门、开窗、空调、灯光等影响都用规则表实现。

优点：

- 最稳。
- 最容易保证可解释和可复现。
- 最适合作为 benchmark 内核起点。

缺点：

- 真实性有限。
- 复杂耦合要手写很多规则。

`方案 B：简化方程 / 差分更新`

- 每个 tick 按简单差分方程更新环境变量。
- 例如温度由设备功率、相邻房间交换和自然回归共同决定。

优点：

- 更连续。
- 更适合表达“逐步达到目标”的过程。
- 与 SimuHome 式时间推进更贴近。

缺点：

- 参数校准要花时间。
- 容易不小心做成小型数值模拟器。

`方案 C：规则表 + 差分更新混合`

- 高层逻辑用规则表。
- 核心环境变量更新用轻量差分公式。
- 设备启停、模式切换、互斥约束继续用状态机。

优点：

- 在真实性和可控性之间最平衡。
- 适合论文里写“轻量但连续”的环境演化。
- 便于以后扩展更多变量。

缺点：

- 比方案 A 稍复杂。
- 需要维护两类规则。

当前推荐：

> 首版优先采用 `方案 C`。设备约束坚持状态机，环境变量更新只做轻量差分，不追求高保真物理仿真。

### 1.3 人物与轨迹层

这一层负责“谁在这个家里生活，以及他在空间中如何移动”。人物不应继续与任务绑在一起，因为人物对象天然同时连接空间、轨迹、交互和渲染。

它至少应包含：

- 人物实体标识
- 人物当前位置
- 当前房间与当前锚点
- 目标位置
- 朝向或视角
- 当前活动标签
- 轨迹记录
- 2D/3D 共用渲染语义

这里特别固定一个边界：

> `persona / 偏好 / 历史记忆 / 对话上下文` 继续作为外部实验配置注入，而不是并入人物层主逻辑。

这层有三条可选技术路线。

`方案 A：轻人物对象 + 外部配置注入`

- 人物层只维护实体、位置、朝向、轨迹和活动标签。
- persona 和偏好在实验启动时注入。

优点：

- 层次最干净。
- 最利于 2D/3D 共享语义。
- 不会把人物层写得过重。

缺点：

- 与长期交互配置的关联需要额外说明。

`方案 B：人物对象内置 persona 与偏好`

- 人物层直接维护 persona 和偏好字段。
- 历史记忆和对话上下文仍放外部。

优点：

- 比方案 A 更完整。
- 对长期交互叙事更直接。

缺点：

- 人物层会开始变重。
- 后期容易继续膨胀。

`方案 C：人物层全包`

- 人物层同时维护实体、轨迹、persona、偏好、长期记忆和交互上下文。

优点：

- 表面上最完整。

缺点：

- 首篇论文明显过重。
- 会让人物层喧宾夺主。

当前推荐：

> 首版优先采用 `方案 A`。人物层只管实体、轨迹和渲染语义，长期交互配置继续作为外部注入。

### 1.4 任务与事件运行时层

这一层负责“世界里有哪些过程在跑，以及哪些关键节点值得被记录和消费”。任务和事件应写在同一层，因为事件本质上就是围绕任务生命周期和世界变化长出来的运行时对象。

它至少应包含：

- 任务对象
- 定时任务
- 持续任务
- 长期任务
- 并行任务状态
- 任务阶段切换
- 事件生成
- 事件消费
- 任务与人物、设备、环境之间的联动

这里的边界必须明确锁成 `仅执行型`：

> 任务与事件运行时层只负责执行、跟踪和产出事件，不做高层计划分解，不自动生成 schedule，不替模型做多设备 orchestration。

这层有三条可选技术路线。

`方案 A：纯任务对象运行时`

- 任务是中心对象。
- 事件只作为任务状态变化的附属记录。

优点：

- 实现简单。
- 任务生命周期比较清晰。

缺点：

- 事件语义不够突出。
- 长期交互时不够灵活。

`方案 B：事件中心运行时`

- 世界里所有变化都先表现为事件。
- 任务只是被事件推进的对象。

优点：

- 事件驱动表达更统一。
- 很适合复杂异步系统。

缺点：

- 对首篇论文偏重。
- 任务语义容易被冲淡。

`方案 C：任务与事件并重的运行时`

- 任务维护生命周期。
- 事件维护关键触发和可消费节点。
- 两者互相映射但不互相吞并。

优点：

- 最平衡。
- 既利于 benchmark 表达，也利于工程实现。
- 与时间控制核的对接最自然。

缺点：

- 设计时要明确对象边界。

当前推荐：

> 首版优先采用 `方案 C`，并固定为 `仅执行型` 边界。

## 2. 为什么时间机制应成为核心控制核

到这里才能谈时间机制。因为时间机制真正要控制的，是上面这些世界内容，而不是凭空独立存在。

这里的核心判断需要明确写死：

> 时间机制不是普通并列子层，而是贯穿所有内容层的全局控制核。

原因有五个。

第一，空间层本身只是静态骨架。人物在空间中的移动、设备在空间中的作用范围、跨房间影响的传播，只有在时间推进下才会真正发生。

第二，设备与环境动力学只有放到时间中才有意义。温度、湿度、光照都不是瞬时完成的，它们是持续变化过程。

第三，任务与事件的生命周期本质上由时间推进触发。任务开始、持续、完成、阶段切换、后续跟进，全部依赖时间控制。

第四，长期交互、快进、暂停、回放和可重复实验，本质上都需要一个统一的时钟与控制逻辑，否则世界会失去一致性。

第五，后续如果要做 Gym-friendly 的决策点式环境，`step()` 的本质就是由时间控制核把世界从一个暂停点推进到下一个暂停点。

因此，更准确的结构不是“时间机制属于某一个业务层”，而是：

- 世界内容层描述“世界里有什么”
- 时间控制核描述“这些东西按什么节奏变化，以及什么时候暂停”

## 3. 时间控制核应该如何设计

既然时间机制是核心控制核，它就必须单独定义职责，而不能继续和任务语义、人物语义混写。

时间控制核负责：

- `virtual time`
- `tick`
- `fast-forward`
- `pause policy`
- `snapshot / restore`
- `deterministic replay`

时间控制核驱动：

- 人物移动
- 环境变量演化
- 任务生命周期推进
- 事件触发
- 回放与暂停

时间控制核不承载：

- 人物语义状态
- 任务业务语义
- 设备环境规则本体

这层仍有三条可比较的技术路线，但首版推荐项已经锁定。

`方案 A：固定 tick 全量推进`

- 每一步都按固定 tick 更新世界。
- 人物、设备、环境、任务都逐 tick 推进。

优点：

- 最容易理解。
- 一致性最好。

缺点：

- 长程实验太慢。
- 不适合大规模 benchmark。

`方案 B：纯事件驱动推进`

- 世界主要靠关键事件跳转。
- 没有事件就不更新，或只做极少更新。

优点：

- 很快。
- 高层任务表达直接。

缺点：

- 连续变量处理麻烦。
- 回放和解释性会变差。

`方案 C：tick 内核 + 事件快进 + 交互暂停`

- 世界内部保留固定 tick。
- 事件层决定下一次值得关注的时间点。
- pause policy 决定是否把控制权交给外部 agent。

优点：

- 兼顾连续更新、长程效率和语义暂停。
- 与 SimuHome 现有内核最容易衔接。
- 最适合本项目的长期交互与 Gym-friendly 目标。

缺点：

- 实现复杂度高于前两者。
- 需要清楚定义事件语义。

当前推荐：

> 首版固定采用 `方案 C：tick 内核 + 事件快进 + 交互暂停`。

首版暂停点建议只保留两类：

- `人类发起语言交互`
- `设备或任务完成后需要高层决策`

普通异常、普通失败、冲突和偏差先只记录日志，不自动暂停。这样可以先把系统跑顺，再逐步考虑是否引入异常类暂停点。

## 4. 2D/3D 视图层与接口层应挂在什么位置

当世界内容层和时间控制核都明确之后，2D/3D 视图层与接口层的位置就会自然清楚。

### 4.1 2D/3D 双视图层

2D 与 3D 不是两套世界，而是同一个世界的两种视图。它们应当挂在世界内容层与时间控制核之外，作为观察与校准视图存在。

它至少要共享：

- 相同房间拓扑
- 相同设备锚点
- 相同人物位置与轨迹
- 相同环境变量
- 相同任务与事件日志
- 相同虚拟时间

这层有三条路线。

`方案 A：2D 主环境 + 3D 纯展示`

- 2D 执行一切。
- 3D 只用于论文展示。

优点：

- 最省事。

缺点：

- 很容易被质疑 3D 只是 demo。

`方案 B：2D 主执行 + 3D 校准观察`

- 2D 是主 benchmark 环境。
- 3D 用于空间结构、设备位置和人物轨迹的校准观察。
- 两者共享世界真相。

优点：

- 最符合总蓝图主线。
- 成本与论文价值平衡最好。

缺点：

- 需要维护 2D/3D 映射工具链。

`方案 C：2D 与 3D 双向可编辑`

- 两边都能修改世界。
- 需要双向同步和冲突处理。

优点：

- 功能最强。

缺点：

- 首篇论文明显过重。

当前推荐：

> 首版明确采用 `方案 B`。

### 4.2 接口与实验控制层

接口层挂在最外侧，因为它描述的是“外部如何访问世界”，而不是“世界本体如何存在”。

这里必须分成两类接口。

第一类是 `agent-facing 接口`，服务于被测智能家居模型，原则是轻量、克制、不替模型解题。首版建议围绕：

- `get_home_state`
- `find_devices`
- `get_device_state`
- `execute_device_action`
- `check_goal_state`

第二类是 `experiment-facing 接口`，服务于研究者、人物模拟器、调度器、回放器和未来 RL wrapper。首版建议围绕：

- `reset`
- `snapshot`
- `restore`
- `fast_forward`
- `inject_task`
- `inject_human_event`
- `get_event_log`

这层有三条路线。

`方案 A：全部做成 MCP`

优点：

- 表面形式统一。

缺点：

- 不适合高频实验控制。
- 容易把实验接口和模型接口混在一起。

`方案 B：模型侧用 MCP 风格，实验侧用内部 API`

优点：

- 最符合当前需求。
- 既保留研究叙事，也更适合批量实验。

缺点：

- 需要维护两套入口。

`方案 C：全部走本地 Python API，MCP 只做最外层适配`

优点：

- 工程上最稳。
- 很适合科研代码。

缺点：

- 论文里要额外解释“统一接口语义”。

当前推荐：

> 首版优先采用 `方案 B` 或 `方案 C`。更具体地说，内核最好先做成本地 Python API，MCP 作为 agent-facing 适配层追加。

## 5. 为强化学习预留口子：首版就要 Gym-friendly

这一节必须与新的结构严格对齐，而不能再沿用旧的并列层说法。

这里的关键不是“现在就做 RL”，而是：

> 首版内核不能把未来 RL 路线堵死。

要做到这一点，至少要满足五条约束。

第一，世界内核必须与外部 agent loop 解耦。环境状态推进必须由沙箱自己负责，而不是嵌在某个 LLM demo loop 里。

第二，内核应自然映射到标准 Gym 语义：

- `reset()`
- `step(action)`
- `observation`
- `reward`
- `terminated / truncated`
- `info`

第三，决策点必须是稀疏的，而不是每 tick 都决策。更合理的定义是：

> 由 `时间控制核` 负责把世界从当前暂停点推进到下一个暂停点，作为一次高层 `step()`。

第四，observation 应从一开始就区分两层：

- `world state observation`
- `agent-facing observation`

前者更完整，服务于内部调试和 RL。后者更克制，服务于被测模型，避免工具层泄漏过多信息。

第五，必须支持并行副本、固定随机种子和 snapshot 快速复制，因为后续只要做 RL 或大规模评测，几乎一定需要这些能力。

Gym-friendly 的实现路线仍有三条。

`方案 A：后期再包 wrapper`

优点：

- 当前最省事。

缺点：

- 如果现在内核不规整，后期很容易包不出来。

`方案 B：现在按 Gym 语义设计内核，但先不公开 RL API`

优点：

- 最稳妥。
- 不会干扰当前 benchmark 主线。

缺点：

- 现在设计时要更自律。

`方案 C：直接同步做 Gym 环境`

优点：

- 一步到位。

缺点：

- 首篇论文明显过重。

当前推荐：

> 首版优先采用 `方案 B`。也就是内核从一开始就 Gym-friendly，但 RL wrapper 放到增强项或下一阶段。

在这套结构下，未来 Gym `step()` 的语义可以明确写成：

- `时间控制核` 负责从当前暂停点推进到下一个暂停点
- `任务与事件运行时层` 负责提供当前决策点的事件化状态
- `人物与轨迹层` 负责提供人物相关 observation

这样得到的是一个面向高层决策点的智能家居环境，而不是逐 tick 控制环境。

---

## 6. 首版最推荐的技术组合

如果把世界内容层、时间控制核、2D/3D 主线和 Gym-friendly 诉求一起考虑，当前首版最推荐的组合是：

- 空间结构层：`房间图 + 局部坐标混合表示`
- 设备与环境动力学层：`状态机 + 轻量差分更新混合`
- 人物与轨迹层：`轻人物对象 + 外部配置注入`
- 任务与事件运行时层：`任务与事件并重的仅执行型运行时`
- 时间控制核：`tick 内核 + 事件快进 + 交互暂停`
- 2D/3D 双视图层：`2D 主执行 + 3D 校准观察`
- 接口与实验控制层：`Python 内核 API + agent-facing MCP 适配`

这个组合的优点是：

- 论文主线清楚。
- 工程复杂度可控。
- 与 SimuHome 有承接关系，而不是另起炉灶。
- 对 Home Assistant 接入友好。
- 对后续 Gym wrapper 和 RL 改造友好。

它刻意不做的事情包括：

- 不做重物理仿真
- 不做自动 schedule 求解器
- 不做双向可编辑 2D/3D
- 不把人物模拟器一开始就做成多智能体大工程
- 不把所有接口都做成 MCP

这些不是永远不做，而是首篇论文不该背这么多包袱。

## 7. 当前结论

基于四篇相关工作、第 7 篇总蓝图和当前讨论，第 8 篇现在应收敛到一个更明确的版本：

- 沙箱不是一个小工具，而是一套实验世界。
- 沙箱首先由 `世界内容层` 构成：空间、设备环境、人物轨迹、任务事件。
- 时间机制不应继续被写成普通并列子层，而应被定义为贯穿整套世界的 `时间控制核`。
- 2D/3D 位于视图层，负责观察、校准和展示，不拥有独立世界真相。
- 接口层位于最外侧，负责把这套世界以克制的方式暴露给模型和实验控制器。
- 首版要优先选择“轻量、可复现、可解释、Gym-friendly”的组合。

如果只用一句话概括这一版设计：

> 我们要构建的不是一个会调用智能家居 API 的 demo，而是一套以空间结构为骨架、以设备与环境动力学为内核、以人物轨迹和任务事件运行时承载生活过程、并由统一时间控制核驱动的智能家居研究沙箱；2D/3D 视图与接口层都只是这套世界的外部挂接方式，而不是世界本体本身。
