# 智能家居空间化 Benchmark 总蓝图与研究进展梳理

本文档用于收敛当前研究方向，给出一份面向论文贡献表达的统一大蓝图。它不是普通工程设计说明，也不是只服务于短期实现的任务清单，而是要回答两个核心问题：

1. 与现有四篇相关 benchmark 相比，我们真正的突破口在哪里。
2. 这套工作应如何在保证研究价值的前提下，控制系统复杂度并逐步落地。

本文档默认将当前项目理解为一套完整研究系统，而不是单一数据集或单一模拟器。系统由双层环境、统一接口层、长期交互机制和可复现实验沙箱共同构成。

---

## 1. 相关工作的共同边界与我们的切入点

这四篇论文分别从设备控制、动态环境、个性化与环境接地等方向推动了智能家居 benchmark 的发展，但如果从更高一层看，它们仍大体共享一个核心范式：以结构化家庭状态为基础，通过设备查询与控制接口驱动任务，再根据目标状态或答案完成验证。

这个范式本身没有问题，它解决了“让模型在家庭环境中可测”这一基础问题。但它仍然存在一个明显共同边界：家庭被建模得更像“房间-设备-状态”的可执行状态机，而不是一个真正具备空间语义、持续时间、长期共居演化和现实迁移潜力的仿生环境。

### 1.1 HomeBench 的位置

`HomeBench` 的优势在于大规模任务构造、设备能力覆盖、单设备与多设备控制、以及无效指令检测。它证明了智能家居确实可以作为大模型工具调用和任务执行的重要测评场景。

但它的主要弱点也很清楚：

- 空间语义较弱，家庭结构更接近房间容器与设备列表。
- 时间连续性有限，难以表达长期演化的家庭生活过程。
- 个性化和长期用户建模不是核心。

因此，`HomeBench` 更像是一个强有力的控制与理解基线，但还不是一个空间化、长期化的智能家居生活环境 benchmark。

### 1.2 SimuHome 的位置

`SimuHome` 明显比 `HomeBench` 更进一步。它引入了动态环境变量、时间推进、工具交互、状态验证、隐含意图与调度问题，将智能家居 benchmark 从静态设备控制推进到“持续演化的环境”。

它的价值非常高，因为它已经明确指出：

- 智能家居智能体不能只做设备开关。
- 环境变量会随时间变化。
- 模型需要先观察再执行。
- 调度、验证、依赖关系都是难点。

但它仍有两个关键局限：

- 空间建模并未真正成为核心，环境更多是“房间中的设备与变量”，而非具备强空间拓扑和位置语义的家居场景。
- 调度与验证暴露出明显难题，说明“动态时间环境”虽然被引入了，但长期持续生活过程和更强空间约束尚未被系统吸收。

### 1.3 PersonalHomeBench 的位置

`PersonalHomeBench` 的主要推进在于个性化。它强调 persona、家庭成员、家庭记忆、事件历史、多模态 grounding，以及在个性化家庭环境中对模型的评估。

这篇工作与我们的第二主线最接近，因为它已经把问题从“会不会做设备控制”推进到“能不能理解这个家庭、理解这个人、在长期背景中持续服务”。

但它也存在边界：

- 个性化很强，环境物理性与空间执行语义仍不够强。
- 更重上下文、记忆和角色信息，而不是强时空一致性的家庭仿真。
- 它提示了“长期服务”的必要性，但还没有把长程生活过程真正做成一套强空间约束、强时间推进的双层环境系统。

### 1.4 SMH-Bench 的位置

`SMH-Bench` 的优势在于环境接地、任务分类细、家庭复杂度分层，以及把家庭建模为可持续演化的 `HomeEnv`。它比更早的 benchmark 更强地强调：

- 查询与控制并存。
- 多轮上下文与记忆。
- 自动化与状态驱动推理。
- 在环境中执行并验证结果。

但它仍主要沿着“结构化环境 + 工具接口 + 任务验证”的路线前进。它已经非常接近一个成熟 benchmark 的形态，却依然没有把“真实空间拓扑”、“长期共居过程”、“3D/2D 双表示环境”和“虚拟环境到现实平台的统一迁移接口”真正做成主线贡献。

### 1.5 四篇工作的共同结论

如果把这四篇工作放在一起看，可以得出一个对我们很关键的判断：

> 现有工作已经证明了智能家居 benchmark 值得做，也证明了设备控制、环境变量、个性化和环境接地都重要；但它们整体上仍主要停留在“结构化状态 + 设备调用 + 任务验证”的框架中，尚未真正建立一套兼具空间真实、时间连续、长期共居与现实可迁移性的统一 benchmark 体系。

这正是我们的切入点。

## 2. 我们的研究目标不是“再做一个任务集”，而是升级 benchmark 的世界模型

如果只从表面看，我们似乎也是在做智能家居 benchmark。但更准确地说，我们要做的不是再补一批任务，而是升级 benchmark 背后的“世界模型”。

过去四篇工作的主要世界模型是：

- 房间
- 设备
- 状态
- 控制接口
- 任务验证

而我们想引入的世界模型是：

- 带空间拓扑与设备锚点的家庭结构
- 带持续时间与环境演化的时间系统
- 带生活轨迹与习惯累积的人类活动系统
- 带统一语义接口的虚拟到现实迁移路径

因此，我们的核心不是单点能力增强，而是 benchmark 形态升级。

## 3. 三层主贡献重组

为了避免贡献点过碎，本文将整个研究主线收敛为三层主贡献。后续论文写作也应尽量围绕这三层组织，而不是把很多零散亮点并列堆砌。

### 3.1 第一层贡献：空间化仿生环境

第一层贡献是构建一套 `3D 校准 + 2D 执行` 的双表示智能家居环境。

其核心思想不是“加一个 3D demo 让页面更炫”，而是把 3D 用作科学校准工具，把 2D 用作低成本、高吞吐、可复现的大规模评测环境。两者共同组成一套双表示环境系统。

#### 3D 层的职责

3D 层不是主要测评环境，而是校准环境。它主要负责：

- 校验房屋结构是否合理。
- 校验设备位置是否合理。
- 校验人与设备、人与房间、设备与环境变量之间的交互关系是否符合生活常识。
- 校验可达性、可见性、邻接关系、导航路径和空间锚点。
- 为 2D 层提供一套有根据的空间语义映射。

换句话说，3D 层承担的是“仿生真实性与结构正确性”的责任。

#### 2D 层的职责

2D 层承担的是“实验执行与规模化评测”的责任。它主要负责：

- 大规模 episodic benchmark 运行。
- 长时间生活仿真中的快速时间推进。
- 低渲染成本下的重复实验与批量对比。
- 统一记录状态转移、工具调用、虚拟时间与评价指标。

也就是说，真正的 benchmark 主战场在 2D，而不是 3D。

#### 3D 与 2D 的一致性要求

要避免“3D 只是 demo、2D 才是正片”的质疑，关键在于将两者的关系写清楚，并在系统中做成可验证的约束。至少需要保持以下几类一致性：

- 房间拓扑一致
- 设备锚点一致
- 邻接与可达关系一致
- 导航语义一致
- 设备状态转移逻辑一致
- 环境变量受设备影响的机制一致

这意味着 3D 与 2D 不是松散映射，而是双表示环境中的两种视图。3D 负责校准世界，2D 负责执行世界。

#### 这一层贡献要解决的学术问题

这一层的学术意义在于：

- 让智能家居 benchmark 第一次真正具备空间语义基础。
- 将“仿生真实性”从口头设定变成可校验的环境设计原则。
- 在高真实性与高吞吐评测之间给出一套可操作的折中方案。

### 3.2 第二层贡献：长期主动智能服务 benchmark

第二层贡献是把评测从片段式交互推进到长期生活过程中的主动服务能力。

当前相关 benchmark 普遍偏向：

- 单轮命令
- 多轮澄清
- 结构化控制
- 局部记忆

这些都重要，但它们与真正的智能家居长期使用场景之间还有一段距离。真实的智能家居系统不是每次都从零开始理解用户，而是应当在长期交互中逐渐积累用户偏好、家庭规律与生活模式，并因此“越用越聪明”。

因此，我们提出双层评测结构。

#### Episodic layer

这一层保留传统 benchmark 最有价值的部分，主要覆盖：

- 单指令执行
- 多设备协同控制
- 模糊意图理解
- 空间 grounding
- 指代消歧
- 短时定时与连续任务

它的价值在于：

- 成本低
- 可批量生成
- 易于做清晰对照实验
- 是首篇论文最稳妥的主力评测层

#### Long-horizon layer

这一层是我们相对前人更具差异化的部分。它要模拟的不是“做一道题”，而是“在这个家庭里连续生活与服务一段时间”。

其关键特点包括：

- 交互是持续的，不是独立切片。
- 用户偏好会在长期上下文中逐渐体现。
- 智能家居系统需要记忆并利用历史。
- 多个任务可能并发发生。
- 任务可能跨越较长时间。
- 一个任务结束后，系统可能主动进入下一个服务阶段。

#### 人类侧模拟机制

为了让长期交互成立，我们需要一个由模型或规则混合驱动的人类活动系统。其基本结构可以采用多级 agent 设计：

- `persona / preference` 层
  - 定义住户身份、作息、偏好、禁忌、习惯、对设备的熟悉程度。
- `daily planning` 层
  - 将人物画像映射为日程与活动意图。
- `atomic action` 层
  - 将活动拆分为细粒度行为，并在环境中执行。

这套设计的意义不是把人类行为生成做成论文主角，而是为“长期主动服务 benchmark”提供可信驱动源。

#### 这一层贡献要解决的学术问题

这一层的研究价值在于：

- 把智能家居 benchmark 从“能不能完成命令”推进到“能不能逐渐理解这个家庭”。
- 让用户建模能力、主动服务能力、长期记忆能力有了自然测评环境。
- 使“越用越聪明”从宣传口号变成可比较、可复现、可量化的 benchmark 维度。

### 3.3 第三层贡献：统一接口与现实迁移

第三层贡献是建立一套统一的环境访问语义，使虚拟环境与现实中的 `Home Assistant` 能共享同一层 agent-facing 控制抽象。

这里要明确，贡献点不是“我们重新发明了一个最强 MCP”，而是：

- 定义了一套对大模型友好的智能家居环境交互抽象。
- 让虚拟 2D 环境、3D 校准环境、HA 后端都能对齐到同一语义层。
- 让 benchmark 中学到的行为有机会迁移到现实智能家居编排平台。

#### 为什么不能直接把 HA 官方 MCP 当最终答案

`Home Assistant` 是非常好的开源智能家居平台，但它的官方 MCP 并不是专门为 benchmark 研究设计的。对于我们的研究目标来说，它至少存在三个问题：

- 工具粒度未必适合做严谨测评。
- 接口含义更偏平台集成，而不是研究环境抽象。
- 不同能力混杂在一起时，容易让工具层替模型完成本应被测的推理与编排工作。

因此，我们更合适的路线不是照搬官方 MCP，而是定义一套研究导向的统一语义接口，再分别去适配：

- `2D simulator backend`
- `3D calibration backend`
- `Home Assistant backend`

#### 统一语义比统一实现更重要

这里必须强调一个原则：

> 我们追求的是统一语义，而不是底层实现同构。

虚拟环境与 `Home Assistant` 完全可以各自采用不同实现路径，只要它们对模型暴露的核心环境访问语义一致即可。这样既能降低工程复杂度，也能保留研究贡献。

## 4. 系统设计原则：轻量化、可评测、不偷能力

在具体实现层面，最需要明确的是边界。因为这套系统一旦不加约束，就很容易滑向两个极端：

- 要么工具过碎，模型被迫做大量底层工程拼接，评测变成“谁更会调 API”。
- 要么工具过强，接口层提前把问题解了，benchmark 失去测量意义。

因此，系统设计必须坚持以下三条原则。

### 4.1 环境层不替模型解题

环境访问层可以封装：

- 查询
- 定位
- 执行
- 验证

但不应封装：

- 自动任务分解
- 自动 schedule 生成
- 自动冲突消解
- 自动 workflow 合成
- 自动隐含意图求解
- 自动计划修复

原因很直接：这些能力本身正是 benchmark 想测的对象。如果把它们提前放进接口层，那么模型表面上表现会更好，但测出来的已不是模型能力，而是工具设计能力。

### 4.2 接口层要轻量

这里的“轻量”不是指协议本身有多简单，而是指模型完成一项任务时不应被迫调用过多低层工具。真正影响效率的往往不是 MCP 或 REST 的网络开销，而是：

- 工具过多
- 粒度过碎
- 每一步都要重新思考与重组

因此，工具设计要尽量做到：

- 数量少
- 语义清楚
- 信息密度高
- 足够支撑观察-执行-验证闭环

### 4.3 统一语义优先于统一实现

虚拟环境和 `Home Assistant` 后端没有必要共用同一套内部代码，也没必要强行走一模一样的底层接口。真正重要的是它们对大模型暴露的一组核心环境访问能力一致。

这也意味着：

- 面向大模型的协议层和面向实验编排的控制层可以解耦。
- 人类活动模拟侧未必适合也做成 MCP。
- 系统可以同时保留研究友好的语义抽象与工程上更稳的异构实现。

## 5. 首篇论文建议的统一环境访问 API

考虑到前面的边界约束，首篇论文的 agent-facing 环境访问 API 应采用一个克制版本，而不是急于做成大而全平台。

建议首版围绕以下五类核心能力组织：

### 5.1 `get_home_state`

作用是返回家庭环境的结构化全局快照，用于：

- 初始观察
- 多设备任务前的环境理解
- 长时交互中的状态记录

它应是“全局观察工具”，而不是“帮模型做决策的工具”。

### 5.2 `find_devices`

作用是按房间、类型、状态、功能等约束检索设备，用于：

- 将自然语言中的对象描述 grounding 到设备集合
- 支持空间指代、跨设备协同和目标定位

它提供的是 grounding 能力，不是任务求解能力。

### 5.3 `get_device_state`

作用是读取单个设备的关键状态、支持能力与必要约束。其意义在于：

- 让模型可以在动作前检查设备现状
- 减少直接暴露原始平台字段带来的噪声
- 支持约束判断与动作合法性分析

### 5.4 `execute_device_action`

作用是对设备执行结构化动作。它可以做轻量约束检查，例如：

- 设备是否存在
- 动作是否支持
- 参数是否越界

但不应进一步替模型做任务分解或多设备编排。

### 5.5 `check_goal_state`

作用是验证目标状态是否达成，并可选比较无关状态是否被错误改动。

这对 benchmark 很重要，因为它能把“任务完成判定”从主观自然语言评估转化为环境级可验证过程。

### 5.6 哪些能力不应进入首版 API

以下能力原则上不进入首版 agent-facing 工具集合：

- 自动 schedule 生成
- 自动冲突消解
- 自动多设备 orchestration
- 自动计划修复

原因不是这些能力不重要，而是它们正是 benchmark 要衡量的对象。如果接口层帮模型做完了，评测就失真了。

## 6. 统一蓝图下的模块划分

为了让整套系统结构清晰，可以将其分为四层。

### 6.1 World Construction Layer

这一层负责构建世界本身，包括：

- 户型
- 房间
- 设备
- 人物画像
- 家庭规则
- 时间语义

它解决的是“我们到底在模拟什么样的家庭”。

在多样性上，首版不必追求极端规模，但应追求结构合理、覆盖明确、可解释。你目前提出的“家庭数约 30、人物画像约 30 到 50”是一个相对平衡的方向，足以支持论文中关于多样性与可泛化的基本论证。

### 6.2 Twin Environment Layer

这一层是整套工作的中枢，由两部分组成：

- `3D calibration environment`
- `2D execution environment`

其职责是：

- 保证空间与状态语义的一致性
- 将 3D 校准结果转译为 2D 可执行表示
- 提供可重复、可快进、可验证的实验环境

这一层是我们与前人最不同的地方之一，因为它直接把环境本体设计提升为论文核心。

### 6.3 Interaction Layer

这一层负责把世界开放给外部智能体。

它至少包含两类接口：

- `smart-home agent protocol`
- `human-life simulation protocol`

前者可采用 MCP 风格，面向大模型作为智能家居 agent 调用环境。

后者则未必适合强行使用 MCP。因为人类活动模拟往往需要：

- 高频事件流
- 大量状态推进
- 批量 rollout
- 更细的实验控制

因此，更合理的方式往往是采用独立的 simulator control API 或内部事件协议。这样可以避免把人类模拟系统也硬塞进面向通用 tool calling 的接口形式中。

### 6.4 Evaluation Layer

这一层负责定义 benchmark 本身，包括：

- `episodic benchmark`
- `long-horizon benchmark`
- 评价指标
- 成功判定
- 轨迹记录
- 对比实验

至少应覆盖以下核心维度：

- 空间理解
- 指代消歧
- 跨设备与跨链路协同控制
- 长时依赖
- 并发任务处理
- 用户建模
- 主动服务能力

## 7. Sandbox 的定位与必要性

这里的 `sandbox` 不是安全领域常说的隔离沙箱，而是实验世界的副本机制。它的核心作用是：

- 可重置
- 可快进
- 可回放
- 可并行复制

这对智能家居 benchmark 尤其重要，因为我们的评测并不是一次性静态问答，而是涉及世界状态、时间推进和长期生活轨迹。

### 7.1 Sandbox 能解决什么问题

第一，它能让同一个家庭初始状态被多个模型重复测试，而不必每次重新构建完整环境。

第二，它能支持长时间生活仿真中的快速推进。比如一段生活过程可能在现实中横跨数小时甚至数天，但在实验中需要通过虚拟时间高效推进。

第三，它能让失败样本精确复现。对于 benchmark 来说，能否重放某次失败，是研究有效性的关键。

第四，它能让 episodic 与 long-horizon 两种评测共享同一套世界定义，而不是分裂成两套彼此脱节的环境。

### 7.2 首篇论文中 Sandbox 至少应提供什么能力

首篇论文建议至少提供：

- `reset`
- `snapshot / restore`
- `fast-forward virtual time`
- `deterministic replay`

这已经足以构成一套严肃实验环境，而不必一开始就追求大而全的调度系统。

## 8. Benchmark 的核心任务维度建议

后续实现和论文写作不应继续按零散任务罗列，而应按“场景族”组织。至少建议锁定以下几类。

### 8.1 空间 grounding

这类任务依赖空间锚点和相对位置，例如：

- “把客厅里离沙发最近的那盏灯调暗”

它直接要求环境具备真实空间语义，而不是仅有房间标签。

### 8.2 指代消歧

例如：

- “把我刚刚看的那边的灯关掉”

这类任务需要结合历史、空间方向或当前上下文做 grounding，是传统房间-设备状态机 benchmark 难以自然表达的。

### 8.3 跨设备链式调控

例如：

- 空调、窗帘、空气净化器共同作用于室内温度、照度和空气质量。

这种任务能体现环境变量联动，而不只是多个设备独立开关。

### 8.4 时间延迟与持续任务

例如：

- 预定执行
- 持续运行
- 一段时间后再验证效果

这类任务能充分利用时间推进与环境持续演化机制。

### 8.5 长期记忆与个性化

例如：

- 根据住户习惯调整服务策略
- 识别不同家庭成员偏好
- 观察一段时间后主动推荐或主动执行

这是长期主动智能服务 benchmark 的关键。

### 8.6 并发与连续生活

例如：

- 多任务并存
- 旧任务未结束时出现新意图
- 用户生活行为与家居控制相互交织

这会显著提升 benchmark 的真实感与研究价值。

## 9. 首篇论文的 MVP、增强项与远期项

为了避免第一篇论文承担过重，必须主动分层。

### 9.1 首篇论文必须完成的核心内容

首篇论文建议必须完成以下内容：

- 一个可复现的 `3D 校准 + 2D 执行` 双层环境框架。
- 一套明确的空间一致性定义。
- 一套克制的统一环境访问接口。
- 一组与现有四篇工作显著拉开差异的核心任务维度。
- 一套基础 sandbox 机制。

其中，空间一致性定义至少要明确：

- 房间拓扑
- 设备位置语义
- 邻接与可达关系
- 状态映射

核心任务维度至少应覆盖：

- 空间理解
- 指代消歧
- 跨房间或跨设备协同控制
- 时间连续任务

这是第一篇论文最硬的骨架。

### 9.2 增强项

以下内容非常有价值，但可以作为增强项，而不是首篇必须全部做满：

- 有限规模的长程生活轨迹评测
- persona 驱动的人类生活模拟
- 用户建模效果对比
- 虚拟环境与 `Home Assistant backend` 的接口一致性 demo

这些内容有助于显著提高论文亮点，但应根据实现成本谨慎控制规模。

### 9.3 远期项

以下内容建议明确归入第二阶段或后续论文：

- 大规模长期交互 benchmark
- 基于轨迹的 SFT 或 post-training
- RL 环境改造
- 空间拓扑嵌入、个性化记忆增强等模型侧方法

这些方向都很有价值，但若首篇论文试图全部纳入，很容易导致整体贡献虚胖、实现发散、实验失控。

## 10. 对当前研究进展的阶段性判断

基于目前已读的四篇论文和现有的 `myserver / Home Assistant` 讨论，可以对当前研究状态做一个较明确的判断。

### 10.1 我们已经相对清楚的部分

目前已经比较清楚的，不再属于模糊想法，而是可以视为阶段性共识的内容有：

- 现有 benchmark 的主要共同边界确实存在。
- “3D 校准 + 2D 执行”是有论文叙事价值的，不是单纯展示包装。
- 空间语义、长期交互和统一接口是彼此支撑的三条主线，而不是互不相干的三个点。
- `myserver` 不应成为“替模型解题”的厚重平台。
- 面向模型的环境访问接口应当保持克制，并与实验控制接口解耦。
- `Home Assistant` 更适合作为现实平台适配与迁移桥梁，而不是 benchmark 全部语义的原生来源。

### 10.2 当前最核心的工程与研究难点

当前真正的核心难点，不在于再补多少 API，而在于以下三个结构性问题：

- 如何正式定义 3D 到 2D 的一致性约束，并让它可验证。
- 如何设计长期生活模拟而不把系统复杂度推得过高。
- 如何定义一组足够强、又不偷能力的统一接口语义。

这三个问题解决得好，整套论文就会站得住。若只在任务数量或工具数量上扩展，反而容易稀释主贡献。

### 10.3 对首篇论文的最优策略判断

从当前阶段看，首篇论文最优策略不是“什么都做”，而是：

- 把环境本体做扎实
- 把空间语义做成真正差异化
- 把 benchmark 任务族围绕空间与时间组织清楚
- 把接口层边界严格守住
- 在此基础上加入有限但有力的长期交互展示

也就是说，首篇论文的主心骨应当是：

> 一套空间真实、时间连续、可复现、可迁移的智能家居 benchmark 环境系统。

而不是：

> 一个所有方向都沾一点但每个都不够深的智能家居大杂烩。

## 11. 当前推荐的总叙事

如果将来要把这项工作用一段最浓缩的话讲清楚，我建议当前总叙事可以收敛为：

> 我们提出一套面向智能家居大模型智能体的空间化 benchmark 框架。与现有主要基于房间-设备状态结构的工作不同，该框架通过 `3D 校准 + 2D 执行` 的双表示环境引入可验证的空间语义与时空一致性，并通过统一环境访问接口将虚拟环境与 `Home Assistant` 式现实智能家居平台桥接起来。在此基础上，框架同时支持短程任务测评与长期生活交互测评，从而使空间理解、指代消歧、跨设备调控、用户建模和主动服务能力能够在同一研究体系中被系统评估。

这段话基本可以作为后续摘要、引言和项目主页叙事的雏形。

## 12. 结论

到当前阶段，我们的工作已经不应再被理解为“基于 Home Assistant 做一点智能家居控制实验”，也不应仅仅被理解为“在前人 benchmark 基础上再扩充一些任务”。

更准确的定位是：

- 我们在重新定义智能家居 benchmark 的环境基础。
- 我们在把空间语义正式纳入 benchmark 的主结构。
- 我们在把长期主动服务从补充亮点变成核心测评维度之一。
- 我们在尝试建立一条从虚拟 benchmark 到现实平台控制接口的统一迁移路径。

如果后续能把 3D/2D 一致性、轻量接口边界和有限但有力的长期交互验证落实出来，那么这项工作就不仅是“补一个 benchmark”，而是有希望成为智能家居 agent benchmark 形态升级的一步。
