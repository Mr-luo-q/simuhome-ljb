# 真实沙箱内核应如何分步推进：结合 firstdemo 当前进度的迭代路线

本文在原第 10 篇的基础上重写。它不继续讨论 `viewer`、3D 展示或页面交互细节，而是把当前路线重新压回一个核心问题：

```text
既然 2D/3D 只是观察、校准、修改入口，
真实沙箱内核应该怎样小步快跑，
才能从当前 firstdemo 演示
推进成可复现、可扩展、可迁移的实验世界。
```

这里的“真实沙箱内核”指的是一套可以无头运行的世界。它不依赖浏览器界面才能成立，也不依赖 3D 才能证明自己存在。它必须能被时间机制驱动，能被实验接口和模型接口访问，能快进、回放、重置、复现，最终还能和 Home Assistant 式现实平台在 agent-facing 语义上对齐。

这篇文档承接四个已经稳定的判断：

```text
mcp/doc/7
  智能家居 benchmark 的突破口不是再补任务，
  而是升级世界模型：空间、时间、长期生活、现实迁移。

mcp/doc/8
  沙箱不是工具集合，而是实验世界；
  时间机制不是普通模块，而是时间控制核。

mcp/doc/9
  HA 的 REST / WebSocket / conversation / Assist tool 抽象
  说明了现实平台的接口分层；
  我们追求的是统一 agent-facing 语义，不是统一底层实现。

context/上下文总结6
  当前核心进度已经落到 sandbox/firstdemo；
  下一步应把 firstdemo 从“可演示”推进成“可复现实验内核”。
```

---

## 1. 总判断

当前不应继续把主线放在 viewer、3D 或展示层上。视图层有价值，但它不是世界本体。现在真正要推进的是这条无头运行链：

```text
静态世界定义
  ↓
世界状态初始化
  ↓
外部动作进入时间控制核
  ↓
tick 边界统一执行
  ↓
设备状态变化
  ↓
环境动力学更新
  ↓
调度与事件触发
  ↓
状态、事件、命令结果可观察
  ↓
snapshot / restore / replay 可复现
```

如果这条链没有立住，后续补 MCP、补人物、补长期生活智能体都会变成架空叙事。相反，只要这条链跑稳，2D/3D、设备扩展、人类活动、HA adapter 都可以逐层挂上去。

因此当前最推荐路线是：

```text
以 firstdemo 为主战场
  ↓
先完成最小无头内核闭环
  ↓
再补最小 MCP / agent-facing 接口
  ↓
再做轻量 2D 空间语义展示
  ↓
再扩设备族与环境变量
  ↓
再引入人物、生活接口、长期智能体
```

这不是保守路线，而是避免返工的路线。智能家居沙箱最容易失控的地方，不是功能不够多，而是时间、事件、命令、状态没有统一排序。firstdemo 下一步的关键，就是把所有外部动作真正接回时间控制核。

```text
sandbox/firstdemo
```

它已经不是早期 `mcp/sandbox_v1_demo` 那种结构验证原型，而是第一版可运行薄切片。它已经具备：

当前已经验证的事实是：

```text
设备动作可以执行

浏览器能观察温度曲线
LLM 可以通过工具完成设备设置
reset 深拷贝问题已修复
```

当前也有一个必须正视的缺口：

```text
TimeControlKernel 中已有 api_queue

```

也就是说，当前 firstdemo 仍然更像“演示能跑的同步调用系统”，还没有完全成为“所有变化都进入同一条 tick 时间轴排序的实验内核”。

## 3. 当前最核心的问题不是扩功能，而是接回时间控制核

现在 firstdemo 的关键矛盾可以画成这样：

```text
理想结构

外部动作
  ↓
TimeControlKernel.api_queue
  ↓
tick 边界
  ↓
CommandGateway
  ↓
WorldState.device_states
  ↓
后续 tick 中 Aggregator 读到新设备状态
  ↓
WorldState.room_env 变化
```

当前实际结构更接近：

```text
HTTP / demo / adapter
  ↓
Sandbox.execute_device_action
  ↓
CommandGateway.execute
  ↓
立即写 WorldState.device_states
```

这条同步路径在首版演示中是合理取舍，因为它简单、直观、方便 LLM 工具调用。但从研究沙箱角度看，它会带来几个后续风险：

```text
命令发生在哪个 tick 不清楚
并发命令顺序不清楚
调度任务和即时命令先后关系不清楚
replay 很难严格复现
Gym-friendly step 语义会混乱
server / demo 容易继续承担业务逻辑
```

因此下一步不应先补很多设备，也不应先加人物，而应先把动作入口改成：

```text
所有外部动作
  ↓
submit_device_action
  ↓
api_queue
  ↓
tick
  ↓
command_result
  ↓
event_log
  ↓
world_state observation
```

这一步完成后，firstdemo 的性质会发生变化：

```text
从：
  一个 LLM 演示 demo

变成：
  一个同一初始状态 + 同一动作序列 + 同一 tick 推进
  就能复现同一轨迹的实验内核
```

## 4. 不推荐的推进顺序

这里把几条容易回退的路线写清楚。

### 4.1 不推荐继续优先打磨 viewer

原因很简单：

```text
viewer 是观察与编辑入口
不是沙箱世界本体
```

如果现在继续扩 2D/3D，很容易把精力重新拖回布局、交互、颜色、相机、截图，而不是推进无头运行链。

### 4.2 不推荐先补全所有设备

没有稳定时间轴时，大量设备只是更多静态状态和更多动作枚举。真正重要的是先证明：

```text
少量设备
  +
单一环境变量
  +
时间控制核
  +
调度与事件
  =
可复现实验轨迹
```

设备扩展应该发生在内核可复现之后。

### 4.3 不推荐先做人和长期生活智能体

人物层会放大所有底层不稳定：

```text
时间不稳
  人物行为不可复现

事件不稳
  生活流不可解释

环境不稳
  主动服务目标不可验证

接口不稳
  agent 交互轨迹不可比较
```

所以人物和长期生活智能体必须后置。

### 4.4 不推荐先把三套接口完整工程化

接口语义要尽早收敛，但工程实现不能太早做满。当前更合适的是：

```text
先定义薄语义
  ↓
让 firstdemo 内核满足薄语义
  ↓
等运行机制稳定后
  ↓
再做 MCP adapter / HA adapter / benchmark runner
```

否则接口会被还没稳定的 runtime 反复牵动。

## 5. 当前推荐的小步快跑路线

结合 `context/上下文总结6`，后续建议按六个阶段推进。每个阶段都应有明确验收标准，不要把多个阶段混成一个“大系统升级”。

```text
阶段 A：firstdemo 核心机制补全
  ↓
阶段 B：MCP / agent-facing 最小接口补全
  ↓
阶段 C：2D 空间语义展示
  ↓
阶段 D：设备族与环境变量扩展
  ↓
阶段 E：人生活接口
  ↓
阶段 F：人生活智能体
```

### 5.1 阶段 A：firstdemo 核心机制补全

阶段 A 是当前最该立刻推进的部分。它不追求新设备、新页面、新人物，而是把内核主路径收稳。

```text
阶段 A 目标

所有外部动作都进入 api_queue
所有延迟 / 定时动作都进入 scheduler_queue
每个 tick 产出 command_result 与 event
任务完成判断进入 task_state
server / web 只观察状态，不承担业务逻辑
snapshot / restore 语义明确
```

建议拆成几个很小的改动：

```text
A1：command_result
  TimeControlKernel 增加 last_command_results
  _process_api_queue 每处理一个命令就记录 Result
  step 返回 world + command_results

A2：api_queue 主路径
  Sandbox 新增 submit_device_action(...)
  HTTP execute_action 内部走 submit + step once
  旧 execute_device_action 保留为内部/测试入口或标注 legacy

A3：event_log
  WorldState.task_events.event_log 开始真实写入
  记录 command_submitted / command_executed / command_failed
  记录 temperature_changed 或 env_updated 的摘要事件

A4：scheduler_queue 实际执行
  支持在 due_tick 提交设备动作
  到期任务走同一套 CommandGateway
  生成 scheduler_task_executed 事件

A5：task_state 最小化
  支持一个温度目标任务
  每 tick 检查是否达成
  任务状态写入 task_events 或独立 task_state

A6：snapshot / restore 语义确认
  明确是否恢复队列
  首版建议：snapshot 只覆盖 WorldState，队列清空并记录说明
  后续再考虑完整 replay snapshot
```

阶段 A 的验收标准应该写成：

```text
同一个初始场景
  +
同一组 agent actions
  +
同一组 wait_ticks
  =
同一条可复现实验轨迹
```

更具体一点：

```text
设备动作不再绕过时间控制核
本 tick 执行动作，后续 tick 体现环境变化
command_results 顺序稳定
event_log 顺序稳定
fast_forward(n) 与连续 step n 次结果一致
reset 后轨迹可重跑
```

### 5.2 阶段 B：MCP / agent-facing 最小接口补全

阶段 B 不应一上来做完整 MCP server。更稳的方式是先定义 firstdemo 内部的 agent-facing 语义，再把它投影成 MCP。

建议最小工具集合：

```text
observe_home
  返回克制版 home state

inspect_room
  返回房间温度、邻接房间、房间内设备摘要

inspect_device
  返回设备状态、可执行动作、参数约束、前置条件

execute_device_action
  提交一个设备动作
  内部走 api_queue
  返回 command_result

wait_ticks
  推进指定 tick 数
  返回状态摘要、事件摘要、任务状态

query_events
  查询 event_log

query_task
  查询当前任务目标与完成状态
```

这一阶段要继承第 7、9 篇的原则：

```text
接口要克制
不替模型自动编排
不自动生成 schedule
不自动做多设备 orchestration
不把所有 world truth 一次性塞给模型
```

它和 HA 的对齐关系可以先写成：

```text
firstdemo observe_home
  ↔ HA GET /api/states 或 WS get_states

firstdemo execute_device_action
  ↔ HA call_service

firstdemo query_events
  ↔ HA subscribe_events / logbook / history

firstdemo conversation 未来扩展
  ↔ HA conversation/process
```

这里对齐的是语义，不是强行复刻 HA 的字段。

### 5.3 阶段 C：2D 空间语义展示

阶段 C 才重新接回展示层，而且先接 2D，不急着回 3D。

目标不是做漂亮页面，而是让无头内核的空间语义可观察：

```text
房间
设备
人物位置（后续）
事件位置
温度 / 环境场
任务状态
```

这一阶段可以复用之前 `sandbox/viewer` 的经验，但要注意主从关系：

```text
firstdemo 内核是真相
2D 页面只是观察投影
```

不要让页面重新承担业务逻辑。

### 5.4 阶段 D：设备族与环境变量扩展

阶段 D 才适合扩大设备与环境覆盖。

建议顺序：

```text
先扩环境变量
  temperature
  humidity
  illumination

再扩典型设备族
  空调
  风扇
  取暖器
  灯
  门窗
  传感器
  厨电
  安防

最后扩派生指标
  噪声
  能耗
  空气质量
```

扩展时要保持一个原则：

```text
每加一类设备
必须说明：
  它有什么状态
  它有什么动作
  它有什么约束
  它如何影响环境
  它如何被任务验证
  它如何映射到 agent-facing 接口
```

如果某类设备只是在 JSON 里多一个开关，但不参与任务、事件或环境变化，就不急着加。

### 5.5 阶段 E：人生活接口

人物进入前，先定义“人生活接口”，不要一上来就做重 persona agent。

建议从这些字段开始：

```text
location
activity
preference
schedule
comfort
request
disturbance
```

这阶段重点是把人物行为变成沙箱可消费的事件：

```text
human_location_changed
human_activity_started
human_request_created
comfort_threshold_crossed
disturbance_observed
```

人生活接口的意义不是“让人看起来丰富”，而是为长期主动服务 benchmark 提供稳定驱动源。

### 5.6 阶段 F：人生活智能体

最后才进入人生活智能体。

推荐顺序：

```text
规则 / 脚本生活流
  ↓
模板化 persona + schedule
  ↓
LLM persona 驱动
  ↓
长期主动服务 benchmark
```

这样做的原因是可复现性。先用规则生活流，可以确认内核、事件、任务和接口都稳定；再接 LLM persona，才知道问题到底来自模型行为，还是来自沙箱内核。

## 6. 阶段 A 的推荐实现形态

阶段 A 是最重要的近期目标，这里单独写得更具体一点。

### 6.1 api_queue 主路径

建议把当前调用链改成：

```text
HTTP / MCP / demo
  ↓
Sandbox.submit_device_action(...)
  ↓
TimeControlKernel.submit_command(...)
  ↓
TimeControlKernel.tick()
  ↓
_process_api_queue()
  ↓
CommandGateway.execute(...)
  ↓
command_results
  ↓
event_log
```

对 LLM 来说，`execute_device_action` 仍然可以表现为一次工具调用：

```text
模型调用 execute_device_action
  ↓
server 内部 submit command
  ↓
server 内部 step once
  ↓
返回该 command 的 Result
```

这样外部体验不变，但内部已经回到时间控制核。

### 6.2 step 返回值

当前 `step()` 只返回 home state。后续建议改成：

```json
{
  "world": {
    "virtual_time": 12,
    "rooms": {},
    "devices": {}
  },
  "command_results": [],
  "events": [],
  "task_state": {}
}
```

这会让实验脚本、MCP 工具、浏览器面板都能从同一套语义读结果，而不是各自拼状态。

### 6.3 event_log 最小事件类型

首版不需要复杂事件总线，但至少要有：

```text
command_submitted
command_executed
command_failed
tick_started
tick_finished
environment_updated
scheduler_task_due
scheduler_task_executed
task_started
task_completed
```

事件不只是给页面看的，它是 replay、debug、benchmark 轨迹分析的基础。

### 6.4 scheduler_queue 最小语义

当前 `scheduler_queue` 只是结构预留。下一步建议先支持一种任务：

```text
schedule_device_action(
  due_tick,
  device_id,
  action,
  params
)
```

执行路径必须和即时动作一致：

```text
scheduler 到期
  ↓
生成 command
  ↓
CommandGateway 执行
  ↓
写 command_result
  ↓
写 event_log
```

不要给 scheduler 单独开一条绕过网关的状态写入路径。

### 6.5 task_state 最小语义

首版可以只支持温度目标任务：

```text
Task:
  id
  room_id
  target_temperature
  tolerance
  status
  started_tick
  completed_tick
```

每 tick 检查：

```text
abs(room.temperature - target_temperature) <= tolerance
```

任务完成后写事件：

```text
task_completed
```

这已经足够支撑第一版 benchmark runner 的雏形。

## 7. 与 HA / MCP 的关系

第 9 篇已经说明，HA 的接口分层大致是：

```text
REST / WebSocket
  平台通用状态读取、服务调用、事件订阅

conversation / assist_pipeline
  文本对话与语音流水线

Built-in Assist API for LLMs
  HA 内部给 conversation agent 的 tool 抽象
```

这对 firstdemo 的启发是：

```text
不要把 MCP 当成内核
不要把 HA 字段当成沙箱真相
不要把 Assist tool 抽象直接照搬成外部 API

应该做的是：
  firstdemo 内核稳定自己的世界状态和时间语义
  agent-facing 接口对齐状态读取、动作执行、事件查询
  HA adapter 以后把这些语义映射到 states / services / events / conversation
```

对应关系可以先写成：

```text
firstdemo
  observe_home
  inspect_device
  execute_device_action
  query_events
  wait_ticks

HA
  GET /api/states
  GET /api/services
  POST /api/services/{domain}/{service}
  subscribe_events
  conversation/process
```

关键仍然是统一语义：

```text
同一个模型在 firstdemo 中学到：
  先观察
  再检查设备
  再执行动作
  再等待时间
  再验证目标

迁移到 HA 时仍然应看到类似语义，
只是底层实现换成 HA states / services / events。
```

## 9. 最终结论

当前项目已经过了“只讨论方向”的阶段，也已经过了“只做展示原型”的阶段。现在最重要的是把 `sandbox/firstdemo` 变成真正的实验内核。

最终路线可以压成一句：

```text
先让 firstdemo 成为一个可复现的无头时间世界，
再把 MCP、2D、设备扩展、人物生活、长期智能体逐层挂上去。
```

当前第一步不是大改架构，也不是扩很多功能，而是：

```text
所有外部动作进入 api_queue
所有延迟动作进入 scheduler_queue
每个 tick 产生 command_result 与 event_log
任务状态进入 task_state
server / web 退回观察层
snapshot / restore / replay 能支撑复现实验
```

这一步完成后，firstdemo 才真正从“能演示”进入“能评测”。后面的 MCP、HA adapter、人生活智能体和长期主动服务 benchmark，才会有稳固地基。
